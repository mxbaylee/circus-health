# Delivery questions and resumable extraction

The importer retains a `health-intake-workflow-v1` journal inside each delivery’s curation-owned source metadata. Existing durable transactions publish it outside SQLite. It contains candidate versions, question/answer history, explicit acceptance decisions, extraction plans and batch receipts. Originals and proposal JSONL remain separate immutable files. Backup and deterministic rebuild retain the workflow without model access.

Questions have stable delivery/candidate/evidence references. An answer saves a record-scoped draft; it does not accept the model’s interpretation or create a reusable mapping. The existing clinical review must explicitly accept that record, including any suggested corrected fields, before its answered questions become resolved. Other records can be accepted independently. Omitted review decisions stay pending. Existing accepted source occurrences remain intact on later passes.

## Background reading and profile locks

After the upload has completed and the server has accepted a reading job, leaving the import page or closing the browser tab only stops browser polling. The server continues across model turns and pending reading windows while the profile and server remain available. A new page visit reloads the retained job state. An upload that has not finished receiving is different: its interrupted transfer must be retried.

Resume is a recovery action, not a required step between normal pages or model windows. Reading pauses on an explicit Stop, provider/tool failure, no progress, a time/context limit, or a profile/server interruption. These bounds prevent repeated work and unbounded model requests; they do not mean that available proposals were lost. The UI must explain the pause reason and distinguish resumable partial work from exhausted read windows. Exhausted windows do not prove complete clinical extraction.

Locking a profile, including switching to another profile, stops its reader and assistant before the decrypted database is closed, key material is cleared and the decrypted working cache is removed. Completed proposals and checkpoints remain in the encrypted archive. Authorized unlock restores durable automatic-run intent; explicitly stopped jobs remain stopped. See [automatic recovery](automatic-recovery.md) for the separate CRS-081 authority boundary. The application does not secretly keep a locked profile open until a task finishes.

## Clinical imports and People proposals

The clinical upload review path accepts observations, medications, procedures and documents whose clinical subject has been confirmed as Self. Optical prescriptions are structured document records. Named clinicians and relatives use a separate People proposal path: their contact details and history are never coerced into Self's clinical results.

The optional envelope `people` array carries named clinician/relative proposals with literal, same-envelope evidence passages and explicit field-support lists. Every supporting passage must include the proposed name and supplied field. Package evidence repeats the host-verified report member. Role-only or organization-only labels stay source text; a clinician mention does not establish a current PCP or emergency role. These checks validate internal evidence alignment, not the model's interpretation of the original. Uncertain associations stay visible for human review.

The People tab appears only when named proposals exist, including reports containing no clinical rows. Users explicitly add a new person or choose an existing exact-name candidate to update at its current version. A name match offers a choice; it never merges automatically. Supplied reviewed fields update that Person, unrelated fields remain unchanged, and incoming family/medical history is appended to that relative's history. A known canonical Self match cannot create another Person. When Self's full name is absent, the host cannot resolve aliases from a display name alone.

People proposals support Review later and exclusion without deleting their originals. Apply first durably retains its source evidence, then commits the editable Person, evidence association and exact-request receipt through the existing personal-entry transaction. If the personal write fails, the proposal remains pending and the exact request can recover; retaining a source alone does not mark a Person saved. Backup/rebuild preserves the separate source and personal histories. Moxie chat continues to use `health_propose_note` with `kind:"person"` and explicit Apply. See [the named People API](../../src/server/INTAKE.md#named-people-review) for upload proposals.

An accepted assistant procedure-category correction uses the same individual-exception precedence as import review. Distinct corrections retain distinct history, even when a value returns to an earlier category; a repeated source assertion reuses the corrected entity.

A reviewed individual field correction records a source-identity/version-specific exception in the accepted curation journal. Exceptions take precedence over later general rules and repeated source copies. General mapping previews exclude existing records protected by an overlapping individual exception. Reusable rules remain explicit and narrowly limited to supported naming/category fields; original dates/values never establish event identity.

### Persisted identity domains

Clinical source identity, candidate review identity and report presentation grouping serve different purposes and have persisted consumers. The v1 clinical key uses the trimmed issuing system/record identifier, or an original-hash/locator/envelope-ID fallback. The candidate key additionally binds the delivery and, when present, report member and the complete subject anchor; it also has different discriminator and whitespace behavior. Report-group identity includes the original ID/hash, source system, member, full report and subject anchors including locators, and proposed clinical subject role. None of these keys alone establishes a person's identity.

The extra locators can split a coherent running-header report across pages; omitting report scope from the clinical key can instead collide across subjects or members. Fixing one hash in isolation is unsafe. Current v1 key bytes remain unchanged. Their consumers include candidate/group versions, drafts, identity/source confirmations, acceptance and contribution receipts, clinical entity IDs and evidence links, and individual correction exceptions. The current-format equivalence and report-grouping work is [CRS-144](../todo/CRS-144.md); it preserves accepted history and human decision scope. Old-schema migration is outside the owner's preproduction scope.

### Refuse unsafe clinical source reuse

Before reusing a clinical source key, review and acceptance check its retained source occurrences and individual corrections against the incoming report subject and package-member scope. The check covers observations, medications, procedures and documents, including different clinical versions and additional evidence attached to an existing record. Equal values, a matching issuing identifier, or the current Self name do not resolve a scope conflict. Literal scope comparison is a collision check, not proof of real-person identity; the existing identity review and confirmation requirements still apply.

When a clinical payload omits a header retained elsewhere on the original, the host's exact current original-subject proof can establish its report scope without another identity confirmation. This applies equally to Self and People and is pinned to source, member, report, candidate version and occurrence. New automatic identity attributions retain the host-only `originalSubjectFingerprint`; after recovery, a retained accepted occurrence can use that marker only with its exact historical group membership and original fingerprint. Model-supplied markers and legacy automatic attributions without the marker grant no authority. A raw original JSONL occurrence separately supplies literal source scope when the exact candidate version and original line ID have a host-recorded null proposal; a converted proposal cannot claim that exception. Explicit original-review receipts remain supported for either owner and cover only their exact displayed assignment targets. These proofs do not bypass ownership, conflicting-subject or cross-member checks.

Incompatible or insufficiently evidenced reuse returns HTTP 409 `CLINICAL_SOURCE_SCOPE_COLLISION` before accepted writes. The incoming original remains available for review; the full review's coverage notes explain the blocker. A refusal does not merge or relabel existing records, inherit another scope's correction, or publish a successful acceptance receipt. Compound report acceptance rolls back if a later selected block collides with an earlier one. Pair decisions cannot bypass the guard.

This deliberately tightens compatibility for older imports with incomplete scope: missing evidence is not a matching subject. A refusal calls for inspecting and correcting the source assertion or its report scope, not changing a person's identity to make the record fit. It does not automatically repair historical merges or migrate stored keys. Representative-document reachability and coordinated current-format identity scope remain open requirements.

In particular, repeated reports in different ZIP member scopes remain pending even when their bytes and printed subject match. Their issuing identifiers may be entirely valid; never invent replacement identifiers to bypass the refusal. The former cross-member acceptance/consolidation gate is open again under [CRS-144](../todo/CRS-144.md), with complete-file validation in [CRS-062](../todo/readme.md#crs-062). Scope equality and the cross-member consolidation decision remain unresolved under CRS-144. Same retained occurrence retries and evidenced same-scope copies remain supported; this guard does not change PDF-first delivery or its fallback.

Accepted-record corrections can reclassify observations, procedures, and documents through a reviewed append-only operation. `record-corrections.ts` preserves the stable record ID, records the transition, moves the current projection, and keeps evidence, versions, links, backlinks, exports, and old route references resolvable. Medication cross-kind changes remain rejected because personal medication-use history needs a separate design. A future-import classification rule is a distinct reviewed decision and never rewrites an already accepted record.

Direct correction preview/apply uses the same accepted-operation engine as assistant correction proposals. A required reason and exact before/after preview pin the accepted record and optional selected incoming evidence. Supporting originals are validated against the current candidate/version/proposal and exact retained original/member; the correction records that reference durably without accepting the candidate or changing its review draft. Deferred or superseded incoming work does not erase previously accepted correction attribution. Exact lost-response replay returns the original operation receipt while navigation resolves the record's current destination. This is an individual correction; it creates no reusable rule and does not supply identity authority to other incoming records. See the direct correction contract in [API.md](../../src/server/API.md).

## Related-record discovery and exact pair review

The Import list highlights an observation when its already-discovered saved candidates include the same literal value, unit and known date in the same retained original. This is a nonblocking link to the exact record review, not a duplicate verdict. Different labels can describe repeated evidence, while equal values can still describe distinct measurements. A current explicit pair decision suppresses the cue; stale or unresolved decisions remain visible. The cue neither merges records nor changes selection or acceptance. Unknown dates/units do not manufacture a match.

Related-record discovery ranks same-kind retained evidence by exact code and code system, normalized exact label, and shared label terms. Dates and issuers only break ties among evidence candidates. These signals never establish clinical equivalence, and no unit conversion or automatic merge occurs. Exact source-identity/version reuse remains a separate path. Reviews provide discovery reasons and a first page of 20 comparisons; the `getIntakeRelatedRecords` profile-authorized service supports explicit label, source-record-ID or code searches, 1–50 results per page, and a bounded 200-result window. Truncation is explicit so a caller can ask the user to refine the search. Cursors bind the query, page size and current profile revision. Application routes and UI consume this service separately.

Every newly explicit incoming pair decision must echo its displayed `IntakePairScope` unchanged. The scope binds the profile, incoming source occurrence and exact candidate envelope, its reviewed clinical mapping version, the saved record's exact accepted row, and both sides' original evidence hashes. Thus a saved correction from A to B and back to A still invalidates the earlier scope. An acceptance from any discovery/search page revalidates those references and the actual saved original bytes inside the transaction; the first displayed page is not an allowlist. Mapping edits require a fresh comparison scope. The accepted pair journal retains the exact scope alongside its existing decision history. A pending autosave may carry an existing stale or missing-scope choice forward verbatim so unrelated edits can persist; this retains its review-required status and never grants acceptance authority.

Older accepted pair journals remain readable and are never rewritten to manufacture scope. Pending legacy choices without scope are returned as `missing`; choices whose evidence or record versions changed are `stale`. Those drafts stay retained, but cannot be silently rebound by hydration/autosave or accepted without explicit fresh review. Review DTOs expose statuses for all retained comparison drafts, including targets outside the current discovery page. Existing exact-scope decisions are distinguishable from legacy or stale history. `changed_version` remains a generic pair relationship; it does not assert a provider-issued amendment or select a preferred displayed value.

The mounted record editor can carry an unchanged human choice across its own acknowledged draft save. A memory-only receipt must match the exact profile, intake, proposal, candidate, draft operation and complete effective decision (the stored editable mapping is combined with the full current mapping); both the intake version and request revision must advance by exactly that one write. A fresh review must retain every semantic pair pin, including record versions, mapping, original evidence, context and attachment state. Only the transient version/revision/token may then be refreshed for explicit acceptance. A remount, missing or failed acknowledgment, intervening mutation, changed choice or changed evidence grants no such permission. The server still validates the entire submitted scope inside the acceptance transaction.

## Evidence reading and retained decisions

PDF plans index original pages; newly created PDF plans default to non-overlapping two-page target units, while explicit overlap remains supported. HTML plans index literal table rows, shared headings, surrounding text and image references without executing scripts or fetching dependencies. Work units can overlap, and long literal units are paginated. A report that crosses a PDF unit boundary keeps its exact evidenced report/context anchors and result locators; adjacency alone does not establish shared clinical identity. Dense units may use several pending batches with partial coverage before a final truthful disposition. Candidate grouping requires explicit source identity, or the same original/locator/envelope identity. Additional unaccepted contributions create retained candidate versions; accepted versions remain accepted while later contributions await another review. Existing retained plans keep their serialized units, IDs and pins and are not rewritten from a later default.

Plans pin the original hash, configured/tested model identity, extraction instructions and active mapping versions. Batch submission atomically retains an immutable JSONL proposal with extracted/inspected/context/unreadable coverage and an idempotent operation receipt. Retries reuse the operation ID. A changed pin requires explicit plan replacement; previous plans and completed work remain retained. Inspecting all pages does not itself establish complete extraction, and submitting a batch never accepts its records.

Ordinary review can advance a delivery version while the model is preparing a batch. Only the exact `VERSION_CONFLICT` raised before a batch write is eligible for bounded in-run repair: reread the current plan, revalidate its active plan, batches, candidate versions, questions, accepted history and evidence, then retry an unchanged batch with the same operation ID. If the batch contents or scope must change, use a new operation ID. Two repair responses are allowed without related durable batch progress, and the third consecutive stale attempt pauses. Only a successful batch that adds a candidate version or newly accounts a source unit replenishes this local budget; reads, questions, new operation IDs, unrelated success and repeated inspected/no-op batches do not. Whole-job request, token, turn and time limits remain finite. Operation-receipt conflicts, changed pins, source/scope failures and uncertain publication remain terminal.

API additions use the existing profile-scoped envelope:

- `POST /intakes/:id/questions`: version, stable key, candidateId, prompt, locator, optional field.
- `POST /intakes/:id/answers`: version, operationId, questionId, answer, optional record mapping draft.
- `GET /intakes/:id/plan`: plans, candidates, questions and remaining work.
- `POST /intakes/:id/plan`: version, optional unitSize/overlap; explicit replacePlanId when replacing a pinned plan.
- `GET /intakes/:id/unit?unitId=...&offset=...`: bounded literal text/shared headings, or PDF pages to inspect through the existing image-aware evidence tool.
- `POST /intakes/:id/batch`: version, planId, operationId, JSONL proposal, summary and explicit per-unit coverage.

The host and Moxie tools retain the active extraction plan and earlier plan coverage. Replacing a plan remains an explicit versioned operation using `replacePlanId`; earlier candidates, batches and accepted records stay retained, and an unchanged configuration reuses its existing plan. The ordinary Sources page is evidence/provenance browsing and does not expose import-plan controls. Import keeps bounded package/original diagnostics while plan mutation remains a separate host/tool contract.

Moxie can read/create plans, submit batches and ask durable questions through scoped host tools. It cannot answer those questions as the user or accept a proposal. The existing provider image-capability gate remains in force.

Synthetic validation covers a three-page PDF producing two artifacts with shared page-2 evidence, independent acceptance, answer retries and profile isolation, backup/rebuild of unfinished work, later evidence for an accepted candidate, malformed/stale batches, configuration changes, supplied/missing HTML image references, long table-row pagination and individual exceptions versus later mappings. Ambiguous same-event grouping and real-provider extraction quality remain separate review/verification work.

## Large original uploads

`POST /intakes` streams the raw request to a private runtime `.upload-staging` directory outside profile snapshots. It computes SHA-256 while receiving chunks, checks the complete length and optional `X-Content-SHA256` digest, fsyncs the completed file, and only then publishes the original and its metadata. Interrupted, oversized or mismatched uploads create no source/provider records. A repeated completed upload reuses its exact delivery identity. The client retries the whole file after an interrupted transfer; byte-range upload resume is not implemented. Extraction plans and completed batches resume independently after receipt.

The upload limit is `CRS_INTAKE_UPLOAD_MIB` (default 128; integer 1–1024). HTML/image and other extraction paths that load a complete document have a separate `CRS_INTAKE_EXTRACTION_MIB` limit (default 64; integer 1–256). PDFs within the upload limit instead use one isolated profile/source-hash-scoped PDF.js session: it verifies the unchanged retained file once in fixed-size chunks and reuses bounded range reads for indexing and page evidence. The session caps range allocations, page count, text, render pixels, PNG/attachment output, worker heap and wall time, and is disposed on cancellation, teardown, source change, failure or idle expiry. `GET /intakes/limits` returns effective `uploadBytes` and non-PDF whole-document `extractionBytes` inside the standard profile API envelope. Invalid settings fail explicitly. `npm run start` forwards these environment variables into the application container when configured.

JSONL validation and each conversion proposal remain bounded to 25 MiB, with the existing per-row and row-count limits. Larger original documents are retained in full as pending conversion, without claiming JSONL validation or extraction completeness. A non-PDF extraction above its configured limit returns `EXTRACTION_LIMIT`; the original stays retained and downloadable. PDF parser/resource-bound failures likewise preserve the original and return a specific bounded failure without falling back to a whole-file buffer. Raising a configured limit also raises possible work. Hash verification and literal text paging use fixed-size file chunks even when a whole-document parser cannot run.

ZIP members must use stored or DEFLATE compression. BZIP2, LZMA and other ZIP methods are refused with an explicit unsupported-method error; re-export those packages using DEFLATE. Inspection runs in a bounded Node worker and verifies sizes, local headers and CRCs.

The [streamed ZIP member path](../data/streamed-package-originals.md) has no per-member or aggregate expanded-byte cap: it writes selected contents to a verified private stage and publishes through the existing original-retention transaction. Inventory metadata still accepts at most 10,000 total entries, 5,000 files and 2 MiB of encoded names. Located pending package failures survive reload and remain visible when inventory fails; they never imply completed reading. A package is inventoried before explicitly selected members are read. Nested ZIPs require a separate inventory call and may be followed through three source levels; they are not recursively expanded in one operation.

Staging files are removed on ordinary success/failure. In the encrypted runtime the root is disposable plaintext storage, so a profile lock or runtime restart removes crash leftovers as well. Publication rechecks the live profile database after receipt; a closed/locked profile cannot publish a late upload. No partial staging file is included in an accepted profile backup. Synthetic tests cover fragmented receipt, checksum/length failures, interruption, HTTP chunked oversize, a 26 MiB original surviving conversion/backup/rebuild, Unicode text offsets across read chunks, extraction limits and lock during upload.

## Accepted kind changes and future rules

Reviewed procedure/observation/document transitions retain a stable record identity, append a tombstone in the previous projection kind and a new accepted version in the destination kind, and preserve original evidence. Medication cross-kind changes are rejected until their personal-use relationships can be handled explicitly. Old bookmarks and immutable note-link tuples resolve to the current kind; backlinks and exports use the same resolver. `GET /record-history?kind=…&recordId=…` is profile scoped and paginates complete transition sequences. The browser API retains full contents.

Future classification rules match provider, source system, original kind and exact label, and only propose mappings for future review. They cannot rewrite old accepted records. Individual exceptions fingerprint all explicit clinical fields while excluding only delivery-generated non-document title/text fallbacks. Retained earlier fingerprints are verified using their original evidence and replayed without mutation.

Extraction plans pin the current LiteLLM alias and instruction identity. Earlier plan coverage, questions, batches, and accepted records remain retained when a plan is replaced.

## Durable report references

A `health-record-v1` envelope may carry `report:{key,title,anchor:{locator,text},subject:{locator,text}|null,memberId?,section?:{key,title,anchor:{locator,text}}}`. Keys, titles, quotes and locators must be nonempty bounded strings; subject evidence must be explicit or `null`. The anchor identifies a particular printed report boundary or identifier at a particular source location. A section has its own printed heading and location. Dates, values, extraction chunks, shared model keys and the uploaded filename do not establish report identity. The instructions require a discriminating report anchor and omit grouping when the boundary is uncertain.

`workflow.reportGroups` retains presentation groups in curation-owned delivery metadata. A report group is scoped to the original source ID/hash, source system, exact package occurrence, report anchor, printed subject anchor and proposed subject role. Model keys and display titles do not establish group identity. Exact package `memberId` values are checked against retained extraction-plan inventories; missing package occurrence references and unrecognized member IDs fall back to independent candidate groups. Child deliveries remain scoped to their own retained original. This foundation does not combine reports across separate originals or package occurrences, including exact-byte copies.

Anchor validation checks shape and bounds; a model-provided quote remains an unverified extraction claim. It is not proof that the quote exists in the original, a verified geometric highlight, patient identity confirmation or clinical equivalence. Pure source-context envelopes do not create report-group members or clinical candidates. Unsupported clinical proposals remain reviewable candidates until an explicit decision; group membership does not claim a clinical projection. Grouping itself supplies no identity confirmation or acceptance; the separately bounded common-identity action below requires explicit human review. Contradictory source/member/subject scope produces separate groups. Missing subject evidence remains unknown and cannot authorize shared identity confirmation. Original inspection and deliberate clinical review remain necessary.

Each group has append-only versions. A version contains pinned `candidateId`/`candidateVersionId` members, optional section references, and exact proposal/line/batch/locator occurrences. Subsequent extraction can append results or versions of earlier candidates to the same report. Earlier snapshots remain unchanged; the newest snapshot retains all discovered candidate versions, including accepted history. **Membership length is therefore not a pending-result count.** Consumers must use individual candidate statuses and decisions, and must not treat historical versions as new selected results. Report groups carry neither clinical entity identity nor acceptance state. An optical prescription remains one document with side-specific Vision fields; a DEXA report can reference 28 independently reviewed observations.

Contribution receipts are derived from the scoped group and exact pinned evidence. Retrying an already recorded contribution adds no group version, and replaying an earlier proposal cannot erase later membership. New occurrences from another retained proposal can append provenance without changing an earlier acceptance. Candidate identities with report references additionally scope explicit member and subject evidence; an old unscoped candidate is not silently promoted into a new scoped identity. Every changed envelope has its own candidate version. Record drafts, identity resolutions and acceptance continue to use their existing candidate-version scope, so changed candidates do not inherit a prior draft or acceptance.

`IntakeReview.records[].reportGroups` exposes the latest group-version reference containing that exact candidate version and proposal occurrence. References can point to historical versions when appropriate; callers must retain both IDs rather than infer membership from titles. Group source descriptors preserve the first extraction claim, while version titles and member sections retain later contributions. Existing sources without persisted groups use deterministic, independent candidate fallback references at read time, without rewriting old curation history or treating an entire legacy file as one report. Missing legacy original identifiers in that fallback are `null` rather than inferred from a proposal ID.

The existing durable source-metadata transaction publishes groups alongside candidates, originals and immutable proposals. Backup/rebuild restores their exact IDs, snapshots, decisions and references from curation metadata without model access; SQLite remains disposable. The report review queue uses these persistent groups and displays selected-result counts before acceptance. The common-identity endpoint separately checks literal report/subject quote occurrence where available; grouping itself never verifies these claims.

Fictional tests cover 28 independently accepted/pending measurements in one report, anchored sections, multiple reports sharing dates and model keys, different issuers and subjects, known and unknown package occurrences, repeated proposals/batches, changed versions after identity drafts, accepted-history preservation, deterministic legacy fallback, optical single-document projection, and backup/rebuild/reopen with unchanged group references.

## Stable report review queue

The review screen keeps its drop zone visible and presents compact clinical rows with their literal values, units, dates and distinguishing qualifiers. The original opens on demand; the default workspace is for reviewing results. Kind/status tabs appear only for loaded content. Search and bulk selection describe the shown, loaded scope; unreviewed blockers and unloaded records cannot be swept into acceptance. Per-row Confirm & save uses the same exact-version transaction as counted selections. Review later preserves the pending proposal and removes it from the current queue. A pending row's More actions control opens inline field correction; Open full review leads to its exact record's questions, comparison and acceptance controls. Explicit report links open the report overview, whose rows link to full record review.

The dedicated `/import` route owns both this feed and exact `group`/`intake`/`proposal`/`record`/`person` detail selections. Record links retain inline correction by default; links from the report overview and Open full review add `review=full` to expose the complete record workspace, including after reload. It validates the complete group/intake/proposal/record tuple against the report queue, following bounded queue pagination before declaring an exact selection stale; it never opens a record from a supplied intake under a different report header. Detail composes the shared review workspace, draft queue, related-record and correction controls, source context, reviewed file metadata, package inventory and People matching rather than cloning those contracts. A historical `/sources?view=import` link redirects to `/import` with every remaining selection parameter preserved; `/sources` itself continues to inspect retained evidence and provenance. There is no client fallback to the removed Sources Import view.

Successful People Apply responses expose their exact retained Person destination immediately, including when a later item in a sequential multi-Person save fails. Saved People rows use the durable proposal receipt's destination; proposal IDs, feed IDs and clinical acceptance receipts are never substituted for the saved Person note ID.

Bounded related-record discovery runs automatically for visible pending rows. A suggested match opens explicit paired review; similarity does not authorize a merge or prevent saving an unrelated result. Failed discovery remains retryable from the detailed record. Browser polling ends on unmount without sending a reading cancellation request.

The profile-scoped report queue is available at `GET /intakes/report-queue` and `GET /intakes/report-queue/:groupId`; [the intake API contract](../../src/server/INTAKE.md#report-review-queue) describes views, cursors, counts and mutation receipts. It selects each candidate's newest discovered version across all original/proposal occurrences, derives older unaccepted versions as superseded, and preserves accepted/kept history. Repeating an old envelope in a newer proposal never makes that envelope current again. Earlier proposals can still hold independent current results, so a coherent report detail can contain several exact proposal/review-token blocks.

Active and deferred work remain distinct. Blocked and unanswered counts derive from the exact record review, including candidate-version drafts. Historic group membership is not a pending count. Legacy identity answers lacking a version cannot resolve changed evidence without an exact-version draft or acceptance; their original journal remains intact.

New groups receive profile-wide monotonic discovery ordinals within the existing durable source-publication transaction. Later groups from older files append after already discovered groups. Cursor pagination and stable group IDs permit reload/selection restoration without persisting UI position on the server. Existing unsequenced metadata uses deterministic legacy ordering without a read-time migration. New valid retained JSONL children initialize their candidate/group workflow during publication. Backup/rebuild retains group ordinals and current selections' evidence references without model access.

Reading activity is separate from review completion and extraction completeness. Empty active work can coexist with deferred work, an active reader, unread plan units or unknown extraction completeness. Mutations still use existing per-proposal review/draft/import operations; reload between blocks and preserve each explicit receipt. Counted cross-block acceptance is described below. Common report identity is a separate explicit mutation described below.

## Atomic counted selections and reconnect receipts

Without an explicit mode, `POST /intakes/report-acceptance` explicitly selects exact current candidate versions across source/proposal blocks and accepts them in one durable profile transaction. All source hashes, intake versions, review tokens and blockers are validated against frozen review inputs before projection; no stale mapping or token is refreshed automatically. Same-source blocks merge sequentially within the transaction without overwriting prior decisions. Unselected work stays unchanged, and explicitly selected deferred work is counted in the same operation. Any selected stale/blocked/kept/superseded candidate or projection failure rejects the whole transaction.

For this legacy atomic mode, the operation UUID, exact-request fingerprint and immutable receipt are retained in curation-owned source workflow metadata and the durable transaction journal. Receipt counts cover selected accepted assertions, with actual destination IDs/kinds and added/matched/updated outcomes. `GET /intakes/report-acceptance/:operationId` and exact-request POST replay return the original receipt after later imports, reconnect, unlock or rebuild. Reusing an operation ID for a changed request conflicts. A cache behind durable history reports recovery required, never a fabricated absence/success. After an uncertain response, Import gates new acceptance and offers receipt checking or an explicit byte-for-byte retry of the pending selection before considering another operation. See [the counted acceptance API](../../src/server/INTAKE.md#counted-report-acceptance) for bounds and complete request/receipt fields.

The browser opts into `partial-v1`: each independent selected record receives a saved, needs-review, failed or not-attempted outcome, with bounded optional label, kind, person ID and report name for readable outcomes after reload. Per-selection review tokens prevent background substitution while allowing unchanged siblings to save. Explicit shared effects remain atomic. More than 1000 selected records are sent as sequential operations of at most 200 selections; an unknown child stops the remaining operations. Confirmed child outcomes combine in one summary, while omitted selections appear separately as not sent. Parent manifests and bounded item results survive recovery; an unknown reply is reconciled by its original ID, never guessed to be a failure. See [reliable review and partial saves](review-reliability.md) for the complete behavior and owner rationale.

## Explicit common identity scope

The [common report identity API](../../src/server/INTAKE.md#common-report-identity-review) returns an authoritative evidenced-match, prior-confirmation, confirmation-required, missing-warning or conflict state for one exact original/member and report group. It never infers human identity from a model claim or quote occurrence. Text/HTML and explicit PDF page text support literal quote checks; images and PDF pages with no extracted text have no automatic quote verification. A compact identity action records confirmation of the displayed report subject; a legacy attestation can still record explicit original and membership review. Neither implies that clinical results have been accepted. Additional identity questions are included in the exact scope and must all be displayed before the stronger `confirmed_displayed_identity_questions` attestation; generic or legacy attestation cannot resolve them. Missing identity warns without blocking, while unmatched or contradictory supported facts block shared confirmation. Package membership requires the exact retained occurrence, not another equal-byte member.

One durable transaction appends exact candidate-version/occurrence draft resolutions and an immutable scope receipt. When the same action includes exact evidenced values offered for blank Self name or birth-date fields, it also applies those selected fields with the displayed Self version; a stale, nonblank, changed or unoffered value rejects the whole transaction. It preserves earlier mapping history and accepted records and performs no clinical acceptance. Added members, changed candidates, new occurrences or changed drafts require a new preview and deliberate action; retrying an earlier operation cannot expand its scope. Independent fictional tests cover text and actual synthetic PDF parsing, a no-text PDF attestation path, mixed-person/equal-byte ZIP occurrence isolation, mutation rejection, history and backup/rebuild. These fixtures do not establish real-provider extraction quality, scanned-report readability or detection of every semantic contradiction. The review UI displays the exact common-identity scope and selected blank-Self values before its single explicit action.

## Source accounting and clinical completeness

The [reading accounting API](../../src/server/INTAKE.md#source-reading-accounting) reports current host scope plus explicit batch-backed unit dispositions independently from reading-window progress and clinical quality. Missing/stale plans, incomplete inventories, exact duplicate occurrences, contextual/unreadable sections, unknown roles and dependencies remain distinguishable. An exact retained child can inherit only its own parent inventory occurrence's accounting; equal bytes alone are insufficient. Fully accounted sources do not certify that every clinical fact was extracted.

Context/unreadable dispositions remain partial source evidence with append-only receipts. They stop redundant automatic processing in their exact known scope, while a new inspected disposition deliberately reopens that work and its retained cursors. Bounded continuation can advance on newly accounted units without promoting them to extracted status or accepting records. Missing dependencies and clinical unknowns remain visible after accounting is finished. Fictional checks cover state distinctions, exact ZIP copies/children, source/profile pins, checkpoint reasons, explicit reopening, bounded assistant progression and backup/rebuild. Real large-document/provider completeness and human source-quality review remain open acceptance work.

## Suggested organization labels

Shared context can be retained separately from measurement envelopes. The optional top-level `contextId` (or compatible legacy `payload.contextId`) resolves only a unique context in the same proposal and original/member/source/report/subject scope. Conflicting IDs or ambiguous scope produce separate groups with an explanation. Bounded retained `payload.text`, `literal` or `transcript` can anchor the shared context. A legacy `branding` label must actually occur in that text to become a suggestion; its presence in metadata alone is insufficient. Context grouping changes neither clinical subject nor original provenance.

The context link alone does not establish a clinical field. When exact shared report, section or table-column text unambiguously applies to a linked result, the converter must also copy the supported date, method/modality, unit or category into that result's canonical `clinical` mapping. Scope each fact independently: an explicit report-wide method, modality, unit or category may span that report's sections and current/history columns, while a row-, section- or column-specific fact cannot. Current and historical columns keep their own dates, literal result-cell spelling and unit glyphs. No field crosses an original, package member, report or printed-subject boundary. Ambiguous scope remains unknown and reviewable rather than receiving a host-invented backfill. An explicit historical procedure mention remains a valid historical mention when undated; if its own date is printed, retain the supported value and precision. A historical measurement column never creates a procedure by itself.

An evidenced source suggestion appears once in the report header. Use or Change confirms a personal source label for the exact current pending candidate/version members through the [report-source API](../../src/server/INTAKE.md#report-scoped-source-confirmation). The confirmation records the group version, context and frozen members in durable workflow metadata. Later members inherit only through an append-only exact-version extension when the retained original, report anchor, printed and clinical subject scopes, source system, package occurrence and linked/shared source context are unchanged. Changed or mixed context stays unconfirmed, and returning to the earlier context never backfills an incompatible intervening member. Saving covered members projects the reviewed provider into the clinical list and source-record evidence; acquisition attribution, issuer claims, raw envelopes, unrelated groups and earlier accepted versions remain unchanged. Source inspection presents that occurrence-level record source separately from original and extraction file attribution; it does not rewrite either file attribution to match the reviewed label. The UI renders the canonical missing file-acquisition value as “Not recorded at upload” so it is not mistaken for a lost reviewed record/source label; genuinely recorded acquisition text is preserved.

When acceptance reuses an exact existing assertion, the new evidence occurrence and reviewed source receipt are retained. A scalar `Unknown source` destination may be enriched from that valid reviewed source; a known destination provider is never overwritten, so consumers should use the retained occurrence evidence when presenting multiple sources. Counted acceptance receipts identify whether the source was assigned, enriched from Unknown or retained as additional evidence beside a known provider. Confirmations, extensions, providers and receipts rebuild from retained workflow/accepted history without a model call.

Review issues may propose source labels, `metadataSuggestion:{careArea?,documentType?,topics?}`, date choices and missing Self fields. The review DTO exposes these unreviewed hints only when their exact anchor occurs in retained payload text and package evidence has the matching host-validated report/member scope. A suggested source label must occur literally in that anchor. Self suggestions require an identity issue targeting `subject`, the report's printed subject claim when report-scoped, a literal name and an unambiguous birth-date interpretation. These checks establish internal evidence alignment; they do not certify a model's transcription of a photo.

Date choices preserve printed precision and exact timestamps. An ambiguous four-digit-year numeric date can offer both supported interpretations for explicit selection. The host does not infer a century from a two-digit year, truncate a timestamp into a day, or turn an embedded date fragment into a separate date. Unknown dates and manual reviewed corrections remain available.

Import also supports a correction-first path for selected pending drafts. A user can preview and atomically apply one shared date, method or test-classification field across exact rows in one report; each row links back to its retained source, and stale or mixed selections fail without partial writes. Undo appends the inverse as another exact versioned operation, preserving both steps in draft history. A focused Moxie request remains a repair-only conversation across follow-ups and retries: the host exposes only progress, one bounded original-window reader, and the review tool, and rejects generic conversion/mapping/accepted-record calls before dispatch. Each proposed field must cite a host receipt for an exact hash-pinned original PDF page, scaled image or bounded text window tied to that row and locator. Earlier model output and a locator alone are not source proof. The model returns a compact source-linked proposal and unresolved notes, then requires a separate Apply. The server revalidates scope, values, original reads and evidence before preview and apply. Originals, identity/source attribution and acceptance never change. Missing-row extraction remains outside this repair path, and direct editing remains available after an unavailable, uncertain, over-bound or malformed source/model response.

The exact Import detail's file metadata editor offers separate per-value Use/Replace actions for ordinary metadata hints and manual source, care-area, document-type and topic edits. A stale version displays both the newer saved metadata and the requested reviewed metadata, then requires an explicit choice to keep the newer values or reapply the reviewed values against a freshly checked version. An uncertain transport retains the exact operation body for deliberate retry, dirty values survive unrelated intake refreshes, and navigation waits for resolution rather than discarding them. The report identity control instead combines identity confirmation with any checked exact values for blank Self fields in one versioned request. Conflicting saved values remain unchanged. Neither automatic identity matching nor merely displaying a suggestion changes Self, clinical facts, issuing provenance or acquisition attribution. Unsupported hints are omitted from the current review DTO without rewriting the retained envelope or accepted history. The shared JSON schema describes new converter output; runtime reading remains compatible with older accepted envelopes and their rebuild receipts.

## Bounded synchronous review work

A clinical review parses its retained workflow once and collects shared report identity facts once per report. Original-grounding lookups are scoped to that synchronous review and discarded before any await or write; a new review checks the current database, source and report boundary again. No review cache becomes durable authority.

Comparison context tokens bind the complete reviewed source confirmation through its digest plus the exact selected coverage identifiers. The digest is computed once per confirmation per synchronous pass, while each row still pins its own candidate, occurrence, mapping and evidence. Any confirmation change invalidates the context; preparation and application recompute their own digests. Existing open reviews may need refreshing after an app update. Durable records, original evidence and accepted receipts keep their existing format.
