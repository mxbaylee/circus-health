# Import performance diagnostics

When an upload, reading run or review feels slow, use **Download performance diagnostics** above the profile switcher in the sidebar (including the mobile navigation drawer). The control is available after an authorized status response even when detailed recording is off; its label explains that coverage before download. The JSON contains bounded browser operations, server timelines and page attribution for the unlocked profile. It excludes medical text, filenames, profile identity, credentials, raw model messages and clinical locators. Random operation/request IDs connect browser and server; source/run IDs are salted for each export. Protect exported files outside Git. This is reduced-content debugging metadata, not anonymous data: timestamps, request references, provider/model identifiers, document sizes/page counts and usage patterns can be correlated with other logs. Inspect an export before sharing.

Bounded operational summaries are captured by default. To collect detailed server events for a future reproduction, set `CRS_IMPORT_DIAGNOSTICS=true` in the Compose environment and restart with `npm start` before reproducing the problem. This cannot recover events that were never captured. Turning detailed recording off stops new detailed capture; previously retained encrypted events remain available to the authorized download within retention limits. `GET /api/profiles/:profile/import-diagnostics/status` exposes only whether detailed recording is enabled, after ordinary profile authorization. Failed, invalid or pending status responses do not expose the download control. Private tracing is a separate explicit opt-in and can contain health data; the download includes only its status, never its payloads.

Browser `identityReviews` entries retain only whether a name, an evidenced DOB, and a Self DOB were present, whether DOBs conflicted, and the policy status/blocking flag. They contain no identity values or identifiers. This helps distinguish missing extraction from a policy failure in future reproductions. Older downloads cannot reconstruct evidence they never captured.

## Event-window coverage

`server.eventWindow` labels detailed recording as enabled/disabled and storage as `memory_only`. `capacity` bounds retained events; `observedEvents` counts observations for this profile since the current memory window began, with `observedSince` identifying its first observation (null if none). With recording off, `notRetainedWhileDisabled` counts those observations that were not retained as detailed events. `server.events.length` and `server.droppedEvents` describe retained events and capacity eviction within this window. Counts reset after profile lock, clear or process restart. Recovered bounded summaries and the retained event archive are separate views; neither repopulates the live memory window. `omittedBeforeWindow: null` means earlier omissions are unknown, never zero; `completeness: not_established` prevents an empty or loss-free current window from claiming full-run coverage. These fields are additive to the version-1 bundle.

## Retained event archive

With detailed recording enabled, sanitized events are also written to a separate encrypted profile archive. The pending buffer holds at most 128 events and 64 KiB including the chunk envelope. A full buffer, a five-second coalescing timer, export, or normal lock/close attempts publication. Only the new chunk is serialized and written; older event payloads and the medical manifest are not rewritten. Retention is at most 256 chunks and 16 MiB of ciphertext. See the [storage and recovery boundary](../data/record-version-storage.md#diagnostic-chunk-storage-boundary). These are bounded defaults, not verified budgets for an 800–900-page run.

`server.eventArchive` reports recording state independently of availability: `available`, `partial`, `unavailable`, or `not_attached`. It includes retained chunk/byte counts, internal sequence gaps, read failures, invalid chunks/events, output truncation and current-window observed/persisted/pending/dropped/oversized events and write failures. A publication failure freezes that chunk's exact bytes for retry and drops subsequent observations while blocked; retry occurs on the timer or explicit flush. Failure never authorizes a clinical write or changes its outcome. Unknown earlier omissions and an abrupt-shutdown tail are always `null`, and completeness remains `not_established`. Even an available, empty or apparently loss-free inventory cannot prove complete capture. The five-second timer is a flush attempt, not a maximum loss window: delayed execution or failed publication can extend it, and abrupt termination loses unpublished plaintext and counter changes.

Each retained observation carries a random `windowId` plus the event's sequence. The live `eventWindow.windowId` identifies matching observations: deduplicate archive/live entries using that pair, and keep different windows separate across lock/restart. All sections of one HTTP export use the same salt for source/run references and preserve approved random request/operation references. Recovered schema versions, event names, contexts and fields are validated before export; unsupported or malformed metadata is omitted with explicit counts. Lock clears plaintext and the writer index; an export interrupted by detach discards collected archive events and checkpoints.

The compact serialized archive section is capped at 24 MiB after identifier anonymization, with truncation explicit. This cap excludes the other independently bounded bundle sections and browser JSON indentation. Export yields between bounded chunk reads so other requests can run. It reads encrypted files through the unlocked vault and remains available with future recording off. Missing/corrupt ciphertext cannot be recovered from SQLite; diagnostics are optional metadata, not medical evidence. Backups may retain older encrypted history beyond live retention.

Focused fictional tests verify encrypted session isolation, lock flushing, fresh-runtime/cache-loss recovery, default-off capture, replay/failure bounds, unsafe/corrupt metadata rejection, export bounds and a mounted download of actual retained data. Work-count checks at 256 and 512 events produce two and four chunk writes without prior payload rereads. These checks do not establish actual release-browser complaint reconstruction, full-run retention, provider speed or clinical completeness.

## Retained window checkpoints

New encrypted chunks use the strict `circus-import-events-v2` envelope: a window ID, bounded events and one fixed cumulative checkpoint containing `observedEvents`, `persistedEvents`, `droppedEvents`, `oversizedEvents` and `writeFailures`. Counters describe the boundary when the chunk bytes were built. Persisted events include that chunk's payload if publication succeeds; observed counts can include work not yet published. They do not establish that every observation became a retained event.

The complete envelope freezes on the first append attempt. An ambiguous publication retries identical bytes; later failures and dropped observations never modify the frozen checkpoint. After a successful retry, changed accounting is published in one coalesced checkpoint-only chunk when necessary. Oversized-only activity also schedules a flush. Timer, download and normal lock/close attempt publication; unchanged flushes append nothing. Persistent failure retains a bounded frozen buffer and cannot change clinical outcomes. If final publication fails or the process ends abruptly, its later counter changes remain unknown after restart.

`server.eventArchive.windowCheckpoints` exports the latest retained valid checkpoint for each window. Never sum cumulative checkpoints for the same window or add them to overlapping `currentWindow` counters. The collection is bounded by retained chunks and included in the 24-MiB serialized export budget; space is reserved so truncating events does not hide later checkpoints. Known retained dropped/oversized events or write failures keep the archive `partial`, even when the new live window has clean counters. Exact envelope/checkpoint keys, safe nonnegative integer counts, conservative accounting and nonregressing window counts are validated; invalid or unsupported envelopes are counted as invalid chunks, with no legacy decoding or automatic reset.

Checkpoints remain subject to eviction, corruption and publication failure. An entirely evicted window leaves no recoverable checkpoint; `omittedBeforeInventory` and `crashTailEvents` remain null, and `completeness` remains `not_established`. These protected metadata counters preserve known retained losses, not collection-start/run scope or complete-run qualification. ## Request input composition

With detailed recording enabled, each physical `model.request.started` observation measures the outgoing body after transcript compaction. Its `providerRequestId` distinguishes physical requests, including retries and replacement requests. These measurements do not change the request, fit limits or retry behavior. Detailed recording off skips composition measurement.

`inputMessageCount` counts message array entries. Fixed `inputSystem`, `inputDeveloper`, `inputUser`, `inputAssistant`, `inputTool` and `inputOther` prefixes expose `Messages`, `Characters` and `Bytes`: message counts, content-text UTF-16 code units (JavaScript string length) and UTF-8 bytes. Text content arrays contribute their text parts; tool-result text belongs to the Tool bucket. Unknown roles and non-object entries belong to Other and mark the measurement incomplete. The bucket never retains an arbitrary role name.

`inputArgumentCharacters` and `inputArgumentBytes` count assistant function-call argument strings separately from assistant content. `inputToolDefinitionCharacters` and `inputToolDefinitionBytes` measure the serialized tools array, including its JSON framing and schemas. `inputMediaTransportBytes` counts file-data and image-URL strings, including data-URL/base64 overhead and remote URL bytes. It does not measure decoded media, remotely fetched bytes, image/PDF content or provider tokenization. Existing `requestBytes`, `pdfParts`, `imageParts` and transcript-fit measurements keep their existing meanings. Message/argument text excludes JSON framing; category bytes need not add up to the total serialized request bytes.

`inputUnsupportedShapes` counts unsupported message, role, content-part, function-call or tools shapes. `inputCompositionComplete: false` means recognized subsets were counted but unsupported content remains unmeasured; zero subset counts must not be read as zero total content. If measurement throws, all composition counters are null and completeness is false. No content, arguments, schemas, names, URLs, credentials or content fingerprints appear in these new fields. The fixed counters fit the normal observation field bound alongside private-trace linkage and survive the encrypted archive's schema validation.

These are per-request metadata counters, not full-run qualification. Archive budgets, earlier omissions and shutdown-tail limits above still apply. ## Reading a complaint

1. Find the operation by time, kind and outcome. Inspect its total browser duration and request IDs. Server timelines expose current stage, last progress, elapsed time, interruption/error state and dropped observations.
2. For upload, compare browser transfer progress with server stream wait, hash/write/fsync, original retention and encrypted/curation publication. Transfer completion does not mean the original is durably retained. `upload_receive` includes publication; dividing its duration by bytes is not network throughput.
3. For processing, inspect the queued stage and queue wall time, then preflight, page queue/setup/render or native-PDF extraction, provider requests, retry backoff, tool calls, journals and continuation. An explicit resume starts a fresh queue-wait observation so user-paused time is excluded; older unmeasured queue time stays unknown. Resource peaks can indicate local contention. Provider request time includes transport, upstream queueing and response transfer; it does not measure upstream compute separately.
4. For review, compare API wait/response decode with server query, assembly, identity and acceptance validation/application/publication. `review_open` measures a resource load followed by a render opportunity; secondary resources can complete later. `review_save` ends with receipt/status presentation, not every subsequent background refresh. `action_work` includes awaited child requests. Human reading/thinking time is not counted as application latency.

Browser API wait includes safe-read coalescing, bounded recovery and buffered body transport (and XHR's buffered upload response). `response_decode` measures the subsequent JSON decode/body access. The two cannot establish an exact network/server split. `render_wait` spans a state update to two animation frames, with a 250 ms fallback timer when frames are throttled (a blocked main thread can delay that timer); it is not pure React CPU time or proof that hidden-tab pixels were painted. Visibility and `renderObservation: two_frames|timeout` are retained. Cumulative count/total/max/failure statistics (up to 64 phase types, with `phaseTotalsTruncated` on overflow) preserve slow stages after detailed events are evicted; their totals include nested/overlapping work and are not end-to-end latency. Server phase union excludes coarse request/active-run envelopes and avoids double-counting overlaps; the remaining wall time is explicitly unattributed, not assigned to network or model compute. Process CPU/RSS/event-loop and free runtime/tmpfs samples are process-wide, shared by concurrent work; worker RSS is a post-read sample, not a worker peak. `resourceSampleCount: 0` means the operation finished without a process sample, so its zero-initialized peaks are unmeasured; `pdfWorkerSampleCount: 0` likewise means no worker RSS was observed even when process samples exist. A null count means an older retained summary has unknown sampling history. Worker counts count observations of the post-read sample, which may repeat across ticks.

## Large-import proposal reconciliation

`gradeLargeImportReview(input)` in `src/scripts/large-import-review-grader.ts` is a pure read-only function. Supply the versioned 901-assertion oracle, `stage: proposal|review`, the retained `originalId`, an explicit binding of both fictional person keys to distinct current `IntakeIdentityPerson` snapshots, and actual `IntakeReview` snapshots. Each authority combines its `IntakeReportQueueGroup`, `IntakeIdentityReview` and retained `Intake.workflow.reportGroups` entry. Capture coherent current snapshots; do not create authority from expected labels or silently combine stale queue/review versions. Duplicate/conflicting authorities and absent or ambiguous People bindings prevent a passing result.

Normal Self confirmation returns `subject: self` with no mapping Person ID or assigned-Person object. The grader recognizes this projection only with the explicit `person-note:self`/`patient` binding, an exact current Self name/date/version snapshot, a matching `scope.selfVersion`, complete matching scoped name/DOB evidence and exact retained membership. Both report and record identity readings must be resolved, nonblocking and nonconflicting with exact expected evidence. A present contradictory Person ID or assigned-Person object fails; another person's records cannot use this Self path. Missing evidence never supplies default ownership.

The grader indexes exact clinical labels and retained occurrence membership. It checks expected literals and canonical classifications without removing signs, decimal zeros or internal spaces, and reports missing/extra/duplicate assertions and duplicate proposal occurrences separately. Original evidence must identify the bound original and exact expected pages. Report keys, printed report/subject anchors, page boundaries, candidate versions and proposal occurrences must agree with supplied authority. An occurrence's retained introducing group version may precede the latest queue header; membership is checked in that retained version, rather than assuming their version IDs must match.

The current review API exposes one original locator from `provenance.locator`. `exactLargeImportPages()` reuses `exactQualificationPage()` for each explicit semicolon-separated single-page clause, such as `page 149 analyte; page 150 result unit reference`. All clauses must validate; ranges, bare page-number lists, empty clauses, wrong originals and uncertainty in any clause fail. Both pages of the split row are required. This interpretation adds no production protocol or evidence fields.

Unspecified clinical fields must be empty. Narrow host-derived allowances follow `mappingFrom()` and the review projection in `src/server/clinical-import.ts`: a host label exactly equal to the kind-specific expected label; default recorded date role, unknown medication kind and unspecified procedure category; document date equal to the asserted date; envelope-derived document title and payload-derived text identified by allowed `mappingOrigins`; empty uncertainty lists and assets identifying only the bound original. Explicit clinical text/title, invented terminology/specimen/method fields, other assets and unknown populated fields fail. Person ID and subject are graded separately against explicit People bindings, assigned identities and evidenced name/DOB. Assignment snapshots may omit their optional DOB only when the required current Person binding and both identity readings still supply the exact DOB; a present contradictory assignment DOB fails. Missing ownership stays unresolved; contradictions fail at either stage. An optional record-level identity scope must agree with actual group scope and occurrence membership.

The `circus-large-import-review-grade-v1` result contains fixture keys/counts and fixed mismatch categories, without runtime IDs, names, source text, questions or mapping values. `exactRecords` counts unique clinically/provenance-correct assertions within a snapshot; missing assertions still prevent a complete pass. `clinicalProvenancePassed` requires the complete oracle with valid authority. `ownershipResolved` requires complete, nonconflicting assignments, nonblocking resolved identity and no unresolved review issues or unanswered questions. Proposal-stage `passed` permits unresolved ownership while refusing contradictions; review-stage `passed` requires ownership resolution. `reviewReady` requires both dimensions at either stage. None is acceptance permission or proof of extraction coverage, diagnostic collection, accepted public projections, original integrity or recovery.

Focused tests include full synthetic oracle/adversarial cases and a real profile-authorized HTTP upload→proposal→review path with independently written envelopes, two saved People, all three clinical kinds and the split assertion. ## Finding a processing failure

Inspect `model.tool.failed` and failed phase observations for `reasonCode`, `errorType` and `errorCategory`. Host validation errors retain their named code even when wrapped for model feedback. When a trusted validator supplies them, `validationCode`, `validationPath` and `validationLine` identify the failed check and JSONL line. Paths include only approved schema fields; array indexes are generalized and unknown property names are replaced. Exception prose, argument values, record text and arbitrary error properties are excluded. An unexpected exception retains its safe type, without guessing its cause.

Default-on timelines retain `firstFailure`, `latestFailure` and `latestValidationFailure` independently of the detailed event ring, within the same operation, age and total-size limits below. A later `no_progress` therefore does not erase an earlier retained validation failure. These are observed failures, not a claim that the first one caused the final outcome. Historical exports without these fields cannot retrospectively recover a specific validation failure.

### Version conflicts and repeated reads

`VERSION_CONFLICT` includes `expectedVersion` and `currentVersion`. When observed in this unlocked runtime, it also includes `lastChangeCategory`, its age, and counts of intervening identity, proposal, acceptance, review, question, plan and source-text changes. `versionHistoryComplete` is false after missing observations, restart, eviction or a state fingerprint mismatch; zero observed changes then does not prove no changes occurred. The optional ledger holds at most 64 sources and 32 version changes per source, uses host-selected categories rather than request labels, and is not medical recovery authority. Mutations outside this instrumented path remain unknown. A recorded category is evidence of a version change, not proof that it alone caused the model's later behavior.

The stale-batch handler preserves these facts through model feedback. It asks for fresh pinned context and records the bounded recovery attempt and its limit. This remains a safe pre-write rejection; it does not automatically replay or rebase a proposal. Only durable batch progress resets that consecutive stale-version budget; successful reads alone do not. No retry or acceptance policy is changed by diagnostics.

Each successful source/context read records a run-local `windowOrdinal`, numeric page/offset when available, an approved context-section name, repeated-window count/limit and the counts used by the progress baseline (seen windows, candidates and accounted units). These explain `CONVERSION_NO_PROGRESS`: the third successful read of the same window at an unchanged progress baseline pauses reading. The ordinal distinguishes windows without exposing source/member IDs, JSON pointers or text. It is local to the active run state, not a durable source identity, and restarts can reset it. Page/offset can be absent for non-page windows. Host read completion does not establish that the provider consumed the result.

`recoverySequence` retains up to 48 ordered failure, recovery, read and post-failure tool-completion observations independently of the ordinary detail ring. `recoverySequenceDropped` reports its evictions; first/latest failure summaries remain separate. The sequence survives normal summary persistence within the existing total-size/age bounds, but is not a complete audit log. Read entries emitted immediately before a no-progress exception can precede its terminal failure observation. These fields describe new observations only; older downloads cannot recover missing version provenance or intermediate steps retroactively.

### Source text prerequisites

Older builds report `SOURCE_TEXT_CHANGED` for several different conditions. A missing or stale proposal revision pin, or an unread current durable text revision, now reports `SOURCE_TEXT_REQUIRED`. A detected change to previously observed source text retains `SOURCE_TEXT_CHANGED`. New exports distinguish these using `hasSuppliedSourceTextRevision`, `suppliedSourceTextRevisionMatches`, `currentSourceTextRead`, `sourceTextChangedSinceRead`, and `sourceTextRepairable`, without exporting revision IDs or source text. Older downloads cannot distinguish these cases retroactively.

Only the host's pre-publication prerequisite check can offer repair when no observed source revision has changed externally. The model must read the relevant current durable passages, rebuild the proposal, and supply the current text and intake versions; the host never patches or replays a stale proposal. Every plan/batch/proposal handoff carries `proposalSourceText` with the current revision and read requirement, independently of the intake version. This uses the existing run-wide malformed-input budget (third failure pauses; successful reads do not reset it). A detected external correction, downstream publication error, or uncertain write remains terminal. Reaching this prerequisite says nothing about name confirmation or clinical completeness.

## Capture and retention

Lightweight summaries are captured by default: at most 64 operations, 256 events per operation, 512 KiB serialized per profile, and a seven-day inactivity expiry. An operation still receiving events can retain an older start timestamp. Each operation also retains up to 128 related import IDs, with an explicit truncation flag, so upload-to-processing links survive detail eviction. The separate encrypted diagnostics sidecar uses the unlocked vault key and is outside the medical evidence manifest and SQLite recovery authority. Writes coalesce for five seconds and flush best-effort on normal close/lock; hard termination can lose pending observations, and event-loop delay or publication failure can extend that loss window. Lock clears plaintext. Inactive-operation pruning happens on capture/load/export/write; ciphertext in a locked archive is not autonomously rewritten until unlock. Exports report eviction and read/write failures. Diagnostics failures do not alter clinical outcomes.

Live-stage state is retained separately from bounded timeline detail, with at most 128 open spans per operation. Interrupted spans and spans whose terminal detail was evicted keep their duration unknown; `lifecycleIncomplete` discloses unavailable or overflowed tracking.

Default summary capture accounts for immutable event sizes and bounded metadata for the changed operation, rather than serializing the whole retained state on each event or eviction. A persistence flush serializes once. CPU/RSS and event-loop samples remain periodic; free filesystem capacity is sampled asynchronously at most every 30 seconds, with explicit sample age, pending state and unknown values before a sample is available. These observations are not a reservation or an instantaneous capacity guarantee.

Host plan creation has a distinct `source_indexing` phase and visible indexing state. Reading activity reports observed recent intervals between page-read completions within the current turn and the last host page-preparation duration. Intervals include repeated reads and intervening model/tool work; they are not provider compute time or an ETA. Continuation resets the sample and shows a restart notice. Accounted-section counts do not certify extraction completeness.

Every started provider request receives a terminal observation, including a successful HTTP status with no response body (`empty_response`), reader setup failures and interrupted streams. A failed run must not remain displayed as an active provider wait.

Detailed server events require `CRS_IMPORT_DIAGNOSTICS=true` and retain at most 10,000 events in memory. `CRS_IMPORT_DIAGNOSTICS_CONSOLE=true` additionally emits metadata to the server console; browser console output requires `sessionStorage['circus:import-debug']='1'`. These are distinct from protected, explicitly enabled private payload traces; private payloads are excluded from this download.

The browser retains 500 API events and 64 completed operations in memory, clears them on profile change/lock, and posts strict summaries to the same profile. Each operation retains at most 32 request references and 64 phase observations, marks truncation, and never stores them in localStorage. Reporting is bounded, cancellable, best-effort and does not block the user action. `GET` and `POST /api/profiles/:profile/import-diagnostics` require the normal unlocked-profile session authorization. Summary ingestion accepts at most 32 KiB and does not flush the medical archive.

## Page attribution

Durable conversion checkpoints count successful logical host reads, provider-acknowledged reads and physical request attempts separately. A PDF compatibility retry does not repeat the logical tool read; its extra host rendering has a separate fallback timing. Native-PDF/image part counts describe actual wire requests. Repeated exposure of retained evidence is recorded even when the host did not reread a page. Canonical request totals count each attempt once, including retries/failures. Input/output/cache usage is retained only when reported; missing usage/cache remains explicitly unknown. Page token shares divide reported request usage equally among its attached evidence scopes; these are estimates, not exact token billing or exclusive page cost. A request can expose several pages, so page request-exposure counts must not be added as unique requests. Unallocated requests remain separate.

The export joins current/superseded extraction units, batches, proposal occurrences, candidate versions and acceptance receipts. Overlapping or multi-page unit associations are shared and must not be summed as unique records. Coverage is durable unit disposition, not a claim of clinical completeness. Legacy or unscoped records and missing history stay explicit; absence of a measured proposal is not proof of a zero-yield page. The export selects at most the latest 100 intakes, reads at most 8 MiB per selected journal and 32 MiB across journals (with a bounded 10,000-entry generation scan), and caps output at 4,096 aggregate page scopes and 50,000 metadata work items. It reports omissions; incomplete selection/history makes page yield and whole-import usage incomplete. It does not reread every historical chat at download time.

Whole-page text-layer character counts and host-read timing aggregates are retained in the conversion checkpoint alongside page attribution, so event-ring eviction does not erase only the text-count side of a yield comparison. Counts explicitly distinguish known, unknown and conflicting measurements. Historical missing counts are null, not zero. An observed zero text-layer count can describe a scanned page with substantial clinical content; it does not justify skipping extraction. Token shares remain estimates and no triage feature is enabled by this measurement.

## Representative provider qualification

For a bounded diagnostics exercise on a real adopted route, use `CRS_QUALIFICATION_SCENARIO=tiny`, `CRS_QUALIFICATION_FORMAT=auto`, `CRS_QUALIFICATION_REPEAT=1`, `CRS_QUALIFICATION_ACCEPT=1` and `CRS_QUALIFICATION_DIAGNOSTICS=1` with the same opt-in and external paths shown below. The fixture has one PDF page with four independently fictional observations. After a complete normal Import batch and exact review, the harness accepts only oracle-exact rows, captures the diagnostics export before lock/recovery, and checks durable acceptance and cache-loss recovery. Its diagnostics grade requires untruncated detailed and recent-operation evidence; model requests, active work and original-page reads correlated in order; the tagged upload's original-publication and retained-import events joined through their shared curation span; import-correlated acceptance phases after reading; and absence of the fixture's patient name, DOB, source system and row markers from the metadata export. The tagged review-feed query is an ordered profile-wide witness; the export does not give it an import ID, so exact report review rests on the separate acceptance oracle. A canary check establishes only that these known strings are absent. The recent-operation timeline has a 256-event detail bound and can report dropped events even for a one-page route; this grade rejects that incomplete evidence. A passing tiny run does not qualify representative clinical accuracy, browser download behavior, arbitrary private content or a future provider complaint. The remaining diagnostic complaint gate is tracked in [CRS-154](../todo/CRS-154.md).

Runtime fictional capability checks occur before first model work on the selected route after startup/configuration changes. They establish basic tool/PDF/image acceptance, not extraction accuracy or cache savings. Readiness/boot checks do not incur inference. Native PDF remains preferred after successful proof; lossless PNG preserves small text on unsupported or unsafe native pages.

The opt-in qualification harness creates its own fictional encrypted archive and uses the supported npm → Compose → LiteLLM deployment. From the repository root, with existing absolute output and `CRS_STATE_DIR` directories outside Git and operator-owned configuration:

```sh
CRS_PROVIDER_QUALIFICATION=1 \
CRS_QUALIFICATION_OUTPUT_DIR=/absolute/path/to/qualification-receipts \
CRS_MODEL=health-primary \
CRS_LITELLM_CONFIG=/absolute/path/to/proxy/config/litellm.yaml \
CRS_STATE_DIR=/absolute/path/to/proxy/state \
CRS_LITELLM_ENV_FILE=/absolute/path/to/proxy/credentials/provider.env \
CRS_QUALIFICATION_REPEAT=2 \
node src/scripts/qualify-provider-pdf.ts --run
```

Omit `CRS_LITELLM_ENV_FILE` when the route does not need it. The default `CRS_QUALIFICATION_SCENARIO=quick` compares autonomous extraction against 64 literal lab records across four dense/scanned fictional pages. `CRS_QUALIFICATION_SCENARIO=long` uses 100 pages with 400 observation, medication-order and performed-imaging records, alternating text and scanned pages. The harness creates one normal Import batch and polls its coordinator through productive automatic slices, without calling direct conversion or manually resuming a paused run. Long qualification has a 125-minute wall bound (a qualification harness deadline, not an application reading allowance); quick qualification keeps its 16-minute bound. These harness deadlines do not limit productive application jobs. Both formats are checked against an independent literal oracle, including missing/extra/duplicate records, unsupported added clinical fields, exact original file and unambiguous page provenance, complete coverage and actual wire media. Complete-file qualification also requires observed host reads and provider-acknowledged exposure for every original page; a completed plan or correct answers inferred from a partial read cannot substitute. Missing or truncated delivery history cannot pass. An unsupported PDF route is reported unavailable and cannot pass both-format qualification.

The fixture explicitly identifies its issuing software and separates result cells from unit labels. Pre-review extraction grading permits a cautiously unknown subject while preserving every literal clinical and provenance check; accepted grading requires Self after exact identity review. By default proposals stay unaccepted. `CRS_QUALIFICATION_ACCEPT=1` additionally uses counted acceptance only for oracle-exact records in the harness's own fictional profiles. It checks public accepted values, numeric comparators, date precision, statuses and provenance; fields without an independent public projection, such as specimen/method, are checked in retained accepted mapping metadata. It also checks idempotent receipt replay and equality after lock, deletion of that profile's disposable cache and recovery unlock. The source fixtures, encrypted fictional archive and receipts remain outside Git. The opt-in acceptance step can explicitly confirm an image-only page without a host-readable DOB only for the unchanged, hash-checked fictional original and its known patient. Conflicting identity evidence still stops qualification. The harness refreshes current scopes and records after each confirmation.

For one shared long-import measurement, use `CRS_QUALIFICATION_SCENARIO=long`, `CRS_QUALIFICATION_FORMAT=auto`, `CRS_QUALIFICATION_REPEAT=1` and `CRS_QUALIFICATION_CACHE=configured`. This schedules one PDF-first import with verified PNG fallback if native PDF is unsupported. It does not schedule a second raster comparison or a cache matrix. `FORMAT=pdf` or `png` restricts an explicit comparison to that format; the default `both` preserves the two-format comparison. The same run retains its bounded diagnostic export alongside the qualification report, including after extraction failure when the application remains reachable, and again after optional acceptance. Use that timeline and durable page attribution for latency, continuation and yield together. Missing/truncated history remains unknown; one run cannot establish causal cache savings. The report records setup, media-probe, upload and conversion stages with timestamps, and saves failures before teardown. After cancellation, read-only diagnostic, batch and partial-review capture shares an independent ten-second cleanup window; stack teardown then stops remaining server work. The runner retains generated fictional recovery material and proposal evidence in mode-600 files under its mode-700 external attempt directory, separately from the privacy-safe diagnostic export. Those private receipts support later failure inspection and stay outside Git. Conversion status is polled every five seconds: each successful encrypted-profile request can also flush the workspace, so frequent polling adds work and consumes diagnostic retention. Slower polling leaves more room but does not guarantee a complete event history. Grade exact extraction, durable delivery/usage attribution and detailed timeline completeness separately; a truncated timeline still prevents an overall qualification pass.

`CRS_QUALIFICATION_CACHE=paired` runs cache off/on/on/off for PDF, then off/on/on/off for PNG; each position uses fresh fictional profiles. `CRS_QUALIFICATION_REPEAT=1|2` controls repetitions within each position. The default `configured` mode uses the launcher setting `CRS_PROMPT_CACHE=false` unless explicitly set to `true`; the launcher maps it to the runtime capability. Provider-reported cache usage is retained; absent usage stays unknown. Run order, request counts and durations are observations, not proof of savings: provider cache temperature cannot be reset by this harness, and upstream load/model variability remain confounders. The report therefore does not claim causal cache savings. Long-run acceptance and representative live-provider evidence remain release gates until these checks actually pass on the configured route.

## Upload admission and retention

A completed upload staging file is adopted by rename within the runtime filesystem (`upload_original_adopt`), then hash-verified by rereading that same inode and fsynced before publication. This checks the retained bytes against the receive hash; it is not verification of an independently written second copy. Cross-filesystem mounts fall back to exclusive copy (`upload_original_copy`) and verify the copied bytes. Retained originals remain byte-identical. Receive, retention and encrypted-publication verification remain separate stages.

An authenticated upload with a known `Content-Length` is refused before body staging when it exceeds the configured upload limit or reported runtime capacity cannot hold the full planning allowance: twice the original size plus the larger of the extraction limit and 100 MiB. The refusal names the actual limit or capacity and corrective action; archive requirements depend on verified reuse after hashing. Unknown capacity is not treated as zero, and chunked uploads retain downstream bounded receive/storage-failure checks. This is admission based on an observation, not a reservation or a measured peak guarantee; publication, cross-filesystem copies, concurrent work and unreported quotas can still fail later. Unlock separately checks its eager workspace/database and configured upload allowance; originals are decrypted per file on demand as described in [runtime capacity](../setup/docker-runtime.md#runtime-capacity-and-containment).

## Build identity in diagnostics

Downloads include `clientBuild` from the loaded browser bundle and `server.recentPerformance.runtime` from the server artifact captured when diagnostics starts, even when detailed events are off. Each contains the existing `buildId` UUID, the full Git `revision`, and `worktree` (`clean`, `dirty`, or `unknown`). The UUID still identifies the actual build; a dirty revision names its base commit, not an exact committed source tree. Different client/server UUIDs reveal a stale browser bundle. This is the exporting runtime identity, not retroactive proof that every retained historical operation ran on that build.

The supported `npm run start` and `npm run image:build` launchers read Git without mutation and pass only the revision and worktree state into Docker build arguments. Vite embeds these fields in both the client and its manifest. Docker never receives `.git`, paths, branch names, or diffs. Direct Docker builds without those arguments, source archives without Git, and old manifests explicitly report unknown revision/state; legacy manifests still retain their valid build UUID. Rebuilding is required to add metadata to old images. The running server does not inspect a later host checkout or invent a SHA.

## Simple Import progress

The Import activity strip shows how many files are queued or being read, the number of source records discovered across the current batch, and one calendar elapsed time since that batch was created. Provider waits, preparation and earlier pauses are included; the displayed clock freezes at the recorded batch update when reading is paused or complete. It never sums file durations. These discovered records are proposals, not a claim of complete extraction or accepted clinical records.

Local preparation time is not an estimate of model completion. The strip shows read/accounted units and located exceptions separately from proposed records. It says **Estimating…** before a useful rate exists or while availability is unknown. Once rates are available, a broad heuristic combines remaining file work and known retry delays, using hours for long imports. These ranges are not calibrated completion guarantees. Detailed model passes, page timings and diagnostics remain available for investigation. See [automatic recovery](automatic-recovery.md) for the progress and wait contract.
