# Profile management

Profiles are independent encrypted local archives. The default runtime implements required recovery verification and session-scoped authorization, with one unlocked profile at a time across the application. Successful unlock or setup activation locks other profiles and revokes their access; invalid proof leaves the existing profile usable. See [encrypted profiles](profile-encryption.md) and the [current storage contract](profile-storage-and-rebuild.md). Real-device passkey compatibility remains a release validation gate.

## Creation and selection

The required creation flow is Profile name/icon and Self identity → Save recovery key and acknowledge it → Verify recovery key → Open profile with full recovery phrase/file verification → explicit optional Add passkey / Skip choice → skippable clinical onboarding. New ordinary profiles require the actual full name used on health records and a complete, valid, nonfuture birth date before allocating an archive or keyring. The profile display name is separate from that identity. Copies preserve their source identity and generated Placebo accounts supply fictional identity. Existing profiles and already-staged legacy setups remain usable without retroactively imposing the new creation requirement. Passkey enrollment starts only after Add passkey. Verify recovery key is disabled before acknowledgment and only advances to the separate empty verification form; actual recovery proof is mandatory before Open profile activates the archive. The recovery key is reusable; passwords and an unprotected mode are outside the agreed design. Verification is a login-style form with a hidden profile name and password-style recovery field; the password manager controls whether it offers to save it.

The UI implements separate save/acknowledgment and phrase/file verification screens, plus Add passkey / Skip after ordinary recovery. Both initial passkey choice and recovery-unlock choice must survive profile-shell remounts. The backend checks the submitted recovery secret against profile-bound encrypted staging before activation. See the [current work list](application-todo.md#product-work-and-verification).

The sidebar uses one current-profile name/icon button opening the profile modal. Rows show icon, display name, state and compact MB/GB totals. Background/border and `aria-current` identify the selected row without a redundant check. Size sits at the right edge; Self identity updates preserve the card's storage and authorization metadata. The unlocked profile's actions remain visible beneath its identity as compact icon buttons. One equal-width grid, with up to three columns, orders Resume setup while Self setup is unfinished, Add passkey when the current hostname has no confirmed key, Lock profile, and Manage passkeys when any saved key exists. Resume setup, Add passkey, and Lock profile use the primary accent; Manage passkeys remains secondary. Four actions wrap after the third, and the grid becomes one column on narrow mobile screens. A missing working passkey keeps **Setup incomplete** visible even after onboarding finishes because passkey is the primary access method and recovery remains its fallback. **Danger Zone** is a collapsed native details section containing secondary View storage and Copy profile actions plus the distinct danger-styled Delete profile action. Returning from one of these child screens restores the collapsed profile list. Retain deletion confirmation. The generated fictional profile classification is canonical `placebo` throughout data, API and code, with no obsolete profile-format compatibility in the fresh-data release. Use **Placebo account** / **Create Placebo account** in the UI; a private copy still contains private data. Locked rows retain public identity and stored-byte totals and open through the unlock flow. The unlock screen shows the profile icon beside **Open {profile name}** and a compact Back control. It presents one sign-in method at a time. A confirmed passkey for the current hostname starts sign-in once automatically. While waiting it says **Approve in your password manager.**, with **Use recovery key** available and no recovery form or disabled retry button. Choosing recovery cancels the outstanding prompt and focuses the recovery key in the login-style form; **Use passkey instead** switches modes and starts one explicit passkey attempt immediately. Cancellation and failure never trigger an automatic retry. A failed attempt offers **Try passkey again**; before the first attempt, including after returning from an unsaved-changes guard, the button says **Use passkey**. Profiles without a confirmed passkey open directly in recovery mode. Initial creation verification remains titled **Open profile** with its existing password-manager form semantics. See [storage accounting](storage-accounting.md) for shared-object counting and separately reported backups.

## Actions

- Create a profile with its own Self identity and blank editable Annual Planning note.
- Create a Placebo account containing only invented records and matching fictional source evidence.
- Make a private copy when an independent working copy of an existing profile is explicitly required. A private copy retains sensitive source bytes and is never described as anonymized.
- Delete a live profile only after exact name and version confirmation. Existing backup packages remain separate.

Profile operations stage a complete result before publication. A copy validates source containment, rewrites only profile-owned storage paths, assigns a new owner ID, publishes a fresh encrypted record baseline, and opens the result only after validation. Creation and copying must not reset another profile or reuse its open database.

When local switching, locking or setup activation would leave unsaved notes, show **Save changes before continuing?** with Back, Save and continue, and Discard and continue. Save uses each mounted editor's actual save/retry path, including linked notes in the third column, and stops on failure. Discard suspends local writers for the transition without reverting accepted versions. A cancelled or failed unlock restores the same draft. Pending attachment/history work must finish or be resolved before continuing. A lock from another session still revokes access immediately; local confirmation cannot defer it.

Generated Placebo accounts are seeded from inline deterministic fictional fixtures. They never inspect or copy a private profile, archived Placebo account, or repository health record.

## Onboarding and later actions

Self's editor supports up to 32 explicitly saved known names, each at most 200 characters, with normalized duplicate checking. Exact saved names and aliases participate in import identity review; names are never appended from model output or confirmation receipts. Exact name plus complete DOB gives strong evidence, one exact fact or a compatible partial-DOB match gives limited evidence. Initials or omitted-middle-name similarities that do not match an explicitly saved name give only a possible match requiring human confirmation. Contradictions and explicit refusals remain blocking. Matching does not accept clinical records. Later editing and legacy profiles still support partial birth dates.

Recovery options lead directly to the short, skippable Primary care provider and Emergency contact steps in **Care contacts**; no manual medication entry; a blank editable **Annual Planning** note for each new profile; and a separate post-import activation screen. New prescriptions default to personally Inactive, merging Not reviewed in the UI without rewriting old versions. Turning on a prescription creates a personal assertion distinct from provider status. Save/Done/Skip/resume and repeat imports preserve these distinctions. Earlier four-step onboarding metadata is retained as history; completion no longer demands review of every inactive prescription.

Profile details are collected before recovery setup and are not requested again. Pronouns remain editable from Self. Care answers persist through ordinary versioned Self/People operations. Provider and emergency contact each have a separate short screen with name and optional phone fields, identified by Stethoscope and HeartHandshake icons. Each screen saves or skips independently; Back returns to the preceding step, and resume opens the first unfinished step with saved contact values. Phone changes update that same linked Person, and a phone without a contact name must be completed or cleared before saving. Earlier completed or skipped `care-team` progress covers both care steps without rewriting saved records or reopening completed setup. Historical `about-you` progress is preserved but no longer required; opening care setup does not write a synthetic skipped/completed Self step. Back from Primary care provider returns to recovery options during initial setup, or Profiles when resuming; Back from Emergency contact returns to Primary care provider. Care note IDs use `note:<UUID>` and are saved in Self before creating contacts, so retries and resumed setup retain stable identity. Previously staged descriptive prefixes are repaired by retaining their UUID suffix when no corresponding Person note exists. Scheduling URL is absent from onboarding; existing scheduling and other People metadata survive setup edits. Finishing or skipping both care steps hides Resume setup after the committed Self state is loaded, including after reload. The post-import activation screen saves each switch through the existing medication status API; Done or Skip closes the screen without manufacturing assertions for untouched prescriptions. Ordinary prescription detail controls remain in the ellipsis actions, while the activation screen presents its switch directly.

Each onboarding care contact has explicitly labeled name and phone fields. A phone is saved as contact metadata on that contact's linked Person note, never as another person's name. Resuming setup loads both values from the saved contact. Phone-only entries require a name before saving; existing saved contacts are not automatically merged or rewritten to repair past ambiguous input.

View storage preserves its intended profile and offers Back to profiles. Locked profiles have no action group; the unlocked profile keeps its actions visible, including after returning from a child screen. Unlocked profiles expose Add passkey when the current hostname lacks a confirmed key, using the same profile-bound PRF enrollment and recovery fallback as initial setup. Confirmed keys remain independently usable; enrollment adds another key. Manage passkeys is available whenever the authenticated profile has any saved key, including keys for other hostnames. Its private list shows each key's hostname, creation time, and last recorded successful profile unlock, or **No recorded use** when no timestamp is available. Public profile cards retain only their hostname-specific availability hint. Last-use recording occurs after successful profile activation and is best effort: optional metadata read/write failure never turns a completed unlock into an authentication failure. Confirmation during enrollment, failed proof, cancellation and failed activation do not count as use.

Manage passkeys returns Back to profiles. Add another passkey opens the existing automatic PRF enrollment and returns to the manager on success, Skip or Back. Removing a selected key requires a separate confirmation identifying its hostname and creation time; Back returns to the manager without removing it. Removal deletes only that profile's chosen wrapped credential, preserving other keys, recovery and clinical versions. The user's password-manager entry is not deleted. Removal and usage updates reread the current keyring and publish synchronously; a removed key cannot finish an outstanding unlock assertion. Profile lock/switch clears the private list and prevents stale async results from restoring it. See action-button verification. Real-device behavior remains an external release check.

Rename edits one passkey name inline, with explicit Save name and Cancel. Names are trimmed, limited to 80 characters and cannot contain control characters; an empty or unchanged draft cannot save. New passkeys use the friendly name associated with the verified registration AAGUID, or **Passkey** when the identifier is missing, zeroed or unknown. Names are allocated once after successful PRF confirmation; case-insensitive collisions within the profile use the first available suffix starting at 2. Allocation reads the current keyring at publication, including manually renamed keys and legacy unnamed keys displayed as **Passkey**. Existing names are never renumbered after deletion, and legacy keys are not rewritten. The bundled name-only registry comes from [passkeydeveloper/passkey-authenticator-aaguids](https://github.com/passkeydeveloper/passkey-authenticator-aaguids/blob/774b3cfc940a4138bc451ae4ec9b943bf9a44c1b/aaguid.json), pinned at `774b3cfc940a4138bc451ae4ec9b943bf9a44c1b`; icons and external enrollment-time lookups are not used. Provider names are display hints, not proof of authenticator identity or PRF support. The raw AAGUID is not persisted. The saved name appears in the list and removal confirmation. Names are encrypted in current key-management metadata, bound to the profile and credential; they are available only through authorized profile access and do not appear in public cards. Renaming preserves the credential, key wrapper, recovery method, usage counter and clinical history. It changes the label in Circus Health, not the entry in the user's password manager.

Modal child screens return to their immediate parent, including nested icon selection and mobile Navigation → Profiles. Back preserves staged recovery identity and never bypasses acknowledgment or verification. Details of an already-issued setup remain fixed until activation; returning and continuing reuses the same pending setup and recovery key. New modal flows must preserve their origin, focus return, cancellation, busy state, and recovery boundaries in focused tests.

## Repository boundary

Application code, schemas, generic documentation, and synthetic tests belong in Git. Profile sources, notes, exports, backups, operational receipts, and patient-specific migration documents belong in untracked profile storage.

## Acceptance checks

- Creation works from an empty registry and survives a portable rebuild.
- Copying retains source checksums and current personal state while assigning a new owner.
- Generated Placebo accounts contain explicit fictional markers and deterministic relationships.
- Deletion requires current identity/version and cannot affect another profile.
- Closing the runtime or losing a staged operation does not publish a partial profile.
- Local profile switches resolve pending edits through save/discard confirmation, then clear mounted clinical drafts and cancel pending reads. Failed saves do not switch or lock profiles.

## Implemented classification

Fresh profiles use the canonical boolean `placebo` throughout encrypted public cards, the unlocked registry, API response metadata, shared types and lifecycle operations. **Create Placebo account** invokes `server/synthetic-placebo.ts`, which generates invented clinical records, personal notes and source evidence without reading another profile or an archived delivery. Private copies serialize `placebo: false`. The classification does not change encryption or access checks. The obsolete archived enrichment recipe and its external-fixture integration were retired; generated profiles are covered by self-contained synthetic tests, including encrypted creation, copy and cache-loss rebuild.

Circus Health's project-owned branded portable, backup, lineage and evidence formats use the `circus-health` slug. Old-brand identifiers and obsolete profile flags have no compatibility alias in this fresh-data release. Existing neutral contracts such as `health-record-v1` remain unchanged.

Provider-name validation covers 34 focused backend checks and 49 mounted UI checks, with additional removal-stability assertions. A separate actual Make/Docker stack passed chat and encrypted recreation/cache-loss checks using a controlled provider and fictional archive. These checks do not establish physical authenticator or browser PRF compatibility.


Report identity review defaults to Self when DOB is missing or compatible; a unique grounded saved-name match does not need repeated confirmation. An unfamiliar name can be explicitly added as an alias when DOB does not conflict. A differing evidenced DOB requires another person and cannot be bypassed through either the report sidebar or a clinical draft. Clinical field drafts remain editable while ownership is unresolved.
