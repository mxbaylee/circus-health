# Model providers through LiteLLM

Status: Docker Compose plus LiteLLM Proxy is the only supported application and model path. This specification covers both Moxie's Assistant and the dedicated **Import** page. The pinned proxy and encrypted app have a controlled-upstream tool-loop check; real-account authentication and real-model workflow gates remain open. Physical-passkey and print gates are tracked separately in the application checklist.

## Required topology

The supported route is:

`Circus Health → private LiteLLM Proxy → one explicitly configured upstream model`

Circus Health owns profile scope, source selection, tool execution, review, acceptance, journals, and durable publication. LiteLLM translates the application-owned tool loop to the selected provider. The proxy receives no health archive mount and cannot write accepted records. Direct native adapters and the operator-supplied MCP worker are superseded deployment paths; their code and historical validation receipts do not define current setup.

For runnable ChatGPT, hosted API, and local Ollama setup, follow [installation](installation.md#choose-a-model-route). Start the two-container stack with an exact LiteLLM `model_name` alias:

```sh
DATA_DIR=/absolute/path/to/archive/data MODEL=health-primary LITELLM_CONFIG=/absolute/path/to/proxy/config/litellm.yaml STATE_DIR=/absolute/path/to/proxy/state npm run start
```

`DATA_DIR` must be an existing absolute external directory ending in `/data`. `LITELLM_CONFIG` must be an existing YAML file outside Git and the archive and is mounted read-only into the proxy. `LITELLM_ENV_FILE` optionally supplies raw `KEY=value` provider variables only to that proxy; values are not shell-evaluated. `STATE_DIR` defaults to `~/.local/state/circus-health` and retains the generated proxy master key and provider OAuth state; it may be changed to another external directory. `PORT` defaults to `3001` on loopback.

`MODEL` is an alias, not an inferred provider or model. The alias must match exactly one intended LiteLLM deployment in the supplied configuration. Do not silently switch providers, models, or local/cloud execution after a failure.

## Provider routes

The default [ChatGPT template](../deploy/litellm/config.chatgpt.example.yaml) selects `chatgpt/gpt-6-astra` with `model_info.mode: responses`, `supports_vision: true`, and an explicit `supports_pdf_input: true` declaration. [OpenAI documents the Astra model identifier](https://developers.openai.com/api/docs/models/gpt-6-astra) and [PDF file input for vision-capable API models](https://developers.openai.com/api/docs/guides/file-inputs); those API documents do not establish acceptance by this subscription backend. The pinned LiteLLM proxy bridges the application's chat-completions requests to Responses, including structured tools and native PDF file parts. The route authenticates through its own OAuth device flow and `CHATGPT_TOKEN_DIR`, independently of host CLI credentials. This subscription route is distinct from Platform API-key billing. Model access still depends on the signed-in account, and configured image capability still requires a fictional image check. Native PDF translation is tested offline; actual account/backend acceptance is checked dynamically with fictional evidence before private PDF use. See [LiteLLM's provider contract](https://docs.litellm.ai/docs/providers/chatgpt) and [OpenAI authentication](https://learn.chatgpt.com/docs/auth).

Run `STATE_DIR=/absolute/path/to/proxy/state DATA_DIR=/absolute/path/to/archive/data npm run login:chatgpt` in the user's terminal before first inference. Device-code login must be enabled in the account/workspace settings. The command prints the device URL/code there, runs no model request, mounts no archive, and verifies tokens were saved to `STATE_DIR/chatgpt/auth.json`. Use that same state directory at launch. Do not copy host auth files or paste login material into chat.

The [login helper](../deploy/litellm/login.py) invokes the pinned [`Authenticator.get_access_token`](https://github.com/BerriAI/litellm/blob/v1.99.1/litellm/llms/chatgpt/authenticator.py), which implements login, cache reuse and refresh. The helper verifies persistence because the underlying writer can log a file-write failure without raising it. Network-disabled tests exercise those branches with fictional responses; they do not prove real account access or refresh eligibility. First inference can also initiate device login, but the app's shorter connection-test timeout and disabled persistent proxy logs make it unsuitable as the setup interface.

Hosted API providers use their supported LiteLLM model routes and credentials. Put secrets in the proxy-only environment file or another LiteLLM-supported secret source outside Git and `DATA_DIR`. Do not place credentials in the YAML when that file may be shared, in the model alias, or in URLs.

The [Ollama template](../deploy/litellm/config.ollama.example.yaml) selects `ollama_chat/qwen3:4b`, a text/tool starting model. Its listed Q4_K_M weights are about 2.5 GB; memory use also includes context and other processes. The operator installs the exact local model and disables cloud features. The health stack neither downloads weights nor infers local execution from an alias. Confirm the actual endpoint, installed model metadata and absence of remote fallback. Existing tool-capable local models can be selected explicitly without another download. See the [Ollama model card](https://ollama.com/library/qwen3:4b), [server configuration](https://docs.ollama.com/faq) and [LiteLLM Ollama route](https://docs.litellm.ai/docs/providers/ollama).

Every selected model must support the tool calls required by the application. PDF pages prefer native PDF input when a fictional PDF check verifies the selected route. Otherwise they require lossless PNG input; photos and other image evidence also require image support. Unsupported media remains an explicit coverage gap; the model must never claim to have inspected omitted evidence.

## Configuration and routing controls

The operator-owned LiteLLM YAML defines `model_list` and provider parameters. The selected alias must match exactly one non-wildcard entry. The launcher retains only that entry in the runtime proxy configuration and disables proxy retries, fallbacks, and automatic rerouting. The application owns its narrow request recovery and stable operation-id/idempotency controls: an HTTP 503 received before any model reply is accepted or host tool dispatched retries the exact same request at most twice, after one- and two-second cancellable delays. Every physical attempt counts toward import diagnostics and the cumulative reading request budget. Persisted counters, current active time and explicit-extension offsets are checked immediately before each attempt, including rounds after a batch attaches to a live linked conversion, so a retry at the whole-job boundary is neither sent nor counted. Passive batch observation does not cancel an already-admitted attempt or its guarded tool result. Transport failures, timeouts, rate limits and other HTTP statuses do not enter this retry path.

Configured prompt/payload logging, callbacks, caches, databases, and external observability are rejected. Docker's persistent log driver is disabled, although the attached proxy terminal may report provider errors. Provider-side files, logs, retention, and training policies remain the operator's responsibility. Local-only operation must not use hosted OCR, callbacks, or fallback models.

The launcher generates a persistent LiteLLM master key in `STATE_DIR`, supplies it to both containers, and does not expose it in command arguments. The configuration is read-only; provider environment variables enter only the proxy. The health archive is mounted only into the application. Credentials, OAuth tokens, proxy state, and model weights remain outside profile data and require separate backup and access controls.

The launcher derives the expected response identity by stripping the provider prefix from the selected entry's `litellm_params.model`, and derives image declaration from `model_info.supports_vision`, defaulting to false. `RESPONSE_MODEL=EXACT_RETURNED_IDENTITY` and `IMAGES=true|false` are advanced overrides for provider-specific replies. A matching identity helps detect some routing mistakes but cannot attest provider infrastructure; image declaration still requires a successful fictional image test.

Native PDF defaults to `PDF=auto`; Compose passes `HEALTH_AI_PROXY_PDF` to the application. Static `model_info.supports_pdf_input` and bundled model metadata are hints only. At first use after process startup, the application sends a tiny independently fictional PDF through the actual route and requires a tool challenge plus the code present only in its PDF bytes. HTTP readiness and container boot perform no model requests. `PDF=true` requests the same proof; `PDF=false` opts out. Receipts are ephemeral and bound to the exact configuration, credential and profile. A restart or changed configuration requires a fresh test. Tools-only success does not establish media readiness. PDF failures caused by unsupported format or an incorrect challenge can select a separately verified image fallback; authentication, rate-limit, timeout and server failures are not evidence of unsupported PDF. Connection details expose PDF status and allow an explicit fictional retest. No capability check changes the selected model or provider.

The host extracts only the requested original page in its isolated qpdf worker and sends a Chat Completions `file` part containing a PDF data URL; [LiteLLM documents this file-input format](https://docs.litellm.ai/docs/completion/document_understanding). PNG is the fallback because lossless encoding preserves small text and it is supported by the existing image routes. A native page is limited to 5 MiB; pages that cannot be safely extracted or exceed that bound use the same page's lossless PNG when image support is available. If the selected route explicitly rejects PDF input with HTTP 400 or 422, the bridge can replace the scoped PDF parts using host-provided PNG readers and retry once on the same route, then use PNG for later bridges on the same configuration/profile until an explicit successful PDF retest. Authentication, timeout, rate-limit and context failures do not trigger this PDF compatibility fallback. The fictional probe verifies basic route acceptance and reading, not complete document coverage, extraction accuracy or performance on representative records.

Prompt caching has a separate optional capability. The launcher reads the boolean `model_info.supports_prompt_caching` on the selected deployment, defaulting to false; `PROMPT_CACHE=true|false` overrides it and Compose supplies `HEALTH_AI_PROXY_PROMPT_CACHE` to the application. When enabled, the first system message uses a text block with `cache_control: {type: "ephemeral"}` at the end of the static instructions, and the continuation notice becomes a separate system message. Both that first message and the tool definitions stay identical across rounds. The marker belongs after the instructions: [Claude orders its cache prefix as tools, system, then messages](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), so marking only the last tool does not cover the system instructions; [LiteLLM supports cache markers on system content blocks](https://docs.litellm.ai/docs/tutorials/prompt_caching). With caching disabled, the existing request shape is preserved. This provider prompt-prefix feature does not enable a LiteLLM response cache or change accepted records.

A missing caching capability leaves ordinary requests without an explicit cache marker working without failing the request or displaying a warning. Request diagnostics and whole-turn usage expose `cachedInputTokens` when reported; an omitted value remains `null`, and the whole-turn count remains unknown if any contributing request omits it. No cache-hit rate or latency saving is implied by the declaration. Both the breakpoint and the additional system message still need acceptance testing against each selected route. A provider rejection of the cache field fails explicitly with `HEALTH_AI_PROXY_PROMPT_CACHE=false` guidance; use `PROMPT_CACHE=false` with `npm run start`. There is no automatic retry without the field or provider rerouting.

The application sends `disable_fallbacks: true`, validates tool names and JSON arguments, limits tool rounds and response size, and rejects mismatched response identities when configured. These controls cannot prove that the external YAML, network, provider account, or local model honors the intended route.

Inference requests have a 300-second deadline, including the response body. Operators can set `HEALTH_AI_PROXY_TIMEOUT_SECONDS=30..600` to an integer number of seconds in the environment used for `npm run start`; Compose forwards it to the application. The fictional tool-loop connection check retains its separate 60-second overall deadline; direct proxy requests without a caller cancellation signal retain a 15-second deadline. The assistant's overall run remains bounded to 15 minutes. Stop cancels an active request or 503 backoff immediately, and the host deadline is checked again before every physical retry. A longer request deadline allows a slower selected model to respond; it does not increase the fixed retry count, change models, or establish complete extraction.

Transport failures, request timeouts, caller cancellation and transient HTTP 503 responses produce distinct safe diagnostics containing only a correlation reference, HTTP status (null for transport failures), elapsed milliseconds and classification. Request contents, provider error text and credentials are omitted. Each 503 attempt is classified `transient_availability`; exhausting the two retries returns the existing visible provider failure and pauses import reading with its completed work and originals retained. A retry never selects another alias, endpoint or provider, and it never replays a host tool whose result may already have been applied.

When the application's bounded import recorder is explicitly enabled, each proxy request also emits in-memory start/completed/failed events correlated with the current request, import, batch, run, slice and turn when those scopes are available. Completed events contain HTTP status, elapsed time, request/response byte counts and validated aggregate token usage when the provider supplies it. A separate response-shape event counts JSON nodes, properties, arrays, strings and bytes without retaining keys or values. Tool events retain only the registered `health_*` tool name, index, timing, outcome and bounded argument/result structural counts. These events never include instructions, conversation text, tool argument/result values, images, authorization, endpoint URLs or provider error bodies.

A host tool rejection that synchronously ends a run still emits one metadata-only `model.tool.failed` event before the bridge returns, with the fixed `tool_rejected_after_close` code and no application error text or raw status. The process-local terminal marker distinguishes that path from callbacks arriving after Stop or profile lock, which neither dispatch another tool nor append late failure data. When the separate private trace is explicitly granted for that exact profile, the host captures a bounded error name/code/status/message before closing while the profile/run generation is still active; the normal grant, path, size and credential-redaction checks continue to apply. Errors thrown by action extensions retain only a static extension-failure classification at this boundary, so extension-defined messages, codes and statuses cannot introduce unregistered secrets into the trace.

The Import page's **Download performance diagnostics** control combines browser timings with the profile-authorized `GET /api/profiles/:profile/import-diagnostics` export. Bounded recent performance summaries are captured by default and retained in an encrypted profile sidecar; detailed server events require `HEALTH_IMPORT_DIAGNOSTICS=true`. The export includes page-level request/usage/coverage/yield attribution from retained conversion metadata. A shared export salt joins source references across sections, while random request/operation IDs join browser and server. It excludes health content and credentials. Provider-internal queueing, CPU, memory, logging and retention remain outside this local instrumentation. See [Import performance diagnostics](import-performance.md) for retention, limitations and fictional provider qualification.

## Shared application behavior

All model reads and proposals remain bound to an unlocked profile and explicit evidence. The model cannot write profile files, execute arbitrary shell commands, access another profile, or accept its own import. User acceptance calls the same versioned application API and encrypted durable publication path regardless of the provider behind LiteLLM.

Conversations, extraction plans, accepted originals, mappings, and personal record generations remain provider independent. Changing `MODEL` does not migrate or reinterpret accepted data. Startup and deterministic SQLite rebuild require no model access. A continuation uses the application's retained messages and scoped context rather than a provider conversation ID.

Setup status must distinguish archive readiness from model readiness. Report missing configuration, failed OAuth, rejected API credentials, unreachable Ollama, unknown aliases, unsupported tools, missing image support, and incompatible responses explicitly. Preserve access to saved data while the upstream provider is unavailable. Initial stack startup requires a healthy LiteLLM container.

Chat and import conversion automatically check the connection with fictional content before sending private task content. Image delivery also checks image capability; `IMAGES=true` declares support but is not sufficient by itself. Native PDF capability requires its own fictional PDF/tool challenge before private evidence is sent; static declarations do not grant it. Manual text, image and PDF diagnostics remain available in Moxie the Assistant for troubleshooting. A successful challenge establishes the checked protocol capability, not clinical interpretation quality or complete PDF coverage.

## ChatGPT streaming compatibility

The pinned LiteLLM 1.99.1 contains the forced-stream regression described in [upstream issue #34094](https://github.com/BerriAI/litellm/issues/34094) and [proposed fix #34095](https://github.com/BerriAI/litellm/pull/34095). ChatGPT forces SSE transport, but that does not mean Circus Health requested a streaming response. The affected handler conflates those choices, bypasses the ChatGPT aggregate parser and its output recovery, and can discard earlier output items when the terminal event has `output: []`. It also bypasses the post-response logging callback, so a failure observation with `raw_shape: missing` is not proof that the upstream sent no body.

Compose builds a project-scoped proxy image from the pinned digest using [the compatibility Dockerfile](../deploy/litellm/Dockerfile). Its guarded build-time patch keeps the caller's response-shape choice for ChatGPT while leaving the outbound SSE request intact. Other providers keep their existing routing. This restores the existing ChatGPT SSE parser and completed-item recovery; it does not synthesize missing clinical content or switch models. The login and configuration preflight helpers continue using the unmodified pinned base, because neither performs inference. The build also guards and patches the Responses-to-chat converter: text and function calls from one Responses output sequence are retained in one tool-call choice. Genuine Chat Completions alternatives remain rejected by the app; they are not merged. Remove the patch only after an upstream upgrade passes the exact ChatGPT regression. The exact fictional text and function-call recovery cases passed on the patched image; the later full Make lifecycle run was interrupted by host disk exhaustion and Docker Desktop failure, so that run is not passing evidence. Disposable test artifacts and untagged project builds were cleaned up during recovery; real-account verification remains open.

## Verification boundary

The opt-in [launcher integration test](../src/server/test/launch.integration.test.ts) builds the application image and runs the pinned proxy in a separate temporary Compose project with a controlled HTTP upstream. It covers tool advertisement, scoped fictional Self data returned to the model, a pending note proposal, review before acceptance, idempotent acceptance, and accepted-note survival through container recreation and SQLite-cache loss. Its scripted upstream tests protocol and application persistence, not model reasoning or a real provider.

The current launcher integration also verifies a fictional PDF challenge through the pinned LiteLLM container, checks the effective kernel/container restrictions and compares final deployed source hashes. The 2026-09-22 run passed recreation, cache-loss rebuild and crash recovery with those restrictions enabled. Its deterministic upstream verifies transport and control flow; it does not establish real-account permissions, extraction quality or provider token/cache savings.

The [offline login test](../deploy/litellm/test_chatgpt_login.py) exercises fictional device exchange, token reuse, refresh, restricted file permissions, and persistence failure with networking disabled. It does not establish real account access, eligibility, refresh, or post-recreation authentication. Separately, the hardened login helper completed a real device sign-in on 2026-09-23 and saved mode-600 authentication state. The sign-in receipt alone does not establish inference. A subsequent fictional run separately verified tool, image and native-PDF input on the default Astra route after stack recreation with the same authentication state. Full extraction/acceptance and live token refresh remain open. Real ChatGPT, hosted API, and Ollama routes still require the completion gates below.

The [offline native PDF test](../deploy/litellm/test_native_pdf.py) sends a fictional one-page PDF through the actual LiteLLM Router and ChatGPT-to-Responses bridge to a loopback fixture. It verifies identical PDF bytes in `input_file`, preserved tool history and the unchanged `chatgpt/gpt-6-astra` route. Its subprocess uses a fresh home directory, no inherited provider credentials, process-lifetime fictional authentication and a permanent guard against non-loopback networking. The test passed with LiteLLM 1.99.1 from upstream tag commit `10f4033437df30b91b5dbf2b64711d0a8683fc52`, whose three patched source hashes matched the pinned image guards, plus locally resolved Python dependencies. The same nine offline native-PDF, stream-semantics and response-diagnostics tests also pass in the exact pinned compatibility image with networking disabled (2026-09-22). CI runs the same regression in the pinned compatibility image with `--network none`. Neither result proves live ChatGPT PDF acceptance.

Run deployment checks from the repository root:

```sh
npm run test:deploy
HEALTH_LAUNCH_TEST=1 node --test src/server/test/launch.integration.test.ts
```

The second command requires Docker, Node and available build resources. It creates only temporary fictional data; do not substitute a user archive.

All provider task status and acceptance criteria are maintained in the [single application work list](application-todo.md#detailed-release-acceptance), including [authentication and refresh](application-todo.md#crs-063), [complete route workflows](application-todo.md#crs-066), [PDF/fallback coverage](application-todo.md#crs-076), [offline recovery](application-todo.md#crs-077) and [test coverage](application-todo.md#crs-078).
