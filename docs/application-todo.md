Use stable `CRS-001` identifiers (Circus), with one global sequence. Allocate the next unused number; never renumber or reuse a retired ID. Numbers do not indicate priority. Categories are descriptive only. Each item has a permanent `#crs-NNN` link. Historical IDs are mapped at the end so old reviews remain usable.

Checkboxes retain their existing meaning and status. An unchecked item may have implemented code while still awaiting real-provider, document, device or capacity acceptance. ### CRS-088

- [ ] **Profile-less passkey unlock.** Approved first-class feature, not a release gate or authorization to deploy. Re-entry today costs three steps — choose a profile, choose Use passkey, authenticate — and every restart logs everyone out by two independent mechanisms: the session map is process memory and the profile data key exists only in the running process, so a replacement instance starts locked. That logout is correct for medical records and must not be removed; only its cost should fall, to a single authenticator gesture. The cryptography already exists. An unlock passkey's PRF output unwraps the profile data key and each credential carries its own salt, so a sign-in that does not yet know the credential must supply every candidate salt keyed by credential; `profile-passkeys.ts` already builds `prf.evalByCredential` this way because one profile may hold several passkeys. The limitation is scope, not cryptography: `authenticationOptions` requires a profile identifier and reads one keyring. Add an options path taking no profile identifier that unions passkeys across keyrings filtered to the current `rpID`, retain the candidate set on the challenge record rather than a single profile, resolve the profile from the returned credential identifier, then continue through the existing verification, unwrap and unlock path unchanged, applying the existing generation and freshness assertions to the resolved profile. Keep `allowCredentials` populated with the union rather than empty; it is indistinguishable to the user and avoids depending on whether an empty allow list may be combined with per-credential PRF evaluation. Conditional mediation through autofill is a separate additive improvement and is not required for this benefit. Three constraints bind. The union discloses how many passkey-bearing profiles exist to an unauthenticated caller; `GET /api/profiles` already discloses display names before login so this is not a new category, but it must be decided together with that pre-login question rather than inherited. Credentials are filtered by `rpID`, and moving to a new hostname requires fresh recovery and passkey enrollment for that origin, so fix any hosted hostname before enrolling or plan to enroll twice. Most importantly the foundation is unverified: CRS-072 records that real-device passkey and PRF acceptance remains open, and a usernameless flow must not be built on an unlock path that has not been confirmed against actual authenticators. Sequence CRS-072 first. Referenced by section D of [remote-deployment-design.md](remote-deployment-design.md), which motivates it but does not own it.
