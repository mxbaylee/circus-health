# Bifrost gateway evaluation

Status: approved first-class feature idea, **unbuilt**. [CRS-089](application-todo.md#crs-089) owns its status and adoption criteria. This document records the design questions and evidence; it does not add a supported deployment or replace LiteLLM. Reviewed 2026-09-24 against Bifrost documentation/source at [`b3d6c024`](https://github.com/maximhq/bifrost/tree/b3d6c02489480f8d9751d145305b6d041cf23fed) and the linked upstream proposal.

## Intended benefit

Evaluate replacing LiteLLM with Bifrost to reduce local memory/CPU pressure, startup time and gateway overhead, and possibly remove our Python compatibility image. A smaller gateway could make a home computer sufficient and defer the need for cloud hosting. These are hypotheses, not measured Circus Health results.

Bifrost is a Go gateway with an OpenAI-compatible interface and packaged binary/container options. That makes it a credible candidate for a Python-free proxy. It does not remove the health application's deployment, credential protection, configuration, updates, supervision or recovery requirements. Running Bifrost in Docker still incurs Docker Desktop's VM cost on macOS; native execution would be a separate supported-runtime decision. [Bifrost project](https://github.com/maximhq/bifrost), [gateway setup](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/quickstart/gateway/setting-up.mdx).

Upstream benchmarks demonstrate workload-dependent throughput and resource behavior. Their high-concurrency results do not establish savings for one household's serial, large-context PDF import. Bifrost's own benchmark documentation describes a speed/memory tradeoff through worker-pool configuration. Measure the chosen small deployment rather than inheriting a production-sized pool or quoting a marketing multiplier as an expected app speedup. [Upstream benchmark methodology](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/benchmarking/getting-started.mdx).

## Compatibility questions that decide feasibility

**ChatGPT subscription authentication is the first gate.** Our supported subscription route owns a separate device login, protected token persistence, reuse and refresh; it does not consume a host CLI login. Bifrost's [ChatGPT passthrough proposal #4548](https://github.com/maximhq/bifrost/pull/4548) was open and unmerged when checked. It proposes forwarding an existing client's subscription token through `/v1/responses`; that is not evidence of an independent device-login/refresh implementation or of our chat-completions route working. A normal OpenAI API-key route, enterprise SSO or MCP OAuth does not establish this capability. Do not silently replace subscription access with separately billed API access, borrow host credentials or add another compatibility fork without an explicit decision.

The independent [ChatGPT/Codex device-login request #2316](https://github.com/maximhq/bifrost/issues/2316) also remained open in the 2026-09-24 follow-up review. Subscription authentication remains unproven; recheck the selected released version before experimentation. A forwarding proposal and a feature request are not shipped support.

**The current application speaks chat completions.** [The bridge](../src/server/proxy-model-bridge.ts) calls `/v1/chat/completions` and expects one aggregated assistant choice with text and function calls. Our [LiteLLM patch](../deploy/litellm/patch_chatgpt_stream_semantics.py) preserves the distinction between upstream forced SSE and the caller's non-streaming response, recovers completed output items when the terminal output is empty, and combines sequential text/tool output into one choice. Bifrost documents Chat Completions and Responses support, but endpoint availability does not prove those exact transformations. Reuse these regression cases with Bifrost before declaring the Python patch unnecessary. Reject genuine alternative choices and malformed tools as today. [Bifrost OpenAI provider behavior](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/providers/supported-providers/openai.mdx).

**PDF remains the preferred delivery format.** Preserve the [existing capability contract](model-providers.md#configuration-and-routing-controls): prove the exact route using a fictional PDF/tool challenge before private work; send scoped original PDF pages when supported; use the same page's lossless PNG only when native PDF is unavailable or unsuitable and image capability is separately verified. Preserve original bytes, provenance and visible unsupported-media gaps. Check base64 file translation end to end through the selected endpoint/provider; generic multimodal support is insufficient. Authentication, rate-limit and timeout failures must not become capability fallback or provider switching.

**Prompt caching needs independent verification.** Preserve opt-in prefix markers, continuation messages, reported token usage and unknown-versus-zero accounting. Bifrost documents route-dependent cache-field transformations, including stripping some `cache_control` fields. Prove the selected model's actual behavior and savings; a successful HTTP reply is insufficient. Provider prompt caching is distinct from gateway semantic/result caching, which must remain disabled for health requests. [OpenAI translation details](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/providers/supported-providers/openai.mdx).

## Preserve the security and operational boundary

Keep one explicit upstream/model mapping, backend-only revocable credentials, local-only routing when selected, no automatic fallback, and application-owned retry accounting and cancellation. The gateway gets no health archive mount and no authority to execute health tools or accept records. Preserve profile/session scope, review before acceptance and provider-independent encrypted recovery.

Audit Bifrost's effective configuration rather than relying on defaults: protect inference and management access, keep management private, restrict CORS, and disable payload logging, raw request storage, semantic caches, callbacks and unnecessary connectors. Its client content-logging flag does not control each observability connector; hiding logs in the UI is not deletion. Verify metadata-only diagnostics using fictional canaries across stdout, stores and outbound traffic. [Client and logging configuration](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/deployment-guides/config-json/client.mdx).

Prefer a minimal single-instance configuration without optional external stores. Pin a released image/binary and record its digest, license, required feature edition and architecture support. If a config database is used, account for credentials, encryption keys, backup and migration behavior. Bifrost applies database migrations at startup; reverting the image alone is not a database rollback. A lighter binary can simplify deployment, not eliminate it. [Runtime and upgrade contract](https://github.com/maximhq/bifrost/blob/b3d6c02489480f8d9751d145305b6d041cf23fed/docs/deployment-guides/runtime-contract.mdx).

## Evidence required for an adoption decision

Start with credential-free compatibility fixtures and configuration inspection. Stop before performance qualification if the intended authentication route cannot be supported without reintroducing the patch burden this idea is meant to remove. An API-key-only experiment can still inform resource feasibility but cannot qualify replacement of the subscription route.

Compare pinned LiteLLM and Bifrost sequentially on the same host with equal limits, model, prompts, concurrency, diagnostics and disclosed cold/warm cache conditions. Measure idle/peak RSS, CPU, startup, request serialization, first-byte/full-response latency, gateway versus upstream time, errors, cancellation, Docker VM pressure and end-to-end import time. Use a controlled upstream to isolate gateway overhead, then separately authorized real-provider fictional imports for actual behavior. Preserve [CRS-079's attribution distinction](application-todo.md#crs-079): context growth and upstream inference can dominate a gateway improvement.

Adoption requires the [existing complete-provider workflow](application-todo.md#crs-066), authentication refresh/recreation, native-PDF/PNG/text-only coverage, tool/stream regressions, accurate usage diagnostics, no fallback or payload retention, explicit review/acceptance and unchanged originals/accepted records after cache-loss rebuild. Use independent extraction oracles; delivery, throughput and plausible record counts do not establish extraction quality. Keep a tested return path to LiteLLM without changing profile data. Record a measured adopt/defer decision with any remaining route limitations; do not close existing provider release gates from a proxy benchmark.

## Proposed experiment sequence — 2026-09-24

This is a saved proposal, not completed experimentation or authorization to deploy. Prioritize extraction-context efficiency under [CRS-086](application-todo.md#crs-086); gateway efficiency is a separate variable. Current transcript eviction already removes older consumed page text and media, so the historical token-growth receipt is not the current-code baseline.

1. **Qualify compatibility before replacement performance.** Select a released image and digest; inspect independent login, protected persistence, refresh and recreation. Reuse the existing fictional offline contract cases against both gateways: unchanged PDF bytes, verified same-page PNG fallback, text/tool aggregation, forced SSE, empty terminal output, usage/cache fields, malformed responses, cancellation, authentication/rate-limit/timeouts and no model fallback. Keep the application's endpoint contract constant. If subscription authentication is unavailable, defer full replacement; label any API-key-only experiment as such.
2. **Use an explicit small, secure configuration.** One route and household-scale concurrency, authenticated inference and private management, no archive mount, no payload logs or result/semantic caches, and no unnecessary connectors. Inspect connector logging independently of the main content-logging flag. Use fictional canaries to check persistence and outbound traffic. Compare tuned configurations transparently rather than equating unrelated defaults.
3. **Separate gateway overhead from inference.** Replay fixed fictional requests against a controlled upstream with known delays and output sizes. Run gateways sequentially on the same host with equal CPU/memory limits and disclosed background load and cold/warm state. Measure idle/peak RSS, CPU, startup, serialization/translation, first-byte/full-response latency, cancellation, host swap/memory pressure and Docker VM footprint. Upstream high-throughput benchmarks do not predict serial household imports.
4. **Compare four configurations.** Current context plus LiteLLM is the baseline; bounded context plus LiteLLM isolates prompt changes; current context plus Bifrost isolates gateway changes; bounded context plus Bifrost measures their combined effect. Start with controlled fictional 20-, 200- and 800-page traces. These establish scaling and contract behavior, not autonomous extraction quality. Keep the model revision, media path, diagnostics and resource limits matched; counterbalance run order and distinguish cold/warm cache observations. Do not assume gains add or multiply.
5. **Escalate provider tests selectively.** After compatibility passes and a live-provider budget is authorized, start with a short representative fictional case and independent exact-extraction oracle. Escalate promising configurations to long documents; do not automatically run all four full 800-page combinations. Compare whole-job and per-page tokens, requests/rereads, coverage, omissions, duplicate occurrences, wrong associations, proposal yield, separately reviewed accepted-record yield and elapsed time. Missing usage remains unknown. Preserve complete workflow/recovery gates and tested LiteLLM rollback.

A repeatable reduction in household memory pressure can justify the gateway even if import latency changes little. Conversely, a faster gateway that loses evidence, authentication persistence or observability is not an improvement. An unmodified pinned image could remove the custom Python image build, but configuration, upgrades, credentials and rollback remain deployment responsibilities. No resource saving or combined speedup has yet been measured.
