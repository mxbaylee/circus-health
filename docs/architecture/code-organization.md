# Code organization and maintenance guide

This guide maps the implemented application, its change boundaries, and maintenance risks. It is a source review, not a security certification or a record of release-test completion. No profile storage needs to be opened to maintain this reference.

The supported product entry point is **npm → Docker Compose → encrypted Node runtime**, with **LiteLLM Proxy** as the model route. A file's presence, an exported function, or a passing synthetic test does not by itself make a path a supported deployment option. See [installation](../setup/installation.md), [current remaining work](../todo/readme.md), and [model provider completion gates](../setup/model-providers.md#compatibility-limits).

## Repository layout

The tracked tree has these ownership boundaries:

- Repository-root dotfiles control Git attributes, ignored/private paths, Docker context, and formatting. Review them when adding generated files, large assets, or new file kinds.
- `.github/workflows/` owns public CI. Workflow checkout scope and commands must include every configuration or script they depend on.
- `package.json`, `compose.yaml`, `Dockerfile`, and `deploy/` own the supported runtime. TypeScript supplies host launchers, locking and ZIP inspection. Python is confined to `deploy/litellm/` for the proxy and its compatibility tests.
- `docs/` contains maintained product, operation, API-adjacent, security, data, and design contracts. Personal coordination journals, raw validation logs, generated inventories and private reference artwork are excluded from the public source tree.
- The repository root is the Node package; `src/` holds application sources. `app/` owns browser runtime and styles, `server/` owns HTTP, storage, import, and model runtime, `shared/` owns cross-runtime contracts and `shared/schemas/health-record-v1.schema.json`, `assets/` owns source brand assets, `public/` contains generated served assets, and `scripts/` contains build or verification utilities. Ordered SQL migrations live beside the server because the server applies them.
- Tests intentionally occupy three places: `src/server/test/` for Node domain/runtime tests, `src/tests/mounted/` and `src/tests/browser/` for central UI/browser tests, and colocated `*.test.ts` files for pure state and feature helpers. Top-level `src/tests/*.test.*` supply additional pure transformation/render-state coverage.
- Test fixtures belong beside their tests or under an explicitly named fixture directory. Generated screenshots and archives must contain independently fictional content; bulky output stays untracked.

Ignored and external boundaries are not enumerated as repository files. `.git/` is Git metadata; `node_modules/` is installed third-party code; `src/dist/` is generated build output; `/data/` is external durable profile storage; `.env*`, `.downloads/`, `*.part`, Python caches, and TypeScript build info are local or generated state. The Docker build context includes source and fictional tests for typechecking, plus root formatter configuration and inventory tooling; it excludes `node_modules/` and `src/dist/`. The final runtime stage copies only deployed server/shared files, required data helpers, production dependencies and built browser assets. None of those exclusions authorizes reading a private data directory, and none should be added to the inventory unless it becomes intentionally tracked.

## Execution and packaging

1. [Root npm scripts](../../package.json) delegate `help`, `start`, `image:build`, and `check:data` to [deploy/run.ts](../../deploy/run.ts). That launcher validates external data/configuration/state paths, establishes the writer lease, prepares proxy configuration and credentials, and invokes Compose. Its TypeScript path validation and lease handling are part of deployment behavior, not frontend configuration.
2. [compose.yaml](../../compose.yaml) defines the health and LiteLLM services, loopback browser publishing, separate archive/configuration/authentication mounts, temporary runtime filesystems, proxy networking, health checks, and logging settings. [deploy/litellm/configure.py](../../deploy/litellm/configure.py) and [entrypoint.sh](../../deploy/litellm/entrypoint.sh) prepare the selected proxy alias and start the proxy. Operator-owned YAML chooses the upstream provider; the application does not select a fallback provider.
3. [Dockerfile](../../Dockerfile) builds the browser application, retains production Node dependencies, installs Chromium for server PDF exports, and starts `node src/server/runtime.ts` as the non-root application user. It copies `server`, `shared`, two frontend data helpers used by exports, and the complete `dist` output. Changes to server imports can therefore require a packaging change even when local tests resolve them successfully.
4. [runtime.ts](../../src/server/runtime.ts), `startRuntime`, validates the runtime locations/origins, holds the storage lease, serves static assets and readiness, and creates the encrypted application. `/api/runtime` and `/health/ready` describe runtime readiness; they are not a model availability check. Shutdown and writer-lease failure stop private request serving.
5. [index.html](../../src/index.html) loads [app/main.tsx](../../src/app/main.tsx). React runs inside a data hash router so editors can block route navigation. [App.tsx](../../src/app/App.tsx) supplies routes and places `ConnectionBoundary` outside `ProfileProvider` and the selected-profile shell.

[Vite configuration](../../vite.config.ts) and [scripts/build-identity.ts](../../src/scripts/build-identity.ts) generate one identity per production build, inject it through [app/data/build.ts](../../src/app/data/build.ts), and emit `dist/build-info.json`. [server/build-identity.ts](../../src/server/build-identity.ts) reads that manifest once at boot. The browser compares its bundled identity with the running server's identity; an unknown identity is not a mismatch. The Vite development proxy and native runtime imports remain useful contributor/test facilities, but the launcher does not offer a native product startup mode.

## Frontend ownership

### Routes and page state

[App.tsx](../../src/app/App.tsx), `App` and `CollectionPage`, owns this route map:

- `/`: [Patient.tsx](../../src/app/pages/Patient.tsx), the canonical Self person editor and patient export entry point.
- `/tests`: [TestResults.tsx](../../src/app/pages/TestResults.tsx), result lists, series, comparisons and selected result detail; [test-navigation.ts](../../src/app/pages/test-navigation.ts) owns its URL-navigation helpers.
- `/medications` and `/procedures`: `Medications` and `Procedures` in [ClinicalRecords.tsx](../../src/app/pages/ClinicalRecords.tsx), including personal medication activation and provider evidence.
- `/notes` and `/people`: [NotesPage.tsx](../../src/app/features/notes/NotesPage.tsx), with distinct collection presentation over the shared note/person model. `CollectionPage` redirects older person links and canonical Self links to their destinations.
- `/sources`: [Sources.tsx](../../src/app/pages/Sources.tsx), original files, source records, documents and provenance inspection. Historical `?view=import` URLs redirect to `/import` while preserving their exact report/intake/proposal/record selection.
- `/import`: [ImportPage.tsx](../../src/app/features/import/ImportPage.tsx) owns upload, reading activity, the global review feed and identity/source decisions; [ImportDetailReview.tsx](../../src/app/features/import/ImportDetailReview.tsx) owns exact report, record and People review without a Sources fallback.

Collection/detail selection, searches, filters and pagination largely live in URL parameters. They are not interchangeable across pages: test comparison selections, clinical record visibility, historical-note source/type filters, and People activity/tag rules have different meanings. Follow each page's parser and its backend query before adding a new parameter. Assistant context must also receive the effective page state through [pageContext.tsx](../../src/app/features/assistant/pageContext.tsx) and [server/assistant-context.ts](../../src/server/assistant-context.ts).

[Shell.tsx](../../src/app/components/Shell.tsx) owns desktop/mobile navigation and the selected-profile outlet key. Changing profile identity remounts private page state; renaming a person must not do so. [profile.ts](../../src/app/data/profile.ts) separates identity notifications from versioned name/icon metadata updates. It retains the selected opaque profile ID in browser storage, while notes and private form drafts stay in memory. [ThemeProvider.tsx](../../src/app/components/ThemeProvider.tsx) separately owns System/Light/Dark preference and cross-tab appearance updates.

### Profile entry and setup

[ProfileProvider.tsx](../../src/app/components/ProfileProvider.tsx), `ProfileSession`, loads public cards, reconciles remembered selection only when allowed, and supplies startup/locked views. Focus, visibility and successful reconnection refresh lock state without choosing another profile automatically.

[ProfileManagement.tsx](../../src/app/components/ProfileManagement.tsx) owns the profile modal state machine: list, create/copy, recovery material and proof, unlock, optional passkey enrollment, saved passkey management, deletion, and skippable Self setup. The short setup screens are About you, Primary care provider, and Emergency contact. Their completion metadata and staged linked contact IDs are persistence contracts, including compatibility with the earlier combined `care-team` step. Changing screen order is not permission to rewrite completed setup records or merge People.

[profile-management.ts](../../src/app/data/profile-management.ts) intentionally sends lifecycle requests to explicit profile/setup IDs independently of the selected clinical profile. [passkey-enrollment.ts](../../src/app/components/passkey-enrollment.ts), [passkey-unlock.ts](../../src/app/components/passkey-unlock.ts), and [passkey-prf.ts](../../src/app/components/passkey-prf.ts) isolate prompt cancellation, enrollment/authentication progress and PRF-byte handling. [PasskeyNameEditor.tsx](../../src/app/components/PasskeyNameEditor.tsx) owns the small label-edit form. Browser-owned authenticator prompts remain distinct from application dialogs and synthetic credential tests.

[SelectionChip](../../src/app/components/SelectionChip.tsx) owns selected-value presentation. Sidebar links return to Self. `shared/person-display.ts` normalizes display-name/icon identity for server collision checks and disambiguated dropdown labels, separately from medical identity matching. Keep invalid/unsupported saved conditions visible and preserve backend behavior. The simple-field and rich-row state models are intentionally different.

### Reads, writes, recovery and notifications

There is no universal fetch client or general persistent offline queue.

[api.ts](../../src/app/data/api.ts), `api`, adds the selected profile prefix, rejects cross-profile URLs, cancels on profile identity changes, validates the JSON envelope, updates versioned profile/durability metadata, and handles authoritative profile-lock responses. Its mutation counter covers calls through this function. [read-recovery.ts](../../src/app/data/read-recovery.ts), `readWithRecovery`, shares only in-flight safe GETs, isolates subscribers' cancellation, separates reads across mutation generations, and permits one bounded retry after a successful independent runtime probe. It has an in-memory entry/time bound and does not replay mutations.

`useResource` keeps data only for the same profile/path key during reload or failure; `ResourceState` shows retained data with a stale-read message instead of unmounting the editor. A key change hides the old resource immediately. [connection.ts](../../src/app/data/connection.ts) independently probes `/api/runtime` with timeout/backoff and focus/visibility wake-ups. Browser offline events are hints, not proof that localhost is unreachable. [ConnectionStatus.tsx](../../src/app/components/ConnectionStatus.tsx) owns status details, one notification per outage/restoration, and the persistent update notice. Build-pair dismissal stays in tab memory, and refresh is always explicit.

Other request paths retain their own requirements:

- Lifecycle/setup requests use `profile-management.ts` direct fetch because they can activate a different profile. Modal layering prevents the update notice from interrupting those operations.
- [AttachmentPanel.tsx](../../src/app/features/notes/AttachmentPanel.tsx), `uploadOriginal`, uses XHR for upload progress and aborts on disposal. Owner creation, link associations and metadata changes use the note writer/API lane; upload and association are separate operations with separate retry state.
- `ImportPage.upload` uses **`api` POST with a File body**, not that XHR helper. Accepted bytes, extraction progress and review/acceptance remain distinct stages.
- [NoteExportDialog.tsx](../../src/app/features/notes/NoteExportDialog.tsx) uses API calls for preview operations and direct fetch for PDF/evidence downloads; [PdfPreview.tsx](../../src/app/components/PdfPreview.tsx) fetches binary content and PDF resources. Browser download links are another transport path.
- [ProfileStorage.tsx](../../src/app/components/ProfileStorage.tsx) uses a direct app-wide archive-storage read alongside protected profile data. The runtime probe also deliberately bypasses `api` and safe-read recovery.
- [useAssistantChat.ts](../../src/app/features/assistant/useAssistantChat.ts) and [useIntakeBatch.ts](../../src/app/features/intake/useIntakeBatch.ts) each have running-operation polling state on top of `api`. They do not become general `useResource` subscriptions merely because GET retries exist.

[Toasts.tsx](../../src/app/components/Toasts.tsx) distinguishes profile-scoped operation notices from app-level connection notices. Durable failures and uncertain saves belong at the operation/editor as well; a connection-restored toast is not a save receipt.

### Personal editor and history

[NoteEditor.tsx](../../src/app/features/notes/NoteEditor.tsx) renders editable Note, Historical draft, Person and Self forms. [note-form.ts](../../src/app/features/notes/note-form.ts) maps server records to form snapshots and outgoing input. [DraftWriter](../../src/app/features/notes/draft-writer.ts) serializes autosave, explicit save, finishing, conversion and owner-affecting attachment work with expected versions and stable identity. It preserves an uncertain request's original snapshot for reconciliation; it does not silently replace it with newer typing. `adoptClean` accepts a refreshed record only when no dirty, failed or queued work needs protection.

[NoteHistoryPanel.tsx](../../src/app/features/notes/NoteHistoryPanel.tsx) handles preview and selected-field restoration. [ProviderNoteDetail.tsx](../../src/app/features/notes/ProviderNoteDetail.tsx) displays read-only provider evidence; it is intentionally distinct from an editable historical draft. [NoteText.tsx](../../src/app/features/notes/NoteText.tsx), [markdown-model.ts](../../src/app/features/notes/markdown-model.ts), and [NoteLinks.tsx](../../src/app/features/notes/NoteLinks.tsx) handle stored text formats and related targets. Clinical details reuse [RelatedNotes](../../src/app/components/RelatedNotes.tsx), attachments and history without turning clinical imports into personal freeform drafts.

[profile-transition.ts](../../src/app/data/profile-transition.ts), `prepareProfileTransition`, gathers mounted editors, checks readiness, saves when explicitly selected, and pauses writers during a lifecycle action. [ProfileTransitionGuard.tsx](../../src/app/components/ProfileTransitionGuard.tsx) exposes this as Save/Discard/Back, including update refresh. Router navigation has a separate destination guard in the editor, and browser unload has its own warning. These entry points share an obligation to preserve uncertain work but are not equivalent events: an unsuccessful unlock must resume the original draft, whereas a confirmed route departure changes the mounted editor.

## Backend request and storage paths

### Dispatcher, authorization and projection

The normal chain is `startRuntime` → [createVaultApp](../../src/server/vault-app.ts) → authorized profile state → [createApp](../../src/server/index.ts).

`createVaultApp` owns session cookies, grants, public profile cards, setup/unlock/passkey routes, serialized successful activation, grant revocation, storage summaries and lock/delete operations. `requireAccess` checks both the session grant and an open profile. `activate` verifies and opens the new profile before revoking others, and locks newly materialized state on failed activation. Its `profileApp` creates the inner API with exactly the selected open database; successful delegated responses recheck access and flush the encrypted profile before acknowledgement.

`createApp` is the domain HTTP dispatcher. It performs its own Host/Origin checks and explicit profile-path/database lookup, routes domain reads and writes, delegates intake and export routes, and constructs response envelopes with revision, durability and Self metadata. Its direct use with supplied databases is valuable in tests; it does **not** add the outer encrypted session boundary by itself.

[database.ts](../../src/server/database.ts), `openDatabase`, owns SQLite initialization, migration sequencing and owner checks. SQL files under [migrations](../../src/server/migrations) define the schema. `transaction` calls registered durability hooks around the SQLite transaction and supports operation receipt replay. New accepted mutations must enter that boundary; writing a row directly can bypass durable publication even if the immediate query looks correct.

[queries.ts](../../src/server/queries.ts) provides the application's domain list/detail queries. [query.ts](../../src/server/query.ts), `readQuery`, is a separate bounded SQL worker facility; [query-worker.ts](../../src/server/query-worker.ts) opens a read-only defensive SQLite connection with an authorizer, limited output and process resource bounds. At this baseline `readQuery` is consumed by backend tests, not the current HTTP dispatcher or assistant tool list; the assistant uses fixed domain collections through `scopedQuery`. Similar names do not indicate duplicate implementations, and the retained worker must not be described as an exposed SQL console.

### Durable records, encryption and compatibility

[encrypted-profiles.ts](../../src/server/encrypted-profiles.ts), `createEncryptedProfiles`, manages staged creation/recovery proof, encrypted profile materialization, original-reference verification, projection cache validation/rebuild, copying, locking and disposal. [vault-crypto.ts](../../src/server/vault-crypto.ts) owns cryptographic primitives and recovery/key wrapping; [vault-store.ts](../../src/server/vault-store.ts) owns authenticated encrypted objects and caches. [vault-index.ts](../../src/server/vault-index.ts) publishes the [incremental encrypted index](../security/vault-index.md) and atomic manifest committing its tip with the accepted record head. [profile-passkeys.ts](../../src/server/profile-passkeys.ts) owns challenge binding, credential confirmation, wrapping and saved credential metadata. Changing credential UX alone must not weaken those publication gates.

[record-versions.ts](../../src/server/record-versions.ts), `attachRecordDurability`, connects SQLite changes to immutable record/commit objects and the published head. `rebuildRecordDatabase` reconstructs current rows and retained version indexes from committed ancestry. Its [compact history projection](../data/record-version-storage.md#compact-history-projection) stores one contents copy per version and changed-field references; paginated history and `readIndexedRecordVersion` reconstruct validated envelopes from selected indexed rows. A valid cache accelerates opening; it is not the authoritative archive. Restoration appends a new version rather than replacing an earlier accepted record. [note-history.ts](../../src/server/note-history.ts) and [clinical-history.ts](../../src/server/clinical-history.ts) expose different history views over those retained contracts.

[portable.ts](../../src/server/portable.ts) is not dead code: `attachPersonalDurability` selects record durability when record storage is supplied, while the file also retains portable snapshot/generation, copy, recovery and legacy projection helpers. [profile-storage.ts](../../src/server/profile-storage.ts), [profile-registry.ts](../../src/server/profile-registry.ts), and [profiles.ts](../../src/server/profiles.ts) retain path/registry/legacy-ID compatibility. [profile-lifecycle.ts](../../src/server/profile-lifecycle.ts) implements the inner/legacy lifecycle, while the encrypted wrapper intercepts the supported setup/copy/lock path. These similarly named layers should not be collapsed without tracing both callers.

[startup-rebuild.ts](../../src/server/startup-rebuild.ts), [startup-worker.ts](../../src/server/startup-worker.ts), and `startLegacyRuntime` remain legacy portable-startup machinery used by tests. [recovery-cli.ts](../../src/server/recovery-cli.ts) and [recovery.ts](../../src/server/recovery.ts) implement offline portable backup/restore/rebuild paths; the package still exposes `backup` and `restore` scripts. Do not infer that these commands are interchangeable with encrypted-profile recovery-key login or that they are the default way to back up a new vault. Consult [profile encryption](../security/profile-encryption.md), [storage/rebuild](../data/profile-storage-and-rebuild.md), and the exact operation's storage format first.

### Domain writes and evidence

- [notes.ts](../../src/server/notes.ts), `createNote` and `saveNote`, validates personal state, stable person/note linkage and versions; it also provides Self metadata, link targets, collection queries and options. Person tags/contact normalization is shared through [person-care.ts](../../src/shared/person-care.ts). New care fields must preserve unknown existing person fields and the canonical Self identity.
- [assets.ts](../../src/server/assets.ts) owns original asset containment/type checks, uploads, attachment owner/version validation, associations and metadata. Unlinking is different from deleting retained original bytes. [source-view.ts](../../src/server/source-view.ts) resolves displayed source evidence.
- [medication-preferences.ts](../../src/server/medication-preferences.ts) owns personal medication-use assertions independently of imported provider status. [visibility.ts](../../src/server/visibility.ts) owns archival visibility events; it does not delete evidence.
- [record-corrections.ts](../../src/server/record-corrections.ts), [duplicate-review.ts](../../src/server/duplicate-review.ts), and [mapping-actions.ts](../../src/server/mapping-actions.ts) distinguish individual accepted corrections, reviewed duplicate/event relationships, and future-import classification rules. [clinical-references.ts](../../src/server/clinical-references.ts) preserves old links across accepted kind changes. Similar clinical values are not a sufficient reason to merge records.

### Intake and assistant operations

[handleIntakeRoute](../../src/server/intake-routes.ts) is the HTTP adapter. [intake.ts](../../src/server/intake.ts) coordinates upload registration, staged proposals, review, acceptance, questions and extraction batches. Supporting modules have narrower roles:

- [intake-batches.ts](../../src/server/intake-batches.ts) schedules sequential uploaded originals, while [intake-batch-journal.ts](../../src/server/intake-batch-journal.ts) retains append-only reading-batch events through encrypted publication. This is separate from extraction coverage batches in `intake-workflow.ts`. [useIntakeBatch.ts](../../src/app/features/intake/useIntakeBatch.ts) restores/polls batch state and retains uncertain create operation IDs; it never automatically replays a save.
- [intake-continuation.ts](../../src/server/intake-continuation.ts) checkpoints bounded source reads for linked model runs. Read cursors, retained proposals and accepted clinical records are separate states; [reviewQueue.ts](../../src/app/features/intake/reviewQueue.ts) advances exact candidate versions across proposal groups and uploaded originals.
- [intake-upload.ts](../../src/server/intake-upload.ts) receives bounded upload streams; [intake-files.ts](../../src/server/intake-files.ts) supplies configured upload/extraction limits and format inspection.
- [intake-format.ts](../../src/server/intake-format.ts) validates literal JSONL, including duplicate-key/numeric-token behavior. Its envelope roles are not clinical classifications.
- [intake-review.ts](../../src/server/intake-review.ts) defines typed review issues and draft validation; [useReviewDrafts.ts](../../src/app/features/intake/useReviewDrafts.ts) queues versioned draft operations, while [ReviewWorkspace.tsx](../../src/app/features/intake/ReviewWorkspace.tsx) presents original text, issue anchors and metadata. Mounted fixtures alone do not establish compatibility with the server DTO; the encrypted [review-draft browser journey](../../src/tests/browser/intake-review-draft.test.ts) covers that boundary.
- [intake-report-context.ts](../../src/server/intake-report-context.ts) resolves uniquely scoped retained context and evidenced source-label suggestions. [intake-report-queue.ts](../../src/server/intake-report-queue.ts) serves stable groups and exact clinical versions; [ImportPage.tsx](../../src/app/features/import/ImportPage.tsx) renders the bounded global feed and [ImportDetailReview.tsx](../../src/app/features/import/ImportDetailReview.tsx) composes the shared review workspace, related discovery, corrections, questions, originals and People decisions for exact deep links. Grouping, source confirmation, identity confirmation and acceptance remain distinct operations.
- [intake-people-format.ts](../../src/server/intake-people-format.ts) validates named-person evidence; [intake-people.ts](../../src/server/intake-people.ts) owns separate People proposals, matching, disposition and reviewed add/update receipts. [shared/intake-people.ts](../../src/shared/intake-people.ts) is the cross-runtime contract, consumed by [ReportPeopleReview.tsx](../../src/app/features/intake/ReportPeopleReview.tsx). People reuse personal-entry history and source evidence; relatives are not Self clinical records. Source publication and personal-entry publication have separate recovery boundaries.
- [intake-package.ts](../../src/server/intake-package.ts) and its Node worker perform bounded ZIP inventory/member inspection; [intake-json.ts](../../src/server/intake-json.ts) retains literal JSON structure windows. Package role decisions and extraction completion remain separate.
- [optical-prescription.ts](../../src/server/optical-prescription.ts) validates the nested literal document field, [vision.ts](../../src/server/vision.ts) queries accepted source occurrences, and the shared [preview](../../src/app/components/OpticalPrescriptionPreview.tsx)/[editor](../../src/app/components/OpticalPrescriptionEditor.tsx) support review and history. Their schema is [shared/vision.ts](../../src/shared/vision.ts); these are documents, not medication records.
- [intake-evidence.ts](../../src/server/intake-evidence.ts) indexes/reads bounded original evidence; [intake-pdf-session.ts](../../src/server/intake-pdf-session.ts) owns the single profile/source-hash-scoped PDF worker session, and [intake-pdf-worker.ts](../../src/server/intake-pdf-worker.ts) verifies the retained descriptor and isolates bounded PDF.js range/text/render work. [intake-navigation.ts](../../src/server/intake-navigation.ts) supports original navigation. [intake-plan.ts](../../src/server/intake-plan.ts) computes extraction pins and units; [intake-workflow.ts](../../src/server/intake-workflow.ts) tracks candidate versions, questions and decisions.
- [clinical-import.ts](../../src/server/clinical-import.ts), `buildClinicalReview` and `projectClinicalReview`, turns validated candidates into review classifications and accepted projections, with retained source/version identity and mapping exceptions. UI `RecordEditor` edits a review decision; it does not directly update accepted tables.

[assistant.ts](../../src/server/assistant.ts), `createAssistant`, owns chat state, allowed `HEALTH_TOOLS`, tool dispatch, reviewed proposals, apply receipts and durable reconciliation. [tool-arguments.ts](../../src/server/tool-arguments.ts) and `assistant-context.ts` validate input/context. [assistant-journal.ts](../../src/server/assistant-journal.ts) retains linked changed-content generations; [chat-journal-codec.ts](../../src/server/chat-journal-codec.ts) validates generic JSON deltas. The encrypted wrapper flushes journal updates through its manager; [conversation storage](../data/conversation-journal.md) defines publication, bounded reads, cache disposal and backup. ## Where to make a change

- **Add a page or destination:** start with `App`, `Shell`, page URL parsing and assistant page context; use existing detail/collection scaffolding. Add a mounted navigation check, including profile change and browser Back where an editor is present.
- **Add a person or note field:** update the shared contract, form mapping/validation, UI adapter, backend validation/projection, and relevant history/export behavior. Verify autosave, a failed/uncertain save, reload/rebuild and unknown-field preservation. Do not create a second Person merely to attach a contact value.
- **Add a filter:** define supported semantics and serialization, implement server predicates/options, connect the page URL and assistant context, then use shared filter presentation. Test unknown/unsupported saved values, paging, Back/Forward and profile isolation. A pill label change alone should not change the URL contract.
- **Add an accepted domain mutation:** implement a domain function using `transaction`, expected-version/operation identity as appropriate, and an explicit route/apply adapter. Test failure around publication and replay/rebuild; direct SQL success is insufficient.
- **Add a model tool:** extend tool metadata, argument/context validation and dispatch, plus proposal preview/apply and receipt reconciliation for writes. Test invalid input, cancellation, stale proposal and retry. Do not add an alternate direct-provider route as a side effect.
- **Support a new intake representation:** retain original bytes, add bounded evidence inspection and literal/source validation, expose unsupported/partial coverage, and integrate review before projection. Keep received-file transport retry distinct from resumable extraction.
- **Change loading or recovery:** trace whether the caller uses `useResource`, custom polling, direct fetch, XHR or download links. Preserve the same editor instance and let `adoptClean` decide whether refreshed data can replace its form. Never route mutations through safe-GET retry.
- **Change setup, unlock or refresh:** inspect the modal origin/Back path, transition participants, browser prompt cancellation, in-flight operation state and server activation. Preserve recovery proof and unknown write outcomes.
- **Change storage/schema:** update migrations, schema/version validation, durable record capture/replay and cache/rebuild checks together. Check encrypted and applicable compatibility fixtures; use a fresh synthetic archive.
- **Change deployment or dependencies:** check npm/TypeScript, Compose and Docker copies as well as npm. Verify the built client and deployed manifest agree, and test the actual encrypted runtime with the packaged dependency set.

## Maintenance boundaries

Runtime validation remains necessary alongside TypeScript: HTTP, archive and model inputs are untrusted. Frontend form metadata and server allowlists describe different responsibilities. Server imports of browser-adjacent formatting helpers must remain free of browser runtime dependencies.

HTTP body bounds, binary uploads, recovered reads and mutation recovery differ by route. The lifecycle wrapper and domain dispatcher both enforce their own request boundaries. Notes, profile dialogs and uploads have different transition guards; generic API mutation counts do not cover every XHR operation.

Vite, native Node TypeScript, workers and packaged imports use different loaders. Controlled CI checks do not establish physical-device or real-provider acceptance. Known refactoring and obsolete-entry-point work is tracked in [TODOs](../todo/readme.md).

### Brand regeneration and short explanations

`npm run icons` calls `deploy/icons.ts`, which builds the pinned Docker `brand-tools` stage and runs it without network access. The tool mounts only canonical brand inputs and generated output directories; the launcher uses host Node, while rendering uses pinned container Node. `src/assets/brand/logo.svg` supplies the complete geometry, including fold lines, to the generated React mark, theme SVGs and all raster sizes. Contributor builds on supported Node can use `brand:generate` directly; normal builds check that generated outputs are current.

`src/scripts/brand-raster.ts` loads the pinned `@resvg/resvg-wasm` renderer and PNG encoder from local package bytes, with system fonts disabled. Using the same WebAssembly binary avoids native rasterizer differences between CPU architectures that previously made Linux x64 CI reject icons generated on macOS ARM64. The native canvas package remains in use elsewhere; it does not generate brand assets. `brand:check` compares exact bytes without rewriting them, and the focused macOS/Linux CI job also tests missing, modified and stale exports.

`ContextHelp` is a small native disclosure for short explanations that must work with keyboard, touch and pointer input. Imports use it for source reading outcomes and gaps. It does not introduce an additional modal or rely on hover.
