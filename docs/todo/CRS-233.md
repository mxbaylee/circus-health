# 🪣 CRS-233: Admit imports according to actual storage capacity

Status: open. Storage-policy remainder of CRS-043. The owner questions below have been asked and remain unanswered. Capacity design can proceed independently. The [paged inventory and plan authority](../data/intake-state-storage.md#v4-collections-and-selected-publication) foundation is implemented; removing the remaining protective processing caps requires CRS-232's bounded consumers and this ticket's storage admission rule. Package publication and inventory qualification do not establish storage-only admission or resolve the owner questions.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want the app to accept files my installation can keep and explain genuine space shortages,
So that I can plan storage without guessing at arbitrary file limits or losing uploaded evidence.

## Plain-English User Walkthrough

1. I add a file and see whether there is enough room to keep it.
2. If room is available but reading must wait, the original stays available with a clear explanation.
3. If space is insufficient, I see how much is needed and what I can change before retrying.

## Acceptance Criteria

### Scenario: Use storage as the admission rule

Given an original fits available storage and any operator maximum,
When it is uploaded,
Then retain it without a product-defined upload-size ceiling,
And distinguish retention capacity from later extraction capacity,
And keep a retained original with a located unfinished outcome when processing must wait.

### Scenario: Explain refusal and handle uncertain capacity

Given retaining a file would exceed observed free space or the operator maximum,
When admission or a streaming write detects the shortage,
Then explain required bytes and an actionable operator change,
And distinguish archive capacity from runtime/staging capacity and unknown quotas,
And account for shared versus distinct filesystems, concurrent app reservations, cross-device copy overlap and encryption/publication overhead,
And handle changing free space, ENOSPC/EDQUOT and uncertain durable publication without deleting evidence or acknowledging a failed save.

### Scenario: Unlock without reserving an imaginary largest upload

Given a retained profile can materialize the workspace needed for unlock,
When the operator opens it,
Then calculate actual eager workspace/database needs independently of the configured maximum upload allowance,
And continue checking lazy original access and subsequent processing capacity when required.

### Scenario: Qualify the one supported rule

Given the agreed configuration and bounded processing replacements,
When large fictional direct and ZIP imports, interruptions and encrypted recovery are exercised,
Then measure peak buffered bytes and staged, written, reread and hashed bytes in counts,
And keep buffers independent of file size and total byte work proportional to processed scope,
And the upload API, client limit display, deployment configuration, storage accounting and Docker guidance describe the same implemented rule.

## Owner decisions still needed

- How to configure the storage maximum: environment variable at startup, app setting, or both. Startup configuration is the recommendation already presented, not an adopted choice.
- Whether to remove `CRS_INTAKE_UPLOAD_MIB` and `CRS_INTAKE_EXTRACTION_MIB` once streaming replaces their safeguards, or retain optional operator ceilings disabled by default. Retirement was recommended, not approved.

The owner's standing intent from 2026-09-30 remains: “if the app can store a file, it can import it”; default capacity is free disk space, with an optional operator maximum. Silence on configuration details is not approval. Note attachments are a separate feature outside this scope unless they expose a relevant failure.

## Engineering context

`archive-storage.ts:importStorageEstimate` currently plans two original copies plus `max(extractionBytes, 100 MiB)` and reports runtime availability without reserving it. `assertImportCapacity`, `intake-upload.ts` and contributor upload code still enforce `uploadBytes`; `encrypted-profiles.ts` reserves an upload allowance during unlock. Reuse safe staged adoption and existing authority recovery. Design phase-specific capacity checks and bounded reservations; filesystem free bytes are observations, not proof of remote quota or guaranteed future availability. Never reserve full ZIP expansion merely to retain the compressed original.

Update [storage accounting](../data/storage-accounting.md), [Docker runtime guidance](../setup/docker-runtime.md), upload/environment contracts and release operator actions. Run focused upload, intake-format, archive-storage and encrypted-profile suites, large fictional ZIP/direct qualification, and independent review. Keep model work measured in counts; do not substitute higher limits for verified streaming.
