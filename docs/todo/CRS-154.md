# 🩺 CRS-154: Reconstruct real-provider import complaints from private-safe diagnostics

Status: open. Remainder of CRS-038. A one-page, four-observation fictional Import qualification now provides a bounded route through model reading, review, acceptance, diagnostic export and cache-loss recovery. It checks exact clinical facts and the absence of known fixture canaries in the metadata export. That cannot establish that every real-provider complaint can be reconstructed, or that a canary test excludes every possible health string.

Reuse this complaint/download qualification rather than creating a parallel collector. Full-size retention readiness belongs to CRS-194 and does not wait for CRS-086's independent async-processing implementation. Owner feedback and the bundle must produce scoped, prioritized production follow-ups; small-fixture success alone does not establish that readiness.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to understand an import problem from a safe diagnostic download,
So that I can find the affected work and next action without exposing the records.

## Plain-English walkthrough

1. Use a small fictional import on the adopted provider and observe an actual problem.
2. Download its diagnostics from the protected import screen and keep a separate account of what happened.
3. Use only the download to reconstruct the problem and resolution, then repeat the inspection after recovery.

## Given–When–Then acceptance

The detailed contracts, owner decisions and evidence gates below remain required.

- **Given** the adopted provider and independently fictional content, **when** an actual import problem is observed, **then** a separate expected-event timeline and full lifecycle export record cause, affected source/page or operation, continuation and resolution; an injected fixture failure alone does not satisfy live observation.

- **Given** the diagnostic download and a post-recovery view, **when** a reviewer reconstructs the complaint without original/provider payload, **then** correlation, attribution, build identity and work/retry/review outcomes are present with honest loss counts; missing usage is not zero and missing/truncated evidence cannot pass.

- **Given** the tiny qualification oracle and a real exported schema, **when** privacy and browser download are verified, **then** the protected UI produces the intended file, representative values are inspected beyond fixture canaries, and health text, names, dates, filenames, secrets and provider error bodies stay out of public evidence.

- **Given** CRS-194’s impending 800–900-page owner trial, **when** download readiness is assessed, **then** early/late complaint reconstruction and full-run AI/import/processing/UX evidence follow CRS-194’s capacity gate, with prioritized follow-ups; tiny-fixture success and harness deadlines are not full-size or model-speed qualification.

## Remaining acceptance

1. On the adopted provider route, exercise at least one actual import problem (for example an incomplete model response, source-delivery gap, blocked review, retry or unavailable provider) using independently fictional content. Keep the complete lifecycle's diagnostics export and a separate expected-event timeline. The export should let a reviewer locate the cause, affected source/page or operation, continuation and resolution without opening the original or provider payload. A deterministic injected failure is useful for instrumentation tests but does not replace this live-provider observation.
2. Reconstruct the complaint from the export alone, using correlation IDs, retained event and attribution coverage, loss/truncation counters, model requests and retries, page reads, review/acceptance outcomes and build identity. Reject missing or truncated evidence; never infer zero work from missing usage. Check both an unlocked download and the supported post-recovery view where a person may investigate later. Keep private raw qualification artifacts outside Git.
   The recent-operation detail ring can report dropped events on a one-page import while the larger event window remains intact. Decide which surviving timeline and phase totals suffice for a specific reconstruction, or increase the bounded retention within the storage contract. Do not mark a loss-bearing export complete merely because the model and batch finished.
3. Inspect for clinical text, names, dates, filenames, credential material and provider error bodies. Fixture canary absence is a narrow automated check; inspect a real exported schema and representative values, and preserve only redacted counts or safe metadata in public documentation. Include the receiving clinician and operator personas: the former needs provenance and a clear statement of incomplete work, and the latter needs actionable troubleshooting without exposing records.
4. Verify the browser's Download performance diagnostics control for the live completed import, including its protected profile session and resulting file. Server export checks do not prove this UI path. Document the verified behaviors and current limits, obtain an independent passing grade, then delete this ticket and its index entry.

The owner has authorized small billed fictional provider runs. A provider sign-in may still require their gesture if the adopted route's credentials expire. The [maintained diagnostics guide](../import/import-performance.md#representative-provider-qualification) describes the bounded fixture and retained output.

A harness deadline only limits the operator's run. If a provider finishes after that bound, the result is incomplete qualification evidence, not a model-speed failure or an application performance target. Acceptance depends on completed work and retained evidence counts.
