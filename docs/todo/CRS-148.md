# 🧳 CRS-148: Export everything in a portable form

Status: open. Filed during backlog grooming on 2026-09-30, from the "move or checkpoint everything" job now contrasted with [selective printed packets](CRS-150.md).

## Decision and why

The owner wants a Google Takeout–style export containing everything (owner, 2026-09-30). It serves two uses: moving to another storage provider, and keeping a checkpoint somewhere else. Unlike the [selective printed packets](CRS-150.md), this output is not written for a reader. It must be complete, and another tool must be able to read it without this app.

- **High-precision tracker:** has years of records from about fifteen sources. The export is the way out, and the insurance against losing them.
- **Operator:** a checkpoint outside the laptop, usable even if the app itself is gone.
- **Caregiver:** moving a managed person's records to that person or to another caregiver.

## Where it stands

- Backups today are user-managed copies of the encrypted durable directory plus the recovery kit ([profile storage](../data/profile-storage-and-rebuild.md)). Only this app can read them.
- The legacy recovery CLI's portable snapshot "must not be mistaken for a current encrypted-vault backup command" (same doc).
- Project-owned portable formats use the `circus-health` slug, and `health-record-v1` is an existing neutral contract ([profile management](../features/profile-management.md)).
- No in-app action exports every original, record, note, correction and version in a portable form. Checked by searching the docs; the code was not checked exhaustively.

## Requirements

1. One action exports a person's records, or the whole profile. The export contains:
   - every original, byte-for-byte;
   - accepted records in a documented, standard-leaning format (for example, a FHIR bundle alongside `health-record-v1`);
   - notes, people and their relationships;
   - corrections and ownership history;
   - version history;
   - a manifest listing every file with its hash.
2. The export states what it omits, if anything: for example, working caches, or model state that doesn't belong in it.
3. The export's contents are health records. Nothing lands in the repository or logs, and where it goes is always the person's choice. Decide whether the export is encrypted (for example, with a passphrase) or plaintext with a clear warning.
4. Its size scales with the data, and it streams to disk rather than holding the profile in memory (see [CRS-043](CRS-043.md)).
5. Add a round-trip test on fictional data: export, then check against the manifest, and ideally re-import into a fresh profile with nothing lost.

## Owner decisions needed

- Plaintext with a warning, encrypted with a passphrase, or a choice between the two?
- Should re-importing an export into this app be a requirement, or only readability by other tools?
- Which standard formats matter most (FHIR, C-CDA, CSV for measurements)?

## Completion

Document the export format in maintained data documentation. Run the new round-trip test and the storage suites. Obtain an independent passing grade before deleting this ticket, per `AGENTS.md`.
