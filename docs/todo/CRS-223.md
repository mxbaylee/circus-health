# 🧺 CRS-223: Integrate target-bound intake in contributor private copies

Status: open. Contributor durability/lifecycle integration split from high-effort CRS-208 before implementation on 2026-10-02. Builds on the implemented [unpublished-target bootstrap](../data/intake-state-storage.md#unpublished-target-bootstrap); unblocks [CRS-209](CRS-209.md) alongside CRS-220. The [encrypted private-copy integration](../data/intake-state-storage.md#encrypted-private-copy-publication-and-retry) is implemented; this contributor path remains separate. This contributor facility does not change the supported npm → Compose product boundary or activate production intake persistence.

## User story

As an [Operator](../design/personas.md#operate-and-recover), I want contributor-created private copies to preserve their staged intake evidence through the contributor rebuild procedure, so testing copy and recovery does not silently discard pending work. Portable retention is distinct from ordinary runtime reader/writer support; this ticket must preserve the former without claiming the latter is ready.

## Contract

Integrate target-bound preparation in the contributor `profile-lifecycle` backup/stage/rename/registry flow, preserving its actual portable-generation publication and rebuild contract. This slice covers copy preparation and portable retention/rebuild of staged fictional authority only; production writers remain unchanged. This path's `attachPersonalDurability` has no `recordStorage`, so the current intake primitive cannot simply read or mutate there. Normal contributor runtime reader/writer support remains an explicit CRS-209 requirement, with durability-backend reassessment before implementation.

## Acceptance

1. Specify a legitimate target copy/retention strategy compatible with contributor portable-generation publication and rebuild, including `exportCuration`, `loadPortable` and `rebuildProfile` retention of intake `app_meta`. Contributor curation-change capture currently excludes `app_meta`; verify portable retention explicitly rather than treating that capture as implemented mutation support. Never attach a fake configured backend, weaken the runtime primitive's durability guards or silently replace the contributor recovery contract. No normal contributor runtime mutation activation is in scope. Reassess before coding if copy retention/rebuild requires a portable-backend migration or generic profile-storage redesign. Preserve this ticket's copy-only scope; scope genuine additional backend work separately where useful.
2. With a coherent backup and source writer lease, validate selected source state via the [bootstrap API](../data/intake-state-storage.md#unpublished-target-bootstrap) before owner/path changes. Rebind copied source-text revision authority, which the current contributor copy path does not do; copied source `__record_*` projections must not become target record authority, and their current preservation needs deliberate correction. Transactionally replace only source-bound intake contributions with prepared target evidence; preserve unrelated metadata, unchanged source files and accepted clinical rows, modulo intentional profile/path/Self-display rebinding. No source-owned contribution may be selected as valid destination authority even briefly.
3. Retain and verify actual original files/hashes; preserve source archive and authorization/session boundaries. Preserve exact pending proposals/questions/plan units/decisions/stored intake and effective source-pin versions/pins/proposal-review identities/public acceptance and operation receipts, distinguishing preserved public IDs from fresh internal bootstrap/replay identities. Preserve complete outer-envelope order, intake-slot position and nested exact normalized serialization. Untouched raw `details_json` whitespace, duplicate-property spelling and escape spelling remain original durable/search bytes until an authorized rewrite or separately specified raw-text solution.
4. Exercise failures at validation/preparation, staging, immutable writes, before actual portable publication, after publication before registry/activation and ambiguous completion, as applicable to this path's real publication boundary. Define when a target becomes selected published authority and how retry/restart recognizes and preserves that survivor instead of recopying changed source state. Preserve unpublished-stage cleanup separately from already-published target recovery; no unpublished target may appear active. Unsupported/missing/corrupt/cross-profile/source/hash evidence fails explicitly without reset or discarded scope.
5. Use real contributor lifecycle copies of staged fictional incremental state. Prove source unchanged, original hashes and raw details exact, pending/public-receipt/pin and accepted-record equality modulo intentional profile/path/Self-display rebinding, independent source/target reopen and complete cache-loss/rebuild without inference, and preservation/isolation through the copy/retention strategy from item 1. Normal runtime read/write and changed-evidence mutation support must be qualified separately in CRS-209; do not claim the primitive already works in the contributor runtime. Verify source-text rebind, target owner/path binding, retry and activation ordering rather than testing only a prepared SQL image.
6. Document implemented contributor copy retention/rebuild and its readiness limits. Disclose one-time preparation/copy costs separately from the future changed-evidence mutations required by CRS-209. Do not claim encrypted-copy integration, supported product persistence cutover, general backend migration or broad capacity/large-import qualification.

Use independently fictional data, no inference and no heavy import retry. Before implementation, confirm the copy-only scope and use separate complexity boundaries where useful; effort alone is not a gate. Completion requires focused contributor lifecycle/storage/recovery tests, formatting/types, full PR CI and independent grading; delete this ticket and its index entry only when implemented, preserving unmet requirements and repointing dependents to maintained documentation.
