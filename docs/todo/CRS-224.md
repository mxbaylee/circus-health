# 🧶 CRS-224: Implement a bounded explicit text-piece edit engine

Status: open. Pure explicit-edit engine split from high-effort CRS-218 before implementation on 2026-10-02. Complements the implemented [durable serialization-order contract](../data/intake-state-storage.md#exact-serialization-domain); unblocks [CRS-225](CRS-225.md). Inputs are exact serialized text, retained piece/occurrence anchors and validated explicit edits, not parsed operational intake views. No SQL, source-search replacement, persistence switch or parallel recovery authority is in scope.

## User story

As a [Records assembler](../design/personas.md#file-and-review), I want small changes or reordered source details to preserve exact text while updating only affected pieces, so future storage changes do not distort evidence or amplify unchanged data. This engine applies explicit edits; success here does not yet show that the app can derive those edits automatically.

## Contract

A narrow TypeScript primitive preserves exact serialized bytes through bounded content/occurrence rows and explicit splice/move operations. Success with supplied edits does not establish automatic dirty-source reconciliation; CRS-225 must derive those edits from old/new snapshots before CRS-219 can use this engine.

## Acceptance

1. Define immutable bounded content rows, stable distinct occurrence/slice/next rows and a small selected head. Return individual changed rows transiently for later transactional storage, never a growing occurrence/reference list serialized into one row. Repeated equal pieces have separate occurrence identities; content hashes identify bytes, not position. Preserve unrelated content and links without global rebalance or fresh global chunking on every edit.
2. Validate sequential explicit UTF-16 splice/move operations against the expected old head and exact expected result. Define UTF-16 versus UTF-8 offsets, scalar-safe boundaries and the accepted text domain, including any explicitly unsupported raw unpaired-surrogate input. Preserve punctuation, whitespace, alternative escape spellings, non-BMP characters and literal lone-surrogate escape spellings exactly; never silently replace or normalize text. Boundary splits reference slices of the same immutable content, and moved interior content/links remain unchanged. Chunk only new inserted content within stated per-row limits.
3. Reject malformed chains, cycles/dangling references, invalid occurrence identity, inconsistent expected heads/results, invalid boundaries, unknown edits and exhausted limits explicitly. Define limits and complexity for pieces, operations and reconstruction; a whole snapshot, giant replacement middle span for distant changes, rewritten occurrence array or global rebalance is not a fallback.
4. Use independent exact-string and UTF-8 byte oracles for tiny prefix/middle insertion and deletion, multiple distant edits, repeated/periodic text, maximum-size piece boundaries, reorder/moves in both directions and multibyte/surrogate boundaries. Include adversaries that shift global chunk boundaries. Verify small explicit changes leave unrelated content and links unchanged; pure moves must reuse content rather than writing copies of unchanged values.
5. Measure initial cost and 100/200/300 explicit updates: changed content/link bytes and rows, existing content rereads, scan/validation/reconstruction work, hashing and copied bytes separately. Disclose full input/result comparison and other linear host work, including limits; bounded changed writes do not imply changed-only computation. Keep every piece/link/head individually bounded as the retained sequence grows.
6. Publish and document the tested primitive, exact-byte/offset/identity contracts, failure behavior and measured scope. It adds no SQL schema or durable authority and does not qualify automatic snapshot reconciliation, production source search, full intake-authority write growth or large imports. Carry automatic edit derivation into CRS-225 and storage/query integration into CRS-219/220.

Use independently fictional data, no heavy imports and no model calls. Reassess scope before implementation; split only at useful complexity boundaries. Completion requires focused algorithm/oracle tests, formatting/types, full PR CI and independent review; delete this ticket and its index entry only when the bounded implementation ships, and repoint dependents to maintained documentation.
