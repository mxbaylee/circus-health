# 🧬 CRS-241: Expire internal byte readers after logical changes

Status: open; scoped internal-reader finding from PR #71. Selected/public callers
have additional freshness guards; no stale accepted HTTP write was demonstrated.
This does not establish that every direct consumer is safe.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want a reopened detail to match the revision I am reviewing,
So that an old value cannot be mistaken for the current evidence.

## Plain-English User Walkthrough

1. I open a record and then change its reviewed details.
2. Any still-open detail either reads the current revision or asks me to reload;
   it does not quietly continue presenting the previous revision as current.

## Acceptance Criteria

### Scenario: A retained byte reader outlives a logical change

Given a fictional V4 collection and a retained byte or field-stream capability,
When its selected logical generation changes,
Then every subsequent direct byte read and resumed field-stream read refuses
the stale capability, including reads after a cooperative yield,
And foreign owners, cache disposal and profile closure also refuse,
And auxiliary-only changes preserve valid logical bindings.

### Scenario: Protection is enforced at the consuming boundary

Given both guarded public consumers and direct internal consumers,
When the reader contract is audited and tested,
Then the tests distinguish stale descriptor binding from actual byte consumption,
And count selected work without adding unrelated-original scans or whole-value copies.

## Evidence and Implementation Scope

`intake-state-collections.ts` checks logical binding in `byteValueBinding`, but
`readBytes` can consume an older registered byte value after a logical mutation.
The schema field-stream path delegates to this reader. Independently fictional
review probes reproduced old bytes through both direct interfaces. Audit their
consumers and enforce freshness at the lowest shared consumption boundary;
do not replace accepted authority or widen this into the separate recovery work.

Owner decision, 2026-10-15: track this guarded internal defect separately from the
confirmed user-facing PR #71 fixes. Independent review and current regressions
are required before retirement; the mitigation is not proof of completion.
