# CRS-137: Do not reuse another report's confirmation when the printed name is in doubt

Status: open. Narrow corrective follow-up to CRS-132, implemented at `4c073f9` with its ticket deleted there. Independent grading of that commit found one remaining hole and three test gaps. Persona review on 2026-09-30 widened the scope to a second, related case: reuse between two saved people who share a printed name, with no banner at all. Nothing else in CRS-132's behavior is reopened.

## Decision rationale and limits

[CRS-126 D5](CRS-126.md#d5-identity-evidence-human-decisions-and-incorrect-printed-dobs-are-different-facts) makes identity assignment report-scoped: confirming report A does not answer report B's unreviewed discrepancy. The maintained rule is in [banner compatibility and report-scoped decisions](../import/identity-review.md#banner-compatibility-and-report-scoped-decisions). CRS-132 said the check runs "against the current uniquely matched person", so it silently assumed a receipt's owner and the name-matched owner are the same. They are not once two saved owners share the printed name.

- **Caregiver** uploading a mixed family archive ([CRS-130](CRS-130.md)) is the person most likely to hold two same-named owners, for example a parent and a child, or Self plus a relative. Their confirmation of one report must not quietly file the next report, with a date that does not fit, into Self.
- **Low-effort self-tracker** should not be asked more often. Both fixes ask only when two saved people share the printed name, or when B's own banner is incompatible with the owner A's receipt would assign. A person whose name is unique in the profile sees no new prompt.
- **Receiving clinician** ([CRS-130](CRS-130.md#medical-records-practice)): a record filed under the wrong person reaches a provider packet as that person's history. Medical-records practice treats names with generational suffixes (Jr./Sr.) and relatives sharing a name as classic matching failures (ONC patient-matching guidance names both; not re-checked against its current text), so a shared name must be a reason to ask, not to reuse.

Limits. B's own explicit confirmation still resolves B; a compatible banner never becomes DOB evidence; labelled-DOB and model-only-DOB rules, the receipt format, the API and the model prompt are unchanged. This is not [CRS-133](CRS-133.md): a banner ownership answer never authorizes a verified printed-DOB conflict. It does not depend on [current name authority](../import/identity-review.md#historical-attribution-and-current-name-authority) (see below).

## The defect

`incompatibleBanner` is computed only when exactly one saved owner matches the printed name (`src/server/intake-identity-policy.ts:747-752`). The receipt-reuse gate at `:839-846` and the `prior_confirmation` return at `:909-925` both rely on it, and both run before the `distinctOwners.length > 1` question at `:929`. Reproduction source: `adv132.test.ts`, test `ADV5`, in the grader scratchpad `g132-head/src/server/test/adv132.test.ts` (not copied into the repo). Verified at `4c073f9` and again at HEAD `46e8b95` (the policy file is unchanged), where B returns `prior_confirmation`, `blocking: false`.

1. Save Self as Rowan River, DOB `1982-04-17`, and a Person named Iris Meadow, DOB `1982-04-17`.
2. Retain one original with two reports for `Iris Meadow`: A has an unlabelled `Female  4/17/1982` banner, B has `Female  4/17/1970`. Neither proposal carries a model identity question.
3. Confirm A as Self. That adds the printed name as a Self alias, so two saved owners now match, `matchedOwner` is undefined and `incompatibleBanner` is false.
4. Preview B: nonblocking `prior_confirmation`, so individual acceptance saves B into Self without B ever being reviewed. Before step 3, B was correctly blocked.

## Same-named owners with no banner

Reasoned from the code, not yet run. The reuse gate (`:839-846`) and the `prior_confirmation` return (`:909-925`) both run before the "saved for more than one person" question (`:929`). So when Self and a saved Person share a printed name, one report's Self confirmation can answer every other report on the same original that has no banner or a compatible one.

Fictional example: a caregiver saved as Robin Lane Sr. (Self) keeps a Person Robin Lane Jr. and uploads one family export. They confirm one Sr. report as Self. A Jr. report in the same export, with no printed DOB, then reuses that confirmation and saves to Self without a question.

Required: when more than one saved owner matches the current report's printed name, a receipt from a different report is not reused; the report asks, as `:929` intends. A report's own receipt still resolves it. Write the reproduction as a failing test first; if it does not reproduce, record why here and keep the test.

## Implementation

1. Add the reproduction as a failing regression first, then the cases below. Keep every existing CRS-132 case.
2. In `assessIdentityPolicy` (`:661`), factor the banner test into one helper taking an owner and using the existing `compatibleBirthDates` comparison. Keep `incompatibleBanner` for the fresh-evidence block (`:965`) as now. For the reuse gate (`:839-846`), evaluate the helper against the owner the reused `this_is_me` receipt would assign, which is Self (`owners[0]`, `personId: 'patient'`), not `matchedOwner`. A `this_is_person` receipt is already forced to equal the unique matched person at `:829`; keep that and test it. Do not test every same-named candidate: a banner that fits the assigned owner is compatible, and same-named ambiguity is a separate question (below).
3. Keep the check in the shared policy so preview, the feed, individual acceptance and bulk acceptance all see it. An owner with no saved DOB stays "nothing to compare", as today. B's own receipt (`scope.groupId === group.id`) still resolves B, and receipts with no incompatible banner reuse exactly as before.
4. Apply the same-named-owner rule above in the same shared reuse gate, before `prior_confirmation`.
5. No new endpoint, receipt field or migration. If one turns out to be needed, record why here before widening scope.

## Acceptance checks

- Regressions in `src/server/test/intake-identity-boundaries.test.ts` beside the existing report-scoped cases (`:125`), each with a short why comment: A's receipt cannot answer B because confirmation belongs to the reviewed report, even when an alias made two owners match.
- Required cases: the ADV5 reproduction with and without a routine model question; B blocked in preview, feed (`selectable: false`), individual and bulk acceptance, with zero clinical writes; B's own confirmation as Self then accepts with the saved DOB unchanged. Add what the grader's scratch run showed holds but the suite does not pin: B's receipt does not answer a third incompatible report C, and a labelled ambiguous or conflicting B after A is confirmed stays blocked.
- Prove the tests guard the fix: run the new tests once against the pre-fix expression (a temporary local edit or scratch copy, never committed) and record which fail. The current "confirming A leaves B blocked" variants do not do this: the grader found that only Self with no question fails on pre-CRS-132 code, while the Person and routine-question variants pass either way.
- Pin cross-original isolation: a receipt from one original never applies to another original with the same printed name. Receipts live in each intake's `workflow.identityConfirmations`, so this should already hold; the test makes it a checked fact.
- Same-named owners: the Robin Lane Sr./Jr. export above, with and without a banner, asks for the Jr. report in preview, feed, individual and bulk acceptance, for Self and for another Person as the confirmed owner. **Why:** a shared name is a known matching failure, not evidence of the same person.
- Name suffixes (not verified): check whether printed names with "Jr.", "Sr.", "II" or "III" are compared with or without the suffix, and pin the result with a test. If the suffix is dropped, Sr. and Jr. are indistinguishable by name alone, which this ticket then relies on the ask to catch.
- Mounted test (suspected gap, not verified): in `src/tests/mounted/` show a second report whose feed record has blocking `confirmation_required` and the banner message. `ImportPage.tsx:170-175` and `:777` pass the server message through, and `ImportReviewPresentation.tsx:1886` renders it, so assert B's message and disabled save are visible beside a confirmed A. With a mocked API this proves display only; the server tests carry the behavior.
- Update `identity-review.md` (the "Valid confirmation reuse" sentence at `:13`) with the assigned-owner rule and rationale. Until this lands, that paragraph overstates the guarantee for same-named owners.

## Interactions and open questions

- **CRS-134.** The alias that confirming A creates is exactly a name [current name authority](../import/identity-review.md#historical-attribution-and-current-name-authority) governs, because `effectiveKnownNames` (`src/server/name-associations.ts:121`) currently drops names whose authority is not `active`, and CRS-134 changes how `unresolved` ones count. This fix must not depend on that outcome: it checks the receipt's assigned owner, whether the alias is effective, ambiguous or removed. Test with the alias present, and record the result when it is absent.
- **Saved DOB edited after B is confirmed** (not verified): B's receipt matches by report and version, not by saved DOB. Proposed default: B's own answer stays valid, consistent with "unrelated profile edits leave the assignment usable" in `identity-review.md`. Confirm with the owner, then pin with a test whichever way it is decided.
- A `this_is_me` receipt has no assigned-owner-still-matches check like `:829`. Cross-report Self receipt reuse now rechecks current ownership; preserve that guard.

Independent capable review against this ticket is required before deletion, per `AGENTS.md`. Move the rationale into `docs/import/identity-review.md` and repoint links when it lands.
