# 📦 CRS-043: If the app can store a file, it can import it

Status: open. Promoted from a one-line index entry during backlog grooming on 2026-09-30, when it turned out the app has several file-size limits rather than the one the entry named. Line numbers were checked at `1e6fa50`; re-verify before editing.

## Decision and why

**The person-facing rule is "if the app can store a file, it can import it"** (owner, 2026-09-30). The only real limit is storage. By default that is free disk space. An operator may instead set a storage maximum at startup, which makes size an operator setting rather than a product limit. This follows [CRS-126 P14](CRS-126.md#principles), "no limits of our own". Every other size limit in the code is a memory safeguard the app controls, and it should be removed by streaming, not tuned.

- **High-precision tracker:** these limits hurt this persona. Full-history exports and takeouts are often hundreds of MB, and one scanned 300-page PDF can exceed 25 MiB. Today the same PDF can be accepted when uploaded directly and rejected inside a ZIP.
- **Low-effort self-tracker:** a single report never reaches a limit. When a file is refused, the message must say what to do.
- **Operator:** runs the app on a small laptop, so the limits exist to protect its memory and disk. Storage is the operator's to set; memory use is the app's to keep bounded.

The disk estimate already exists. `importStorageEstimate` and `statfsSync` in `src/server/archive-storage.ts` estimate an import's space, and unlock checks free space against one configured upload allowance (`encrypted-profiles.ts` near `:333`). Both are tied to `uploadBytes` today.

## Requirements

1. Stream ZIP members and text extraction to disk, the way uploads already are. Then the per-member, per-call and extraction caps go away, and a PDF inside a ZIP behaves exactly like the same PDF uploaded on its own.
2. Replace the upload cap with a storage check. Refuse a file only when storing it would exceed free disk space or the operator's maximum. The refusal says how much space the import needs and what the operator can change. Decouple unlock's headroom check from `uploadBytes`.
3. Until requirement 1 lands, keep a file the app cannot process yet as an original with a located exception naming it, never reject it. This is consistent with D1, where a mismatch never rejects a file.
4. Measure in counts on large fictional files, per `AGENTS.md`. Peak buffered bytes per step must stay independent of file size, and bytes staged, written, reread and hashed must scale with file size. See [CRS-128](CRS-128.md).
5. Update the upload and storage documentation (`docs/data/storage-accounting.md`, `docs/setup/docker-runtime.md`) so they describe one rule.

## Owner decisions needed

- The storage maximum's form: an environment variable read at startup, a setting in the app, or both.
- Once streaming lands, should `CRS_INTAKE_UPLOAD_MIB` and `CRS_INTAKE_EXTRACTION_MIB` be removed, or kept as optional operator ceilings that are off by default?

Record of the 2026-10-01 backlog discussion; these are proposed boundaries, not allocated child IDs or completed work:

- Retain temporarily unprocessable originals: requirement 3, with an explicit located exception and retained evidence. This can improve today's behavior before streaming lands.
- Stream ZIP members: the ZIP portion of requirement 1, including large direct-versus-packaged parity, bounded member buffering, and removal of the 25 MiB member, 100 MiB expanded-per-call and 300-members-per-call product caps through streamed/checkpointed iteration.
- Stream text extraction and verification: the extraction portion of requirement 1, including the 25 MiB MAX_INTAKE_BYTES JSONL/text/direct-review paths and configured extraction limits, with bounded buffers and complete retained text.
- Storage-based admission: requirement 2 and both storage-setting decisions (maximum configuration form and retirement or optional operator-ceiling replacement of upload/extraction settings); replace product size caps only after the relevant memory safeguards have been replaced by streaming. Coordinate retained originals with temporary/output space and unlock headroom.

Carry requirements 4 and 5 into every applicable child: counted reads/hashes/writes, bounded buffers and accurate supported procedures are acceptance criteria, not a final cleanup ticket. Size each child and record its production mark and ordering separately; never remove a protective cap before its replacement is verified. Preserve all remaining scope here until transferred, then follow the remainder/deletion policy.
