## Owner decision and production priority

Large-document imports are a common primary experience, not an optional optimization (owner, 2026-10-01). Establish their actual behavior, work counts, completion, recovery and user experience before relying on the app for real records. This ticket is a production requirement. Representative cases include an 800-page PDF around 115 MB and a 900-page PDF around 15 MB, both as direct uploads: bytes and pages alone cannot predict model work or completion time. Use independently fictional equivalents for public qualification; owner originals, feedback and raw artifacts stay outside Git. The 115 MB case fits the current 128 MiB direct-upload default, but not the current ZIP member/expanded extraction limits. Packaged equivalents depend on [CRS-043](CRS-043.md); report that limitation rather than claiming direct-upload qualification covers ZIPs.

The owner may try an actual upload personally and return a downloadable diagnostics bundle with feedback. **Before that trial, verify that the normal release UI collects and downloads the evidence needed to debug AI behavior, import, local processing and the user experience from the beginning of a long run.** A finished upload or a successful download alone does not establish adequate evidence. Prepare instrumentation and a serial baseline first. Async processing and bounded context remain an independent production requirement in [CRS-086](CRS-086.md); preparatory design can proceed alongside diagnostics readiness, and implementation need not wait for the paid qualification or owner trial. The current scripted baseline below precedes writing the full CRS-086 specification; that baseline and the owner trial do not wait for parallel workers. Diagnostics readiness supplies the instrumented baseline for CRS-086's before/after work-count validation.

Expect this exercise to uncover additional work. Turn observed findings into scoped CRS tickets with reproductions, affected personas, evidence, acceptance checks, dependencies and effort/impact sizes. Fixes required for a usable, correct large-document experience are production requirements. Prioritize high-impact, low-effort fixes as soon as evidence identifies them; do not defer them until the whole processing redesign finishes or assume their size before investigating.

## Scripted full-size baseline before the async specification

Feedback adopted on 2026-10-01 restores a baseline omitted from the earlier ticket draft: run the current pipeline once on the scripted provider at 900 pages, with no paid inference, before writing CRS-086's full implementation specification. The supplied review reports that the owner previously found a 900-page upload did not work; retain that as a reported complaint, not a reproduced current defect or qualification result. Ownership, partial saves and identity confirmation have changed since the earlier experiments, so old receipts cannot answer it.

1. Generate an independently fictional 900-page PDF with a scanned/OCR portion, native-text portion, several reports, at least two people and a cross-page table, plus a literal oracle. Upload through the normal supported workflow with only the upstream provider scripted; retain normal extraction, scheduling, ownership and review behavior. Record whether default upload/extraction/context limits refuse any part and exactly where. Retain refused inputs and failures as evidence; do not raise limits or secretly repair the fixture to call the default path a pass.
2. Establish the required collection first, then count requests/attempts per unit, input characters by category per physical request and growth over the run, rereads, journal/source-text writes and bytes, peak buffered bytes with measurement method/coverage, and proposals produced. Count text-layer/raster/OCR pages, extraction-step timeouts/retries and queue depth on the same file. Provider tokens may be synthetic or unavailable; label them accordingly rather than reporting scripted usage as live billing evidence.
3. Open the resulting release review UI as the patient would. Count proposals, identity/clinical questions, source-page approvals actually required, and actions to reach acceptance; record unusable list/render/review behavior at this size and work until the first reviewable and oracle-correct result. Link review-effort findings to [CRS-116](CRS-116.md) and source-attestation/gate findings to [CRS-129](CRS-129.md); distinguish current behavior from that ticket's proposed page-approval gate.
4. Use this full-size run to verify diagnostics retention budgets, download early/late evidence after supported recovery, and reconstruct problems. Missing evidence is a finding to fix before the owner trial, not permission to declare readiness. File each distinct failure as a scoped ticket, record safe measured counts and current limitations in maintained `import-performance.md` only after verification, and update CRS-086's specification questions from the results.
5. Inventory the actual continuation and harness controls. The [historical scripted experiment](../experiments/processing-follow-up-experiments.md) completed 800 pages in 1,222 requests with two-page units and 896 with ten-page units; the former needed one explicit Resume at that experiment's 16-session allowance. These are historical counts, not targets or proof of today's behavior. Record any current harness-only bound separately from app/provider limits; an operator-bound stop is incomplete evidence, not a model-speed failure. The baseline must reveal whether a patient needs Resume or other babysitting, without hiding it behind harness calls.
