# CRS-143: Show which version of a corrected record is current

Status: open. Split from [CRS-126](CRS-126.md) scenario 5 during backlog grooming on 2026-09-30; no other ticket owned it. Line numbers were checked at `1e6fa50`; re-verify before editing.

## Decision and why

The owner-approved [corrections and versions](CRS-126.md#corrections-and-versions) rules, and scenario 5 ("The potassium was re-run and changed"):

- A corrected result keeps both versions. The version the source **issued later** (by amendment or report date, not upload order) is current, so an old export uploaded later never restores a corrected value.
- When the app is confident (same source record issued later, or a report labelled amended or corrected), the current value is shown automatically with a "corrected" mark. Otherwise the pair goes to "Differs".
- Charts show the current value on the line. The older one is hidden or a separate point off the line, and is listed below the chart as outdated. The person can choose the other version, and the choice is recorded.

Who it serves ([CRS-130](CRS-130.md)):

- **Chronic-condition tracker:** a corrected potassium or A1c left on the line as a second point makes the trend wrong.
- **High-precision tracker:** re-uploads full-history exports. An old export arriving later must not bring back a value the lab corrected.
- **Receiving clinician:** needs the current value, a clear mark that it was corrected, and whether the correction came from the provider or from the patient.

## Where it stands

- **The importer keeps both versions and chooses neither ✅.** A changed assertion under the same source identity gets a separate version and a `source_version` relationship; "the importer does not infer which is current" (`docs/import/import-and-rebuild.md:57`). The code records the same rationale: "both retained without assuming which is current" (`src/server/clinical-import.ts` ~:2041-2050).
- **Choosing is an explicit human review today ✅.** Relationship review ([clinical relationships](../data/clinical-relationships.md)) has a `provider_amendment` confirmation and a separate `display_preference` (`prefer_left`, `prefer_right`, `show_both`). A provider amendment "does not choose a display preference" (`clinical-relationships.md:23`), and "the service never selects the newest value or averages alternatives" (`:33`).
- **Charts honor reviewed choices but show no outdated list ✅.** `MeasurementCharts.tsx` labels points "Reviewed provider amendment", "Relationship needs review" and "Shares one reviewed event" (`src/app/components/MeasurementCharts.tsx` ~:320-330) and follows a reviewed display preference. Nothing marks a value as outdated or lists the older version below the chart. The "outdated" in `src/app/features/import/SourceReaderObservations.tsx:38` is about intake coverage, not clinical versions.
- **Disagreement to record, not resolve silently:** CRS-126 asks the app to pick the current version automatically when confident. The implemented relationship model deliberately never picks one without a person's review. One of them has to change. That is the first owner decision below.

## Requirements

1. Decide "issued later" only from source evidence: an amended or corrected label, the report's issue date, or the same issuing system and record ID with a later issue. Never upload order or extraction order.
2. In a confident case, once both versions are accepted, show the later-issued one as current with a "corrected" mark, and keep both with their sources (P4, P7). Anything less than confident goes to "Differs" for review, one pair at a time, never in bulk.
3. Charts: the current value on the line; the older one off the line or hidden, and listed below the chart as outdated, with both sources reachable.
4. The person can choose the other version. Record that choice through the existing relationship decisions (`display_preference`, with its history and withdrawal) rather than a parallel mechanism.
5. An old export uploaded after a correction never restores the corrected value, and says so in the import receipt.
6. Provider packets and evidence JSON show the current value with its corrected mark and cite both versions. A provider correction and a patient's own correction stay distinguishable.
7. Fictional-fixture tests: a potassium re-run labelled corrected, uploaded in both orders; an unlabelled different value on the same date and test, which goes to "Differs"; the old export re-uploaded after the correction; and a relative's corrected result, which never enters Self's chart.

## Owner decisions needed

- **Automatic versus reviewed.** May the app choose the current version automatically in the confident cases, which CRS-126 requires and `clinical-relationships.md` currently forbids? Recommendation, unconfirmed: yes, but only for evidence-labelled amendments and same-record later issues, shown as a reversible default with the "corrected" mark. Inferred cases stay a human decision.
- **Confidence.** Is a later report date on the same issuing record ID enough by itself, or must the report also be labelled amended or corrected?
- **Outdated in the chart:** hidden by default, or shown as a separate faded point?
