# 🔎 CRS-193: Check diagnostic recording before an upload

Status: open. Medium-effort, large-impact production prerequisite split from CRS-192. The normal sidebar exposes only whether detailed recording is enabled, so an operator cannot check this unlocked profile's current encrypted attachment before reproducing an import problem. Reuse implemented collection origins and the existing bounded archive reader; this is a point-in-time observation, not complete-run qualification.

## Requirements

1. Add an explicit “Check diagnostic recording” action to the existing diagnostics control, available before file submission on desktop and narrow navigation. Do not block uploads, introduce runtime recording policy changes or require diagnostics for ordinary use. Explain the existing opt-in and supported npm → Compose restart procedure when recording is off.
2. An owning-session, profile-authorized endpoint performs one existing bounded `exportArchive()` inspection per explicit check, including its existing flush behavior and yields. Do not inspect archives from status polling or every upload, create another collector, perform model calls or write a new check receipt. Inspection may publish only pending diagnostic work through the existing incremental path.
3. Return a small typed, dated observation distinguishing disabled recording, absent attachment, readable current origin, current origin unproven and inspection unavailable. Match all immutable fields of a validated retained origin against the current attachment; an older origin or append acknowledgement alone cannot satisfy the check. Preserve the distinction between lost acknowledgement with readable evidence and acknowledged but unreadable evidence. Never infer a collection date from a surviving event.
4. Report current-origin evidence separately from archive coverage warnings. Historical loss can make the archive partial while current attachment evidence remains readable. Keep pre-attachment observation counts explicit; those counts are not archived-event proof. The result does not establish uninterrupted capture, pre-upload run scope, future retention, browser delivery or whole-run completeness.
5. Show plain-language, accessible progress/error and “Checked at” feedback, without raw window IDs or implementation details unrelated to an operator decision. Pending, unavailable or malformed responses must not imply success. Clear results on profile identity, lock/session and component lifecycle changes and discard late responses. Each new explicit check replaces the previous dated observation.
6. Include the bounded latest observation in the normal diagnostic JSON only for its current profile/session. Label it superseded when a later download observes a different current attachment; retain its original date and meaning rather than presenting it as a new check. Keep old observations distinct from the download's current archive evidence. No clinical text, filenames, credentials, recovery material or raw payloads in the check.
7. Verify independently fictional real encrypted-store/API cases: enabled zero-event origin, disabled with older retained origins, absent attachment, failed/lost-ack publication, acknowledged but unreadable evidence, old-only retained origin, reattachment, historical partial coverage with valid current origin, and lock during inspection. Mounted coverage verifies pre-upload availability, explicit-only inspection, dated truthful messages, failure and late-response isolation, and the downloaded/superseded observation. Verify bounded inspection work and no added diagnostic receipt/clinical writes or inference. Keep owner/demo data untouched.
8. Update maintained API/diagnostic documentation; run focused local checks and full PR CI, then independent review. Retire this ticket and carry CRS-192's remaining requirements into a scoped successor. Use current contracts only; no old-schema decoder or migration.

## Remaining work

This check does not establish run selection, historical build/config attribution, browser delivery accounting, full-size budgets or restart/container qualification. Recording remains operator opt-in. The scripted 900-page upload/review baseline and adopted-route qualification remain open and cannot be replaced by a successful attachment check.
