# CRS-132: Preserve banner identity review across confirmations and date formats

Status: open. Corrective follow-up to the report identity work merged at `e892e5d`.

The host now checks unlabelled name/sex/date banners independently of model questions. Compatible readings leave a limited name-only match; incompatible readings ask who the report belongs to. A banner never becomes verified DOB evidence or updates a saved person. Two remaining defects were reproduced during review of the merged code.

## Another report's confirmation bypasses a conflicting banner

In `src/server/intake-identity-policy.ts`, `assessIdentityPolicy` returns `prior_confirmation` before evaluating `bannerBirthDates`. Receipt reuse can therefore answer a banner mismatch that the person has never reviewed.

Fictional reproduction:

1. Save Self as Cookie Doe, DOB `1988-04-12`.
2. Retain one original with two distinct reports for `Doe, Cookie`: report A has an unlabelled `Female  4/12/1988` banner; report B has `Female  4/12/1970`. Neither proposal contains a model identity question.
3. Preview B: it correctly returns blocking `confirmation_required`.
4. Explicitly confirm A as Self, then preview B again: it incorrectly returns nonblocking `prior_confirmation`. Individual acceptance of B succeeds into Self without confirmation of B.

Require review of the incompatible banner for that report. A confirmation of a different report must not bypass it. Preserve valid reuse where there is no unresolved mismatch, and preserve an explicit confirmation of the affected report as a way to resolve its ownership question. Do not simply place an unconditional blocker ahead of every receipt, which would make the question impossible to resolve.

## Compatible short years depend on whether the model asks

The original reader calls `numericDateReadings(raw, true)` for banners, while `isGenericNameConfirmation` calls it without short-year support. With saved DOB `1988-04-12` and banner `4/12/88`, the same original becomes `evidenced_match` without a model question but blocking `confirmation_required` with the routine ownership question.

Use consistent compatibility rules for unlabelled banners in both paths. Preserve the stricter labelled-DOB rules: a labelled ambiguous or two-digit DOB still requires review. Do not turn a compatible unlabelled reading into evidenced or offered DOB, stronger confidence, or a profile update. Model-only DOB warnings remain advisory as already decided.

## Implementation

1. Add failing regressions for both reproductions before changing the policy. Retain the existing compatible-banner, labelled-DOB and explicit-confirmation cases.
2. In `assessIdentityPolicy`, calculate banner incompatibility once against the current uniquely matched person's saved DOB. Use it when deciding whether a receipt from another report can be reused, before returning nonblocking `prior_confirmation`. An applicable explicit receipt for this report can resolve its banner ownership question; an unrelated report's receipt cannot. Continue to validate the original fingerprint, report boundary, membership and explicit issue resolutions using the existing receipt helpers. Do not make every banner mismatch a permanent DOB conflict.
3. Keep the mismatch check in the shared policy used by preview and acceptance. Do not fix only the UI or asynchronous identity preview. A changed saved person, ungrounded original, explicit refusal or stale review must still be checked at acceptance.
4. In `isGenericNameConfirmation`, use the same short-year compatibility helper as the original reader for unlabelled banners. Do not enable this permissive path for labelled DOBs. Keep date readings as private review clues; add no fields to evidenced identity or saved demographics.
5. Preserve the existing report confirmation API, durable receipt format and original bytes. No migration, new endpoint or model prompt change is expected. If implementation reveals a need for one, document the reason here before expanding scope.

## Acceptance checks

- Add permanent regressions to `src/server/test/intake-generic-name-question.test.ts` and the relevant identity boundary tests. The existing suite passes without covering these paths.
- With two reports on one original, confirming A must leave incompatible B blocked in the identity preview, feed, individual acceptance and bulk acceptance. Rejected acceptance must write no clinical records.
- Explicitly confirming B must allow its intended assignment and acceptance, while retaining a report-scoped receipt and unchanged saved DOB. Cover Self and another Person where the receipt paths differ.
- Cover compatible and incompatible short-year banners with and without a routine model question, with name-only and full-banner subject claims. Preserve labelled ambiguity, refusal and ungrounded-evidence blockers.
- Update maintained identity documentation to describe the final behavior. Run formatting, typechecks and focused tests; obtain an independent passing grade against both defects before completing this ticket.

This does not add accepted-record reassignment ([CRS-119](CRS-119.md)) or change the approved model-only DOB warning policy.
