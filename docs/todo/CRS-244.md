## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want a failed import check to show what stopped progressing,
So that I can distinguish an app defect from a slow installation without guessing.

## Plain-English User Walkthrough

1. A controlled fictional import fails to finish its verification run.
2. Its failure report shows the last observed completed work and outstanding work,
   or explicitly says which information could not be captured.
3. A later successful retry remains a separate result, not an invented explanation.

## Acceptance Criteria

### Scenario: A controlled run misses its completion guard

Given the existing controlled continuation fixture and unchanged correctness checks,
When completion, progress, assertion or setup fails,
Then bounded diagnostics retain available page/coverage counts, request and slice
counts, current work and the last observed progress without clinical contents,
And missing observations remain unknown rather than implying zero work,
And diagnostic failures cannot mask the original test failure.

### Scenario: Diagnostics do not weaken qualification

Given a successful run and deterministic injected failures,
When diagnostic coverage is tested,
Then existing completion/progress/outer/CI guards and full oracle assertions remain
unchanged, with no timeout increase or reduced fixture,
And no pass/fail model-speed SLA is introduced into the application,
And instrumentation adds bounded work and no durable clinical writes.

## Scope and Evidence Limits

Inspect the controlled continuation fixture and its CI reporting path, not the
separate real-provider qualification suite. Retain fictional failure evidence
outside Git and keep public reproduction instructions self-contained. Missing
progress, a slow productive run and an abrupt host exit must be distinguished
where evidence permits. A page number alone does not establish the cause.
