# 🔎 CRS-220: Integrate exact source-search projection and parity checks

Status: open. Integration remainder of CRS-207, builds on the implemented [exact serialization contract](../data/intake-state-storage.md#exact-serialization-domain) and depends on CRS-219's disposable text storage; unblocks CRS-209. Current search uses path LIKE OR the entire stored details_json LIKE, shared by count/page queries. This ticket preserves that behavior while selecting request-scoped reconstructed text through the existing access adapter.

## User Story

As a [Records assembler](../design/personas.md#file-and-review),
I want my searches to keep finding the document information I need,
So that I can trust search results and avoid overlooking evidence.

## Plain-English User Walkthrough

1. I search for information and inspect the results and counts.
2. When I return to my collection later, the same searches still find the same evidence.

## Acceptance Criteria

### Scenario: Keep exact search parity

Given source details include wildcards, unusual Unicode and a match spanning serialized boundaries,
When source-list count and page requests run against the new projection,
Then matching, filters, order, counts and complete DTOs equal the existing SQL LIKE oracle.

### Scenario: Refuse corrupt search authority

Given a selected source has missing or corrupt durable text evidence,
When a source-list request evaluates that source,
Then the request fails explicitly rather than normalizing away the problem or searching a guessed reconstruction.

### Engineer context

Matching fields independently is not equivalent to searching the exact serialized envelope, including matches across boundaries.

## Detailed engineering requirements

1. Preserve path OR details matching, embedded %/_ wildcards, SQLite ASCII case/non-ASCII behavior, punctuation/escaping, object/property order and matches spanning piece/key/value boundaries. Use SQLite LIKE or prove exact parity against it; per-field tokens/FTS are not equivalent. Preserve provider/reviewed-provider/acquisition/visibility/kind filters, path ordering, total counts, pagination and complete selected source-file DTOs.
2. Compare against the current SQL predicate on the exact authoritative serialized envelope, including all source kinds, null/empty metadata, unusual Unicode, reordered properties, renamed paths and already-retained raw text. Preserve the maintained normalized-serialization contract, complete outer-envelope order and intake-slot position. Untouched raw whitespace, duplicate-property spelling and escape spelling remain original durable/search bytes until an authorized rewrite or separately specified raw-text solution; reject unsupported authority rather than silently normalize search semantics. Integrate CRS-219 without adding another growing copy.
3. Reconstruct candidate serialized text without parsing every source into an operational intake object. Bound and clear request-local caches across count/page evaluation, exceptions, authorization/session changes, lock and close. Initial authoritative reconstruction may hydrate views once; the selected head/profile/source/version determines freshness. Preserve the existing single transaction for source mutation and derived changes.
4. Exercise actual source-list requests across insertion/deletion, distant changes, repeated/periodic text, reordering, escaped/multibyte boundaries, rollback, reopen, real private copy and total cache loss. Independently compare count, page membership/order and DTOs to the prechange SQL oracle. Missing/corrupt durable authority fails; disposable loss repairs only from verified selected evidence.
5. At 100/200/300 changes count initial bytes, changed content/link writes, SQL allocation, authority writes, rereads, reconstruction, serialization/diff/copy work and query-scoped reads separately. Preserve the implemented [explicit text-piece engine](../data/text-piece-edits.md), CRS-225 automatic retained-anchor reconciliation and CRS-219 transactional storage locality guarantees. Existing full source rows may remain until CRS-209; do not claim the complete production write path is incremental before CRS-210's real mutation/recovery qualification.
6. Ship a coherent adapter against current source authority, document implemented behavior and exact obligations for CRS-209, and retire this ticket after focused source/query/projection/recovery tests, formatting/types, full PR CI and independent review. Reassess scope and split only at useful complexity boundaries. No production authority cutover or heavy import retry.
