# 🛟 CRS-214: Qualify an independent encrypted-archive restore

Status: open. Depends on [CRS-213](CRS-213.md); unblocks [CRS-215](CRS-215.md). Serves the Operator and Caregiver's [operate and recover](../design/personas.md#operate-and-recover) job. Cache reconstruction and container recreation are implemented, but neither is proof that an independently retained archive backup restores.

## Fixed qualification scope

Use one small, independently fictional current-format encrypted installation on the supported npm → Docker Compose path. Include Self and one managed person, retained originals, explicitly accepted clinical records, a note and attachment, a field/ownership correction, history, pending review and an explicitly stopped import. Reuse existing fixtures and recovery mechanisms. No paid inference, private archive, old-schema migration, backup scheduler, Takeout format or new cloud service is in scope.

## Acceptance

1. Stop the archive writer cleanly and produce a consistent complete encrypted-directory copy into fresh owner-only external storage. Keep its usable recovery kit separately. Record a bounded content-free inventory/hash receipt and app/build/format identity; do not claim that copying selected files or live copying is consistent. Provider authentication/state is separate from health history.
2. Restore that copy to a distinct empty archive path and isolated Compose project/browser session. No process may write the source archive, the two installations must not share unlocked sessions, and an existing destination is never overwritten. Unlock with the independently retained fictional recovery kit rather than a cached key or source runtime.
3. Verify exact original hashes; accepted records and person attribution; note/attachment; correction actor/time/source and prior versions; pending review and explicit Stop. Delete only the restored installation's disposable caches, recreate it and reproduce those results from authority without OCR or inference. Verify locked private-access refusal. Original/source authority remains unchanged throughout.
4. Exercise a missing required backup component and an unusable recovery kit: fail explicitly, preserve both copies and disclose unavailable scope. Do not silently reset, discard history, bypass integrity checks or adopt another profile's key. Authenticated older copies can still be accepted today; the drill must disclose restored clinical/key state rather than claim rollback prevention.
5. Add a self-contained maintained runbook and repeatable fictional qualification procedure. Distinguish access recovery, archive restore, cache rebuild and portable export in ordinary language. Record operator-chosen backup locations/retention and last verified restore as a proposal/workflow, not an invented schedule or automatic deletion policy. State that passkey removal/profile deletion does not revoke independent old backups, and keep recovery material separate.
6. Gate CRS-061 on current release-build drill evidence, separate from CRS-152's filesystem/provider and recreation evidence. Publish only safe counts and scoped conclusions; keep raw archives, kits and receipts outside Git. Run focused lifecycle/recovery tests, formatting/types, full PR CI and independent grading.

A successful fictional restore does not certify power-loss behavior, forensic erasure, every filesystem or an absent device. If this fixed drill needs a new general backup service, split that implementation before expanding this ticket.
