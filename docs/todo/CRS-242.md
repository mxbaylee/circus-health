# 🧭 CRS-242: Certify negative compatibility acceptance lookups

Status: open; scoped compatibility-path finding from PR #71. Prepared public
asynchronous lookup independently validates its catalog and refuses the reproduced
damage. The unprepared synchronous helper can instead return a false negative.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want the app to recognize a save that already happened,
So that a damaged working index cannot make my accepted history appear absent.

## Plain-English User Walkthrough

1. I reopen a previously reviewed import after its working files need rebuilding.
2. The app finds the accepted result or clearly refuses an unverified lookup;
   it does not report that there was no save merely because its index is incomplete.

## Acceptance Criteria

### Scenario: An incomplete index cannot prove absence

Given a fictional accepted operation and an unprepared synchronous lookup,
When its derived operation key is deleted or changed while completeness markers remain,
Then the helper reconstructs and validates the required scope or refuses explicitly,
And it never returns a successful absence based only on the damaged index.

### Scenario: Compatibility and prepared lookups agree

Given duplicate operations across and within originals, true absence and changed sources,
When cold synchronous and prepared asynchronous paths are compared,
Then both preserve first occurrence in the earliest source and exact source binding,
And prepared warm lookups retain their counted selected-work bounds,
And compatibility tables cannot mint native acceptance authority.

## Evidence and Implementation Scope

`retainedIntakeAcceptanceReference` in `intake-lookup-projection.ts` reads the
per-original `lookup-acceptance-operation-first` index without the independent
prepared certificate on its synchronous fallback. A fictional missing-key probe
returned null; `prepareIntakeLookupIndices` refused the same damaged state.
Audit direct callers and certify negative results without making every prepared
lookup scan unrelated originals. Accepted receipts remain authority.

Owner decision, 2026-10-15: keep this separate from the PR #71 user-facing fixes,
with the public preparation guard documented rather than treating the defect as fixed.
