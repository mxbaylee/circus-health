# 🔍 CRS-247: Bound exact source search work per request

Status: open; PR #71 review finding. At PR #71 head the default source-details
search limits are `Number.MAX_SAFE_INTEGER`, and matching runs synchronously
inside a SQLite callback, so one long search over a large profile can stall every
other request. The docs disclose the missing aggregate limit; nothing bounds it.

## User Story

As a [Records assembler](../design/personas.md#file-and-review),
I want to search the text of my sources for an exact phrase,
So that I can find the right document without the app freezing for me or anyone
else using it.

## Plain-English User Walkthrough

1. I type a long phrase into the source search on a profile with many large
   documents.
2. The results arrive, or the app tells me plainly that this search is too large
   and how to narrow it.
3. Meanwhile other pages and imports keep responding.

## Acceptance Criteria

### Scenario: A very large search is bounded by counted work

Given a fictional profile with hundreds of MB of retained source text and a
pattern near the accepted pattern budget,
When a count/page search request runs,
Then aggregate matcher work (text units × pattern words, fragments, evaluations)
is charged against a counted per-request cap, or the matcher yields
cooperatively,
And exhaustion refuses the whole request explicitly rather than returning
truncated counts.

### Scenario: Other requests stay answered

Given that search in progress,
When another session requests an ordinary page,
Then that request is answered without waiting for the full search to finish,
And responsiveness is judged by work counts and same-machine ratios, not a
fixed seconds bound.

### Scenario: Count and page do not double the work, and parity holds

Given a search with both a total count and a page of results,
When the request completes,
Then each source's text is matched at most once per request (or the reuse is
counted and justified),
And results still equal native SQLite `LIKE` semantics on the existing parity
fixtures.

## Evidence and Implementation Scope

- `src/server/source-details-search.ts:28-32`: limits changed from 100,000
  evaluations / 268,435,456 UTF-16 units / 536,870,912 bytes at `b8a5a01` to
  `Number.MAX_SAFE_INTEGER` (`git diff b8a5a01 2706c5d -- <file>`).
- `:195-223`: the registered function creates a matcher and drains every
  fragment through `consumeSourceTextProjection` synchronously, with no yield.
- `src/server/queries.ts:829-843`: the source list runs `COUNT(*)` and then
  `ORDER BY f.path LIMIT/OFFSET` with the same predicate, so matched text is
  traversed about twice per request.
- `src/server/source-details-like.ts:6,26-29`: bit-parallel matcher, cost about
  text length × ⌈pattern/32⌉ words; `SQLITE_LIKE_PATTERN_BYTES = 50_000`. In
  practice the `q` query parameter is also limited by the HTTP request header
  size.
- `docs/data/source-details-search.md:23,25` say there is "no default
  source-count or aggregate-text product limit" and that compatibility reads are
  not "a responsiveness guarantee"; update them with the chosen bound.
- AGENTS.md: keep interactive requests answered while background work runs.

Open question: should the owner prefer a counted refusal, cooperative yielding
(moving matching out of the synchronous SQLite callback), or both?
