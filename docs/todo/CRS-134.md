# CRS-134: Keep challenged names ambiguous and finish accepted-ownership correction

Status: open. Corrective follow-up to CRS-119 (reliability review R13), implemented at `ef6821d` and deleted there without an independent passing grade. Independent grading against HEAD `46e8b95` (no ownership or identity source changed since `ef6821d`) gave C+. The owner decisions in [CRS-126 D6](CRS-126.md#d6-ownership-corrections-change-current-authority-while-preserving-history) stand; nothing here reopens them. Requirement 1 is a safety defect and comes first.

## Decision and why

D6 separates two facts: who a report was assigned to at the time (immutable evidence) and whether its printed name may help match a later report (current authority, correctable). CRS-119 also required that a challenged name "require identity review rather than silently assigning future records", and that a selected-record correction "requires review instead of silently applying either owner" to the rest of its report. The implementation treats _unresolved_ as _removed_. Removing a challenged name from one person makes the same spelling unique to another, so the app files records to that other person with no question. That is the opposite of review.

- **Caregiver** ([CRS-130](CRS-130.md)): moves one mistaken record or report out of Self. The correction must not quietly file the rest of that report, or the next report with the same printed name, to a relative instead.
- **Low-effort self-tracker:** gets a question only where the correction created real doubt: the challenged name and the undermined report, not every report in the profile.
- **High-precision tracker:** re-uploads full exports. A reimport or later report must not be resolved by stale or challenged authority in either direction.
- **Records assembler:** must see that a saved record was once attributed to someone else, when and why, without reading the journal.
- **Receiving clinician** ([CRS-130](CRS-130.md#medical-records-practice)): reads only the packet. A record that moved between people must say so there, and a packet generated before the correction may already carry it under the wrong person. Medical-records practice corrects a misfiled record forward, including telling whoever already received it.

## Requirements, in priority order

### 1. An unresolved name stays an ambiguity (safety)

`effectiveKnownNames` (`name-associations.ts:137-141`) drops every name whose latest authority is not `active`. `commitOwnershipNames` (`src/server/ownership-names.ts:241-257`) writes `unresolved` for that decision and supersedes every affected receipt (`:258-273`). The shared policy then sees only the remaining owners (`src/server/intake-identity-policy.ts:719-745`), so the "saved for more than one person" question (`:929-937`) no longer fires and the report falls through to a non-blocking `evidenced_match` (`:997`).

- **G0 baseline:** with two Self confirmations of the name, a new report is `confirmation_required`, blocking.
- **G1:** move report B only. The name proposal is `unresolved` because report A still supports Self. Self's effective names become `[]`, and a new report becomes a non-blocking `evidenced_match` to Robin.
- **G3:** a three-record report confirmed as Self, two accepted. Move one accepted record. Pending record 3 goes from `prior_confirmation` (Self) to a non-blocking `evidenced_match` (Robin) for both `unresolved` and `destination`, and accepting it stores it under Robin. With `old` it asks, but only because Robin's full name happens to collide.
- **G4:** Self has the manual name "Robin Lane"; move the whole confirmed report. Preview shows `independentSupport: true`, `unresolved`. The manual name is removed as well and the next report goes to Robin without a question.

Required behavior, enforced in the shared server policy used by identity preview, the feed, individual and bulk acceptance, and reimport. A UI-only fix does not count.

1. Current name authority has three outcomes for matching. _Active_ matches normally. _Superseded_ is removed. _Unresolved_ never produces a positive match for anyone, and any report whose printed full name equals a challenged association returns blocking `confirmation_required` with a message naming the correction. It counts as a competing owner, so it can never make the spelling unique to someone else. Implement it as a separate challenged-name input on `IdentityPolicyPersonSnapshot` (`intake-identity-policy.ts:36-39`) and the Self snapshot, rather than overloading `knownNames`.
2. The status governs only the learned association. A primary name, or a name whose latest `Manual name assertion` is active, stays a positive name after an `unresolved` decision (G4). The hold covers the challenged association and its supporting decisions, not every occurrence of the spelling.
3. A selected-record correction that moves part of a report confirmed through ordinary identity confirmation holds that report's remaining unaccepted members for renewed review, whatever the name outcome is, and even when the name is single-token and produces no name effect. Today holds exist only for an earlier ownership `Report ownership default` (`src/server/record-ownership-authority.ts:354-395`). Reuse that hold and its explicit-reconfirmation release (`:254-265`) instead of adding another mechanism.
4. Evaluate the challenged-name check before another report's receipt is reused (`intake-identity-policy.ts:842-876`) and before `evidenced_match`. A new explicit confirmation of the affected report resolves it. Take on the check [CRS-137](CRS-137.md) handed here: a `this_is_me` receipt has no "assigned owner still matches" test like the `this_is_person` one at `:827-838`.
5. Audit and test every consumer of `effectiveKnownNames`: `src/server/intake-identity.ts:532` (Self snapshot) and `:1108` (Self-name veto on a new Person), `src/server/intake.ts:1367` (review and acceptance), `src/server/intake-identity-people.ts:17` (People snapshots) and `src/server/intake-people.ts:200` (`canonicalSelfMatch`). Also audit the next correction's preview (`ownership-names.ts:180-203`) and rebuild from the journal (`nameAuthorities`, `name-associations.ts:108-119`).
6. Write failing regressions for G1, G3 (all three outcomes plus acceptance) and G4 before changing code.
7. Let the person settle a challenged name once. The blocking question offers, beside confirming this report, a choice for future reports: "Always Robin Lane", "Always me" or "Ask each time". Choosing a person records an active association through the existing confirmation path; "Ask each time" keeps it unresolved. The correction preview states that leaving the name unresolved means later reports with that printed name will ask. **Why:** a hold that asks on every report of a long-running export is the alert fatigue the self-tracker cannot absorb, but the choice must stay the person's.

### 2. Link or keep both needs an explicit choice (item 3)

`decide()` in `src/app/features/clinical-review/RecordOwnershipAction.tsx:167-181` fills in `action: 'keep_both'` for any patch. Ticking "I reviewed both records' exact contents" (`:457-479`) therefore creates a keep-both decision, and that satisfies the server's check (`src/server/record-ownership.ts:369-370`), which asks only that some decision exists. The server must require an explicit `action` whenever matches exist. Keep split review and the match choice as separate fields in `src/shared/record-ownership.ts` and in the UI, and add no default. Write the failing server test first: a decision with only `reviewedSplit` is blocked. **Why:** equal-looking records are not the same event (D6); a checkbox about contents is not a matching decision.

### 3. A failed commit shows its reason and needs a fresh preview (item 4)

After a 409 from `save()` (`RecordOwnershipAction.tsx:145-165`), the dialog enters the uncertain state and reconciles. On `OWNERSHIP_NOT_FOUND`, the server's message is replaced with "No correction was published. You can retry…" (`:61-64`), and retry resends the same stale `commit.current`. A definite server rejection (409 or 403 with a code) must show the server message, drop the pinned commit and require **Update preview**. Only network failures and unknown outcomes reconcile. Key recovery by dialog and operation, not only by profile (`:45`), so one dialog cannot adopt another's operation. Write failing mounted tests first. **Why:** the caregiver needs to know that the evidence changed, not retry blindly.

### 4. Earlier attribution is visible (item 2)

A whole-record move keeps the record ID. `clinicalRedirect` (`src/server/clinical-references.ts:109-118`) and `ClinicalRedirect.tsx:11` explain a correction only when the ID changed, and no app code calls `GET …/record-history` (`src/server/index.ts:506`). Record details for each kind must show "Previously attributed to X; corrected on DATE" with the reason and a link to the accepted history, drawn from the `Record ownership event` journal (`record-ownership.ts:875-889`). Show it for moves, splits and links, and keep the moved record out of the former owner's lists. **Why:** the records assembler must not mistake current attribution for the original one.

- **Who.** The history says the correction was made by the profile's user, which is all the journal records (`actor: 'profile-user'`, `record-ownership.ts:949`), and presents it as the patient-side assertion it is. The app has no provider-originated correction today; do not imply one.
- **Packets.** Not verified: [note exports](../../src/server/NOTE-EXPORTS.md) do not mention ownership corrections. A packet generated after the correction shows "Owner corrected on DATE" for that record, in the PDF and the evidence JSON. The correction preview and the record's history say whether the record was included in a packet generated before the correction, so the person knows who may need a corrected copy. Settle first whether export receipts retain enough to answer that; if not, record what they do retain.

## Regression scenarios

- G1, G3 and G4 above block with no clinical write until explicitly confirmed; an explicit confirmation then saves to the chosen person. **Why:** an unresolved name is doubt, not permission for the other person.
- G2 (whole-report move with sole support, then `superseded`) and the distinct later report still match Robin without a question. **Why:** a complete, reviewed correction should not become a permanent prompt for the self-tracker.
- A report whose own receipt was never undermined, with no challenged printed name, still reuses its receipt. **Why:** the hold is limited to what the correction challenged.
- After rebuild and replay, all of the above behave identically. **Why:** current authority is rebuilt from the journal, not from a derived index.
- Requirements 2 and 3 fail before their fixes. **Why:** they were verified defects that the existing suite passes.

Prove the item 1–3 tests guard the fix by running them once against the pre-fix code and recording which fail.

## Open questions

- **The report's own unaffected receipt** (G1, report A): today it stays active (`record-ownership.test.ts:630`) while its name is challenged. Recommended: it keeps authorizing A's own later members but is not reused for other reports.
- **`destination` or `superseded` on a name with independent manual support:** should the correction also remove the manual Self name? Recommended: never silently. The preview states that it stays and links to People to remove it.
- **Challenged names and the Self-name veto** (`intake-identity.ts:1105-1115`) and `canonicalSelfMatch`: recommended that a challenged name neither vetoes a new Person nor counts as a Self match.
- **Undo:** CRS-119 defines undo as a new reviewed correction against current versions. Recommended: a "Review undo" action on the result screen and in record history that opens a prefilled preview in the reverse direction; no one-click reversal.
- **The "(you?)" pill after correction:** recommended to hide it once an accepted-ownership correction covers the report, and to show "Corrected to X" with **Change person**.
