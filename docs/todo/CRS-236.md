## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want my failed passkey tests to produce useful evidence and preserve access that already works,
So that the builders can improve compatibility without making me repeat unexplained failures.

## Plain-English User Walkthrough

1. I reload the reviewed hosted checker, check its revision and start the new diagnostic round. Old results are separate, not silently counted as current passes.
2. I use the default request first. I create and verify A, then B with the same username, then C with a changed username, following the next button downward. Advanced request modes keep separate saved runs.
3. I retry confirmation of a created passkey instead of creating it again. If an addition fails, checks of earlier passkeys appear below it. I can explicitly continue without pretending a skipped check passed.
4. I recheck the original A/B/C passkeys that were confirmed. At the bottom I download the report, check that it was saved, and explicitly clear only the current run. Previous-round reports stay separately available.
5. The builders debug my new report or add the missing safe evidence. While awaiting my next results, they continue other eligible work.

## Acceptance Criteria

### Scenario: a new error report arrives

Given a new or unprocessed report,
When the agent investigates it,
Then record its date/build, actual combination, each distinct failure, inspected code path, established cause or exact missing signal, implemented fix/capture, regression test and remaining targeted device action.
And a generic retry label, missing clarification or unexplained unknown error is not a technical resolution.

### Scenario: actionable engineering is complete and more reports are pending

Given the applicable software fixes and diagnostic preparation are verified,
When there are no unprocessed error reports or independently actionable checker defects,
Then leave CRS-236 open, retain the findings and exact needed physical observations, and work the next eligible ticket.
And do not fabricate a pass, universally label a provider unsupported, resume broader CRS-163 qualification, or silently discard a failed attempt.

### Scenario: the new round or experiment is used

Given previously saved results or a working A,
When the new round starts, a mode is selected, or a later registration fails,
Then previous-round data is not rewritten/deleted, modes have separately resumed/exported runs, and account identity/exclusions remain stable within each run.
And mode switching is unavailable during a native operation or queued save, missing storage is reported, and failed confirmations can retry the existing credential.
And guided A/B names match, only C's username changes, and the shared display name and user handle remain unchanged; no separate-account result is reported as a same-account pass.

### Scenario: diagnostic reports disclose their actual scope

Given native failures or extension results,
When saving or exporting them,
Then retain the bounded allowlisted type/length/stage/rule/name/code/boolean/enum evidence, including error-property availability and exact available text character counts, without presenting those scalar fields as original messages, stacks or cause contents.
And guided native-message excerpts survive changed-row save, reload and actual download with explicit original lengths, redaction/truncation and missing/empty/inaccessible states; legacy attempts receive no invented text.
And raw native payloads, IDs, salts, PRF bytes, keys and ciphertext remain outside reports; the broader owner request and full original-error export gap remain explicit rather than being declared complete.
And diagnostics cannot replace the native error, change successful decoding, add an await before the native invocation, or weaken mismatched-credential refusal.

### Scenario: the guided sequence ends or a step fails

Given confirmed earlier credentials and a failed or interrupted addition,
When the operator follows the downward flow or explicitly skips an unavailable step,
Then preserve the failed attempt and exact-linked fresh retained-access checks, allow later naming steps, and never substitute earlier successes for new recovery/final checks.
And final rechecks follow the enrollment sequence and decrypt original retained ciphertext without replacing it; skipped and not-applicable outcomes remain non-passes.
And failed downloads, stale exported snapshots, unsaved notes, active saves/prompts and cross-tab conflicts cannot enable unintended clearing; a separate saved-file acknowledgment and explicit Clear reset only the current guided mode.

### Scenario: source maps and environment hints aid debugging without inventing observations

Given an attempt's exact build and recorded environment,
When the agent investigates its failure,
Then match any independently available generated code location to that revision's paired source map, preserve operator labels and advertise OS tokens only as potentially frozen user-agent hints.
And source maps do not recover missing errors, NT tokens do not establish a marketed Windows release, and browser capability or attachment hints do not identify a password manager.

### Scenario: publication and real qualification

Given passing focused tests and independent review,
When required CI passes and the PR is squash merged,
Then publish only the static checker through the reviewed-main workflow and verify the hosted revision before collecting physical results.
And do not claim publication, provider success, or the remaining localhost backend/session/recovery/private-access/locked-refusal/Compose-recreation gates from fixture tests alone.
