## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want my failed passkey tests to produce useful evidence and preserve access that already works,
So that the builders can improve compatibility without making me repeat unexplained failures.

## Plain-English User Walkthrough

1. I reload the reviewed hosted checker, check its revision and start the new diagnostic round. Old results are separate, not silently counted as current passes.
2. I use the existing request first. When useful for a reported problem, I explicitly choose the alternative creation request and test its separate run.
3. I retry confirmation of a created passkey instead of creating it again. After adding or failing to add B, I check A again.
4. I download the report even when something fails, label the actual combination, and upload it for investigation. I can separately export the prior round without deleting it.
5. The builders debug my new report or add the missing safe evidence. While awaiting my next results, they continue other eligible work.

## Acceptance Criteria

### Scenario: a new error report arrives

Given a new or unprocessed report,
When the agent investigates it,
Then record its date/build, actual combination, each distinct failure, inspected code path, established cause or exact missing signal, implemented fix/capture, regression test and remaining targeted device action.
And a generic retry label, missing clarification or unexplained unknown error is not a technical resolution.

### Scenario: actionable engineering is complete and more reports are pending

Given the applicable software fixes and diagnostic preparation are verified,
When there are no unprocessed error reports or independently actionable checker defects,
Then leave CRS-236 open, retain the findings and exact needed physical observations, and work the next eligible ticket.
And do not fabricate a pass, universally label a provider unsupported, resume broader CRS-163 qualification, or silently discard a failed attempt.

### Scenario: the new round or experiment is used

Given previously saved results or a working A,
When the new round starts, a mode is selected, or B registration fails,
Then previous-round data is not rewritten/deleted, modes have separately resumed/exported runs, and A/B identity/exclusions remain stable within each run.
And mode switching is unavailable during a native operation or queued save, missing storage is reported, and failed confirmations can retry the existing credential.

### Scenario: richer diagnostics remain safe

Given native failures or extension results,
When saving or exporting them,
Then retain only bounded allowlisted type/length/stage/rule/name/code/boolean/enum evidence and never native messages/stacks/payloads, IDs, salts, PRF bytes, keys or ciphertext.
And diagnostics cannot replace the native error, change successful decoding, add an await before the native invocation, or weaken mismatched-credential refusal.

### Scenario: publication and real qualification

Given passing focused tests and independent review,
When required CI passes and the PR is squash merged,
Then publish only the static checker through the reviewed-main workflow and verify the hosted revision before collecting physical results.
And do not claim publication, provider success, or the remaining localhost backend/session/recovery/private-access/locked-refusal/Compose-recreation gates from fixture tests alone.
