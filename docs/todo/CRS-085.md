# CRS-085: Make conditions a first-class record; visits stay notes

Status: open, deferred option. Promoted from a one-line index entry during backlog grooming on 2026-09-30, when the owner settled its main question. Line numbers were checked at `1e6fa50`; re-verify before editing.

## Decision and why

Owner, 2026-09-30:

- **A Visit is not a separate entity.** It is a note with a visit tag, and every visit has a note. Not every visit is worth recording. What is worth keeping is the after-visit summary, test results and prescriptions. The app is not a date book.
- **Conditions are a proper noun.** A condition is a first-class entity, perhaps working like prescriptions (below), not a phrase left inside a document.

Who it serves:

- **Chronic-condition tracker** ([CRS-130](CRS-130.md)): tracks one or two values over years because of one condition. The condition is what connects the A1c results, the medication and the visits, and today nothing names it.
- **Receiving clinician:** a problem list is one of the first things a new provider reads. Today the packet carries conditions only as literal source assertions (see below), which is honest but not a list.
- **Low-effort self-tracker:** preparing for a checkup ("help me prepare for my annual physical", CRS-126) goes better when the assistant can find the person's conditions directly.
- **Privacy-sensitive patient:** some conditions (mental health, reproductive, HIV) are exactly what they may want kept out of one provider's packet. A first-class condition makes that choice possible to express. Per-record packet exclusion is unverified today (CRS-130).

## Where it stands

- **No condition or visit tables ✅.** Accepted clinical kinds are observation, medication, procedure and document (`ReviewRecordKind`, `src/shared/intake.ts:345-346`; tables in `src/server/migrations/001-initial.sql:15-19`). `src/server/NOTE-EXPORTS.md:11` says so and that absence of a summary does not mean no conditions.
- **Conditions today survive as retained source assertions ✅.** A provider packet includes unrepresented source records whose kind is `clinical_object` or matches condition, diagnosis, encounter or visit (`src/server/note-exports.ts:686-695`). They are printed literally, not interpreted.
- **Visits are already notes ✅.** Notes carry a free-form `note_type` and `event_date` (`001-initial.sql:21`). Built-in types are Therapy, Primary care and Specialist (`normalizeType`, `src/server/notes.ts:515`), and the type picker offers "Dr. Visit" (`src/app/features/notes/NoteTypeCombobox.tsx:18`). The Notes page heads historical notes "Visits & personal context" (`src/app/features/notes/NotesPage.tsx:290`). An after-visit summary imports as a document, which can carry `visitSpecialty` (`src/shared/intake.ts:367`). So the owner's visit decision needs no new entity; at most a consistent visit tag.
- **How prescriptions work today ✅**, the model "works like prescriptions" points at:
  - Each `medications` row is one sourced event: `kind` is order, reported use, dispense, administration or unknown, with a required `source_record_id` and a `person_id` (`001-initial.sql:17`). Provider rows are never edited.
  - Whether the person currently takes it is a separate personal assertion in `medication_preferences` (`current`, `not_current`, `unknown`), versioned, with who and when in `assertion_json` (`src/server/migrations/004-personal-medication-status.sql`; `appendMedicationPreference`, `src/server/medication-preferences.ts:5`).
  - An imported prescription starts inactive as a system default, not a personal confirmation, and an existing choice always wins (`appendImportedMedicationDefault`, `medication-preferences.ts:49-67`).
  - A document never changes the person's list; an explicit "discontinued" only suggests a change ([CRS-126 medications](CRS-126.md#medications)).
  - Packets summarize only personally confirmed current prescriptions, never an old provider `active` status (`NOTE-EXPORTS.md:7, 11`).

## Requirements

The shape below follows "works like prescriptions". Everything past the owner's two decisions is a recommendation, unconfirmed.

1. A condition is a clinical record kind, reviewed and accepted like the others (P2), with its source and location (P7), person assignment (D1) and version history (P4).
2. Provider mentions stay literal and immutable, one per source occurrence: a problem-list entry, a diagnosis on a visit summary, a FHIR `Condition`. Matching two mentions as the same condition is a reviewed relationship, never an automatic merge (P5).
3. Whether the condition is current for the person (for example active, resolved, unknown) is a separate personal assertion, versioned with who and when, like `medication_preferences`. An imported condition starts as unconfirmed, and no document changes the person's assertion. An explicit "resolved" in a document may only suggest a change.
4. Existing retained `clinical_object`, condition and diagnosis source records can be proposed as conditions for review, without losing the literal assertion. Nothing is reinterpreted silently on upgrade.
5. The provider packet's problem list uses personally confirmed current conditions, with every source still cited. The literal source assertions stay available.
6. Visits: no new entity. If the owner wants one visit tag across note types, define it as a note type or tag; an after-visit summary stays a document linked from its visit note.
7. Records assigned to another person stay out of Self's conditions, lists and exports (D1).

- Coding: store a printed code (ICD-10, SNOMED CT) literally when present. Should matching use a bundled offline vocabulary, as P16 requires for LOINC and RxNorm (CRS-121)? SNOMED CT's licence differs from LOINC's and would need checking.
- Whether a condition can be linked to the results, medications and notes it explains, and whether the assistant and charts use that link.
- Whether visits get one explicit visit tag or keep today's free-form note types.
- Allergies are in the same position today (no table, `NOTE-EXPORTS.md:11`). Same treatment, or separate?
