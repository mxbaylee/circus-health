# 📦 CRS-251: Restore intake state after paged package failure resolution

Status: open; review finding from PR #71. On the paged package path, clearing the
last package failure deletes its receipt but never restores the stored attention
label, so the intake stays **Needs review**. A related resume path can pause the
whole batch on a stale stalled-unit exception. Status derivation for mixed
import/proposal history stays with [CRS-232](CRS-232.md).

Effort re-estimate, 2026-10-16: M for coordinated restoration of intake status/summary from proven workflow evidence and scheduler error isolation, with regressions for both. Impact remains M, unmarked; score 4.

## User Story

As a [Low-effort self-tracker](../design/personas.md#file-and-review),
I want a ZIP import to stop saying it needs review once a failed member reads,
So that I only return to it when there is real work for me.

## Plain-English User Walkthrough

1. One file inside my ZIP fails to read, and the import is flagged for review.
2. I retry it and it now reads successfully.
3. The import returns to its earlier status, or keeps the flag only because other
   work is still waiting, and the list says which.
4. If I resume a paused import whose reading plan has since changed, only that
   import is held for attention; my other imports keep going.

## Acceptance Criteria

### Scenario: Clearing the final paged failure restores a provable state

Given a paged package intake whose only attention came from one package failure,
When the same source-bound operation succeeds and resolves that failure,
Then the stored label returns to the state its existing receipts prove, matching
the non-paged `resolveIntakePackageFailure` result for the same history,
And remaining units, candidates, questions or other failures still keep
**Needs review**, and no acceptance or keep-original decision is minted.

### Scenario: Resume with a stale stalled-unit exception is scoped to its item

Given a batch item with `forceModelResume` and a retained `processing_stalled`
exception for a unit no longer in an active plan,
When the batch resumes,
Then that exception is cleared or the item alone is paused with a specific reason,
And the batch and its other items continue, with no new model request spent on
the stale unit.

### Scenario: Restoration work is bounded

Given a large intake,
When a paged failure resolves,
Then the restored state comes from the checked workflow summary or a refusal to
prepare it, not from a full envelope rescan in the request,
And one resolution performs a bounded number of durable writes.

## Evidence and Implementation Scope

At PR head `2706c5d`:

- `src/server/intake-package-failures.ts:373-405`: `resolveIntakePackageFailurePaged`
  only deletes the failure slot; its comment defers the label to "the bounded
  workflow count owner", but no caller restores it. `recordIntakePackageFailurePaged`
  (`:366-367`) sets `needs_review`. The non-paged `resolveIntakePackageFailure`
  (`:132-190`) restores `details.state` when `workflowSummary` shows no review.
- Paged resolution is live: `durablePackageOwned` (`src/server/intake-package.ts:386`)
  and member reads (`:879`, `:1022`), reached from `assistant.ts:3069-3073`.
- `docs/data/streamed-package-originals.md:29` and CRS-232 (Acceptance, final
  paragraph) say the label returns to a provable state after the final failure
  clears. True for the non-paged path only. Correct that doc in this ticket; CRS-232
  keeps the mixed-history ordering rule.
- `src/server/intake-batches.ts:1551-1617`: the forced-resume loop clears each
  stalled exception via `clear-unit`; `intake-processing-exceptions.ts:142-147` and
  `intake-batches.ts:163-168` throw `PLAN_CHANGED` when the unit's plan is not
  active. The loop sits outside the per-item `try` (`:1694-1758`), so the error
  reaches the pump handler (`:837-856`) and sets `batch.status = 'paused'` with
  `runner_error`. Reproducing this with a fictional superseded plan is part of
  the work.
- `src/server/test/intake-package-paged.test.ts:357-365` checks resolution
  idempotence, not the resulting state.
