# 🎣 CRS-149: Stop assistant links from carrying data out, and prove sessions don't share an unlock

Status: open. Filed on 2026-09-30 after a read-only review asked whether a third party could pose as the model and pull data from an open session. No existing ticket covered it; `docs/todo` and `docs/security/model.md` were searched. Historical line references below are navigation hints, not current validation evidence.

## User Story

As a [Privacy-sensitive patient](../design/personas.md#operate-and-recover),
I want to check where a suggested link goes before opening it,
So that I can avoid sending record details to an unexpected site.

## Plain-English walkthrough

1. Select a web link in an assistant answer or model-written note.
2. See the destination and any warning about information carried in the link.
3. Cancel, confirm, or open the offered version without the extra information carried in the link.

## Given–When–Then acceptance

The detailed contracts, owner decisions and evidence gates below remain required.

- **Given** assistant or model-written note text contains an external web link, **when** the user selects it, **then** the full destination host is visible before confirmation, and a query or fragment produces the data warning and an option that strips both; cancelling opens nothing.

- **Given** internal links, prohibited schemes, credentials in URLs and model-written images, **when** the renderers apply the link rule, **then** existing internal-navigation and unsafe-link/image restrictions remain intact across each renderer, including NoteText.

- **Given** one session has unlocked a fictional profile, **when** a cookie-less or distinct-cookie session requests protected private reads or writes, **then** it receives 423 without private content or model invocation; public profile/setup/authentication routes keep their intended pre-unlock behavior.

- **Given** authorized and unauthorized sessions coexist, **when** the profile is locked, **then** private access is revoked in every session; existing tests are reused and gaps are filled, while documentation describes link confirmation as friction rather than a complete exfiltration prevention guarantee.

Grooming sizes the combined shared-renderer interaction and protected-route inventory as medium effort and medium impact; existing session-isolation tests remain evidence to reuse, not a reason to repeat their implementation.

## Decision and why

The review found no way for someone else to pose as the model or ride an open session, so this is not a fix for a known hole. It adds review before following model-written external links and completes route-coverage evidence for a session boundary already exercised by focused tests.

- **Privacy-sensitive patient:** an imported document is untrusted. Prompt injection ([security model](../security/model.md) R7) can steer the model's reads within the profile. A model-written link can carry read values to another host when the person clicks it; this ticket covers that renderer surface, not an exhaustive proof of every possible data-egress path.
- **Caregiver:** opens several profiles on one machine, so they rely on each browser session unlocking only what it unlocked.

## Where it stands

- **The model channel is closed.** The LiteLLM proxy has no published port, sits on an `internal: true` Docker network, and requires the generated master key (`compose.yaml`). The app talks only to `http://litellm:4000`.
- **Unlock is per session.** `session()` in `src/server/vault-app.ts:71` issues a random 32-byte `circus-session` cookie (HttpOnly, SameSite=Strict) with no profiles unlocked. `requireAccess` returns 423 until that session unlocks the profile. The app port is bound to `127.0.0.1`. Hosts other than localhost are refused, and writes need the app's origin. Existing `src/server/test/vault-app.test.ts` checks cookie-less denial while the owner is unlocked. `vault-api-isolation.test.ts` checks distinct-session denial for notes, history, originals and asset writes, global lock and recovery revocation; `security-boundaries-audit.test.ts` checks cookie-less denial for assistant, export and intake routes without model invocation. Reconcile the protected-route inventory against these fixtures and fill actual gaps rather than claiming the session boundary is untested.
- **External links.** `assistantLink` in `src/app/features/assistant/AssistantText.tsx:15` accepts any `http:`/`https:` URL without credentials and opens it in a new tab. A link such as `https://example.invalid/?d=<record values>` sends its query to that host when clicked. Images render as alt text and are never fetched.
- **Note preview also opens external links directly.** `NoteTextPreview` in `src/app/features/notes/NoteText.tsx` uses `noteUrl` from `markdown-model.ts` and renders accepted external destinations as new-tab anchors. Keep both renderer policies compatible while adding the shared confirmation; the existing safe URL/image rules are not the missing interaction.

## Requirements

1. Before opening an external link from assistant text, show its full destination host, and require a confirmation. When the link has a query string or fragment, say that it carries data and offer to open it without them.
2. Add the same rule to any other renderer of model-written text that allows external links. Check `NoteText.tsx`, which can hold model-proposed notes.
3. Extend the existing server tests where needed to show that a new session, with no cookie or a different cookie, receives 423 for every protected private profile route while another session holds the profile unlocked. Public profile cards, setup and authentication endpoints necessarily remain accessible before unlock. The test should also show that locking revokes access for every session.
4. Update R7 and the assistant boundary section of `docs/security/model.md` with the result, as a detection and friction control, not a prevention control.

## Completion

Run the assistant, vault-app and mounted assistant-text tests plus the existing and extended session-boundary tests. Obtain an independent passing grade before deleting this ticket, per `AGENTS.md`.
