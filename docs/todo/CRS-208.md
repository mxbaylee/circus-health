# 🪴 CRS-208: Prepare target-bound intake authority for private copies

Status: open. Copy/bootstrap prerequisite split from high-effort CRS-205. Builds on the implemented [exact serialization contract](../data/intake-state-storage.md#exact-serialization-domain) and [intake-state storage](../data/intake-state-storage.md); unblocks [CRS-209](CRS-209.md). Production intake has not switched to this representation.

## Contract

A private copy must reconstruct the current pending intake state as destination-profile-bound evidence before its first accepted durable head. Source-profile frames, namespace hashes and links cannot be reused as destination authority. Preserve the source archive unchanged and keep source/session authorization intact.

## Acceptance

1. Add a narrow, validated preparation/bootstrap boundary usable by encrypted-profiles.open(copyState) and contributor profile-lifecycle copy. The existing primitive requires configured current record durability, while target preparation precedes initial publication: resolve this ordering explicitly. A pure validated framing/preparation API or a coherent initial transaction may fit; never bypass readiness guards or install temporary false authority.
2. Validate selected source state before owner/path changes, prepare new target-bound frame chains and bounded heads/receipts, and remove only copied source-bound contributions from the destination. Destination source hashes, identities and references must match retained originals. Keep unchanged source files, accepted records and existing source-text rebind semantics. Distinguish copy bootstrap from unsupported old-schema migration; the owner requires no compatibility migration before production.
3. Preserve exact pending proposals, questions, plan units, decisions, versions, pins and public receipts while rebinding profile-specific internal authority. Specify target replay namespaces and preserve the maintained [serialization-order contract](../data/intake-state-storage.md#exact-serialization-domain), including the complete outer-envelope order and intake-slot position. Untouched raw whitespace, duplicate-property spelling and escape spelling remain original durable/search bytes until an authorized rewrite or separately specified raw-text solution; do not silently normalize them during copy. Destination writes cannot affect the source; both profiles reopen/recover independently without inference. No copied contribution may be published even briefly as valid destination authority before reframing.
4. Test failure before preparation, during immutable writes, before first target publication, after publication/ambiguous flush and before activation. Keep failed unpublished setup invisible and preserve any already-published authority. Cache-loss rebuild, original hashes, pending-state equality and accepted-record equality must hold; wrong-profile/source/hash or unsupported/missing evidence fails explicitly. Include real encrypted and contributor copy paths, with source preservation and activation ordering checks.
5. Document the implemented bootstrap API and its guardrails, and test it against staged fictional incremental state before production activation. Preparation costs scale with the copied state once; subsequent mutations use changed evidence. Do not claim the source-authority cutover or broad capacity qualification is complete.

Validation uses fictional data, focused local tests, formatting/type checking, full PR CI and independent grading. Before implementation, reassess effort and split again if the remaining work exceeds medium effort. On completion delete this ticket and its index entry, document implemented behavior and repoint dependents.
