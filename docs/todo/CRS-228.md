# 🪶 CRS-228: Reduce repeated work when reviewing a growing intake

Status: open. A production prerequisite for [CRS-194](CRS-194.md) before another heavy processing attempt. Builds on the measured [intake mutation and recovery contract](../data/intake-mutation-qualification.md). Durable contributions are incremental; several read, validation and projection paths still process the complete changed intake on ordinary operations.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want reviewing one new or changed record to remain manageable as my history grows,
So that I can keep accurate records without spending more time on each small update.

## Plain-English User Walkthrough

1. I open a collection containing many earlier records and review the next proposed record.
2. I save or revise that decision while the rest of my collection stays intact.
3. I can continue reviewing, searching and reopening my history without longer waits caused by records I already filed.

## Acceptance Criteria

### Scenario: Change one item in a growing collection

Given independently fictional collections qualified at initial, 100, 200 and 300 real batch and review changes,
When the user saves one additional decision or changes one existing item,
Then compare before and after counts for hydration, validation, cloning, serialization, diffing, hashing, reads and projection maintenance,
And eliminate avoidable repeated full-view work while preserving exact clinical values, ordered envelopes, receipts, review requirements and all retained evidence.

### Scenario: Preserve a coherent view across consumers and recovery

Given pending and accepted records, manually entered evidence, duplicates and source-text changes,
When review, search, export, private copy, reopening or cache-loss recovery reads the collection,
Then each consumer uses the selected authoritative state and correct profile and source bindings,
And stale or wrong-person review still refuses without a partial accepted write.

### Scenario: Reuse unchanged proposal classification beyond a small collection

Given a collection retains more than 128 proposals, including proposals with no administrative source-context entries,
When repeated review or complete-view requests classify those unchanged proposals,
Then previous verified positive and negative classification results avoid repeated file reads and hashes without increasing a fixed cache cap,
And changed content, profile or authority bindings cannot reuse a stale result,
And cold reconstruction, missing files, corrupt evidence and concurrent collections retain their existing verification and refusal rules.

### Scenario: Explain work that cannot be incremental

Given initial creation, one-time normalization, cold reconstruction and APIs returning a complete view have different costs,
When qualification reports processing work,
Then those costs are separated from warm changed-item operations and request response assembly,
And any intentionally full-view operation or uninstrumented scope is explicit, with evidence for its necessity and bounded behavior.

## Current implementation and design questions

Use the actual growth fixture and `intakeWorkCounters`, `intakeFileWork`, lookup/search/text-piece counters and accepted storage/SQL inventories. Current `intake-authority.ts`, `intake-state-storage.ts`, `intake-state-codec.ts`, `intake-state-access.ts`, `intake-lookup-projection.ts` and `source-text-projection.ts` contain full-view validation, normalization, cloning, serialization, matching and reconstruction. `sourceDTOEnvelopeBytes` measures reconstructed original envelopes; `dtoDetailsBytes` measures returned source-row details, including compact original markers and proposal details. These differently scoped counters do not establish complete HTTP response serialization cost.

The 20/80/160-group warm locality fixture now retains bounded changed content and source-text rows, but inserting at the front shifts 22/82/162 lookup rows (1,986/5,830/11,235 logical bytes). Preserve observable ordering while deciding whether ordinal maintenance can avoid rewriting unchanged entries. Exact array/window matching is a bounded heuristic, not a promise of globally minimum edits; ambiguous string matching can explicitly exhaust its work budget instead of emitting an unchanged middle as new content. These limits need representative review-path evidence, not raised caps or a snapshot fallback.

The real growth fixture also exposes repeated physical proposal reads: cumulative whole-file reads rise from 315 / 529,998 bytes at checkpoint 100 to 37,358 / 42,479,080 bytes at checkpoint 200. `cachedSourceContextVersions()` in `intake.ts` scans retained proposals for candidate versions without a positive source-context classification. Its process-wide 128-entry FIFO cache churns once the referenced proposal set exceeds that size; sequential rescans then reread and hash the same files. Preserve positive and negative classification, profile/content bindings and independent evidence verification when choosing a durable rebuildable projection, version-bound reuse or another measured solution. Simply raising the cache cap, omitting proposals or dropping retained evidence does not resolve the growth contract.

Choose implementation boundaries from measured hot paths: version-bound reusable validation/materialization, targeted mutation APIs, projection maintenance and complete DTO/search consumers may need different strategies. Keep profile/head binding, rollback invalidation, independent reconstruction and private-copy rules. Add missing accepted-record internal encode/hash/replay work, temporary rebuild-connection processing or other instrumentation where needed to assess a proposed optimization; existing logical counters are not total CPU instructions, SQLite VM work or physical disk traffic. Set work-count goals from the baseline and application-controlled operations, without a model-speed deadline.

This is an implementation and requalification ticket, not permission to indefinitely defer processing work because it is large. Coherent high-effort changes may proceed through independent review. The distinct scheduler journal remains [CRS-227](CRS-227.md); neither ticket alone qualifies the full clinical import, diagnostic download, physical devices or held PR #35. Do not repeat the known-failing dense import or use paid inference as the initial performance probe.
