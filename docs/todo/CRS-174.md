# 🗒️ CRS-174: Personal condition status and Conditions UI

Status: open. Personal assertion and UI remainder of CRS-085, waiting for CRS-173's reviewed condition records. Owner, 2026-10-01: Conditions are active, not deferred. Owner, 2026-09-30: a Condition is first-class, perhaps like prescriptions; a Visit is a note with a visit tag, not a separate entity. Split further if high effort, or obtain owner grading before merge.

Jobs: [Understand conditions](../design/personas.md#understand-conditions), [Build a history](../design/personas.md#build-a-history), [Correct a record](../design/personas.md#correct-a-record) and [Share a packet](../design/personas.md#share-a-packet). The chronic-condition tracker needs one understandable longitudinal view; the low-effort tracker should not confirm the same personal fact repeatedly without a reason; the caregiver and receiving clinician need to see whose assertion a status is and what evidence supports it.

## Requirements

1. Provide person-scoped condition lists and source inspection using existing components/adapters and CRS-173's exact sourced occurrences. Other people's conditions never enter Self's list. Distinguish provider mentions from what the person currently confirms; an absent list does not mean no conditions.
2. Keep personal current-status assertions separate from provider data, versioned with actor/time and earlier versions. Imported conditions start unconfirmed; documents never update a personal assertion automatically. Explicit source “resolved” text may suggest a change only. Preserve originals/literal provider status and use changed-record writes, never nested prior history.
3. Proposed status vocabulary is active/resolved/unknown with an optional resolution date. This is an implementation recommendation, not an owner-adopted policy. Resolve or explicitly record implementation assumptions before work; distinguish “unknown” personal assertion from no assertion. Show the status and its provenance truthfully on desktop/narrow layouts and after recovery.
4. Determine whether a condition links to the results, medications and notes it explains. Reuse existing record-link contracts and require explicit acceptance for assistant/chart interpretation; the owner's linkage question remains open. Do not infer causal relationships from co-occurrence or dates.
5. Visits remain notes. Decide whether to standardize a single visit tag across free-form note types; an after-visit summary remains a document linked from its visit note. Existing Therapy/Primary care/Specialist/Dr. Visit labels are not a separate visit entity and need not be rewritten silently.
6. Qualify explicit confirmation, correction, history, wrong-person exclusion, replay, lock/restart and cache-loss on fictional records. Preserve all source/actor/date distinctions needed by CRS-175. Update maintained procedures and independently review before retiring the ticket.

## Current limits and owner choices

Grooming, 2026-10-02: the implemented condition table stores separate sourced occurrences, not a longitudinal grouping or a personal assertion (`src/server/migrations/007-condition-occurrences.sql:3–11`). Existing clinical references exclude condition (`src/server/clinical-references.ts:4–9`). The relationship API offers provider amendments and same-event display preferences (`src/shared/clinical-relationships.ts:17–30`), requires the same current kind (`src/server/clinical-relationships.ts:405–414`), and supports only disjoint display pairs ([clinical relationships](../data/clinical-relationships.md#display-preference-and-event-counting)). It is not an existing contract for three distinct condition mentions or a condition-to-medication/result association.

The following recommendations are unconfirmed; record the selected policy before implementation. They add specificity to the existing Conditions job, not permission to infer diagnoses.

- **What confirmation belongs to.** Does personal status apply to one occurrence or an explicitly reviewed longitudinal Condition linking several occurrences? Recommendation: offer an explicitly reviewed person-scoped grouping/view with retained occurrence references, while preserving every literal mention. Specify how membership changes, withdrawal/split and an ownership correction affect the assertion; neither equal labels nor a new import inherits authority automatically. Do not create a parallel source-evidence store or collapse originals to achieve the view.
- **Status vocabulary and disagreement.** Resolve requirement 3's proposed active/resolved/unknown vocabulary and whether “I do not have this condition” needs a separate personal assertion rather than “resolved.” No assertion, explicit uncertainty, a personal disagreement and source refutation are different facts. Decide which appear in the default list and in a current-condition packet. Provider active/resolved/verification text remains separate and cannot settle these choices.
- **Personal entry without a document.** Decide whether a person can add a self-reported Condition before obtaining provider evidence. Recommendation: if offered, label its personal author and basis; do not fabricate a provider occurrence or convert a recollection into a provider diagnosis. Existing notes can retain the recollection until this scope is decided. Caregiver entry must name the managed person and preserve who asserted it.
- **Links and interpretation.** Decide whether the first slice includes explicit associations with results, medications and notes, and distinguish “related/supporting record” from “caused by/treatment for.” Extend existing link contracts where suitable, rather than treat same-event deduplication as causal linkage. Assistant suggestions await review; dates, co-occurrence and medications do not establish a diagnosis or causal relation. Keep visit tagging as the separate existing choice, with Visits remaining notes.

## Longitudinal acceptance additions

Use three fictional providers mentioning the same condition at different times, with one conflicting provider status and one relative's matching label. Under the selected contract, show every source, the separate personal assertion and its history, and a usable list without implying automatic clinical equivalence. Test a full-history re-export containing one new mention, an omission, a source “resolved” suggestion, correction/reclassification, withdrawal/split and wrong-person reassignment. None silently changes personal status or lends another person's confirmation to Self.

Qualify known, partial and unknown source dates separately from personal confirmation time and optional personal resolution date. Include an explicit no-assertion state, personal unknown and disagreement, then replay, lock/restart and cache-loss reconstruction. Test desktop/narrow layouts, keyboard source inspection and clear saved destinations; a bulk source acceptance must not also personally confirm conditions unless that is a separately displayed, explicit action. Packet assertions follow CRS-175, and source amendment/display choices follow CRS-143.

Allergy/packet dependencies are CRS-175. Literal code/vocabulary questions remain CRS-173. These requirements continue the recommendations in CRS-085 and do not invent further owner decisions.
