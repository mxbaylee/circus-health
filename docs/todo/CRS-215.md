# 🧭 CRS-215: Qualify safe release updates and unsupported-format refusal

Status: open. Builds on the implemented [independent encrypted restore procedure](../setup/archive-restore.md). Serves the Operator's [operate and recover](../design/personas.md#operate-and-recover) job. The existing update guide says to stop, back up and rebuild; this slice establishes a concrete release procedure and failure check, not old-schema support.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to update the installation with a checked way back if startup fails,
So that my retained records and their history remain usable.

## Plain-English walkthrough

1. Compare the current and candidate release notes and check the saved backup and recovery kit.
2. Stop the installation, start the candidate and verify records and unfinished work.
3. If the candidate fails, keep its evidence and restore a separate copy of the checked pre-update backup with the prior app.

## Given–When–Then acceptance

The detailed contracts, owner decisions and evidence gates below remain required.

- **Given** a stopped sole writer and verified consistent pre-update backup, **when** the candidate release starts with explicit archive/proxy configuration, **then** build, authority-format and disposable-cache identities are recorded without secrets, and original hashes, accepted history, corrections, pending review and Stop survive.

- **Given** unsupported/future authority or failed startup on a protected fictional copy, **when** the candidate refuses access, **then** it reports the scope and operator action, preserves authority bytes and never silently resets, discards history or invents conversion; incompatible disposable caches may rebuild only from supported authority.

- **Given** a failed candidate and usable separately retained kit, **when** the prior app restores an isolated untouched backup copy, **then** the expected state recovers without competing writers, with explicit notice that post-backup writes, general downgrade compatibility and rollback prevention are not promised.

- **Given** the proposed release procedure, **when** completion evidence is reviewed, **then** maintained release/configuration/format notes and CRS-061 gates cover this no-provider small release-build journey, focused startup/storage checks and normal independent review; excluded migrations/updater/remote deployment remain outside scope.

## Acceptance

1. Document a bounded supported update procedure: identify the running and candidate release/build, review their configuration/format notes, stop the sole archive writer, retain a verified consistent backup using the [independent restore procedure](../setup/archive-restore.md), and start the candidate using the same explicit archive/proxy configuration. Keep secrets out of version/diagnostic receipts and distinguish app build, archive authority format and disposable cache schema.
2. A candidate may reconstruct an incompatible disposable cache from supported authority. Unsupported authoritative archive/history/key/index formats fail explicitly with an operator action; never silently initialize an empty archive, discard accepted history, invent a migration or overwrite originals. Preserve archive authority bytes on refusal. No old-schema decoder or automatic conversion is required before production.
3. A fictional supported-current-format update/recreation preserves original hashes, accepted history/current records, corrections, pending review and explicit Stop. Test unsupported/future authority and failed startup with protected snapshots. Existing one-writer enforcement still holds; never run two app versions against one archive.
4. Demonstrate recovery from a failed candidate using an isolated copy of the untouched verified pre-update backup and its usable kit. Restoring the prior app plus that copy is distinct from downgrading an archive the candidate already modified. Do not promise general downgrade compatibility, rollback prevention or lossless return of writes made after the backup. Make those limits visible before the update.
5. Establish where maintained release/configuration/format changes are recorded and how the Operator checks them. Add this update/refusal/recovery journey to CRS-061; use a small fictional release-build fixture, no providers, private data or heavy imports. Run focused startup/storage checks, formatting/types, full PR CI and independent grading.

New schema migration, automatic image promotion, updater UI and deployment beyond localhost are excluded. Split before implementation if the candidate requires those features; retain the safe-refusal contract.

## Current evidence boundary

Source review: `docs/setup/archive-restore.md` and `src/scripts/qualify-archive-restore.ts` supply the separate-copy fictional restore procedure, not a completed release-update drill. `src/server/vault-index.ts` already rejects unsupported encrypted index formats; this narrow decoder check does not establish whole-startup authority preservation or recovery from a failed candidate. Keep the release-level refusal/update checks open.
