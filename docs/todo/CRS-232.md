# 🧾 CRS-232: Finish large text and embedded-file processing without losing scope

Status: open. Remainder of CRS-043. Streamed ZIP payload publication is implemented; whole-document text/JSONL consumers and PDF embedded attachments still have protective bounds. CRS-231's inventory work is independent. CRS-233 owns storage admission and the unresolved operator-setting choices.

## User Story

As a [High-precision tracker](../design/personas.md#read-unusual-evidence),
I want to read and review all of a large export and its attachments,
So that I can finish filing it without losing evidence or repeating already completed work.

## Plain-English User Walkthrough

1. I add my export and review it in manageable portions.
2. I can leave and return without starting the same reading again.
3. If something still cannot be processed, I see the particular file or part that needs attention and can download the original.

## Acceptance Criteria

### Scenario: Capture large text with bounded, proportional work

Given a retained text file fits available storage,
When all its text is captured across successive steps,
Then preserve exact UTF-8 decoding and existing character/line coordinates using bounded chunks,
And avoid rereading and hashing the whole original for each 24K-character window,
And source-text pages, pending ranges, issues and revision publication avoid hydrating or rewriting all prior evidence on each step,
And changed-source detection, correction history, operation receipts and cache-loss recovery remain intact.

### Scenario: Validate and review large clinical exports

Given a retained JSONL export exceeds the current 25 MiB, row-count or row-size safeguard,
When validation, proposal review and acceptance run,
Then replace those memory safeguards through bounded parsing and downstream consumption rather than raising their values,
And preserve exact numeric spellings, duplicate-key detection, duplicate-row accounting, unknown fields, issue order, line locations and bounded previews,
And report/person context, review tokens, mappings and exact reviewed versions remain checked before explicit clinical acceptance,
And no supposedly streamed validator returns an unbounded array for another whole-document consumer.

### Scenario: Preserve unavailable embedded or structured evidence

Given a PDF attachment, large JSON/HTML structure or other extraction scope cannot yet be processed safely,
When the user or converter opens it,
Then retain the original with a durable located exception naming the file and any reliably known attachment/member/page scope,
And expose unfinished work and an original download without inventing page 1 or claiming full extraction,
And repeated failures do not append duplicate exceptions, while only successful processing of that same source-bound scope resolves them.

### Scenario: Replace memory caps only after their consumers are bounded

Given large fictional direct and packaged originals,
When the replacement paths are qualified,
Then peak buffered bytes per step remain independent of file size,
And total staged, written, reread and hashed bytes scale with processed input and changed evidence rather than repeated full scans,
And relevant 25 MiB, 100 MiB per-call, 300-attachment and configured extraction barriers are removed only after their protected consumers are replaced,
And failures or interrupted processing preserve originals and exact pending scope through encrypted recovery.

## Engineering context and questions

`inspectIntakeFile` already reads in 256 KiB chunks; reuse it where appropriate. The gap is repeated whole-file scans and whole-state hydration, not an absent streaming upload implementation. Follow `intake-source-extraction.ts`, `intake-source-text.ts`, `intake-evidence.ts`, `intake-json.ts`, `intake-format.ts`, and direct review/import in `intake.ts` through all consumers. Streamed byte publication alone cannot establish bounded clinical review.

PDF page reads already use the verified range worker. PDF.js attachment extraction currently returns whole attachment buffers; its independent caps and lost filename on failure need explicit treatment. Do not replace working range reads or call ZIP qualification proof of PDF attachment extraction. A streaming attachment reader and incremental JSON/HTML structural index remain design work. Preserve parser/output security safeguards until equivalent bounded behavior exists; retained located pending outcomes are required meanwhile.

Preserve exact proposal/import review scope in status derivation as these consumers change. After a package failure resolves, existing receipts restore provable states; a historical import plus a different latest proposal can still leave a conservative stored `needs_review` label even though the failure list is clear and derived `needsReview` is false. Establish the actual current state from authoritative ordering/scope rather than letting a historical import or keep-original decision imply review of a newer proposal. Do not introduce new clinical approval when normalizing a display label.

Carry CRS-043's storage-only goal through this work, but do not silently choose legacy environment-setting policy owned by CRS-233. Update storage, upload, Docker runtime, source-text and release contracts with actual behavior. Run relevant upload, intake-format, archive-storage and encrypted-profile suites plus counted large fictional direct/package qualification and independent review. No model-speed deadline or physical/provider completion claim follows from these fixtures.
