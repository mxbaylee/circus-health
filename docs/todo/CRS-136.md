# CRS-136: Finish import review reliability after the partial-save change

Status: open. Implementation specification for the unfinished and defective parts of the former CRS-120 (reliability findings R19–R30), implemented in `a17f54c` and `d6f6176`. That ticket was deleted without an independent passing grade; an independent review graded the result C+. Line numbers below were verified at `46e8b95`; re-verify before editing, since later work may have moved them.

## Decision and why

Keep the shipped partial-save design: valid, explicitly approved selections save, every selection gets an exact outcome, and a lost reply is reconciled by its original operation ID rather than retried. See [review reliability](../import/review-reliability.md) and [CRS-126 D7](CRS-126.md#d7-independent-valid-clinical-saves-succeed-coupled-corrections-stay-atomic). This ticket fixes what makes that design unusable at scale or misleading in the list, and replaces the documentation's "covered" claims with evidence.

Preserve throughout: per-selection version tokens, explicit human approval (no silent refresh of an approved value), draft recovery, coupled groups committing atomically, profile/session authorization, and [CRS-133](CRS-133.md)'s rule that partial saves still reject affected records until an applicable exception exists. No optimization or retry may weaken any of these.

Personas ([CRS-130](CRS-130.md)):

- **Low-effort self-tracker:** uses Select all and expects one bad item not to cost the other approvals or leave them guessing.
- **Caregiver:** has several people with identical or similar names and must see whose record saved, failed or needs review.
- **High-precision tracker:** selects hundreds of items from a large backlog; saves must finish reliably and never look lost.
- **Receiving clinician** ([CRS-130](CRS-130.md#medical-records-practice)): sees only what was saved. A panel of which some results saved and others still need review must not read as a complete panel in a packet.

## Owner decisions, 2026-09-30

- **An unsent correction reason survives an unrelated edit.** `useReviewDrafts.ts:285-290` currently drops it when a different field is edited. Keep the typed text in its field, but do not send it with the unrelated patch.
- **Over-cap selections are sent in chunks of 200.** Select all shown selects the records currently loaded, which grows 100 at a time as more are loaded, so a long session can pass the server's 1000-item cap. 200 is a starting value and may change later.

## Requirements

### 1. Partial saves must scale roughly linearly (high-precision tracker)

The grader measured partial saves of 10, 20 and 40 items at 1.1 s, 3.8 s and 16.7 s, while the atomic path saved 160 items in 0.3 s. `reviewIntake` runs per entry in the dependency scan (`intake-partial-acceptance.ts:84-105`, call at `:89`) and again per group (`intake-report-acceptance.ts:276-278`, reached from `processManifest` `:146-162`). The server is synchronous, so a large save blocks every request and the client sees a lost reply at a few hundred items.

Review each intake once per operation and reuse it for dependency grouping, per-selection token checks and comparison resolution. Commit independent groups of one intake in bounded batches while keeping per-item outcomes, atomic coupled groups, isolation of a failing group from its siblings, deterministic child IDs, replay after restart and writes that scale with what changed (no growing copy of the request or earlier results). Keep the CRS-133 identity check per record inside the batch.

Add failing regressions first, measured in work the app controls rather than seconds, because wall-clock time depends on the machine and no model is involved in a save:

- The intake review runs once per intake per operation, whatever the number of selections. Assert it with a call counter at N=10 and N=200.
- Other per-operation work grows linearly with N: count durable writes (journal entries and rows written) and bytes journaled at N=50 and N=200, and require the larger count to be at most four times the smaller plus a fixed allowance for the operation manifest.
- The save commits in bounded batches and yields between them, so a concurrent read (for example the Import feed) issued during an N=500 save is answered before the save finishes.

Set no wall-clock pass or fail bound. The grader's timings above are reproduction evidence of one machine, not a target. **Why:** a save that looks lost invites the duplicate save that the reconciliation design exists to prevent, and a count-based test stays meaningful on any hardware.

### 2. A needs-review item must be retryable from the list (low-effort tracker)

Selection snapshots are stored only when an item is toggled or Select all is used (`ImportReviewPresentation.tsx:318, :595, :876`) and cleared only when the context changes (`:348`). `move` (`:538-580`) sends the snapshot's token and mapping, and removes only confirmed saved IDs. After `needs_review`, the item stays selected with the same stale snapshot, so Save returns `needs_review` again; an edit made after selecting is ignored the same way (the server rejects it safely, but silently to the person).

On any non-saved outcome, drop that item's snapshot and selection, keep its edits and editor, and mark it "Review again, then approve." Approval is taken from the record as currently displayed, never carried over from before the change. Explain the reason in the item's outcome copy. Also drop the snapshot when the displayed record's token changes for any reason (draft edit, source or identity change), and announce it once, for example "3 selected items changed while you were reviewing; approve them again", with each affected item marked. Verify first whether background reading of a still-running import changes the display tokens of items already shown ([CRS-118](CRS-118.md) owns those dependencies). If it does, a person selecting during a long import could lose selections repeatedly, and this requirement must say how that is kept rare. **Why:** re-sending the old approval can never succeed, and quietly substituting new values would change what the person approved.

### 3. Outcomes must identify the record and person (caregiver)

`ImportAcceptanceOutcomes.tsx:44` renders `{item.recordId} · needs review`; IDs look like `intake:<64 hex>:line:1`, and no person is shown. Extend the partial item (`IntakePartialAcceptanceItem`, `shared/intake.ts:986-999`) with bounded, optional display fields: label, kind and assigned `personId`, so the outcome remains readable after a reload with no client snapshot. Resolve the person's current name at display time. Older receipts without these fields render a neutral fallback ("Record in <report name>"), never a raw ID, and are decoded unchanged. Do not copy whole records or earlier results into the item. Add a failing test first with two people named alike, where only one record needs review.

### 4. Accurate, single announcement

`acceptanceSummary` (`ImportAcceptanceOutcomes.tsx:4-13`) produces "2 needs review". Use plural-correct wording ("1 needs review", "2 need review"). The same summary is announced three times: `ImportPage.tsx:483` (notice, `role="status"` at `:2049`), `:1476` (save status, `ImportSaveStatus.tsx:20`) and `ImportAcceptanceOutcomes.tsx:23`. Announce it once, without moving focus. Test with a live-region query that exactly one status region carries the summary after a mixed save.

### 5. Selected items must never be silently dropped from a request (all personas)

Verify first, then fix. In `ImportPage.save`, selected clinical IDs whose record is absent from the displayed feed, or not selectable, are skipped (`:1408-1418`), and when snapshots exist `grouped.clear()` (`:1448-1449`) discards the displayed-feed selections so an ID without a snapshot is omitted. Compute the difference between the selected IDs and the IDs actually sent. Every omitted ID must appear in the outcomes as not sent, with a reason, stay selected and never count toward "saved". If nothing remains to send, do not submit an empty request.

### 6. Selection above the 1000-item server cap

The server rejects the whole request with a generic message (`intake-report-acceptance.ts:84, :107`). The client must split a larger selection into sequential partial operations of a bounded size, each with its own operation ID, combine their outcomes in one summary, and stop after any unknown outcome instead of starting the next chunk. Give direct API callers a message that names the limit. Use chunks of 200 (owner decision above).

### 7. Person-scoped counts, links and medication (caregiver; original R19, R20, R23)

- **R19 counts and links:** `SavedRecordDestinations.tsx:88-96` resolves the owner. `PersonClinicalRecords.tsx` counts from `meta.total` (`:20-21`), but its test (`person-clinical-records.test.tsx:12-19`) answers every path with `total: 1`, so a count is never compared with its destination list. Add a test with per-path responses proving each badge equals its destination list, including after a filter, acceptance and profile change.
- **R20 caregiver medication:** the "other profile" case in `clinical-person-ownership.test.ts:144-152` is only a missing ID. Replace it with a record that exists in a second profile and is addressed through the first profile's route, a wrong-record and a stale-version write, and a positive case where a caregiver marks a relative's medication current and the count moves under that relative, not Self.
- **R23 focus:** `PersonScopeContent` hides all content while the scope is pending (`PersonScope.tsx:121`), including on `reload`, which drops keyboard focus. Verify, then keep content visible during a refresh that leaves the owner unchanged. Add a mounted focus test.

### 8. Accessibility and journeys (original R29 and the dropped acceptance steps)

Status and `aria-describedby` exist (`ImportReviewPresentation.tsx:1165`), but nothing tests announcements or keyboard access to history. Add tests for: announcement of saved, needs-review and unknown outcomes without focus movement; errors associated with their controls; history reachable by keyboard.

Add the journeys the original acceptance steps 4 and 5 required and that no test covers: a mounted test through the real `ImportPage.save` (the existing mounted bulk-save test mocks the presentation layer; `partial-review-save.test.ts` covers one lost reply only); profile switch and lock during a save; filtered and paginated selections; duplicate names; keyboard and narrow layout; and a real process restart, not a simulated one, replaying the original operation.

### 9. Component boundaries (original R30), sequenced last

`ImportDetailReview.tsx` is 2978 lines and grew; `ImportPage.tsx` is 2242 and `ImportReviewPresentation.tsx` 2295. Only small modules (54 and 55 lines) were extracted; `ImportPersonChoice` predates the change. After requirements 1–8 land, split only at the identity, source and record seams: move selection and approval-snapshot state, outcome handling and the identity/source controls into their own modules, keeping state ownership and navigation/draft guards where they are. Do it after the fixes so the behavior diff stays reviewable. No file may grow; the touched files should shrink. If the split proves larger than requirements 1–8 combined, complete it under a new ticket rather than delaying the fixes; state which was chosen in the completion review.

## Regression scenarios

Write failing tests first for requirements 1, 2 and 3. Use independently fictional data.

- Select all with one stale record: the rest save, the stale one shows its name and person, a second Save after re-approving it succeeds. **Why:** the low-effort tracker should not repeat nine approvals or hit an unwinnable retry.
- Edit after selecting: the edited item is not saved with the old mapping and asks for approval of the new values. **Why:** approval covers the values the person saw.
- Two people with identical names: outcome and destination links name the correct person; one owner's failure does not relabel the other's. **Why:** the caregiver must know whose record saved.
- An identity-conflict record inside a large batch still returns `needs_review` while its siblings save (CRS-133). **Why:** batching must not turn a review shortcut into a waiver.
- Lost reply, restart and rebuild at N=200: each item saved once, no duplicates. **Why:** a faster path must keep the unknown-outcome guarantee.
- Selection over 1000: chunks run in order, stop at an unknown outcome, and the combined summary counts every item.
