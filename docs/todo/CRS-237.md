# 🔏 CRS-237: Accept reviewed records without pausing the app for the final original check

Status: open; remaining work from the implemented
[selected clinical review and projection](../data/intake-bounded-views.md#selected-clinical-review-and-projection). Native
report acceptance already proves the complete original consumed-artifact union
cooperatively everywhere except one place: the HEAD-selection closure. That
closure is still one complete synchronous union physical sweep, run inside
`publish()` within the synchronous `transaction()`. This ticket owns making it
cooperative through a prepared acceptance publication, plus the remaining
callback-closure requirements CRS-231 carried for final durable publication.
It does not change CRS-232 or CRS-233 scope.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want to save a large reviewed batch while I keep using the app,
So that filing a long history stays practical and every saved record still comes from the exact original I reviewed.

## Plain-English User Walkthrough

1. I finish reviewing a report and choose to save it.
2. While the app makes its last check that my original files are unchanged, I can still open other records or pages; the app does not freeze.
3. If an original file was changed behind the app's back during that save, nothing is saved, and I am told the save did not happen rather than seeing records built from different bytes.

## Acceptance Criteria

### Scenario: The final original check lets other requests run

Given a fictional native report acceptance of one and of two blocks on vault and contributor storage,
When acceptance reaches HEAD selection and final publication,
Then the complete original union is proved cooperatively (at start, around each yield and at completion) with no synchronous union or session sweep (`unionSync` and `sessionSync` both 0 in the counted regression),
And an unrelated host request completes during that proof, while the current synchronous control blocks it,
And business logic and every callback run once, after which only authenticated frozen changes are replayed at final publication ("execute business logic once, then replay only authenticated frozen changes").

### Scenario: A changed original refuses publication from every callback boundary

Given installed SQL policy and unlock authorization callbacks are supported application boundaries,
When either callback, or a final before-publication observer, performs a raw same-byte replacement of a consumed encrypted object,
Then publication or profile activation refuses, with no receipt and no clinical rows,
And a managed-write counter alone is not accepted as detection,
And the original complete proof is closed after callback-capable work, then publication finishes through an owner-controlled path without another such callback.

### Scenario: The prepared path is not slower than the proof it replaces

Given the record owner stages a prepared acceptance,
When it checkpoints staged index and stringify work,
Then checkpoint cost does not scale the live acceptance proof by staged rows (today about 93,000 parent `current()` calls at about 2.3 ms each, 4–6 minutes, for one 1-block acceptance),
And counted work for one and two blocks is recorded alongside the existing guards.

### Scenario: Paths that cannot be prepared keep a proven fallback

Given a partial acceptance that retains its result, an operation that replays its own receipt, or storage with no read owner,
When acceptance publishes,
Then each either has its own prepared form or keeps the existing synchronous closure with its tested refusals,
And no path adopts a newer physical baseline or a newly observed HEAD as permission.

  one synchronous union sweep (the HEAD-selection closure) instead of 12 and 21.
- Projection preparation verifies sessions and the retained union in workers; a

## Prototype (not landed)

A prototype moved native acceptance onto the record owner's prepared publication:
`prepareRecordTransactionWithOriginals` → `authenticateRecordTransactionPreparation`
→ `stageRecordTransactionPreparation` → `commitRecordTransactionPreparation`, with
`discardRecordTransactionPreparation` and closing the originals in `finally`. It
touched `intake-clinical-projection-plan.ts`, `intake-collection-acceptance(-group).ts`,
`intake-discovery-admission.ts`, `intake-report-acceptance-native.ts`,
`intake-source-context-state.ts`, `intake.ts`, `record-versions.ts` and added
`prepared <backend> <n>-block acceptance publishes with no synchronous union
closure` tests (vault and contributor, 1 and 2 blocks) asserting zero synchronous
union and session sweeps. What it did:

- **Acceptance parent for `RecordPublicationOriginals`.** A new opaque
  `ClinicalProjectionOriginalProof` copies the projection plan's original signed
  union and live acceptance guards (never a newer physical baseline) into
  `captureRecordAcceptancePublicationOriginals`, which shares a generalized
  `capturePublicationOriginals` with the ownership-report parent. Live guards run
  only outside transactions; inside the callback-free replay only the
  scratch-bound proof is consulted. Acceptance never resumes under another
  same-plan child operation (`ownsContinuation` is always false).
- **Group writes through the recipe.** `manual_batches` and the
  `intake_mutation_revision` `app_meta` writes moved through
  `recordMutationStatement` so the recipe captures them.
- **Prepared discovery admission.** The admission is consumed inside the
  rolled-back preparation (recording that preparation's transaction token via an
  identity-only `currentRecordTransactionPreparationOriginals`), then
  re-asserted outside transactions by `assertPreparedIntakeDiscoveryAdmission`
  on every raw component except the connection's own change counter, plus
  authority and cache components.
- **Post-rollback source-context check.** A `capturePublicationCurrent` on the
  source-context classifier runs the exact publication proof while the private
  workspace is still owned and returns the same source-witness proof over the
  frozen witness set, for re-assertion after the rollback.
- **Routing.** Partial acceptance with `retainResult`, an operation that already
  has a `__record_transactions` receipt, and storage without a read owner kept
  the ordinary `withVerifiedPublication` path.

It reached the callback-free replay on vault and contributor storage, where the
replay refused. That and the other findings are the blockers below.

## Blockers

1. **Trigger with a JavaScript function.** The temp trigger
   `__clinical_source_fingerprints_insert` (`src/server/intake-clinical-source-index.ts`)
   calls the JavaScript scalar `__clinical_source_canonical_digest`. It is refused
   inside the terminal callback barrier, so the callback-free replay diverges at
   the first `source_records` insert (event 136 of 382) and is refused. The
   trigger needs a callback-free replay form first.
2. **Staging re-runs live checks.** Staging re-runs the parent `current()` at
   every index/stringify checkpoint, each running the acceptance live checks:
   about 93k calls, 4–6 minutes for a single 1-block acceptance.
3. **Partial acceptance writes outside the recipe.** The partial/`retainResult`
   path in `src/server/intake-partial-acceptance.ts` writes with plain
   `db.prepare`, so the recipe cannot capture it.
4. **No read owner.** Memory/no-durability storage has no read owner, so it has
   no prepared backing.

## Open questions

- **Owner judgement call (open):** the prepared rollback regenerates two
  in-memory cache identities (the collection-registry generation and the lookup
  projection generation). The prototype re-captured them at exactly that
  rollback's own outcome and compared durable components to the original. Is
  re-capturing those two identities at the rollback acceptable, or must the
  rollback preserve them? Not decided; do not treat the prototype as approval.
- Whether the four blockers are fixed in the prepared path or whether some paths
  (partial acceptance, no read owner) keep the synchronous closure with an
  explicit, documented limit.
