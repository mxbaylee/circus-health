# 🌙 CRS-081: Scoped import processing after lock or logout

Status: open. Production requirement for the already decided background-import experience.

Continue only explicitly authorized import work after lock, logout or profile switch using a separately scoped authority. Ordinary Lock must still revoke general archive access. Preserve Stop/deletion, encrypted durable checkpoints, profile isolation and review before clinical acceptance.

After process loss, require authorized unlock before recovery; do not retain general profile keys merely to keep work running. Verify late responses, revocation and restart against the existing security and recovery boundaries. Background work while the current session remains authorized is already supported; this item concerns additional authority.

## Decided product behavior and dependency

CRS-126 P15 and scenarios 2/14 already require leaving the app, signing out or switching profiles to preserve ongoing imports. This is an implementation requirement, not an optional behavior to ask the owner to decide again. Lock still revokes general archive access; only separately authorized import work may continue. Processing proposes records and never accepts clinical records or confirms identity on the person's behalf.

Build on the implemented [automatic recovery coordinator](../import/automatic-recovery.md) and [authorization boundary](../security/profile-encryption.md#import-recovery-authority). Its checkpoints, automatic-run intent, dispatch/publication checks and retry policy are already present. Do not add another scheduler, queue, provider backoff policy or automatic-run flag. This restricted authority and the integration journeys below remain required before claiming the full background-import experience in CRS-126.

**Job-scoped key** (owner, 2026-09-30): a separate key scoped to one import job is acceptable, so a worker can keep writing encrypted checkpoints for profile A while profile B is unlocked. This settles the open design question of how the worker writes A's checkpoints without keeping A's general profile key: it holds only the job's key. Only one profile can be unlocked at a time ([profile encryption](../security/profile-encryption.md#unlock-caching-and-locking)), so the job key is the only way A's work continues during B's session. The key's creation, wrapping, lifetime and revocation still need designing (see the contract below); it is a new security risk for [CRS-084](CRS-084.md) to size. [CRS-145](CRS-145.md)'s emergency-contact access would need the same kind of separately granted key.

**Why:** the caregiver must be able to work in another profile without either stopping the first import or leaving general access to that archive open. A job's restricted processing authority is different from permission to browse, confirm identity or accept clinical records. Sharing the existing coordinator keeps one interpretation of Stop, backoff and recovery. Requiring unlock after process loss avoids turning persisted work intent into an unattended archive-unlock credential. These are the reasons for [CRS-126 D8](CRS-126.md#d8-leaving-does-not-revoke-already-authorized-import-work), not discretionary alternatives for a later implementation to reopen without a new decision.

## Shared implementation contract

- Authorization identifies the exact profile, import job, permitted original/member inputs and allowed extraction/proposal/checkpoint operations. Any needed dependencies must be explicitly bounded by the server. The model cannot expand the grant to unrelated originals, saved records or another profile.
- An authorized upload/start establishes processing intent; scope must be established while authorized and bound to that work. Persist intent and encrypted checkpoints, not a general session credential or profile-unlock secret. Reading and writing under a scoped grant must be enforced independently of the browser's selected profile and ordinary session APIs.
- Dispatch and publication both check the current grant, scope and generation. A lock/logout/profile switch ends general UI/API access as applicable but leaves only a valid separately granted worker authorization. Stop, explicit grant revocation and deletion invalidate the affected worker authority and prevent late publication. Resume requires an authorized user action and restores only the reviewed job scope.
- Do not keep the ordinary unlocked profile runtime accessible simply to preserve the worker. The current `encrypted-profiles.ts` lock path closes the application/database, flushes encrypted state, disposes original access, clears the key and removes temporary workspace state. Design and verify the separate worker's input/key/output lifecycle before changing that teardown; bypassing it is not this feature.
- The worker retains encrypted pending output through the existing durable processing contracts. It cannot perform clinical acceptance, ownership/name confirmation, medication activation, general browsing or exports. An old general session remains unauthorized even when the worker is still active.
- Process loss ends the live grant. The next authorized unlock reconciles durable work and re-establishes eligible scoped processing from its retained intent; explicitly stopped/revoked work remains stopped. Persisted run intent does not independently unlock the archive after restart.
- Reuse shared capacity/fair scheduling across background jobs and foreground work. Status shown after unlock reconciles with the same job IDs and checkpoints; switching profiles must neither duplicate work nor expose the other profile's private progress details.

## Joint acceptance with automatic recovery

The owner confirmed this release-gate reconciliation on 2026-10-01: CRS-061's production gate includes this ticket's scoped continuation and joint journeys, alongside CRS-086's independent async work and CRS-189's large-document qualification. A completed coordinator, a continuing unlocked-session import or a passing diagnostics baseline alone cannot satisfy continuation after lock/logout/profile switch. Process-loss recovery still requires authorized unlock.

1. Start an import, then log out or lock with a valid scoped grant: the worker continues, while original reads, clinical APIs and old-session requests fail authorization. (Closing the tab already leaves authorized work running and is covered by `intake-process-recovery.test.ts`.)
2. Start an import in profile A, switch to profile B and perform foreground work. A continues within its scope and shared limits; B cannot read A's data and no result is published into B. Return to A and reconcile exact progress without duplicate work.
3. Exercise provider backoff and extraction/model stall recovery after lock using the existing recovery state machine. No second coordinator, divergent retry counter or manual Resume is introduced.
4. Stop/revoke/delete while a retry or model/extraction response is in flight. The affected grant becomes unusable and late responses cannot publish. Revocation does not erase retained evidence or already committed proposals.
5. Crash/restart while processing: no dispatch or archive access occurs before authorized unlock; unlocking recovers eligible work exactly once. Explicitly stopped/revoked work stays stopped. Verify encrypted checkpoint recovery and that no retained general credential makes restart equivalent to unlock.
6. Verify that permitted worker writes cannot become accepted clinical records and that general profile key/workspace cleanup remains effective. Document the implemented authority boundary and test its denials as well as successful continuation.

Journeys 3 and 4 depend on [CRS-140 requirement 1](CRS-140.md#requirements): repeated timeouts on one unit must cool down without an attempt cap. Land or account for that recovery behavior first. File-scoped Reprocess has already shipped under [automatic recovery](../import/automatic-recovery.md#durable-scheduling); verify that behavior in the joint journeys rather than treating retired requirement 4 as an unfinished dependency.

On completion, retain the rationale and joint-release boundary in maintained processing and profile-encryption documentation before deleting this ticket. Tests should briefly explain why logout may leave a scoped worker running while its old session is denied, and why explicit Stop/revocation or process loss has a different effect. Link those why comments to maintained rationale and repoint remaining CRS-126 dependencies rather than leaving links to deleted tickets.
