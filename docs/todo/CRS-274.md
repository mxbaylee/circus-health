# 🦺 CRS-274: Diagnose and resolve encrypted-upload bridge refusals

Status: open; retained from PR #91 CI on 2026-10-16. An ordinary fictional upload in an encrypted profile returned HTTP 500 when a legacy-bridge read witness was refused. The cause is not established; a focused local rerun passed. Investigation and any evidence-supported repair belong here, not in the People review change. No owner decision or unfinished ticket blocks diagnosis.

## User Story

As a [Records assembler](../design/personas.md#file-and-review),
I want to add several files to my encrypted profile while earlier files are being processed,
So that I can collect the documents I need to review without unexplained upload failures or losing their evidence.

## Plain-English User Walkthrough

1. I upload several documents to my encrypted profile.
2. I add another file while the app works on the earlier ones.
3. The new file is retained and becomes available for review. If its evidence actually changed during the operation, the app refuses safely and preserves my existing files and saved history.

## Investigation and repair boundary

Identify the changed witness component and the operation that changed it. Reproduce the ordinary upload/background-processing interleaving through the supported encrypted, session-authorized APIs before choosing a fix. Repair application coordination or the fixture only when the evidence identifies the defect; do not stop background work merely to hide an unexplained production refusal.

Preserve the legacy-bridge original-read proof and its actual foreign-mutation refusals, immutable original bytes and accepted history, encryption and profile/session isolation, and writes proportional to the changed data. Do not add blanket retries, loosen a witness check, materialize whole documents for proof, or make SQLite the recovery authority. Follow the existing [intake storage contract](../data/intake-state-storage.md), [record-version write contract](../data/record-version-storage.md) and [profile encryption contract](../security/profile-encryption.md).

## Acceptance Criteria

### Scenario: Explain the observed refusal

Given the retained CI failure and the passing focused local rerun,
When the upload and background-processing interleaving is investigated,
Then bounded evidence identifies the exact witness component and operation responsible for the refusal,
And a deterministic regression or controlled interleaving distinguishes the observed defect from a legitimate foreign change rather than declaring the passing rerun a resolution.

### Scenario: Add a file during authorized processing

Given an isolated encrypted fictional profile processing previously uploaded files,
When another ordinary file is uploaded through a current authorized session in the reproduced interleaving,
Then it is retained and available for review without a spurious bridge-authority refusal,
And a fixture-only repair, if justified, explains why the previous fixture interleaving was invalid and preserves coverage of ordinary concurrent uploads.

### Scenario: Keep real authority changes unsafe to consume

Given a held bridge read proof and an actual foreign mutation to the authority it covers,
When proof preparation or consumption checks that witness,
Then the operation still refuses the changed authority without replacing originals or accepted history,
And regressions preserve encrypted/profile/session boundaries and delta-scaled durable writes without blanket retries or weakened proof checks.
