# 🧵 CRS-199: Persist changed conversation content without repeated full snapshots

Status: open. Focused storage implementation split from CRS-198's measured import-capacity investigation in [PR #35](https://github.com/mxbaylee/circus-health/pull/35). Unblocks the scripted runner's bounded validation and subsequent large-import qualification. No existing production schemas need compatibility support (owner decision).

## Defect and intended boundary

`src/server/assistant-journal.ts` currently writes a complete `{ chat }` snapshot for every immutable event. Assistant request dispatch, attempt completion, tool completion and evidence consumption repeatedly persist a conversation whose operations, requests and checkpoints grow. The encrypted workspace then retains these new full snapshots as durable files. This is a write-amplification defect under the repository's storage contract, irrespective of whether it explains every byte of the observed runtime exhaustion.

A fresh 12-page scripted contributor probe produced 44 requests, six automatic slices and 12 exact clinical proposals. Before closure, its runtime contained 381 files and 19.31 MB of logical content, including 371 JSON files totaling 10.00 MB; chat event snapshots were among the largest individual files at about 75 KB. A larger sparse run filled its normal 1 GiB runtime allocation before reaching late source pages. Raw independently fictional receipts stay outside Git. The full failure's exact file distribution remains unmeasured; the implementation must prove its own work-count improvement rather than assigning all growth to chat history.

## Acceptance

1. Introduce one current conversation-storage contract that retains recovery authority while writing only changed content and bounded incremental generation metadata. Reuse existing durable publication/profile containment patterns. Do not write another complete chat, growing operations/request-attempt array, complete reference table or prior-history snapshot per event, including when only a status or appended text changes. Do not solve amplification by deleting history, disabling persistence or raising runtime limits.
2. Preserve current conversation reconstruction, reasons, ordering and profile isolation across restart, lock/unlock and encrypted cache-loss recovery. A small generation must not require replaying or rereading the whole journal on every write. Any in-memory acceleration is disposable and cannot become recovery authority. Explicitly reject unsupported older envelopes; no legacy decoder or migration is required.
3. Define and validate references/patches, ordering and sequence continuity, value/path bounds and identities. Missing, corrupt, out-of-order, linked or cross-profile content must fail explicitly without exposing another profile or fabricating a successful conversation. Preserve atomic immutable publication and retry/recovery semantics when writing content, publishing a generation or flushing fails; do not let a failed append advance a cached authoritative state.
4. Keep diagnostic reads bounded by aggregate bytes and entries across all content needed for reconstruction. Missing budget or history remains explicit. Backups must snapshot a coherent generation and copy all required immutable content without including partial publication; verify restore from that backup. Update direct consumers and maintained storage/security/diagnostic documentation to the implemented format.
5. Add meaningful focused work-count regressions: append hundreds of fixed-size operations and physical-request attempts, update one existing item and append text, then measure new files/bytes and journal rereads. Demonstrate growth proportional to changed content and bounded metadata, rather than quadratic full snapshots. Verify reconstruction equality, no-op behavior, deletion/truncation semantics where supported, failures, profile isolation, diagnostic budgets, backup and encrypted recovery. Use independently fictional data only.
6. Recheck the affected scripted bounded import under unchanged application/runtime limits after the storage fix. Preserve the earlier capacity failures and account for remaining growth or diagnostic gaps rather than declaring complete production qualification. Run focused local checks and full PR CI, obtain independent review, and update the broader capacity/large-import tickets with the result before retiring this focused item.

## Implementation sizing

Keep this slice to the conversation journal and its direct consumers/recovery checks. If implementing the storage contract requires a broader multi-store redesign, split and size the additional work before proceeding. Original clinical documents and accepted-record authority are outside the mutation scope.
