# 🧭 CRS-235: Keep record review responsive while checking earlier clinical decisions

Status: open. Global mapping decisions, record exceptions and saved-record matching still perform synchronous history reads during clinical preparation. These preexisting cross-intake catalogs have a separate selection and API boundary from [CRS-231](CRS-231.md)'s retained-intake and package authority work; neither ticket depends on completion of the other.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want to keep using my records while the app checks my earlier review decisions,
So that adding to a long history remains practical without losing choices I already made.

## Plain-English User Walkthrough

1. I open newly read records for review after building up a long history.
2. The app checks my earlier choices and saved records while I can still open other records or stop the current review.
3. I see the same applicable choices, duplicates and changed records that a complete check would find. An interrupted check does not pretend that no earlier decision exists.

## Acceptance Criteria

### Scenario: Complete checks allow other work to proceed

Given a fictional profile has many cross-intake mapping decisions, record exceptions and saved versions for an identity,
When asynchronous clinical preparation checks those histories,
Then real unrelated host requests can complete during each long traversal, including histories whose entries do not match,
And preparation does not synchronously materialize or sort the complete retained catalog before its first cooperative checkpoint,
And measured rows inspected, bytes parsed, comparisons, rereads and scratch writes explain cold and warm work without imposing a model-time target.

### Scenario: Earlier decisions retain their exact meaning

Given decisions include replacement, disabling, repeated matching keys, tied sequence/date values and legacy clinical versions,
When the new preparation path chooses active rules and the latest applicable exception,
Then its results and ordering equal the existing complete policy, including JavaScript locale comparison, replacement/deletion and insertion-order behavior,
And legacy optical-envelope and omitted-optical version fallbacks preserve reviewed exceptions without accepting newly available content implicitly,
And saved-record matching preserves person isolation, table precedence, the first exact match and the last changed-record fallback.

### Scenario: Changing authority or stopping invalidates unfinished work

Given a catalog check is in progress,
When cancellation, profile/session revocation, SQL changes including rolled-back writes, cache loss or physical evidence changes invalidate its captured authority,
Then the attempt refuses publication and closes its iterators and owned scratch,
And another active reader remains usable,
And incomplete or corrupt derived state never establishes an empty catalog or valid review token.

### Scenario: Existing clinical and transaction behavior remains intact

Given legacy callers and native review, correction and acceptance routes consume these decisions,
When bounded preparation is introduced,
Then complete policy, canonical values and review-token comparisons establish parity on large retained histories and legacy fixtures,
And transaction-bound synchronous consumers retain their authority checks without asynchronous gaps inside the authoritative transaction,
And caches remain disposable, profile scoped and bounded, with explicit invalidation and recovery evidence.

## Scope and engineering questions

The current entry points are `activeMappingRules`, `latestRecordException` and `previous` in [`clinical-import.ts`](../../src/server/clinical-import.ts). `activeMappingRules` returns a complete `ActiveMappingRule[]`; merely changing its SQL reader to an iterator does not bound the resulting array or its sort. Decide whether to introduce a checked indexed catalog, a selected provider/API, or another bounded preparation contract, and identify which consumers still require a complete output. Preserve the exact comparator and winner rules rather than assuming SQL collation is equivalent.

Choose how changes to global manual decisions and saved clinical history invalidate or incrementally update derived selections. Specify cold preparation, connection/profile lifetime, rollback detection, scratch ownership and recovery before claiming warm reuse. Preserve current accepted history and durable authority; this ticket does not introduce a new clinical policy or automatic acceptance.

CRS-231 continues to own all archive-dependent and retained-intake joins, including nested draft witnesses, report sources, grounding, identity warnings, receipts and canonical traversal. This ticket does not defer those requirements. The separate synchronous source-text search limitation is described in [source details search](../data/source-details-search.md); it is not covered by this clinical-catalog ticket.

## Verification

Add focused fictional regressions around each actual production callback, with late matches and entirely nonmatching histories, real unrelated host progress strictly during traversal, exact legacy parity and cancellation/drift cleanup. Count work and bound retained staging; a yield between records or a small output page alone is insufficient. Run repository formatting, type checking and affected clinical/security tests, obtain independent review and pass required PR CI. Update maintained limits and caller contracts when implementation lands. No new implementation or qualification is claimed by this ticket.
