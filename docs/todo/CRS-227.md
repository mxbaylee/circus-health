# 🧵 CRS-227: Stop replaying the entire processing queue for each saved change

Status: open. A production prerequisite for [CRS-194](CRS-194.md) before another heavy processing attempt or a claim of bounded processing work. This is the separate scheduler journal in `src/server/intake-batch-journal.ts`, not the implemented intake-envelope authority. The [mutation qualification](../data/intake-mutation-qualification.md) measures it independently.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want saving progress and stopping or resuming an import to stay practical as its history grows,
So that I can control a long import without losing earlier progress.

## Plain-English User Walkthrough

1. I start processing a collection and inspect its progress as more work is completed.
2. I stop and resume it when needed, then reopen the app and find the same saved progress.
3. Those small actions do not become increasingly expensive simply because the app has already recorded many earlier actions.

## Acceptance Criteria

### Scenario: Save a small queue change after a long history

Given a real scheduler history retains its initial state and at least 100, 200 and 300 transitions,
When one item or queue field changes through the actual manager,
Then warm reads, hashes, replay, diffing, serialization and durable writes are measured separately and scale with the changed evidence,
And no complete history scan, repeated full snapshot or growing reference-list write is hidden in the operation.

### Scenario: Recover without discarding earlier evidence

Given saved processing history and an interruption at each staging or publication boundary,
When the operator reopens, resumes or retries after an uncertain acknowledgement,
Then acknowledged progress and ordering are recovered exactly without duplicated decisions,
And all original events remain retained, with corruption, stale writers and unsupported authority explicitly refused.

### Scenario: Separate opening cost from ordinary changes

Given a profile is opened cold or loses its rebuildable cache,
When the journal reconstructs its current state and then receives small changes,
Then reconstruction and subsequent warm work are reported independently,
And warm correctness never depends on a stale process-local cache or SQLite as recovery authority.

## Current evidence and engineering scope

The actual manager create/resume/stop fixture retains 2/102/202/302 events and 1,475/56,011/110,611/165,211 journal bytes at initial/100/200/300 transitions. The checkpoint transitions each append 540 bytes but reread 55,471/110,071/164,671 earlier bytes. A final 24-byte reason value appends a 290-byte event while rereading all 302 events/165,211 bytes and replaying 2,860 changes. These are independently fictional logical filesystem payload counts, not an installation capacity claim.

Design a validated incremental current-head/index or equivalent strategy using the existing authority conventions. Preserve profile scope, immutable retained evidence, exact state and atomic publication. Measure every durable and derived representation, original integrity, replay and retry outcomes with unchanged limits. Do not prune history, silently migrate unsupported formats or replace the journal with repeated whole-state checkpoints. Reconcile the current diagnostic `queuedAt` boundary explicitly: stopping clears it in the public response after the durable save, while the saved and reopened state retain its timestamp; decide and test the intended contract rather than accidentally changing it during the storage refactor.

The index/head layout, writer/cache invalidation strategy and crash-consistent publication protocol remain engineering decisions for implementation and independent review. This ticket does not authorize live inference, a repeated known-failing heavy import or release of held PR #35. [CRS-228](CRS-228.md) owns the separate full-envelope processing costs.
