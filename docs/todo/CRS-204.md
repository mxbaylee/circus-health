# 🚪 CRS-204: Centralize intake operational-state access

Status: open. Second focused implementation split from CRS-201; waits for [CRS-203](CRS-203.md). Production persistence stays on its current representation during this boundary refactor. Unblocks [CRS-205](CRS-205.md).

## Purpose and data partition

Intake workflow reads and writes extend beyond `intake.ts`. Centralize them before changing durable representation so discovery, ownership and reviewed acceptance cannot silently read an empty or stale workflow. Reuse the existing [source-pin separation](../data/record-version-storage.md#source-text-write-amplification) and source-text authority.

The source row retains original identity and compact current attribution: original name, creation time, acquisition, received MIME type, parent, locator, derivative flag and current reviewed source metadata. The eventual operational store owns version/state, validation, proposals, metadata/import histories, acceptance/import status, conversion linkage, review fingerprints and the complete workflow. Source-text pins stay in their existing separate records. Preserve the effective intake version, material-change semantics and exact distinction between absent, null and empty values. Inventory every field against current types before implementation; do not accidentally retain a growing history in the compact source metadata.

## Acceptance

1. Introduce shared typed read/write boundaries that reconstruct the same intake view and preserve current source metadata/pins. Keep the existing authoritative persistence unchanged in this ticket; no dual authority, new-format fallback or silent omission. Explicitly document the field partition that CRS-205 will activate.
2. Migrate the operational boundaries in `intake.ts`: `details`, `checkVersion`, DTO/review construction, `update`, proposal publication and `workflowMutation`. Route the additional duplicate-review question writer and atomic report-acceptance receipt writer through the same boundary.
3. Migrate operational readers in People queues/dispositions, ownership blockers/contributions/names, packet review, assistant continuation/retry, package-role dependencies and source-text dependency validation. Search all `source_files.details_json` consumers; document why each remaining direct read only concerns stable source metadata. Tests must expose an omitted consumer rather than mask it with an empty-workflow default.
4. Give report-group discovery ordering and report-acceptance operation lookup explicit adapter APIs. Initially preserve their current SQL semantics. Do not replace indexed or scoped lookups with hydration of every intake; CRS-205 will back these APIs with compact transactional indexes. Preserve global discovery ordering, scoped ownership, exact receipt identity and idempotent replay.
5. Run focused regression coverage for pending proposals/candidates/groups/questions, source confirmations, People disposition, identity refusals, stale review/source pins, package/manual/duplicate paths, clinical acceptance and operation replay. Keep original bytes, accepted records, public DTOs and UI flow behavior unchanged. Validate through real adapter consumers, not only mocked helper calls.
6. Update maintained intake architecture documentation to describe the implemented boundary and current persistence. Run formatting, type checks, focused tests and full PR CI; obtain independent grading. Delete this ticket when it lands and repoint CRS-205 to the maintained contract. This refactor alone does not claim reduced durable growth or complete large-import qualification.
