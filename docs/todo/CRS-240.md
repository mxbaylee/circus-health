# 🗝️ CRS-240: Read encrypted profiles through the accepted source proof

Status: open; remaining accepted-source routing work from the implemented
[selected intake views](../data/intake-bounded-views.md). With
contributor durability, source ancestry, `GET /intakes/:id` and
`GET /sources/:id/content` read under the accepted source proof. Encrypted
(vault) profiles still use the SQL readers, except for rows only the accepted
proof can decode. Routing vault to the accepted reader is implemented as a
one-line switch in `intake-accepted-source-format.ts`
(`recordAcceptedSourceIncremental`), but it is not sound yet, so it stays off.
This ticket owns that remainder.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history) using an encrypted profile,
I want my files and their details to load from the same checked history whether or not my profile is encrypted,
So that a correction I just saved is what I see when I reopen it, with no spurious "changed" errors.

## Plain-English User Walkthrough

1. I correct a value on an imported report in my encrypted profile and save it.
2. I reload the page. The feed, the report, its people and the original file all load at once.
3. Every view shows my corrected value. Nothing reports that the file changed underneath me, and the original downloads completely.

## Acceptance Criteria

### Scenario: Vault reads use the accepted source proof under steady reloads

Given an encrypted fictional profile with a saved correction,
When the browser's concurrent reload burst runs for several rounds (import feed, source attention, the intake, identity review, source issues, review record and content download),
Then every read succeeds through the accepted source proof and shows the corrected value,
And steady rounds count 0 accepted-proof retries and 0 cold replays,
And `src/server/test/intake-accepted-source-correction-reload.test.ts` (both adapters) and `src/tests/browser/import-field-correction.test.ts` pass 5 of 5 with vault routed,
And the legacy-bridge witness, the identity witness, the vault read-owner check and the vault frontier's method-epoch check are not loosened.

### Scenario: GET-path temp maintenance does not land inside other requests' proofs

Given a vault proof is held by one request,
When another request's GET path installs or refreshes temp state,
Then that maintenance either runs before the proof captures its interval or leaves the method epoch and temp schema exactly unchanged,
And a real foreign change is still refused.

## What exists

- Reader-index observations answer an unchanged read with no temp writes, and reader maintenance waits behind accepted-proof admission (`withAcceptedSourceMaintenanceAdmission`).
- After a real foreign commit, the reader index refreshes rows only, with no DDL; any definition difference still rebuilds.
- The source-attention guard reinstalls only for DDL that names its objects.
- The committed-column reader is a second read-only `node:sqlite` connection. The earlier ffi reader reset the live `-shm`, stepped `data_version` and crashed node with SIGBUS; that cause is gone.
- Vault proofs advance across exact own publications, and a head read refused at close no longer retains its frontier.

## Why it remains

Historical browser failures below predate the committed-column reader moving to `node:sqlite`; re-measure routed browser behavior before selecting a repair. The current server reload fixture asserts zero accepted-proof retries and zero cold replays for vault steady reloads (`intake-accepted-source-correction-reload.test.ts`), and its comment describes that expected counted behavior. This source inspection is not a fresh test run or proof of routed browser qualification. Keep the server assertions distinct from the still-unqualified browser path:

- With vault routed, `import-field-correction` failed in every run (0/5 on full files, 0/1 on four single-case runs). The server reload test passed 5/5 at one point but was not rerun after the last edits.
- The blocker was GET-path temp maintenance running inside longer vault proofs and rotating the method epoch under held legacy-bridge reads. The first source was the initial `__intake_queue_transitions` install (`intake-queue-transitions.ts:13`, 4 writes, temp schema and epoch change). Reader-index and source-attention installs added more: 218 rotations in one routed run.
- Identity-review reads then failed with `SOURCE_CHANGED`, report-queue reads with `REPORT_QUEUE_CURSOR`, and vault proofs refused with "original backing verification refused" or "accepted source read owner changed".
- An earlier attempt queued vault proofs behind the clinical-operation queue: refusals fell from 6 to 0, but cold replays stayed, requests queued past the browser's 5 s waits, and the server test still saw `IDENTITY_SCOPE`.

## Open questions

- Does the browser blocker survive the `node:sqlite` committed-column reader? Re-measure rotations and refusals in the routed browser path first and compare current server fixture results.
- Can the queue-transition, reader-index and source-attention installs run once per connection before any proof, so that steady requests never rotate the epoch?
