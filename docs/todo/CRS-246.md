# 🧯 CRS-246: Place and account for disposable scratch databases outside the small /tmp tmpfs

Status: open; PR #71 review finding. At PR #71 head most disposable scratch
SQLite files are created under `os.tmpdir()`, which Compose mounts as a 128 MiB
tmpfs, with no capacity preflight. Real scratch sizes have not been measured, so
the failure size is unknown; measuring them is part of this work. The owner’s
subsequent encryption clarification supersedes the earlier plaintext disk opt-in
interpretation below. Configurable encrypted-disk scratch has not been implemented;
current contributor scratch may already be plaintext on an OS temporary drive.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want temporary working files for large profiles to land where there is room,
and to be told before work starts when there is not,
So that copying, compacting or reopening a large profile does not fail halfway
with a disk-full error I cannot explain.

## Plain-English User Walkthrough

1. I open, copy or compact a large fictional profile on a small laptop install.
2. The app uses temporary space sized for that work, or refuses up front and
   says how much space it needs and where.
3. Temporary health data stays in RAM, or is encrypted before it reaches disk.
   I can see where space is needed and what happens to unfinished temporary work.

## Acceptance Criteria

### Scenario: Large profile scratch fits a sized location

Given a fictional profile whose replay, copy or compaction scratch exceeds the
default `/tmp` tmpfs,
When cold vault replay, encrypted copy, contributor copy comparison or envelope
candidate preparation runs in Compose,
Then scratch is placed on a configured, sized location (or counted against a
documented capacity plan) and the operation completes,
And measured peak scratch bytes per operation are recorded as dated evidence,
not as a target.

### Scenario: Insufficient scratch space refuses before work

Given scratch space that cannot hold the counted requirement,
When such an operation is requested,
Then it refuses before any durable change with an explicit capacity error,
And a later `SQLITE_FULL`/`ENOSPC` is still reported as a capacity failure, not
as corruption, with accepted authority untouched.

### Scenario: Documentation matches actual scratch protection

Given the security and storage documentation,
When it describes the SQLite cache and scratch,
Then it distinguishes the current plaintext working files from encrypted archive
objects and documents the implemented RAM or encrypted-disk mechanism honestly,
And it names placement, key lifetime, crash remnants and cleanup for Compose and
contributor runs without implying the archive key automatically encrypts SQLite,
And no new durable authority writes or rereads are added merely to relocate scratch.

- `src/server/disposable-sqlite.ts:7-17`: `mkdtempSync(join(tmpdir(), prefix))`,
  0700 directory, 0600 file, `journal_mode=OFF`, `temp_store=FILE`. 86 call
  sites in 63 non-test files.
- Direct `tmpdir()` scratch outside that helper: `vault-record-backing.ts:133,142`
  (`accepted.sqlite`), `intake-copy-transfer.ts:112`,
  `intake-copy-incremental-reader.ts:170` (used by contributor copy comparison,
  `contributor-durability.ts:1389-1391`). Envelope candidate scratch:
  `intake-envelope-candidate.ts:97`.
- `compose.yaml:51-52`: `/run/health` tmpfs `CRS_RUNTIME_TMPFS_MIB` (default
  1024 MiB) and `/tmp` tmpfs `CRS_TMP_TMPFS_MIB` (default 128 MiB). Both are RAM.
- `intake-state-bootstrap.ts:273-289`: default bootstrap preparation caps for
  namespaces/rows/bytes are `Number.MAX_SAFE_INTEGER`; nothing bounds scratch.
- Precedent: `docs/setup/docker-runtime.md:44` already moved legacy backup
  projection scratch out of `/tmp`. Upload admission (`intake-upload.ts`) does a
  free-space check; scratch users do not.
- Original PR #71 documentation finding: the security model and storage accounting
  described encrypted cache objects without distinguishing plaintext working
  scratch. Maintained documentation now states that distinction; the encrypted-disk
  mechanism, capacity checks and corresponding supported procedures remain open.

## Owner Clarification and Implementation Direction

On 2026-10-16 the owner initially selected the suggested explicit disk-scratch
option. In a subsequent clarification they asked whether that space would be
encrypted with an in-memory key, said “Not plain text I hope?”, and questioned
why encrypted scratch should require opt-in rather than be a sane default.
The earlier answer must not be treated as approval of plaintext disk writes
under an assumption that they were already encrypted.

Using that clarification and the delegated persona guidance, require encryption
for disk scratch. Keep RAM-backed scratch as the default until an encrypted-disk
implementation has been designed and verified; then assess a sensible default
using the Operator’s capacity/recovery needs and the
[record-integrity lens](../design/personas.md#record-integrity-lens). Plaintext disk
fallback is not an acceptable way to satisfy capacity. An encrypted host drive
must not be described as application/profile-key encryption.

The disk location remains outside the archive. Encryption must cover actual
SQLite database, journal/WAL and spill files before disk writes, with qualified
key and nonce handling using established primitives. An in-memory archive key
alone provides no such protection. Prefer a scoped temporary key lifetime;
do not persist an unprotected key or make crash-orphaned scratch a recovery
authority. Existing profile key wrappers are distinct from a plaintext live key.
Record the chosen mechanism, lifecycle and default rationale in maintained docs
only when implemented; unresolved engineering details may be resolved through
normal implementation and independent review, without another owner policy gate.

Measure peak scratch bytes, account for encryption overhead, implement counted
capacity admission and explicit exhaustion errors, and qualify crash/cleanup and
session/profile boundaries. Large effort now covers this encryption mechanism
and its integration across replay, copy, candidate preparation and deployment;
the former medium estimate covered placement of plaintext scratch only.

### Scenario: Capacity cannot silently remove encryption

Given a Compose or contributor installation with insufficient RAM scratch,
When an operation needs additional temporary space,
Then it either uses the verified encrypted-disk mechanism under its documented
configuration or refuses explicitly before durable changes,
And it never silently writes plaintext working data to disk,
And a crash leaves no unprotected scratch key or plaintext database/spill file.

## Queue context

Keep RAM-backed scratch as the current default and require verified encryption before disk scratch writes; account for capacity, key lifetime, crash remnants and cleanup across Compose and contributor runs. The owner’s 2026-10-16 clarification supersedes the earlier plaintext opt-in interpretation; encrypted disk may become the default after implementation and review.
