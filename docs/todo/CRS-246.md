# 🧯 CRS-246: Place and account for disposable scratch databases outside the small /tmp tmpfs

Status: open; PR #71 review finding. At PR #71 head most disposable scratch
SQLite files are created under `os.tmpdir()`, which Compose mounts as a 128 MiB
tmpfs, with no capacity preflight. Real scratch sizes have not been measured, so
the failure size is unknown; measuring them is part of this work.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want temporary working files for large profiles to land where there is room,
and to be told before work starts when there is not,
So that copying, compacting or reopening a large profile does not fail halfway
with a disk-full error I cannot explain.

## Plain-English User Walkthrough

1. I open, copy or compact a large fictional profile on a small laptop install.
2. The app uses temporary space sized for that work, or refuses up front and
   says how much space it needs and where.
3. The documentation tells me honestly that this temporary working data is not
   encrypted and where it lives, so I can size and protect that location.

## Acceptance Criteria

### Scenario: Large profile scratch fits a sized location

Given a fictional profile whose replay, copy or compaction scratch exceeds the
default `/tmp` tmpfs,
When cold vault replay, encrypted copy, contributor copy comparison or envelope
candidate preparation runs in Compose,
Then scratch is placed on a configured, sized location (or counted against a
documented capacity plan) and the operation completes,
And measured peak scratch bytes per operation are recorded as dated evidence,
not as a target.

### Scenario: Insufficient scratch space refuses before work

Given scratch space that cannot hold the counted requirement,
When such an operation is requested,
Then it refuses before any durable change with an explicit capacity error,
And a later `SQLITE_FULL`/`ENOSPC` is still reported as a capacity failure, not
as corruption, with accepted authority untouched.

### Scenario: Documentation matches plaintext scratch

Given the security and storage documentation,
When it describes the SQLite cache and scratch,
Then it states that disposable scratch is plaintext, where it is placed in
Compose and in direct contributor runs, and when it is removed,
And no new durable writes or rereads are added merely to relocate scratch.

## Evidence and Implementation Scope

- `src/server/disposable-sqlite.ts:7-17`: `mkdtempSync(join(tmpdir(), prefix))`,
  0700 directory, 0600 file, `journal_mode=OFF`, `temp_store=FILE`. 86 call
  sites in 63 non-test files.
- Direct `tmpdir()` scratch outside that helper: `vault-record-backing.ts:133,142`
  (`accepted.sqlite`), `intake-copy-transfer.ts:112`,
  `intake-copy-incremental-reader.ts:170` (used by contributor copy comparison,
  `contributor-durability.ts:1389-1391`). Envelope candidate scratch:
  `intake-envelope-candidate.ts:97`.
- `compose.yaml:51-52`: `/run/health` tmpfs `CRS_RUNTIME_TMPFS_MIB` (default
  1024 MiB) and `/tmp` tmpfs `CRS_TMP_TMPFS_MIB` (default 128 MiB). Both are RAM.
- `intake-state-bootstrap.ts:273-289`: default bootstrap preparation caps for
  namespaces/rows/bytes are `Number.MAX_SAFE_INTEGER`; nothing bounds scratch.
- Precedent: `docs/setup/docker-runtime.md:44` already moved legacy backup
  projection scratch out of `/tmp`. Upload admission (`intake-upload.ts`) does a
  free-space check; scratch users do not.
- Docs to correct: `docs/security/model.md:85` ("SQLite cache and metadata ...
  Separately encrypted") and `docs/data/storage-accounting.md:27,55` ("disposable
  encrypted cache", "an encrypted SQLite cache") do not mention plaintext scratch.

Open question: should scratch move to the runtime volume, a new dedicated
volume, or the profile's durable directory, and does the owner accept plaintext
scratch on disk for direct (non-Compose) contributor runs?
