## User Story

As a [High-precision tracker](../design/personas.md#file-and-review),
I want to save a large reviewed selection and see exactly what saved for each person,
So that growing my history does not make each save harder or lose work when one item needs attention.

## Plain-English User Walkthrough

1. Select the records you reviewed, including records for managed people, and save them.
2. See which records saved, whose records they are and which still need review; linked corrections succeed together.
3. If the reply is lost or you lock or switch profiles, return to check the original save outcome before trying again. Continue with the unsaved work once its state is known.

## Acceptance Criteria

### Scenario: Large selections preserve coupled effects

Given selections exceeding record, proposal-block or aggregate-byte limits, with a coupled pair across a potential boundary,
When the browser plans sequential saves and one pair member is stale,
Then the whole coupled group stays together and cannot partly save,
And admitted operations respect 1000 selections, 100 blocks and 64 MiB while independent valid groups may still save.

### Scenario: Equivalent later saves do bounded work

Given one large fictional intake,
When 200 and 800 selections are saved and equivalent sequential chunks are measured,
Then journal writes and bytes scale with changed records and equivalent later chunks have roughly equal counted work,
And profiling distinguishes whole-intake rereads from changed-data publication; timing alone does not prove this requirement.

### Scenario: Unknown outcome and continuing capture

Given selected records for two alike-named people and background reading,
When a reply is lost or unrelated source content arrives,
Then the original operation is reconciled, every selection has an honest outcome and confirmed saved links name the correct person,
And later chunks wait on unknown outcomes, unrelated capture preserves valid approval, relevant changes require review, and lock/profile authorization remains enforced.

The requirements below retain source-token inventory, browser recovery, packet-disclosure and editor-extraction work; the full original contract still applies.

## Decision and why

Keep the partial-save design and CRS-126 D7: independent approvals save, coupled effects commit together, and a lost reply is reconciled by its operation ID. `AGENTS.md` requires writes that scale with what changed and performance measured in counts.

- **High-precision tracker:** saves hundreds or thousands of items from a large backlog; each save must cost about the same as the last.
- **Caregiver:** must see whose record saved.
- **Receiving clinician:** a partly saved report is marked in packets ("X of Y current report items reviewed and saved").

## Requirements

1. **Coupled groups above the cap.** Above 1000 selections the client still cuts at 200 with no regard for server commit groups (shared source assertion, destination or comparison target). Group before chunking, using grouping the server returns or computes in a planning call, and add a regression where a coupled pair straddles a chunk boundary with one stale member. The grader's reproduction (`GRADER coupled pair split`, scratch only) shows `['saved','needs_review']` where both should need review. The same applies to a selection of at most 1000 records spread over more than 100 proposal blocks, which still falls back to 200-selection chunks; split by block there instead.
   - **Aggregate bytes.** The server also rejects an operation over 64 MiB of retained proposal/original bytes (`intake-report-acceptance.ts:249-266`) with an atomic 413. The client cannot see those sizes, and since 2026-09-30 it sends up to 1000 selections as one operation, so a few large proposal files (for example 600 selections across four files of about 20 MiB) are now rejected where 200-item chunks happened to fit. Expose block sizes in the feed, or split by block and retry on that 413, and test it.
2. **Journal growth within one operation.** Historical CRS-136 grading measured 200 selections journaling 4.06 MB in 1,207 rows and 800 journaling 22.55 MB in 5,419 rows (5.6× bytes, 4.5× rows), including a full `source_files` intake row rewrite once per batch. The [selected intake authority](../data/intake-envelope-authority.md) now retains compact source-row metadata and publishes changed envelope evidence; the former row-rewrite diagnosis is not current proof. Re-measure actual partial acceptance at N=200 versus N=800 in one operation, where batching engages, using accepted-object/head, intake-frame, receipt and SQL inventories. Require writes that scale with changed records across every durable representation. Existing N=50 versus N=200 bulk count coverage and the separate mutation-growth fixture do not settle this larger acceptance shape.
3. **Equivalent sequential chunks need bounded work.** Historical grading measured five 200-item operations on a 1000-record intake journaling 6.1, 5.1, 5.6, 6.0 and 6.5 MB; the suspected cause was full-intake review, not a profiled result. Profile the current selected-authority path before assigning that cause or claiming the newer incremental writes fixed it. Separate review preparation, proposal-file verification, full-view host processing and changed-data publication; then make avoidable work incremental or bounded and assert roughly equal counted work per equivalent chunk. The implemented [verified intake work reuse](../data/intake-processing-work.md) foundation supplies materialization, classification and lookup reuse, with remaining full-view and conservative text-engine work disclosed; this ticket retains actual bulk-save acceptance, counted-work qualification and its safety regressions.
4. **Stale review across batches** (suspected, not reproduced). The review captured at the start of an operation is reused for later batches, so the per-batch review-token check compares the token with itself. Intake version, person, identity stamp and collision checks caught everything tried. Probe changes to other records a comparison depends on, and recheck per batch if one gets through.
5. **Saved outcomes name the person.** `SavedRecordDestinationLink` already resolves current ownership through `/record-owner` for its destination URL, but shows only the destination label. Add the visible person context, and a server-level test with two alike-named people where one saves and one needs review (today's test mocks both needing review).
6. **Tests missing:** stop after an unknown chunk outcome with a combined summary counting every item; the direct-API cap message; UI profile switch and lock during a save; an unknown-outcome announcement without focus moving; a duplicate-names journey.
7. **Background reading and display tokens.** Proposal validity and clinical proposal-review tokens now use measured source dependencies, but other intake review tokens still include the global revision and can churn on unrelated background capture. Inventory those tokens and the human-reviewed fields and resources each protects; narrow invalidation where the dependencies are known, while retaining conservative broad checks for unknown or genuinely whole-source review. Add fictional continuing-import regressions showing stable individual approvals on unrelated publication and rejection after relevant changes, then verify the same with a real continuing import. See [measured source dependencies](../import/processing.md#durable-evidence-and-review-boundaries). This is remaining implementation and qualification work, not merely a missing live receipt.
8. **Split the detail record editor** out of `ImportDetailReview.tsx` (2,687 lines), as CRS-136 requirement 9 asked; its docs already say the editor was not split.
