# ⏱️ CRS-259: Return host-only test guards to counted baselines

Status: open; PR #71 review finding. PR #71 raised nearly every host-only test
guard and CI job budget, several by an order of magnitude, without counted work
explaining the slowdown. Two oracle assertions were also dropped. Related to
[CRS-244](CRS-244.md), which covers diagnostics only.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want the project's checks to fail when host work grows unexpectedly,
So that a slowdown on my small laptop is caught as a defect, not absorbed by a
larger timeout.

## Plain-English User Walkthrough

1. A change makes local processing of a fictional import much slower.
2. The checks report which counted work grew (reads, writes, replays, bytes)
   instead of silently allowing a longer run.
3. Any check that genuinely needs more time says why, in counts.

## Acceptance Criteria

### Scenario: The host slowdown is explained by counts

Given the fictional fixtures whose guards were raised,
When they run against base `b8a5a01` and the closing head on the same machine,
Then the work counts that explain the growth (for example the roughly 13×
host-only increase in provider qualification, which makes no model calls) are
recorded and either reduced or accepted with a named reason,
And timing is used only as a coarse same-machine ratio, never a pass/fail target.

### Scenario: Guards return near base or carry a counted justification

Given each raised guard and CI budget listed below,
When this ticket closes,
Then each is near its base value or documented in `CONTRIBUTING.md` with the
counted work that requires it, as `CONTRIBUTING.md:77` already demands,
And no infinite (`timeout: 0`) wait remains where a bounded wait suffices.

### Scenario: No oracle is weakened

Given the assertions removed or self-referential in PR #71,
When the guards change,
Then they are restored or explicitly retired as obsolete with a reason,
And no fixture is reduced to make a guard pass.

fixture measured. The figures below are same-machine ratios and counts, not targets.

| --------------------------------------- | ---------------------------------- |

| CI PR `2706c5d`, run `38809365037`      | 1,062.5 s (passed; guard 1,080 s)  |
| CI PR `d6f3d59`, run `38829224354`      | 1,087.5 s (failed finite deadline) |

The run is about 13× slower locally and about 46× slower on CI. Half of `main`'s
local time is macOS `fsync`, which narrows the local ratio. The merge-blocker fix
commit is not the cause: `2706c5d` already ran at 98% of the guard.

Work counts from `CRS_PDF_CONTROLLED_WORK_DIAGNOSTICS=1` at completion:
3,558,345 collection node reads, 7,439,176 read-witness queries, 3,999,024 hash
calls hashing 4.11 GB, 154,412 nodes written and 303,110 private-envelope nodes
generated. `main` has no equivalent counters, so the baseline side is the profile
only.

Cost is steady per page, not growing with history. Each read window costs about
6.5 s locally, 25–35 MB hashed and about 29,000 witness queries. Each 10-page batch
commit window costs 120–150 MB and about 400,000 witness queries.

Filesystem calls on the main thread, PR head against `main`:

### Hot paths

1. **Per-read durability recheck.** `ready()` in
   `src/server/intake-state-storage.ts:277` calls `recordDurabilityStatus`
   (`src/server/record-versions.ts:4746`) on every collection read. That call
   re-reads the physical record head (`open` in
   `contributor-record-storage.ts:57`), then `realpath`s and `lstat`s it and its
   parents (`record-head-physical.ts:32,165`). Inclusive cost:
   `recordDurabilityStatus` 90 s (2.3 s on `main`), `ready` 79 s (2.1 s on
   `main`). `main` makes the same call, so both the call count and the per-call
   cost grew.
2. **Contributor record publication per commit.** `commitMaintenance`
   (`src/server/intake-state-collections.ts:3153`, 68 s inclusive) reaches
   record-version `publish`/`prepare` (70 s). Every immutable object is written
   with its own `fsync` (`contributor-record-storage.ts:587`, 37 s), and the head
   identity is rechecked after each write (`observeHeadIdentity`, 42 s).
3. **Backing-worker replay.** `contributor-record-backing-worker.ts` replays own
   publications through `attachRecordDurability`. The worker is busy for 208 s:
   `catchUpRecordsSteps` (`record-versions.ts:4206`) 118 s, `verify` 38 s,
   `advance` 37 s. Meanwhile the main thread is idle for 179 s, against 7.5 s on
   `main`. That idle time is consistent with waiting on the worker, but this has
   not been proven.

Which of these checks are integrity requirements, and which can be cached per
transaction or revision, is not yet established. Any reduction must keep the
physical-identity and durability refusals that the tests already cover.

Reproduce, on the same machine for both checkouts, with the canonical macOS
`TMPDIR`:

```sh
CRS_PDF_CONTROLLED_WORK_DIAGNOSTICS=1 NODE_OPTIONS="--cpu-prof --cpu-prof-dir=<dir>" \
  npm run test:continuation
```

The profiles stay outside Git.
