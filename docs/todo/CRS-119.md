# CRS-119: Correct accepted ownership and remembered-name attribution

Status: open. Implementation specification with owner decisions recorded.

Add audited correction of accepted clinical ownership within the current profile, between Self and People. Pending report assignment already exists; accepted records currently retain their attribution. Preserve originals, earlier record versions and the source's printed identity. Correcting ownership is a user assertion, not a rewrite of the original.

## Owner decisions

- Offer correction from a report and from selected saved records.
- When a prescription moves to another person, default its personal activity to inactive; the caregiver can explicitly activate it. Keep the previous person's assertion in history.
- If the destination has an apparent match, ask whether to link to that existing record or keep both using the existing matching review. Never silently merge or overwrite clinical values.
- An unlinked remembered alternative full name is a simple edit. Linked names need an audited correction rather than rewriting their historical attribution.
- The owner revised the earlier historical-link restriction: preserving a mistaken association for future matching can perpetuate one incorrect assignment. Preserve the historical records and receipts, but allow the active remembered-name association to be superseded through correction. Historical linkage alone must not require a mistaken name to remain active forever.
- Include name correction in the move preview. Propose moving an association when all its supporting assignments move; if other records still support the old association, ask which person(s) the name belongs to before using it for future matching. Historical records and receipts remain unchanged.
- A whole-report correction supplies the default person for later records extracted from that same unchanged report. Every later clinical record still requires acceptance; a selected-record correction does not change the default for the rest of its report.
- If reports A and B contribute to one saved clinical record and only B's person is corrected, split B's contribution to the corrected person while keeping A's record and history with its existing person. Preview the split and any clinical values needing review.
- A genuine printed-DOB error can be resolved through the separate explicit report-scoped exception approved in [CRS-133](CRS-133.md). An ordinary ownership move is not itself that exception and cannot change either the printed or saved DOB.

## Why these decisions fit together

The shared decision record is [CRS-126 D6](CRS-126.md#d6-ownership-corrections-change-current-authority-while-preserving-history). The caregiver needs one correction to stop future mistaken assignments; immutable history must not keep a wrong remembered name active forever. The records assembler needs the original attribution preserved even when current ownership changes. These needs are met by superseding current authority while keeping earlier evidence, rather than rewriting or deleting either.

Report scope and whole-record scope intentionally differ: a tracker re-uploading a large history may have several reports supporting one clinical record. Correcting one report must not move another person's valid contribution. A whole-report default applies to later records from that same report because repeating the same ownership decision adds work without new evidence; selected-row correction cannot assume the rest of the report is wrong. A new contradiction still asks.

Prescription inactivity for a new owner prevents transferring one person's medication-taking assertion to another. Preserving an existing destination prescription's activity protects that person's independent decision. Likewise, link-versus-keep-both review protects distinct events that happen to look alike. Whole-report corrections are atomic because a partially moved report with a fully changed header/name association would misrepresent who owns its remaining records; this differs from independent [partial clinical saves](../import/review-reliability.md).

## Scope and entry points

Use **Change person** in report review for accepted records as well as pending assignment, and expose the same ownership-correction workflow for selected saved clinical records. The preview states which accepted records move, which pending records change assignment, their current owners, the destination and any records excluded or needing a decision. A report action covers the exact displayed report membership; a selected-record action covers only the selected records and must not silently reassign the rest of that report.

Lead the confirmation with its actual scope: **Change person for this report** or **Move these saved records and all their sources**. Explain whether later records from the report inherit the destination, and provide a route back to report correction when the person intended only one contribution. This makes the scope decision understandable without requiring the caregiver to interpret an attachment graph.

Destinations are Self, an active existing Person, or a new Person created in the same correction transaction. Reuse `ImportPersonChoice` and the established DOB/name disambiguation contracts. Scope all reads and writes to the current unlocked profile. Cross-profile transfer, archive merging and changing primary/legal name are outside this operation. Archived destinations are unavailable until restored through the existing flow.

Cover accepted observations, prescriptions, procedures and documents, including their linked clinical/historical note projections. Ordinary personal notes and People entries are not implicitly moved with a clinical selection. Do not infer ownership of unrelated notes or other records merely because they mention the same person.

## Preview and explicit approval

Implement the shared service in `src/server/record-ownership.ts`, contracts in `src/shared/record-ownership.ts`, and route wiring through the existing authentication layer. Use `POST /api/profiles/:profileId/record-ownership/preview` for the exact selection/destination preview, `POST /api/profiles/:profileId/record-ownership` for its approved commit, and `GET /api/profiles/:profileId/record-ownership/:operationId` to reconcile the durable result. The preview input identifies either a report group/version or explicit clinical kind/record/version references, plus an existing destination ID/version or new-Person fields. The commit supplies `operationId`, the echoed preview/scope token, duplicate/relationship decisions and optional reason. Actor/time are server-owned. The preview binds:

- Exact record kind/ID/current version, original owner, displayed report group/version and membership where applicable.
- Exact source occurrence IDs and current attachment versions, including contributions that remain with the old owner, and the proposed clinical contents for any split destination record.
- Destination Person ID/version or the displayed new-Person fields.
- Current original/evidence references, identity issues and relationship/duplicate targets with their versions.
- The selected move/link/keep-both decisions and effects on medication activity, source links and linked projections.
- The affected remembered-name associations, supporting assignment references and versions, proposed future-matching effects and any unresolved ownership of the name. Never silently transfer every name saved on the old person.

Return a deterministic scope token binding the complete preview. Commit echoes that scope with a stable operation ID. Revalidate source/destination authorization, record versions, destination availability, evidence and every comparison decision inside the write transaction. A changed selection, record, destination, report membership or decision requires a fresh displayed preview; never silently expand a report move to unseen records.

If several independent groups create one new destination Person, bind that Person to the parent operation exactly once in the first successful correction transaction and reuse the same ID for later groups/replay. If nothing commits, do not leave an empty Person behind.

A move to the existing current owner is a no-op for ownership, not a new correction or name-learning event. A separately requested CRS-133 DOB exception is still a new reviewed identity decision even when the owner stays the same. Show a concise confirmation with record count and old/new owners; record a default reason such as “Corrected person assignment,” with optional explanatory text. Do not require repetitive free text for every moved result.

## Versioning and durable correction

Append ownership corrections through the existing record-version journal and transaction/replay machinery in `record-versions.ts`, the clinical adapters and correction history. A whole-record move keeps the clinical record's logical identity and appends a current version with the destination owner; a contribution split preserves the existing record for its remaining owner and establishes a distinct destination identity as specified below. In both cases, prior versions remain addressable. Existing acceptance receipts continue to describe what was accepted at that time. The correction records actor, timestamp, prior/current owner, exact affected versions, reason, original references and operation identity.

Update current owner projections and person-scoped lookup/reconciliation indexes together. Preserve historical source/clinical identity keys; do not retroactively rewrite old receipt fingerprints or use equal names as authority to merge records. Audit where current deduplication keys include ownership before implementation and ensure a repeated source import resolves against the corrected current owner rather than resurrecting the old attribution.

The change must remove moved current records from the old person's lists, trends, counts and exports and expose them under the destination. Historical versions remain visible as earlier attribution, clearly marked as such. Stable historical links must resolve to history or a clearly explained current destination, never silently show unrelated records. Source files remain profile-owned evidence and are not copied or moved on disk.

Treat one record and its coupled clinical/source/note projections as one atomic unit. A whole-report correction commits its exact displayed assignment and record set together, so the header cannot claim a completed move while some of its selected records remain under the old owner. Selected records from unrelated reports can be previewed together, but the confirmation must identify the commit groups and return exact outcomes. Preserve already committed group receipts if a later independent group fails. This grouping must remain explicit when integrated with the [itemized clinical-save results](../import/review-reliability.md#outcomes-and-recovery).

Prepare large reports with bounded reads and staging of changed versions using the existing segmented journal, then publish one transaction boundary for the whole-report correction. Do not copy the whole original/history into a receipt, expose staged partial ownership, or silently break the promised atomic report move into visible per-row commits. Revalidate the pinned selection at publication. Resource failure before publication leaves the entire report correction unapplied and preserves a clear retry path.

Persist a small correction receipt per committed unit/group. Replaying an identical operation returns its original outcome; changed input with that operation ID is rejected. A lost response is reconciled before another move is attempted. A process crash or SQLite rebuild cannot restore the former current ownership or publish half a correction. Journal growth scales with changed records and links, not the size of the source or total record history.

A whole-report move also appends a versioned report-assignment decision, bound to this profile, original/member and report/printed-subject boundary. Later membership growth in that unchanged report defaults to the corrected person without extending the old acceptance receipt to those records. Recheck current person availability and evidence; changed boundaries, new contradictory identity evidence or explicit identity refusals require fresh review. A selected-record move never creates this standing report decision.

Undo is another explicitly reviewed ownership correction against current versions, not deletion of the earlier event. It must recheck intervening edits, duplicates and current destination validity.

## Matching, relationships and medication activity

### Shared records and contribution splits

The current occurrence-attachment path in `clinical-import.ts` can link report B to a canonical record created from report A, without creating a separate clinical row for B. Expand the correction preview through those current attachment links; report membership alone is not a complete list of ownership effects. A report-scoped correction operates on that report's exact contributions. When other contributions remain for the old owner, keep the existing canonical record and its ID there, supersede only the selected contributions' current attachment decisions, and create a new destination record or link them to an explicitly reviewed destination match. Do not move A's record because B once matched it. A saved-record selection instead selects the whole current clinical record and must display all affected source contributions before approval; it cannot silently pretend to be a single-report move.

Build a split destination's proposed clinical values from the selected occurrences' accepted mappings, attributable corrections and retained evidence. Never blindly clone the merged canonical record: its values or later corrections may be supported only by A. Show what stays and what transfers, with exact sources. Missing required fields, incompatible values or corrections whose provenance cannot be separated require clinical review before that correction group commits. Preserve the existing original/mapping validation rather than fabricating values to make a split succeed. If removing B's support calls the remaining record's clinical values into question, include those fields in the displayed clinical review and require explicit resolution; do not silently change A's clinical contents. The confirmation approves the exact displayed split contents and any resulting clinical corrections, not just an owner label.

Commit the old record's updated current provenance/version, the new or matched destination, attachment supersession, correction receipt, applicable name decisions and report assignment as one coupled transaction. Maintain historical attachments and acceptance receipts as evidence of the former attribution; current projections and deduplication must follow the corrected attachment graph. Replaying the operation must reuse the split destination identity. Reimporting B resolves to its corrected contribution instead of attaching it back to A. Historical links resolve to the recorded version; current source links identify the new destination explicitly.

On a prescription split, retain the remaining old owner's activity assertion unchanged. The new destination prescription starts inactive, unless attaching to an existing destination prescription that has its own activity decision. Do not copy the old owner's assertion, manual notes or unrelated relationships. Apply the relationship checks below to both resulting records. Undo rechecks both current records and contributions and follows the ordinary reviewed matching/correction rules; it never deletes a split's history or automatically collapses records that have since changed.

### Destination matches and related records

Before committing, run the existing destination-person matching/comparison flow. Present apparent duplicates, their source/date/value differences and the explicit options to link or keep both. Linking retains both original occurrences and the moved record's history while identifying the destination's canonical current record. Do not overwrite different values or activate medication use as a side effect. Keep both creates/retains distinct current records with distinct provenance; similarity alone cannot collapse events.

Check correction/supersession and other clinical relationships during preview. Move coupled representations of the same record together. If a relationship would cross owners, require an explicit existing relationship-resolution choice or include the dependent record in a new displayed selection; never silently move an unselected record, silently drop a relationship, or retain a clinical relationship that incorrectly combines two people's histories.

A newly moved prescription starts inactive for the destination. The old person's taking assertion remains attached to its historical context and does not authorize use by the new person. If the move links to an already-existing destination prescription, retain that destination person's own current activity decision; moving an additional source must not deactivate it. The caregiver can activate an inactive prescription through the normal explicit control after the move.

Keep verified source-DOB conflicts blocking until explicitly resolved. [CRS-133](CRS-133.md) now authorizes a typed human assignment despite an incorrect printed DOB; consume its shared policy and receipt contract rather than inventing a weaker ownership-move bypass. The source discrepancy and saved DOB remain visible and unchanged. A receipt for the former owner never authorizes the new destination. Editing a clinical value does not resolve identity. Unlabelled banner ownership questions remain resolvable by explicit report confirmation under the maintained [banner policy](../import/identity-review.md#banner-compatibility-and-report-scoped-decisions); model-only DOB warnings remain advisory. CRS-119 may land before CRS-133 using the current hard conflict rule, but must disclose that limitation and leave the approved exception work open; it cannot claim to deliver that scenario until integrated.

## Remembered full names and future matching

Separate the historical statement “this name was used to assign this record to A” from the current statement “this name can help match a future report to A.” Historical record versions, printed names and confirmation receipts remain immutable. A versioned correction can supersede the latter association without erasing the former. In `PersonNames`, distinguish active names from historical corrected associations and explain which records/decisions established or corrected them. An unlinked name retains ordinary edit/remove controls; correcting a linked association uses the audited workflow.

Determine support from recorded attribution, confirmation and source-name provenance, not a substring search of clinical prose or another person's equal-looking name. A name association is person-specific and may legitimately exist for two people. Equal spelling does not authorize merging people or moving unrelated records. Distinguish support still affirmed for the old owner from historical support whose assignment has been corrected; merely retaining an old receipt is not continuing support. Unknown legacy provenance requires review rather than guessed transfer or unrestricted reuse of a challenged association.

The current `rememberSourceNameInTransaction` in `notes.ts` returns early when `sourceKnownNames` already contains the exact name and mirrors learned names into `knownNames`. That array is not a complete support ledger, and its first entry cannot prove that all supporting assignments moved. Establish effective name-association authority using all applicable confirmation/acceptance receipts and their corrections, plus independently asserted manual/primary-name provenance where available. Distinguish a mirrored learned name from an independent manual assertion; when existing data cannot establish that distinction, require review instead of inventing independence or sole support. Add versioned per-decision support references for future confirmations rather than continuing the first-evidence-only assumption. Retain the existing `safeSourceIdentityName` rule: a single printed name stays report-scoped and must not become a reusable alias through correction.

### Move preview and name decision

Include name correction in the ownership-move preview. When an association was learned from the mistaken assignments and all its still-effective supporting assignments move, propose superseding it for the old owner and remembering the name for the destination. The displayed move confirmation covers this effect. If independent support remains, or the move concerns only some records in a mixed-person report, ask whether the name belongs to the old person, the destination, both or remains unresolved. Do not infer that a clinical-record move alone transfers the report's printed patient name. A separate explicit name decision may be needed before a new association can be established.

The record correction can proceed with a displayed unresolved name association, but challenged name-based authority must then require identity review rather than silently assigning future records. This hold is limited to the challenged association and supporting decisions, not every occurrence of the same text in the profile. Existing records outside the approved selection retain their current owners. Selected-record correction creates no standing destination assignment for the rest of the report; if it undermines a prior decision, future use of that decision requires review instead of silently applying either owner.

### Required durable behavior

Persist supersession or unresolved status, supporting decision references and any confirmed destination association in the same transaction as the correction that establishes them. Preview pins these inputs; concurrent name learning, record acceptance or another correction must invalidate stale approval. For partial corrections, derive the name effect from the actual committed group and remaining support; never deactivate support for a group that failed to move. If groups share an inseparable name decision, preview and commit them together or leave the challenged association unresolved until reviewed.

All current identity consumers must honor the latest association/decision status: remembered-name matching, confirmation-receipt reuse, report defaults, individual and bulk acceptance, reimports, and rebuilt indexes. An old receipt remains audit evidence but cannot override its correction and revive the wrong assignment. In-flight previews using superseded authority must require renewed review at acceptance. A new report still follows normal identity review rules; remembering its name is not blanket clinical acceptance or verified DOB evidence. Existing independently supported identity evidence remains usable under the normal policy.

Use durable versioned storage and reconstruct current association status on replay/rebuild. Do not depend on deleting a derived index entry. For existing names, retain known provenance without inventing it; legacy associations implicated in a correction whose support cannot be established enter review. Undo is another reviewed decision against current support, not automatic restoration of all prior name authority. Primary/legal names, originals and prior receipts are never rewritten by this operation.

Example: a report for fictional Robin Lane is mistakenly confirmed as Self, teaching Self that name. Correcting the report to Robin's Person record preserves that first confirmation in history, supersedes its authority for Self and records the reviewed destination association. A later Robin Lane report must not be assigned to Self because of the superseded confirmation. If another person independently and legitimately uses that name, retain the ambiguity and ask rather than treating the spelling as unique.
