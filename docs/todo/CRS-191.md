# 🪧 CRS-191: Retain encrypted diagnostic collection origins

Status: open. Medium-effort, large-impact production prerequisite split from CRS-189. The first live observation and first retained event do not establish when encrypted archival collection attached; profile observations can precede that attachment. This slice supplies truthful collection-origin evidence for the normal diagnostics download.

## Requirements

1. Capture small immutable origin metadata at encrypted archive attachment: diagnostic window UUID, attachment timestamp from the injected recorder clock, recording state at attachment and the profile window's observed-event count before attachment. Explicitly distinguish those pre-attachment observations from archived/persisted evidence. Do not infer counts from process-global sequence gaps or infer attachment time from the first surviving event.
2. With detailed recording enabled, attempt one bounded zero-event origin/checkpoint chunk at attachment and repeat the immutable origin in subsequent existing incremental chunks. This permits origin recovery before a first event and after intact-prefix eviction. Use the existing encrypted chunk store; no separate collector, whole-window/document copies or per-event origin writes. Allow one constant additional bounded write per attachment window and keep remaining durable work proportional to changed chunks/counters.
3. Disabled recording still creates no chunks. Distinguish the current attachment's in-memory origin/recording state from recovered persisted origins of earlier windows. Export persisted origin evidence only from validated readable chunks; a current origin whose publication has not been confirmed remains explicitly unconfirmed/pending. An append failure must not prevent unlock or clinical work. Preserve immutable bytes for retries after ambiguous publication and existing failure/loss accounting.
4. Repeated origins for a window must match exactly and pass strict fixed-key/type/timestamp/count validation. Inconsistent or malformed chunks fail explicitly without exposing arbitrary metadata. Entirely evicted/unreadable origin history and an abrupt-shutdown tail remain unknown. A known origin proves attachment only, not uninterrupted capture, run scope, pre-upload readiness or completeness.
5. Genuine reattachment creates a fresh diagnostic window instead of resetting cumulative counters under a reused UUID. Flush/preserve earlier archived windows and reset the corresponding live detail window. Initial attachment may retain the existing live-window identity with an explicit pre-attachment count. Preserve profile isolation and normal live/archive correlation.
6. Keep all origin metadata within chunk and export byte budgets, including failed retries, many windows and truncated event output. Continue yielding between bounded chunks. Lock/detach discards origin metadata with protected export results. The existing owning-session HTTP/browser download carries the new evidence and accurately describes its limits; no new control or default recording-policy change.
7. Verify fictional tests for delayed first observation, pre-attachment observations, enabled zero-event origin recovery, disabled/no-write behavior, failed and ambiguously acknowledged origin publication/retry, prefix eviction, fully evicted origins, interleaved profiles, fresh-window reattachment, inconsistent/malformed origins and lock during export. Verify the fixed attachment-write allowance and incremental byte growth in counts. Include actual encrypted-store HTTP and browser-download coverage. Do not access owner/demo data or live providers.
8. Use only the current format and contracts, updating versioned metadata as needed; no old-schema compatibility decoder, history migration or clinical storage changes. Update maintained documentation, run focused local checks and full PR CI, and obtain independent review. Retire this ticket/index entry on completion and preserve all unfinished CRS-189 requirements in a scoped remainder.
