# 🧮 CRS-198: Qualify storage growth after the scripted import capacity failure

Status: open. A runtime-storage prerequisite for the scripted runner's incomplete bounded two-person/split-row validation and [CRS-196](CRS-196.md). Identify the growing files and preserve authority before changing a default or claiming a complete large-import baseline.

## Current evidence and limits

On 2026-10-02, the contributor runner's denser bounded 151-page mixed fixture stopped after 365 physical requests, 52 automatic slices, 104 delivered pages and 104 exact proposed clinical assertions. The whole-oracle grade retained 797 missing assertions and unresolved ownership. The host tool failed, the batch-stop API returned `ENOSPC`, and final batch-scope evidence was unavailable. Original rehashing still matched and no records were accepted. Diagnostics were partial, with 14,163 known persisted events omitted from the export; their full-run retention requirement remains in CRS-196.

This isolated Linux run configured a 1 GiB `/dev/shm` runtime, but placed its temporary test output and encrypted fictional archive on the container's writable overlay. The failing filesystem, its contemporaneous usage and file-size distribution were not retained. A later fresh-container check found only about 1.16 GB free on the Docker overlay, while the host had about 45.8 GB free. These later measurements are context, not proof of which filesystem filled during the failed run. Do not describe the result as confirmed runtime exhaustion, an inadequate application default or proven write amplification.

The [runner's maintained procedure](../import/import-performance.md#scripted-large-import-runner) preserves this failed attempt separately from its smaller protocol checks. The sparse 151-page protocol fixture is not a successful reproduction of this denser workload. The unchanged 900-page fixture's earlier rendering prerequisite is [CRS-197](CRS-197.md).

A second, sparse 151-page attempt used a fresh host-backed scratch/output directory while preserving the normal 1 GiB runtime allocation. It stopped after 447 requests, 64 slices and 128 delivered pages, with two exact clinical assertions and 899 missing; the late two-person/split-row assertions were not reached. A live capacity receipt **does** establish that `/dev/shm` filled during this run: capacity 1,073,741,824 bytes, zero available, with 3,961 files totaling 1,063,587,194 logical bytes beneath the owned runtime directory at the sampled checkpoint. The dominating file types were not retained before cleanup. The final stop API again returned ENOSPC; original rehashing matched, no records were accepted, and diagnostics omitted 19,228 known persisted events. This second receipt proves runtime exhaustion for that run, not the failing filesystem of the earlier denser attempt.

## Additional storage path to measure

Historical finding, now addressed by the [incremental encrypted index](../security/vault-index.md) in PR #38: code inspection during the conversation-journal fix found `src/server/vault-store.ts` wrote a new encrypted index containing the complete growing `files` and `objects` maps whenever workspace files change, then publishes a small head referencing that index. Earlier index files remain in `vault/indices/`. The small head does not make those repeated index writes incremental. This is separate from conversation event payloads and must be measured in the archive byte/write attribution; a linear plaintext chat journal does not establish linear encrypted archive growth. The focused index-storage fix includes restart, failed-publication and recovery checks; broader workload qualification remains open. Do not discard historical authority or raise runtime limits as a substitute.

## Dense recheck with incremental conversation storage

The 2026-10-02 dense 151-page run used the runner source plus the current conversation-journal implementation from [PR #36](https://github.com/mxbaylee/circus-health/pull/36), with source hashes retained outside Git. It kept host-backed scratch/archive storage and the normal 1 GiB runtime. After 531 requests and 76 automatic slices, all 151 pages had been physically read/delivered, but the final tool failed with ENOSPC and a review grade was unavailable. Original rehashing matched, accepted records remained zero, and diagnostics omitted 41,857 known persisted events. This is an incomplete attempt, not a passing dense fixture or clinical-fidelity result.

The final live receipt proves SQLite-dominated runtime exhaustion: database 1,015,787,520 bytes, WAL 38,822,792 bytes and shared-memory file 98,304 bytes, with zero free runtime space. All JSON files together totaled 4,466,368 logical bytes; this includes both conversation and intake-batch events, not just chats. The largest observed chat event was 2,787 bytes. Separately, 4,598 retained encrypted index files totaled 3,914,790,639 bytes versus 6,374,480 bytes in 7,630 encrypted content objects. Runtime cleanup completed.

A separate table-allocation probe failed before the owned runtime closed, so table/index allocation and the exact SQLite growth mechanism remain unproven. Preserve that uncertainty. The subsequent smaller attribution probe and focused fixes below address this investigation step; the failed large-run table allocation remains unproven. Before another full bounded attempt, resolve the remaining intake-authority storage work; do not enlarge the runtime, clear accepted evidence, disable persistence or repeat the failing run merely to seek a pass. The journal fix satisfies its own recheck requirement but does not unblock runner qualification by itself.

## SQLite write-path candidate and next bounded diagnosis

Current code inspection identifies another amplification candidate: `intake.ts` updates the original's `source_files.details_json` with accumulated proposals, workflow, plans, candidates and groups. Each small batch can version that growing source-file row. The [compact history projection](../data/record-version-storage.md#compact-history-projection) removed duplicate version envelopes and ancestor before/after payloads from the SQLite index. Each durable and indexed source-file version still retains its complete contents once, so small workflow changes keep copying the growing document. That remaining path conflicts with the changed-content write requirement; its share of the earlier failed runtime is still unmeasured.

Use a small fresh fictional batch fixture to record table/index/freelist allocation and entity-grouped byte lengths for `__record_versions`, `__record_fields`, `__record_transactions`, current `source_files` values and `app_meta`. Preserve outputs outside Git, with no clinical payloads in public receipts. Allocate a focused implementation before changing this path: incremental operational intake workflow/proposal state with small committed references, exact candidate/group/operation/unit-status reconstruction after cache loss, original/source identity preservation and unchanged accepted-record authority. Never just exclude operational fields from durable recovery or prune evidence to reduce size. Tests must measure bytes and allocated pages over hundreds of real batch changes, not merely a successful tiny example. The separate [encrypted-index contract/recovery change](../security/vault-index.md) is implemented.

## Measured smaller attribution and implementation prerequisites

The fresh 12-page run, before the compact history projection and incremental encrypted-index changes, completed 44 requests, six slices and 12 exact clinical proposals (889 assertions missing against the full oracle), with unchanged original and zero accepted records. WAL-aware SQLite allocation was 6,524,928 bytes. DBSTAT measured 2,400,256 bytes for record versions and 2,297,856 bytes for field history. Source-file field history retained 571,660 before-value bytes and 870,818 after-value bytes across 290 rows, including duplicated `details_json`, intake and workflow ancestors. Fifteen source-file versions stored 279,732 content bytes and 287,185 duplicate envelope bytes. The app-meta versions and current values also contributed; the subtype grouping was not captured correctly and remains unqualified. The owned runtime closed after this successful attribution.

The [compact rebuildable history index](../data/record-version-storage.md#compact-history-projection) is implemented in merged PR #37, and the [incremental encrypted index](../security/vault-index.md) in merged PR #38. The [transaction-backed intake state primitive](../data/intake-state-storage.md) is implemented in merged PR #39 without changing production intake persistence. The [shared access boundary](../import/intake-state-access.md) is implemented in merged PR #40, preserving current persistence. Remaining implementation is [CRS-205](CRS-205.md), production cutover and actual mutation/recovery qualification. This ticket waits for that work before its broader capacity/failure/recovery requalification. The small measurement does not establish the exact table allocation of the earlier failed large attempt. Retain all earlier failures and diagnostic omissions.

## Acceptance

1. Prepare a fresh independently fictional contributor attempt with the encrypted archive on a protected external host-backed output directory and normal application/runtime limits. Keep credentials, private profiles, existing services and Docker caches untouched. Record source/dependency identities and the actual capacity/mount boundaries for the archive, scratch files, runtime database and temporary extraction output before starting.
2. First use a small owned fictional run to identify which runtime files grow, keeping the runtime open only long enough to retain bounded size/classification evidence. Then reproduce and qualify the affected 151-page input, retaining real OCR, normal upload-created coordination, all clinical kinds, both people and the split row. Count per-phase source capture, physical requests, proposals, archive/runtime/scratch bytes, relevant database/WAL sizes, durable bytes/writes and rereads. Use bounded metadata at substantive progress checkpoints; do not journal repeated whole histories or clinical payloads. Retain filesystem/error-path evidence on failure before cleanup.
3. Distinguish harness scratch exhaustion from application storage growth. Verify that application-controlled writes scale with changed evidence rather than repeatedly copying whole source/revision/table contents. If a distinct implementation defect is found, scope its fix with reproduction and acceptance before implementation; split further if it needs multiple coordinated changes. Do not raise application/default limits, shrink this input or suppress clinical proposals to claim it passed.
4. Verify capacity failures preserve originals and existing authority, remain explicit and actionable, and allow safe cleanup/recovery without falsely reporting completion. Treat inability to retain a stop checkpoint or final diagnostic evidence as a separate finding if reproduced. Retain unresolved scope rather than silently repairing records.
5. Publish safe measured counts and the established cause or explicit remaining uncertainty in maintained documentation. Preserve the first failed run, run the affected focused checks and PR CI, obtain independent review, and carry any unfinished full-size/browser/recovery qualification into CRS-196. A successful contributor rerun alone does not close the production release gate or diagnostics completeness requirements.
