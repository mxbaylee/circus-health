# CRS-120: Review interface reliability

Status: open. Implementation specification; verify historical findings against current code before changing behavior.

Make review outcomes accurate, preserve the person's unsaved work, and keep ownership/source state consistent across the list and detail views. This covers reliability findings R19–R30; their old line references at `2ae9a0f` are starting points, not proof that every defect remains.

## Owner decision

Bulk clinical saves are partial: save valid selected records and provide an itemized result for saved and unsaved records. A stale or invalid record must not prevent unrelated valid selected records from saving. A missing response is not evidence of either success or failure.

Preserve explicit selection, clinical approval, person/profile isolation, source dependencies, version checks and draft recovery. No background refresh may silently substitute a newer record for the version the person approved.

## Current implementation and audit

The current `IntakeReportAcceptanceReceipt` in `src/shared/intake.ts` declares `atomic: true`, and `intake-report-acceptance.ts` prepares all selected blocks before committing. Partial success therefore requires a server/receipt contract change, not just a different toast. `ImportReviewPresentation.move` currently expects a boolean success and marks the entire requested selection saved when true; replace that assumption for the new mode.

Before edits, record each R19–R30 finding as reproduced, already satisfied with named test evidence, or superseded by an owner decision. Add missing regression coverage for satisfied requirements; do not undo correct changes merely to follow old line numbers. Current duplicate-name options already show DOB, relationship and person identifiers. The list/detail and save paths have changed since the original review.

## Partial clinical save contract

Extend the existing profile-scoped acceptance API with an explicit versioned partial mode. Retain the legacy atomic request behavior for old clients/tools and decode old receipts unchanged. New UI requests opt into partial mode; new receipts identify their version and `atomic: false`. Do not rewrite historical receipts to imply partial success.

The request binds a stable parent operation ID and the exact selected occurrences: intake/proposal, record ID, candidate/version, reviewed mapping, comparison decisions and all applicable identity/source authority. Add a server-produced per-selection review token for partial mode, bound to that record's current review inputs and dependencies. Whole-intake transport versions alone cannot establish whether an individual record changed. A changed source dependency or shared identity decision can legitimately invalidate multiple selections; a successful sibling save or unrelated intake mutation must not automatically invalidate an unchanged selection.

Validate the request envelope and authorization before any work. For each selection, revalidate its exact current review inputs inside the write boundary. Never refresh a stale selection to new clinical values on the user's behalf. Keep coupled effects for one record atomic: clinical rows, source occurrences, matched/updated destination records, identity attribution and its acceptance receipt either commit together or do not. If selections have dependencies on one another, validate/commit that dependency group together and explain its failures per item. Independent selections can proceed.

Use a durable parent operation manifest and deterministic child operation identities derived from the parent and exact selection identity. Persist a bounded result per selected item, not a growing copy of the entire request or history on every child commit. Results identify the exact selection and one of:

- **Saved:** durable acceptance receipt and exact destination links, including whether it created, matched or updated a record.
- **Needs review:** stale version, changed source/identity, unresolved question, or invalid clinical mapping; include a stable reason code and actionable message.
- **Failed:** a definitive unsuccessful operation whose lack of clinical publication is known, with an appropriate retry path.
- **Not attempted:** processing could not continue because a shared prerequisite or authorization was lost; distinguish this from an item-level rejection.

A lost HTTP response or ambiguous durable-publication result is displayed as **Checking save status** until the existing operation can be reconciled. Do not invent a final failure or submit a fresh operation ID while the original outcome is unknown. Query/replay by the original parent/child IDs, survive process restart and rebuild, and recover already committed children without duplicating records. A repeated operation with different selection content is rejected. Retrying a terminal item after an edit requires a fresh explicit approval of its new review state and a new operation; completed old results remain immutable.

A shared storage or authorization failure stops further children safely. Preserve already committed results and disclose the remaining not-attempted items. No part of a partial response grants permission to continue after lock or against another profile.

## List/detail UI and draft behavior

Replace the all-or-nothing optimistic saved marker with per-item results. Remove only confirmed saved items from selection; retain failed/needs-review/not-attempted items, their edits and their expanded editors. Show counts such as “8 saved, 2 need review” with accessible links to each outcome. Report People operations separately where they use a different contract; mixed selections must not produce a misleading all-saved message.

Saved destination links must come from the returned exact receipts, not inferred record names or current list order. Background pagination/filter refreshes cannot discard an unsaved draft or mark it saved. When an unknown outcome is resolved, apply its result once and preserve any newer local edit for explicit reconciliation.

In `useReviewDrafts.ts`, bind a correction reason to the actual set of changed fields/values that it explained. Sending a disposition, answer or unrelated later edit must not reuse an earlier explanation. Coalesced unsent edits can share a reason only when the UI shows that reason for the current patch. After successful save, clear the acknowledged patch's transient reason without erasing newer queued edits or historical reasons. Retry of the same exact patch keeps its original reason and operation identity. The server independently validates and journals the patch/reason association.

## Source and person controls

- **Source attention (R26):** `SourceAttentionReview` currently prefers `saved` over the resource response. Reconcile both by source revision, refresh when the intake's source state changes, and do not let a prior local response permanently mask newer data. A pristine editor follows the latest revision. A dirty editor retains its text, shows a conflict and requires explicit comparison/rebase before saving. A stale response from an earlier revision/profile must not replace newer state. Section selection and issue counts use the displayed current revision.
- **Person controls (R23–R25):** preserve keyboard focus and the exact selected Person through refresh, show DOB/relationship/stable identifiers for ambiguous names, and enforce the same create-new-Person versus Self checks in list, detail and server validation. Share the decision helper/contract; a shared component is useful only where the interaction is actually the same. Preserve caregiver assignment and report-scoped identity confirmation.
- **Counts and links (R19):** resolve each clinical record's current owner when generating badges and destination URLs. Person-scoped counts must match the actual destination list, including after filtering, acceptance and profile changes. Original evidence remains scoped to the authorized profile.
- **Medication preferences (R20):** the profile owner may confirm current use for a relative. Do not restore a Self-only write restriction. Verify that the exact medication belongs to the active profile, its version is current, and the resulting status/counts appear under that medication's person. Cross-profile or wrong-record writes are rejected.
- **Accessibility/effects (R29):** save and unknown-outcome states are announced without stealing focus; errors are associated with the affected controls; history can be reached and read by keyboard. Correction effects may reset state only when their actual record/version context changes, never merely because an unstable object was recreated during render.

## Cleanup boundaries

Remove production paths that can show invented prototype records when live data is absent; tests/stories can supply explicit fictional fixtures through supported props. Consolidate owner canonicalization into existing shared domain helpers where behavior is equivalent. Update stale comments only after verifying the current contract. Split large review components at identity, source and record responsibilities when this improves isolation of the changed behaviors; keep state ownership and navigation/draft guards intact. These cleanup items remain completion requirements, but are not a reason for a visual redesign or broad unrelated refactor.

2. Test a selection containing valid, stale, blocked and invalid records. Save only valid explicitly approved versions and return one stable outcome per selection. Confirm exact destination counts and zero writes for rejected items.
3. Test shared dependencies, a source or person change during save, an unchanged sibling after another item commits, and an attempted token/record substitution. Unknown dependency coverage stays conservative.
4. Inject a failure after some children commit, lose the response, restart the server and rebuild the database. Replaying the same operation returns each saved result once, preserves failures and never duplicates publication. Changed payload with an old operation ID fails.
5. Mounted/browser tests retain unsaved selection and drafts, show itemized results, reconcile unknown outcomes and reopen exact destinations. Cover profile switch/lock, filtered/paginated selections, duplicate names and keyboard/narrow layouts.
6. Test source refresh with a pristine editor, dirty editor, stale response and an in-flight save. Test correction-reason coalescing, retry and a subsequent unrelated edit.
7. Verify caregiver medication activity and all owner-scoped counts/links using independently fictional Self and People records.
8. Run formatting, typechecks and relevant server, mounted and encrypted browser journeys. Document the new acceptance contract in maintained API/import docs. Obtain an independent passing grade against every disposition above before completing the ticket; broad suite failures must be investigated or explicitly tracked, not hidden by weaker assertions.
