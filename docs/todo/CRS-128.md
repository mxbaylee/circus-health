# #️⃣ CRS-128: Verify retained originals without a full hash after every restart

Status: open.

Owner decision ([CRS-126 D4](CRS-126.md#d4-storage-writes-scale-with-what-changed)): work per operation scales with what changed, including reads and hashing, and expensive IO stays off interactive paths.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to reopen retained records safely while other work remains usable,
So that checking a large history does not interrupt the household's review work.

## Plain-English User Walkthrough

1. After restarting the installation, open a retained source or resume its import.
2. An unchanged original opens without making the rest of the app wait. When another check is needed, other work remains usable; changed or unsafe files are refused with an explanation.

## Acceptance Criteria

### Scenario: Reopen a large history after restart

Given large fictional originals previously verified successfully,
When the installation restarts and the person lists Sources, opens an original or resumes reading,
Then unchanged originals reuse valid verification state without full synchronous hashing,
And counted full hashes and bytes read identify any necessary background verification, while foreground requests remain usable.

### Scenario: Retained bytes or location changed

Given a replaced file, a same-size rewrite with restored modification time, or a symlink escaping the profile,
When a caller requests verification,
Then it cannot reuse the old check or expose unverified content,
And the requirements below retain hash authority and existing refusal guarantees across restart and cache eviction.

## Where it stands

Retained originals are checked against their recorded SHA-256 and size before use. `verifyIntakeFileHash` (`src/server/intake-files.ts`) skips the full hash while a file's device, inode, size, modification time and change time match its last successful check. It backs `verifyIntakeOriginal` (`src/server/intake.ts`) and direct consumers in clinical import, duplicate review, People, source text and record corrections. Inventory consumers by those symbols when implementing rather than relying on historical line or call counts.

The cache is an in-memory map of at most 256 files (`verified` and `VERIFIED_LIMIT`, `intake-files.ts`). After a restart, or once more than 256 originals are in use, the next check of a file reads and hashes the whole original synchronously inside the request. `inspectIntakeFile` uses a bounded 256 KiB buffer, but hashing still blocks the Node event loop for every other request in that time. Bounded memory does not settle the repeated-read or foreground-responsiveness requirement.

## Requirements

- Keep a successful verification across restarts. For example, store the verified file identity (device, inode, size, modification and change time) beside the source row, so an unchanged original needs no full read. The stored identity is a cache, not evidence: the recorded hash stays authoritative, and any identity mismatch forces a full hash.
- Move any full hash that is still needed off the request path. Either hash in a worker or asynchronously, or report the original as being verified and retry, instead of blocking.
- Keep the current guarantees: a replaced file, a same-size rewrite with its modification time restored, and a symlink that escapes the profile are all still detected. Tests in `src/server/test/intake-source-text.test.ts` cover the last two ("an unchanged original is hashed once…", "original symlink escape…").

## Open questions

- Several callers need the verification synchronously today, for example `verifyIntakeOriginal` before reading proposal content. Decide whether to make those paths asynchronous, or to verify once in the background at startup or first use and gate requests on that result.
- Measure the cost first, in counts per `AGENTS.md`: after a restart, how many full hashes and how many bytes hashed happen on the request path, per operation (import resume, Sources listing, opening an original), on a representative set of large fictional originals. Any timing of the hash itself is host-only work, reported only as a coarse ratio on the same machine.

## Grooming evidence and operator boundary, 2026-10-03

Current `intake-files.ts` still has the process-local 256-entry cache and synchronous `inspectIntakeFile` loop; this is remaining implementation, not just qualification. Use symbols rather than historical line/call counts to inventory every verifier consumer. Include more than 256 originals and restart/cache-loss in counted-work fixtures so warm-cache evidence cannot hide the gap.

A persisted file identity is disposable optimization state. Its trust boundary must be explicit: inode/device/timestamps can change on a restored or replaced filesystem, and recovery must not turn copied cache metadata into proof of unchanged bytes. Qualify cache invalidation for restoration and file replacement, retain the original hash as authority, and gate readers until required verification succeeds. This adds no alternate recovery authority or permission to skip a failed check. CRS-152 still owns physical-filesystem qualification; fixture checks here do not establish device guarantees.
