# 🧮 CRS-250: Keep incremental and cold workflow counts equal for retained package plans

Status: open; review finding from PR #71. An incremental package-batch update on a
retained expanded-unit plan marks the workflow indexes complete without the unit
coverage index that the cold count reads, so a later binding-only rebuild can
count already-read units as pending again. No dependency on other tickets.

## User Story

As a [Low-effort self-tracker](../design/personas.md#file-and-review),
I want the import's remaining-work count to match what is actually left,
So that a finished reading does not keep asking me to review or wait.

## Plain-English User Walkthrough

1. I upload a ZIP of results, and the app reads its files in batches.
2. Partway through, I remember a mapping rule or the source text is re-pinned.
3. The import still shows the same remaining work as before that change, and when
   nothing is left to read it says so instead of staying in "needs review".

## Acceptance Criteria

### Scenario: A binding-only change after an incremental batch keeps counts

Given a retained expanded-unit package plan whose batches were accounted by the
incremental package-batch update,
When the workflow summary binding changes without a logical intake change and the
summary is rebuilt from the selected envelope,
Then pending work, remaining units and needs-review equal the incremental values,
And no unit with recorded coverage is counted pending while the next pending
reading unit finds none.

### Scenario: Cold and incremental derivations are proved equivalent

Given fictional fixtures covering expanded-unit and implicit-unit plans, retries,
cancelled batches and context-only coverage,
When the same history is summarized incrementally and by a cold rebuild,
Then every workflow count fact and index key matches,
And the incremental update still writes work proportional to the changed batch
(at most its 50 coverage rows plus their unit index entries), with no full
plan rescan.

### Scenario: An index that cannot be completed is not marked complete

Given an incremental update that cannot derive a unit's accounted-coverage key,
When the update would publish,
Then it refuses or leaves the indexes incomplete so the cold path rebuilds them,
And it never records `complete` for an index set missing derived entries.

## Evidence and Implementation Scope

At PR head `2706c5d`:

- `src/server/intake-workflow-update.ts:817-862` applies `pendingDelta` and writes
  only `batch-unit-coverage` keys for the changed batch, then `:863` writes
  `indexes.complete` for the new logical root.
- The cold builder derives `unit-accounted-coverage` in a second pass
  (`src/server/intake-workflow-index.ts:298-350`, run from
  `src/server/intake-workflow-state.ts:312-337`), joining unit attempts to
  `batch-unit-coverage` targets.
- The cold summary skips both index passes when `envelope.indexes` is complete
  for the logical root with policy v6 (`intake-workflow-state.ts:258-262`), and
  rebuilds facts whenever the binding (`hash([policy, pins])`, pins including
  `sourceTextPin` and `mappingVersion`, `intake-model-collection-backend.ts:46-54`)
  changes (`intake-workflow-state.ts:160-175`).
- Expanded-unit counting reads `unit-accounted-coverage`
  (`src/server/intake-workflow-collection-reader.ts:253-283`); a missing key yields
  `pending: true`. Implicit v2 plans (`:228-251`) use a separate provider.
- `src/server/test/intake-workflow-state.test.ts` exercises `packageBatch` (~:367)
  but has no cold-versus-incremental equivalence check.

The wrong counts persist until an unrelated write invalidates the indexes. Either
derive the unit index incrementally for affected units or stop claiming the index
set complete; keep the per-operation work bounded by the changed batch.
