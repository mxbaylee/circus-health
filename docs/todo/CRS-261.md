# 🔦 CRS-261: Keep test diagnostics out of the shipped server and UI

Status: open; PR #71 review finding. Test-only tracing is compiled into the
production server error path and the production app bundle, gated by an
environment variable and a page global. Its only consumers are browser fixtures,
and no test asserts on its output.

Effort re-estimate, 2026-10-16: M for coordinated server error-path, browser bundle and fixture-scaffolding removal, with production-artifact and test-consumer checks. Impact remains M, unmarked; score 4.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want the installed app to contain only code that serves its users,
So that a debugging switch cannot expose internal details or change behavior on
my installation.

## Plain-English User Walkthrough

1. I install and run the app; nothing about imports or review changes.
2. The app no longer carries hidden test switches in its server responses or
   pages.
3. When a project check fails, it still explains the failure through what the
   page shows and what the test records itself.

## Acceptance Criteria

### Scenario: The shipped server has no test trace path

Given a production build,
When a report-queue cursor conflict (409 `REPORT_QUEUE_CURSOR`) is returned,
Then no test-only header is set and no stack-derived location is computed,
And `src/server/index.ts` imports no test diagnostic module.

### Scenario: The shipped app has no holdout trace

Given the production app bundle,
When import pages run,
Then no `__CRS_HOLDOUT_TRACE__` global is read or written,
And the holdout browser test's People gate waits on visible UI state instead.

### Scenario: Failures stay diagnosable without weakening checks

Given the import holdout and related browser tests,
When a step fails,
Then the failure message uses test-side observations (responses, visible state),
And no assertion, wait bound or fixture scope is relaxed to compensate.
