# 🧽 CRS-249: Clean up leftovers from interrupted or refused operations

Status: open; PR #71 review finding. At PR #71 head some temporary state is
removed only by in-process `finally` blocks or is published before the step that
may refuse, so a crash or refusal leaves durable leftovers that nothing reclaims.
Distinct from CRS-243 (direct reconstruction targets) and CRS-248 (builds area).

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want an interrupted setup or a refused ownership change to leave nothing
behind,
So that profile sizes, backups and retries reflect only real records.

## Plain-English User Walkthrough

1. My laptop restarts while I am setting up a profile copied from another, or
   an ownership change I previewed is refused when I commit it.
2. When the app starts again or I retry, the abandoned working copy is removed
   automatically.
3. The profile size shown and the backups I take no longer include a hidden
   second copy of my vault.

## Acceptance Criteria

### Scenario: A crashed setup stage is swept

Given a fictional profile directory containing a `.setup-stage-<uuid>` left by a
process that exited during copy-from-profile setup,
When the app next starts or a setup for that profile is admitted,
Then stages owned by no live attempt are removed before `storageBytes` is
reported or a backup is taken,
And a stage owned by a running attempt, the profile's vault and keyring, and
any unrelated file are never removed.

### Scenario: A refused ownership commit does not accumulate snapshots

Given a split-membership preview whose commit refuses,
When the operator previews and commits again several times,
Then `ownership:<uuid>` snapshot catalogs from refused attempts are reclaimed or
reused, so retained snapshots grow by at most one per successful commit,
And no assignment authority or clinical change results from the refused attempt.

### Scenario: Interrupted package inventory staging is reclaimed

Given an `inventory-*` directory left in `.package-index-staging` by an
interrupted inventory build,
When the next inventory build or startup runs,
Then stale staging directories are removed with their size counted,
And cleanup work is bounded by the number of leftover entries.

## Evidence and Implementation Scope

- Setup stage: `src/server/encrypted-profiles.ts:1311` creates
  `.setup-stage-<uuid>` under the durable `pathFor(id)`; it is removed only at
  :1424 (success) and in `finally` at :1502. No other code references the name,
  so nothing sweeps it after a crash. `storageBytes` is `bytesBelow(pathFor(id))`
  (:467), so a stale stage (vault and keyring copy) is counted.
- Ownership snapshots: `ownership-report-plan.ts:937-943` calls
  `factory.finishMaintenance()`, which publishes the snapshot catalog as its own
  maintenance operation (`ownership-source-snapshots.ts:238-243`; ids
  `'ownership:' + randomUUID()` at :140) before the clinical commit.
  `docs/data/ownership-name-evidence.md:29` documents that a canceled or refused
  action "can leave inert immutable snapshots".
- Package staging: `intake-package-index.ts:136` creates
  `.package-index-staging/inventory-*` under the caller's scratch root and
  removes the directory on close/failure (:536, :547), not after a crash.
  The supported encrypted runtime root is disposable; scope durable-leftover
  qualification to contributor callers whose `context.root` is durable, and
  verify cleanup boundaries before retaining this scenario for other callers.
- Excluded after verification: queue-transition temp tables
  (`intake-queue-transitions.ts:14`) are SQLite `TEMP` tables, not durable;
  orphaned report snapshot builds belong to CRS-248.

Open question: should startup sweep stale stages, or only the next admitted
setup for the same profile, given that backups may run before either?

## Current grooming evidence, 2026-10-16

CRS-152’s checked setup-copy path and held copy manifest are reusable foundations, not proof of partial-stage resume or orphan reclamation. Package inventory spools are under `context.root`: supported encrypted runtime use places that root in disposable runtime storage. Qualify crash leftovers where contributor callers use a durable root; do not describe the encrypted runtime spool as a hidden durable vault copy.
