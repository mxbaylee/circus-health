# 👯 CRS-255: Distinguish duplicate legacy report groups by occurrence in review

Status: open; review finding from PR #71. A retained legacy history can place the
same candidate in two report groups with the same group ID (ordinals 0 and 1).
The review feed, client and detail reads key these by intake, group and candidate
only, so the two occurrences collide: saves refuse and refresh in a loop, and the
second group's records are shown under the first group's header.

## User Story

As a [Caregiver](../design/personas.md#file-family-records),
I want each report in an older import to be reviewed under its own title, date
and person,
So that I can save records without the page looping and without filing one
report's records under another report's identity.

## Plain-English User Walkthrough

1. I open an older import in which two reports were grouped under the same label.
2. Each report appears as its own card with its own title, date, source and person.
3. I save, defer or exclude a record once, and the page confirms it without
   repeating the request or refreshing endlessly.

## Acceptance Criteria

### Scenario: Duplicate group occurrences have distinct review identities

Given the fictional duplicate-group fixture with one candidate in ordinals 0 and 1,
When the review feed and report details load,
Then each occurrence has a distinct `feedKey`, client request key and detail read,
And each card shows its own group's title, date, source, ownership and identity.

### Scenario: Actions on a duplicated candidate are sent once and succeed

Given that fixture,
When I save, choose Later or Exclude for the shared candidate,
Then exactly one request per chosen occurrence is posted and the save is not
refused for a row-count mismatch,
And no refresh loop occurs (bounded refresh count asserted in the test).

### Scenario: Precedence between duplicate groups is consistent

Given the same fixture,
When suggested sources and the detail header resolve a group,
Then both use the same documented occurrence rule, and identity review opened from
a card targets that occurrence.

## Evidence and Implementation Scope

At PR head `2706c5d`:

- `src/server/intake-import-feed-collection.ts:749-753`: `feedKey` is
  `[intakeId, candidateId, candidateVersionId]`; `groupOrdinal` is carried at `:760`
  but not used in the key.
- `src/server/test/intake-report-queue-cooperation.test.ts:188-234` pins candidate-0
  in ordinals `[0, 1]` of the same group set.
- `src/app/features/import/collection-display-model.ts:42` (`groupKey` =
  intake + group), `:206-217` (detail requests) and `:356` (header lookup) drop the
  ordinal.
- `src/app/features/import/CollectionImportReview.tsx:622-627`: duplicate
  `feedKey`s make `rows.length !== ids.length`, so save refuses and calls `refresh()`.
- `src/server/intake-queue-page-collection.ts:154`: `findGroup(groupId, intakeId)`
  resolves the first occurrence for detail headers.
- Suggested sources keep the later duplicate group
  (`src/server/test/intake-review-collection-host.test.ts:457-460`), the opposite
  precedence.

Keep keys stable for non-duplicated groups so existing selections survive.
