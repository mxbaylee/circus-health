## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want to keep my unfinished review, decisions and accepted history when I reopen or copy my collection,
So that I can build a large history without losing work or making each small change increasingly burdensome.

## Plain-English User Walkthrough

1. I review records and save decisions, then reopen or copy my collection.
2. I find the same unfinished work and accepted history and can continue from where I left off.

## Acceptance Criteria

### Scenario: Recover saved review and accepted history

Given a source has pending proposals, decisions, pins and public acceptance receipts,
When the profile restarts, locks or loses all disposable caches after an acknowledged change,
Then reconstruction preserves identities, versions, review state and accepted records without inference.

### Scenario: Refuse conflicting or missing authority

Given selected intake evidence is unsupported, missing, duplicated or bound to the wrong source,
When an operational reader or writer accesses it,
Then the operation fails explicitly without resetting the workflow or selecting a hidden second authority.

### Scenario: Reject stale review without changing records

Given review was prepared against an earlier intake or source-pin version,
When a batch review or acceptance action submits that stale version,
Then the existing conflict behavior is preserved and no stale clinical acceptance is fabricated.

### Engineer context

Moving authority out of source details must preserve exact search, review versions and real runtime recovery rather than creating two competing owners.

## Contract

Move operational intake state out of repeatedly versioned source_files.details_json through the shared access adapter. Originals and accepted medical records remain durable evidence. Human review is still required before accepting model proposals. Reconstruction after total cache loss must require no inference. The owner requires no old-schema compatibility before production: reject unsupported, missing or duplicated authority; never reset an archive or fabricate an empty workflow.

## Detailed engineering requirements

1. Switch registration and every operational writer, including proposal publication, workflow mutation, duplicate-review questions and acceptance receipts. Source details retain compact metadata, original identity/downloads/locator and reviewed source metadata. Source-text pins remain in their existing separate durable records and are overlaid by the access boundary; do not duplicate them into details_json. Preserve complete source-file details DTOs and exact search, including the maintained [exact serialization contract](../data/intake-state-storage.md#exact-serialization-domain) and CRS-220 integration. Preserve complete outer-envelope order and intake-slot position; retain untouched raw whitespace, duplicate-property spelling and escape spelling as original durable/search bytes until an authorized rewrite or separately specified raw-text solution. Reject forbidden duplicated operational state rather than retaining a hidden second authority.
2. Preserve proposal/candidate/group/question/operation/plan-unit identities and status, effective version, discovery order, review fingerprints, acceptance receipts and pins across restart/lock/interruption/cache loss. Keep stale-review/source-pin conflicts, idempotent replay, source confirmation, wrong-person refusal, manually created records and duplicate decisions unchanged.
3. Bind compact discovery, replay and identity indexes and exact search to the selected profile/source/intake authority. Updates to contributions, source metadata, indexes, proposal registration and accepted clinical records use the existing single transaction boundary. No all-intake hydration for ordinary lookups, growing receipt/reference row or replacement full-state journal. Remove obsolete operational SQL paths rather than leaving two implementations.
4. Integrate the implemented [target-bound bootstrap](../data/intake-state-storage.md#unpublished-target-bootstrap) through the implemented [encrypted publication/retry contract](../data/intake-state-storage.md#encrypted-private-copy-publication-and-retry) and the implemented [contributor private-copy retention/retry](../data/intake-state-storage.md#contributor-private-copy-publication-and-retry), before first destination publication. Never select copied source-owned authority; preserve an already-published target on retry without recopying an advanced source. Preserve source originals/accepted records and exact destination pending views. Add genuine normal contributor runtime intake reader/writer support: the implemented contributor copy path proves staged copy retention/rebuild only, and its portable durability backend still lacks the primitive's required accepted-record readiness and excludes `app_meta` from curation-change capture. Reassess the genuine durability-backend requirement and separate it if that complexity boundary is useful; never fake configured readiness or silently weaken the contributor recovery contract. Preserve stored intake and effective source-pin versions, proposal/review identities and public acceptance receipts; fresh internal copy chains/replay namespaces cannot make source operations target transaction authority. Accepted clinical equality allows only intentional profile/path/Self-display rebinding. Test actual batch/review/acceptance API paths, all access-boundary consumers, clinical import/scope, ownership/People, packets/exports, source navigation/search and assistant retry/dependencies.
5. Qualify transactional failure before staging, during immutable writes, before publication, after durable publication before SQL commit and ambiguous flush completion. Acknowledged state survives; unpublished candidates disappear; published authority wins over SQL rollback/exception. Retry does not duplicate receipts or lose decisions. Missing/corrupt/cross-profile/source/hash/unsupported evidence fails explicitly. Backup and cache-loss reconstruction select coherent source/intake/accepted state.
6. Document the implemented current representation and recovery behavior. Preserve all unmet scale requirements in CRS-210; a green unit suite is not real-mutation or large-import qualification. Reassess scope and dependencies before starting; high effort alone does not defer implementation. Do not perform known-failing heavy imports to close this ticket.
