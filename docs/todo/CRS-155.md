Status: open. Remainder of CRS-063. On 2026-09-30, the adopted ChatGPT `health-primary` route's saved access token was still unexpired; the guarded probe returned `pending_natural_expiry`. That dated readiness observation does not establish whether the token is unexpired now. Live qualification is still pending; obtain a fresh guarded readiness observation before choosing the next step. Do not alter the expiry field, rotate or copy real tokens, or treat fictional offline responses as this check.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to keep my chosen provider working after its sign-in expires,
So that ordinary use does not unexpectedly require another sign-in.

## Plain-English walkthrough

1. Check whether the adopted provider’s saved sign-in has naturally expired.
2. When eligible, stop the installation using that sign-in state and run the guarded check.
3. Restart fresh containers and use a tiny fictional request to confirm the same route works without another sign-in.

## Given–When–Then acceptance

The detailed contracts, owner decisions and evidence gates below remain required.

- **Given** the selected adopted OAuth token is still valid, **when** the guarded runner probes it, **then** it reports pending_natural_expiry with no authentication write or network refresh; no expiry editing, copied tokens or offline fixture can substitute.

- **Given** natural expiry, stopped credential users and the exact adopted chatgpt route, **when** the live qualification runs, **then** a passed restricted metadata receipt proves refresh and persisted clean-container reuse while device login is forbidden; raw secrets and provider error bodies remain external.

- **Given** a passed authenticator receipt, **when** fresh supported Compose containers run the tiny fictional tool challenge and are recreated again, **then** the intended model route works without interactive sign-in; this evidence remains separate from the refresh receipt and clinical import.

- **Given** multiple adopted routes or expired credentials needing sign-in, **when** coverage is evaluated, **then** every actual OAuth route has current evidence or an explicit outstanding gate, non-OAuth routes have a reason for exclusion, and only the owner completes any necessary device prompt.

## What exists

The supported root `npm run qualify:oauth` command uses the external state and selected LiteLLM config. It requires `CRS_OAUTH_QUALIFICATION=1`, checks that the selected route is exact `chatgpt/...`, and emits a mode-600 metadata receipt outside Git. An unexpired token yields `pending_natural_expiry` without an auth write or network request. After natural expiry, a disposable pinned container forbids device login while calling the real refresh path, checks a changed persisted token and future expiry, then a second clean container checks reuse without a refresh or sign-in. It sends no model request and does not stop an active stack automatically. `refuseActiveAuthContainers` in `src/scripts/qualify-oauth-refresh.ts` refuses active containers whose mounts overlap the selected OAuth state; the operator must stop those containers before eligible live refresh qualification and restart the supported stack afterwards. Its credential-writer lease also refuses an active launcher/login/qualification writer. The maintained [model-provider guide](../setup/model-providers.md#provider-routes) gives the command and evidence limits; the network-disabled pinned compatibility tests use only fictional tokens.

## Remaining acceptance

1. When the adopted token naturally reaches the pinned authenticator's expiry guard, run the command against the actual external state and retain its `passed` metadata receipt. A pending or failed receipt does not close this check. Do not log, attach or commit tokens, device codes, credential paths or provider error bodies.
2. After the observed refresh, create a fresh supported Compose proxy/application container with the same state and selected alias, and run a tiny independently fictional tool challenge. Confirm the route works without interactive sign-in, is still the intended model, and persists through another clean recreation. Keep this evidence separate from the authenticator receipt and from clinical import qualification.
3. Repeat for every OAuth route actually adopted for the installation. If a route does not use OAuth (for example a local Ollama model or an API-key route), record why it is outside this check. If the adopted route changes, do not claim an earlier route's receipt for the new one.
4. Update maintained setup documentation with the result and limitations, obtain an independent passing grade, and delete this ticket and index entry only when the live acceptance above passes.

No further owner decision is needed. The owner has authorized small billed fictional provider requests. If fresh sign-in becomes necessary, the owner must complete the provider's device prompt in their own terminal; the qualification runner itself deliberately refuses login.
