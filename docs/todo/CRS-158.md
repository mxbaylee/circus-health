# 📈 CRS-158: Instrument and qualify common large-document imports

Status: open. Production investigation and diagnostics requirement, separate from CRS-086's async-processing implementation.

## Owner decision and production priority

Large-document imports are a common primary experience, not an optional optimization (owner, 2026-10-01). Establish their actual behavior, work counts, completion, recovery and user experience before relying on the app for real records. This ticket is a production requirement. Representative cases include an 800-page PDF around 115 MB and a 900-page PDF around 15 MB: bytes and pages alone cannot predict model work or completion time. Use independently fictional equivalents for public qualification; owner originals, feedback and raw artifacts stay outside Git.

The owner may try an actual upload personally and return a downloadable diagnostics bundle with feedback. **Before that trial, verify that the normal release UI collects and downloads the evidence needed to debug AI behavior, import, local processing and the user experience from the beginning of a long run.** A finished upload or a successful download alone does not establish adequate evidence. Prepare instrumentation and a serial baseline first. Async processing and bounded context remain an independent production requirement in [CRS-086](CRS-086.md); their implementation does not wait for this investigation, and this trial does not wait for parallel workers. Diagnostics readiness supplies the instrumented baseline for CRS-086's before/after work-count validation.

Expect this exercise to uncover additional work. Turn observed findings into scoped CRS tickets with reproductions, affected personas, evidence, acceptance checks, dependencies and effort/impact sizes. Fixes required for a usable, correct large-document experience are production requirements. Prioritize high-impact, low-effort fixes as soon as evidence identifies them; do not defer them until the whole processing redesign finishes or assume their size before investigating.

## First delivery: diagnostics ready for an owner trial

Reuse the [existing diagnostics download](../import/import-performance.md) and coordinate with [CRS-154](CRS-154.md). Its bounded rings, journal-read limits and omission counters currently do not prove complete evidence for an 800–900-page run. Verify and close those gaps before asking the owner to collect a trial. Reuse this readiness work for CRS-154's complaint/download validation; neither ticket requires a separate collector.

1. Provide a profile-authorized download from the normal desktop and narrow/mobile release UI, while a run is active, waiting, failed or complete, and after supported lock/unlock, process restart and container recreation. Establish collection before upload starts; explain any necessary diagnostic opt-in before the trial rather than requiring a rerun to recover missing history. The bundle identifies its schema, actual client/server builds, route/model configuration and run scope, with correlation references the owner can cite in feedback.
2. Retain correlated upload admission/receive/hash/staging/publication, queue, indexing, native-text, render/OCR, clinical interpretation, proposal/coverage, review and acceptance phases. Include bytes/pages/units, attempts and reason codes, rereads and hashes, retries, durable-write counts/bytes, and original-integrity/rebuild outcomes when exercised. Distinguish captured, delivered, interpreted, proposed, accepted, unresolved and exceptional work; account for every page without treating accounted coverage as clinical correctness.
3. Include each physical model request's identity, logical work unit, evidence exposure/dependency scope, input composition by message/tool category, text/media bytes, context fit/compaction/restarts, reported input/cached/output tokens, tool validation results, retries, provider waits, unknown/possibly billed outcomes and replacements. Preserve unknown measurements as unknown. Retain bounded metadata that can explain a source-delivery failure, repeated context growth, invalid proposal or recovery loop; a summary total alone is insufficient.
4. Retain browser action/API/decode/render observations, feed/polling activity, progress and estimate changes, cancellations, review/save outcomes and safe error classifications. Observe interactive responsiveness during background processing, including assistant-slot contention. Include sampled app/worker resource use and storage capacity with sample counts, attribution limits and missing observations; process samples are not whole-host peaks. Separate provider wait, host work and user review time, and retain a timeline the owner can relate to their feedback.
5. Preserve required request/unit and complaint-reconstruction evidence throughout a full-size run and its supported recovery. Use bounded metadata chunks and aggregates with retention budgets verified at this workload; memory and durable writes must scale with the operations recorded, never repeated whole-document/profile snapshots. Export coverage, dropped/truncated/omitted evidence and unavailable usage explicitly. Missing required history fails diagnostics qualification even if the import finishes. Exercise the actual browser download and reconstruct an early-run and a late-run problem from it after recovery, without requiring terminal logs or a second run.
6. Keep the ordinary bundle free of clinical text, names, filenames, credentials, recovery material and raw model payloads. It remains protected debugging metadata, not anonymous data. Semantic extraction quality needs an independent fictional oracle or the owner's feedback and selectively supplied private evidence; metadata alone cannot certify it. Raw private tracing remains a separate explicit opt-in, outside Git. Validate the export's schema and privacy boundaries alongside its diagnostic usefulness.

## Production qualification and resulting work

- After diagnostics readiness passes, exercise the normal npm → Compose → LiteLLM upload-to-review workflow on representative large fictional PDFs, covering both a large-byte 800-page case and a compact 900-page case on the adopted installation/route. Include dense and scanned evidence, cross-page/report relationships, ownership, interruption/recovery, original retention and accepted-record cache-loss rebuild. Record versions, configuration and evidence scope. The owner may separately contribute an actual trial and feedback; that trial informs defects but cannot replace a known-content correctness oracle.
- Establish current end-to-end work counts and observed rates on the installation, including local capture before model reading, request/context growth, provider waits, review burden and interactive responsiveness. Report actual completion or retained incomplete/exceptional scope. Estimate duration only from observed rates with uncertainty. The historical 20-page provider slice and its overnight extrapolation are not current 800–900-page qualification or a production completion promise. No fixed time-to-finish requirement applies to model work.
- Reconstruct the owner's reported experience from the downloaded bundle and feedback. Publish only safe conclusions and scoped requirements. Open or update tickets for missing diagnostic evidence, correctness defects, avoidable requests/tokens/rereads/writes, recovery problems and UX friction; mark production blockers and rank each by observed impact, effort and dependencies. Track unresolved blockers through CRS-061. Re-run the affected qualification after fixes and obtain independent review against current evidence before claiming large-document production readiness.
- Existing run authorizations retain their scope; listing these cases does not authorize opening private profiles or running the owner's files. Coordinate adopted-route qualification within that scope. Diagnostics completeness is required before the owner trial; all production blockers must be resolved before production qualification passes.

## Completion and release gate

Complete this investigation only after the full-size diagnostics readiness checks and an instrumented current baseline have an independent passing grade, and every finding has a scoped disposition or follow-up ticket. A baseline that exposes an incomplete import or correctness defect is a finding, not a passing import qualification. This investigation can finish with clearly recorded production follow-ups still open; CRS-061 stays blocked until CRS-086 and all identified production blockers are resolved and the affected workflows are requalified. Do not make diagnostics discovery depend on finishing the redesign it is meant to inform. Update maintained diagnostics procedures only when implemented behavior is verified; delete this ticket and its index entry when its scoped work lands, carrying any remaining requirements into named tickets.
