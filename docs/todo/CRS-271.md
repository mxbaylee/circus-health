# 🐧 CRS-271: Qualify deployment on the intended native Linux host and drive

Status: open; unavailable-host remainder of CRS-152. The portable driver and focused Linux probe tests are implemented. The passing macOS Docker Desktop workflow does not qualify a separate native Linux host or its storage.

## User story

As an [Operator](../design/personas.md#operate-and-recover),
I want evidence that my intended Linux installation preserves records and provider access on its chosen drive,
So that I can rely on that installation before using household records.

## Plain-English walkthrough

1. Make the intended Linux installation and drive available, with its already chosen provider.
2. Run the drive checks and the small fictional upload, review and save workflow there.
3. Recreate the containers, then rebuild after removing only the fictional profile's disposable cache, and check the retained records and provider access.
4. Keep the result and its limits with that installation's release evidence.

## Given–When–Then acceptance

- **Given** the intended native Linux host and actual selected filesystem, **when** the extended drive probe runs, **then** nonce-proven mount identity, strict UID 1000 ownership/access, exclusive publication, file/directory sync, concurrent-writer refusal, retained lock identity, kill/reacquire, fresh-container publication retention and owned-scratch cleanup pass there. A macOS Docker VM, container-local temporary filesystem or fixture-only test is not that host's receipt.
- **Given** that supported npm → Docker Compose → LiteLLM installation and its adopted provider, **when** the small independently fictional encrypted profile completes upload, reading, explicit review and acceptance, **then** original hashes and nonempty accepted version histories match after fresh containers and after actual disposable-cache removal/rebuild. Mount probes alone do not establish the complete installation workflow.
- **Given** separate proxy/provider state mounts, **when** both fresh-container stages run real tool challenges, **then** the master key, intended route and actual provider authentication persist without replacing credentials or silently selecting another provider. Natural OAuth refresh has separate [guarded qualification and dated evidence](../setup/model-providers.md#oauth-refresh-qualification); the observed adopted-route result does not qualify another route or this Linux host.
- **Given** retained private receipts and recovery material, **when** results are published, **then** maintained documentation names the qualified build, host/filesystem and provider scope without private paths, secrets or raw diagnostics. Unavailable removable/network drives and physical power loss remain unqualified; fsync success does not certify every filesystem/controller.
