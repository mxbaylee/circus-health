# 👆 CRS-088: Profile-less passkey unlock

Status: open. Implementation waits for baseline physical qualification of the existing select-a-profile flow under [CRS-163](CRS-163.md). Feature-specific username-less and salt-migration qualification happens after this implementation and belongs to this ticket, not to CRS-163's prerequisite gate.

Support passkey sign-in without first selecting a profile. Preserve PRF unwrap, challenge freshness, generation guards and exact relying-party/origin scope. Restart still leaves archives locked.

Verify physical authenticators under CRS-163 before expanding the flow. Keep ordinary recovery and enrollment available.

## Decision and why

**The screen before login stays the same** (owner, 2026-09-30). The work is a proactive passkey check in the client: the browser offers the person's passkey as soon as that screen opens (WebAuthn conditional mediation, the autofill-style prompt), so signing in is just an authenticator gesture. This settles the earlier open question of what to show before login: nothing new is disclosed. It replaces the earlier note that conditional autofill was separate from the single-gesture goal; it is now how that goal is met.

The goal is **quick primary sign-in**, like health-system portals that offer a passkey without asking for a username. That needs no stored username or local storage. The server sends a challenge tied to no account. The browser lists the passkeys saved for this site. The chosen passkey's reply carries its user handle, which says which profile it belongs to.

**PRF salt: one app-wide salt instead of one per passkey** (owner, 2026-09-30). Per-credential salts (`prf.evalByCredential`) only work when the request names the credentials in advance, which a username-less request cannot do. A single salt sent as `prf.eval` works with any passkey the person picks. The salt is not secret: the PRF output is still unique to each passkey and secret, because the authenticator derives it from that passkey's own secret. So the change does not weaken the key wrapping. Keep the salt versioned so it can be rotated later.

## Where it stands

- The client starts a passkey ceremony only after a profile is chosen: `unlockProfilePasskey` in `src/app/components/passkey-unlock.ts` requests options for one `profileId`, then calls `startAuthentication` without conditional mediation.
- The server limits each sign-in to the selected profile's credentials: `authenticationOptions` in `src/server/profile-passkeys.ts` sets `allowCredentials` to that profile's passkeys for the origin's relying party (near `:522`), and `authenticate` rejects a credential that is not the profile's.
- Each passkey has its own random PRF salt, sent as `prf.evalByCredential` keyed by credential ID (near `:531`).
- Enrollment already requires discoverable credentials (`residentKey: 'required'`, near `:351`), which conditional mediation needs.

## Requirements

1. When the sign-in screen opens, start a conditional-mediation passkey request without a selected profile. The person's gesture picks the credential; the server maps that credential to its profile and relying party, then unlocks only that profile with the existing PRF unwrap and generation checks.
2. Keep challenge freshness and origin scope: a conditional challenge is bound to the session and origin like today's, is cancelled when the person chooses a profile or recovery instead, and never reveals which profiles or credentials exist before the gesture.
3. Keep the existing select-a-profile path and recovery key working, including for browsers without conditional mediation.
4. Unlocking still locks every other open profile, as it does today.
5. **Salt migration without re-enrollment.** New enrollments wrap the profile key with the app-wide salt's PRF output. Existing passkeys migrate at their next ordinary select-a-profile unlock. That request already names the credential, so one gesture can evaluate both salts (`evalByCredential` with `first` set to the old per-credential salt and `second` to the new app-wide salt). The app unwraps with the old output, adds a wrapper for the new one, and removes the old wrapper only after the new one is durably written. A passkey not yet migrated simply falls back to the select-a-profile path.
6. **More than one profile in one browser** works through the picker: it lists every passkey saved for this site, one per profile, and the reply identifies which profile was chosen. Test two fictional profiles with a passkey each, where choosing either unlocks only its own profile.
7. The name shown in the operating system's passkey picker is visible to anyone at the device before unlock. Set it at enrollment per the owner decision below, and let a person rename or re-enroll to change it.

## Owner decisions needed

- **Picker label:** the person's name (for example "Robin Lane"), the profile's display name, or a neutral label (for example "Circus Health profile")? Recommended: the profile's display name, which the person already chose and can keep neutral.

## Not verified

- PRF support alongside username-less (discoverable) requests differs by platform: iCloud Keychain, Google Password Manager, Windows Hello and hardware keys. This comes from the WebAuthn specification, not from testing, and belongs to this ticket's post-implementation checks on the device matrix recorded by CRS-163. A platform without it keeps the select-a-profile path.
- The two-salt migration relies on the PRF extension's `second` input being honored by every authenticator in use.

## Browser/CI acceptance

Extend `src/tests/browser/passkey-enrollment.test.ts` for the new username-less request and app-wide-salt enrollment when this feature lands; a successful old/new two-salt migration; and two fictional profiles whose chosen credentials unlock only their own archives. Exercise both migration interruption boundaries: the new wrapper is durably written but the old wrapper is not yet removed, and interruption before the new wrapper is durable. Recover safely with the old wrapper until a valid new one is committed, with no loss of unlock access and no duplicate/incorrect profile publication. Keep challenge freshness, origin/RP binding, cancellation, generation and recovery assertions in those journeys.

Run these browser checks alongside focused profile/passkey server and mounted checks in CI. Virtual-authenticator success proves controlled flow and crash boundaries; it does not replace this ticket's post-implementation physical qualification on the CRS-163 device matrix or prove that every authenticator honors the second PRF input.
