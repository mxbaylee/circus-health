# 🔑 CRS-245: Bound unlock and setup authorization by admission, not elapsed time

Status: open; PR #71 review finding. At PR #71 head the five-minute passkey
challenge and the thirty-minute setup session are rechecked at every preparation
progress message, checkpoint and final seal, so a large cold unlock or copy that
outlasts the window always fails at the end. Base `b8a5a01` checked expiry only at
admission.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want a passkey unlock or profile setup I have already approved to finish,
however large the profile is,
So that a big profile can be opened or copied on a small laptop without an
attempt that can never succeed.

## Plain-English User Walkthrough

1. I unlock a large profile with my passkey, or set up a new profile by copying
   an existing one.
2. The app checks my approval when the work starts, then shows progress for as
   long as the work actually takes.
3. If I cancel, lock the profile, remove the passkey or another change makes my
   approval stale, the work stops and says why.
4. Otherwise it finishes; waiting behind another unlock does not use up my
   approval, and a resumed setup continues rather than starting again.

## Acceptance Criteria

### Scenario: Admitted work outlasts the challenge or session window

Given a fictional profile whose cold unlock or copy-from-profile setup runs longer
than five or thirty minutes respectively,
When the passkey proof or setup session was valid at admission,
Then preparation, vault slices and the final seal complete without an expiry
refusal,
And the bound is expressed by admission and ownership, not by elapsed seconds
(AGENTS.md: host-only work prefers counts over time bounds).

### Scenario: Real revocation still stops admitted work

Given an admitted unlock or setup in progress,
When the operator cancels, the profile is locked, the passkey or keyring changes,
the profile generation changes or the setup is replaced,
Then the work stops at its next checkpoint and the final seal refuses,
And no partial profile is published and key material is zeroed as today.

### Scenario: Queueing and resume do not consume the window

Given a passkey authentication queued behind a running verify/unlock, or a setup
resumed after an interruption,
When it is finally admitted,
Then it is judged at its own admission, not when it was requested,
And resumed setup reuses completed copy work instead of re-copying from scratch,
or the open question below records why it cannot.

## Evidence and Implementation Scope

- Passkey: `src/server/profile-passkeys.ts:251` sets `expires` to five minutes;
  `assertPending` (:277-281) and `passkeyUnlockAuthorized` (:99) recheck
  `expires`. The authorization record copies `challenge.expires` (:656) and
  `authorize` runs as `assertAuthorized` throughout `unlockWithKeyAsync`.
- Setup: `src/server/encrypted-profiles.ts:1047,2001,2078` set thirty minutes;
  `check()` (:1249) and `ownerCurrent()` (:1596) recheck it, and `checkpoint()`
  (:1608-1626) calls both. `encrypted-profile-preparation.ts:152,160` invoke the
  checkpoint on start and every worker message, including `progress`.
  `openVaultAsync` (`vault-store.ts:2327-2339`) calls it per slice.
- Base comparison: `git show b8a5a01:src/server/encrypted-profiles.ts` checks
  `setup.expires` only at :898 (admission).
- Queueing: `vault-app.ts:288` `activate()` serializes switches, and the passkey
  route (:551) calls `passkeys.authenticate` inside it, so the challenge clock
  runs while waiting for an earlier operation.
- Copy setup creates a fresh `.setup-stage-<uuid>` per attempt (:1311) and
  removes it in `finally` (:1502), so an expired attempt discards all copy work.
- Existing context, not scope: the narrow key-zeroing defect around the final
  authorization recheck (`profile-passkeys.ts:~663-675`) is fixed in the CRS-231
  blocker-fix change by transferring key ownership before the recheck.
- Update `docs/security/profile-encryption.md:80-88` ("never renews a changed
  proof") to state that expiry gates admission while revocation stops work.

Open question: should a resumed setup reuse a verified partial stage (overlaps
CRS-249's stale-stage cleanup), or is restarting the copy acceptable once expiry
no longer interrupts it?

## Current grooming evidence, 2026-10-16

CRS-152’s checked setup-copy path and held copy manifest are reusable preparation foundations. They do not establish admission-only expiry semantics, partial-stage resume or orphan cleanup; those remain this ticket’s and CRS-249’s requirements.
