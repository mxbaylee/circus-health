# 🌱 CRS-221: Prepare validated target-bound intake bootstrap evidence

Status: open. Pure preparation/bootstrap prerequisite split from high-effort CRS-208 before implementation on 2026-10-02. Builds on the implemented [intake primitive](../data/intake-state-storage.md) and [exact serialization contract](../data/intake-state-storage.md#exact-serialization-domain); unblocks [CRS-222](CRS-222.md) and [CRS-223](CRS-223.md). Neither production intake nor real copy callers switch representation in this slice.

## Contract

Prepare current selected intake state as new destination-profile-bound evidence before the target's first accepted durable head. Source frames, namespace hashes and UUID links cannot become destination authority. Resolve preparation-before-durability ordering through a narrow validated API; never weaken `createIntakeStateStorage` readiness, attach a dummy backend or certify temporary false authority.

## Acceptance

1. Factor shared bounded validation/framing into a narrow preparation/bootstrap API. Validate a coherent selected source snapshot before any owner/path rewrite: verified profile, `intake_original` kind/ID/hash, namespace identity, v2 head/frame/receipt chains and exact serialized state. Inventory all retained intake namespaces so malformed, unknown-owner or headless contributions cannot be silently dropped. Wrong profile/source/hash and missing/corrupt/unsupported evidence fail explicitly. There is no old-format decoder, migration or reset; the owner requires no compatibility migration before production.
2. Produce fresh destination-profile/source/hash-bound initial frame chains, bounded heads/receipts, internal operation UUIDs and destination replay namespaces. Preserve public operation IDs/receipts, stored intake and effective source-pin versions, proposal/review identities, pins, proposals, questions, plan units and decisions as exact state values; distinguish these from fresh internal bootstrap operation identities and chain versions, which may change only while exposed state remains exact. Source operation receipts cannot become target transaction authority. No source frame or namespace links are reused. Preserve existing frame/head/receipt limits and disclose one-time full-state preparation/copy work separately from subsequent changed-evidence mutations.
3. Install only into a validated unpublished target. In the same bootstrap transaction replace only copied source-owned intake contributions with target evidence, rejecting conflict, partial installation or a published destination. Preserve unrelated `app_meta`, unchanged source files, original bytes/hashes, accepted clinical rows, modulo intentional profile/path/Self-display rebinding and existing source-text rebind obligations. No copied source-bound contribution may be selected even briefly by a target accepted head. Runtime storage must still require real configured current durability after attachment.
4. Preserve the complete outer envelope's member order, intake-slot position and nested normalized serialization under the maintained contract. Untouched raw `details_json` whitespace, duplicate-property spelling and escape spelling remain original durable/search bytes until an actual authorized rewrite or separately specified raw-text solution; preparation may not silently normalize them. These obligations concern operational details, not rewriting literal originals.
5. Test pure preparation and staged fictional SQLite targets: empty inventory, multiple sources, identity/hash failures, unsupported/missing/corrupt evidence, no destination writes on preparation failure, conflicting installation and transactional rollback. A fixture's first real accepted-record publication must select only target-bound evidence; reopen and complete accepted-history cache rebuild must reproduce exact serialized bytes, original hashes, pending/public-receipt/pin state and accepted records. After real attachment, ordinary target mutations remain changed-size and cannot change the source.
6. Document the implemented API, validation and unpublished-target guardrails. This fixture proves bootstrap mechanics, not encrypted/contributor caller integration, production cutover, broad capacity or large-import qualification. Actual copy authorization, publication/retry and activation remain CRS-222/223; production activation remains CRS-209.

Use independently fictional data, no inference and no heavy import retry. Before implementation, reassess effort and split again if the boundary exceeds medium effort. Completion requires focused preparation/state/recovery tests, formatting/types, full PR CI and independent grading; delete this ticket and its index entry only when the bounded implementation ships, and repoint dependents to maintained documentation.
