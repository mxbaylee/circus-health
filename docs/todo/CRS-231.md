# 🗃️ CRS-231: Keep large package inventories and their unfinished work manageable

Status: open. Remainder of CRS-043 after streamed ZIP payload publication and located package failures. The [streamed member path](../data/streamed-package-originals.md) removes the member-byte and aggregate-expanded-byte barriers; it does not remove the inventory's metadata safeguards. This ticket and CRS-232 can proceed independently. Storage admission in CRS-233 must preserve safeguards until their replacements are verified.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want to file a complete collection even when it contains many separate files,
So that I can see and finish all of my history without splitting it by hand.

## Plain-English User Walkthrough

1. I add my collection and browse its files a page at a time.
2. I can pause, reopen the app and continue from the same unfinished files.
3. If a file cannot be read, I see its name and what remains to do, and can still download the original collection.

## Acceptance Criteria

### Scenario: Inventory and process a collection without a file-count product limit

Given a retained ZIP fits available storage,
When its inventory and members are read,
Then replace the 10,000-entry, 5,000-file and 2 MiB filename-total memory safeguards with bounded disk-backed traversal,
And inventory, plan units, role proposals, reference resolution, identity/report scopes, model responses and client views read bounded pages without loading every member or pending unit,
And each occurrence retains its original name, ordinal, locator and source binding.

### Scenario: Recover exact unfinished work

Given some occurrences have reviewed roles, dispositions or accepted evidence,
When processing stops or disposable indexes are lost,
Then originals and selected durable authority reconstruct the same inventory and decisions,
And retry neither duplicates accepted work nor treats uninspected scope as complete,
And every failed scope remains located and downloadable rather than becoming a fictional unreadable page.

### Scenario: Preserve package safety and count work

Given corrupt, unsupported, nested or unusually large fictional packages,
When inventory, selected extraction, replay and recovery run,
Then preserve CRC, exact size, local/central header, path/type, profile, cancellation and source-integrity checks,
And failed partial indexes cannot select successful complete plans,
And peak payload and metadata buffers per step stay independent of archive size and member count,
And staged, written, reread, hashed and durable metadata bytes scale with the processed or changed scope, measured separately from cache rebuilds.

## Engineering boundary and open design work

`intake-package.ts`, `intake-plan.ts` and shared extraction plans currently keep `members`, `sections`, `units` and roles as arrays. Identity policy, report grouping, reading accounting, navigation and continuation consume those arrays. Replacing only the inspector's payload transport does not paginate this authority contract. Use compact source-bound inventory roots and bounded immutable pages or an equivalent reviewed design; any SQLite lookup remains disposable, never the recovery authority. Pending units need not all exist as eagerly materialized objects. Keep durable per-occurrence decisions and operation identities.

Decide inventory/checkpoint persistence, source-pinned rebuild validation, pagination contracts and migration together. Do not call these choices implemented. Keep existing metadata safeguards until all affected consumers are bounded. Preserve unsupported/encrypted ZIP refusal and all-or-nothing safety validation unless a separately reviewed partial-inventory policy is adopted. The three-source-level nesting safeguard also needs a bounded iterative traversal or a clearly located pending exception; silently increasing it is insufficient.

Before an active plan exists, every inventory page/member read currently decompresses and hashes the whole ZIP again. Reuse a source-verified derived inventory independently of plan creation, with correct invalidation and cache-loss reconstruction. Count subprocess inventory work across the whole traversal as well as per-member publication; parent-process file counters alone omit these repeated scans.

Update [storage accounting](../data/storage-accounting.md), [Docker runtime guidance](../setup/docker-runtime.md) and the owning import/release contracts with implemented behavior. Qualify large fictional collections, direct-versus-packaged PDF parity, interruption, exact occurrence separation and encrypted recovery, using the focused upload, intake-format, archive-storage and encrypted-profile suites. Obtain independent review. This is an actual shared authority/API boundary, not an effort-only deferral.
