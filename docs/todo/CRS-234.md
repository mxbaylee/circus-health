# 🔄 CRS-234: Keep a fresh unlock usable when the app restarts

Status: open. An active page can replace a newly authorized session with an unauthorized session after a real server restart. This preexisting session-lifecycle race was observed during CRS-231 verification; the paged package authority work is a separate boundary and is not blocked by this ticket.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to unlock my records and continue reliably after restarting the app,
So that I can recover interrupted work without repeated unlocks or uncertainty about whether a save happened.

## Plain-English User Walkthrough

1. I leave the app open while restarting its local service.
2. The app asks me to unlock my profile again, and I do so.
3. I can continue reviewing and saving without an older page request undoing that unlock. If a save's result was lost, the app checks what happened before I retry it.

## Acceptance Criteria

### Scenario: Resume from an active page after an actual restart

Given an encrypted fictional profile is open in a live browser page,
When the actual server process stops and a new process starts, and I provide valid fresh unlock proof,
Then the page's concurrent or delayed requests cannot replace or invalidate that successful unlock,
And authorized reads and an explicitly retried interrupted save succeed without another unlock,
And the receipt and recovered accepted state prove that retry publishes each accepted operation exactly once.

### Scenario: Reordered requests preserve authorization boundaries

Given requests carry a session cookie from before restart,
When a fresh unlock response and concurrent old-session requests complete in either order, including an old-session response arriving last,
Then the successful unlock remains usable by its intended browser session,
And unknown or stale cookies alone never grant access or borrow another session's grants,
And unauthorized private requests still receive the existing locked-profile refusal.

### Scenario: Profile changes and logout remain authoritative

Given independent browser sessions and multiple fictional profiles,
When restart recovery overlaps profile switching, explicit lock or logout, and delayed reads or save replay,
Then access remains session authorized and profile scoped,
And a delayed response cannot restore revoked access, select the wrong profile or replay a mutation implicitly,
And a verified save replay retains its operation identity and never duplicates accepted history.

## Context, decisions, and evidence

Observed 2026-10-04 during CRS-231's encrypted partial-save browser qualification. In the new server process, the unlock request carried the old cookie. Its response succeeded with HTTP 200 and replacement cookie A. One millisecond later, the still-active document requested intake batches with the old cookie; its HTTP 423 response set replacement cookie B. The explicit report-acceptance replay then sent B and received HTTP 423. The forwarding hook recorded each exchange twice; these are duplicate observations, not evidence of separate requests. Cookie values, hashes, private paths and raw logs are intentionally excluded from this sanitized prose summary.

The inspected [`session` and `requireAccess`](../../src/server/vault-app.ts) implementations were byte-identical between the tested CRS-231 candidate and main `1d5fb5ec11adf3773b7f913032994a3ff4093748`: unknown cookies create new ungranted sessions and set the browser cookie, while private access requires both a session grant and an open profile. The trace establishes cookie replacement and the resulting refusal; the final engineering remedy remains open. Preserve the [security model](../security/model.md), including fresh proof after restart and existing bearer-session limits.

A separate replay with the old document navigated to a blank page in the **same browser context** before restart passed after a real new server process and fresh unlock: all 18 original oracles and two additional receipt assertions passed in approximately 33.8 seconds. This supports the narrow interrupted-save/reconstruction behavior when competing page requests are quiesced. It does **not** qualify active-page recovery across restart, fix this race or supply physical passkey evidence. The measurement is evidence, not a performance target.

## Dependencies and scope

This ticket owns session establishment, stale response ordering and active-page restart recovery. [CRS-231](CRS-231.md) owns paged package inventory/plan authority; neither ticket waits for the other. No broader testing pause or new physical-device, provider or paid-run requirement is introduced. Do not implement a remedy by trusting unknown cookies, granting unauthenticated access, weakening lock/logout, or bypassing profile isolation. Choose server and browser coordination together as needed; no particular engineering option is mandated.
