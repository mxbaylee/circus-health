# ☑️ CRS-254: Revoke People selections when the displayed proposal changes

Status: open; review finding from PR #71. Clinical selections are revoked when the
reviewed values change after they were ticked, but People selections are not: a
person ticked at one proposal version can be added at a later version with
different details and no "changed, approve again" notice.

## User Story

As a [Caregiver](../design/personas.md#file-family-records),
I want a person I ticked to be added only as I saw them,
So that a background update cannot add a family member with a name or
relationship I never approved.

## Plain-English User Walkthrough

1. I review an import and tick a proposed person, "Alex Example, child".
2. While I am still on the page, reading updates that proposal to a different name
   or relationship.
3. The tick is cleared, and the page tells me the person changed and must be
   approved again, the same as for a changed clinical record.
4. When I tick them again and press Add, the app adds the version I now see.

## Acceptance Criteria

### Scenario: A changed People proposal loses its selection

Given a fictional People proposal ticked at version 1,
When a page refresh shows version 2 with a different name, relationship or tags,
Then the selection is revoked and the changed-item notice counts it,
And no `/intakes/people-apply` or `/intakes/people-disposition` request is sent.

### Scenario: Add binds to the version that was displayed when ticked

Given a ticked person whose displayed version is 1,
When Add or a disposition runs after the shown page now carries version 2,
Then the preflight compares the server's current version to the ticked snapshot,
not to the refreshed row, and refuses with the "changed, approve again" outcome,
And an unchanged proposal still saves with one preflight read and one POST per
person, as today.

### Scenario: Unrelated refreshes keep valid selections

Given a ticked person whose proposal version and displayed details are unchanged,
When background reading refreshes the page,
Then the selection remains and Add succeeds.

## Evidence and Implementation Scope

At PR head `2706c5d`:

- `src/app/features/import/useReviewApprovalSelection.ts:37-50`: `revokeChanged`
  compares `approval?.selections` of the ticked snapshot and the current row.
- `src/app/features/import/collection-display-model.ts:157-182`:
  `collectionDisplayPerson` sets no `approval`, so both sides are `undefined` and
  a People row is never revoked. Clinical rows set `approval` (`:114-125`).
- `src/app/features/import/CollectionImportReview.tsx:591-620`: `save` builds the
  People list from the current `shownPeople` (`:253-258`) and `disposition`
  (`:636-641`) does the same.
- `src/app/features/import/useCollectionBulkActions.ts:124-171`: the People
  preflight checks `selected.person.version !== item.person.version`, where
  `item.person` is that refreshed row, then posts `proposalVersion: person.version`.
- The notice is raised from `ImportReviewPresentation.tsx:452-460`.

Bind People selections to a snapshot of the displayed version (for example by
giving People rows an `approval` with `proposalVersion`) and send that version.
Add component tests with fictional people for revoke, refusal and the unchanged
case.
