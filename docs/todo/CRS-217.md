# 🧵 CRS-217: Preserve exact intake serialization order in durable state

Status: open. First bounded prerequisite split from high-effort CRS-207 on 2026-10-02. Unblocks CRS-208's target-bound copy and CRS-220's exact search contract. Production intake remains in source_files.details_json until CRS-209; this slice must not activate the cutover.

## Evidence and contract

writeIntakeDetails in intake-state-access.ts serializes the parsed outer envelope with JSON.stringify. Source-list search matches that exact stored string. The current primitive's stable() sorts object keys and chatChanges emits no pure-key-order change: a fictional {first:a,second:b} → {second:b,first:a} probe produces zero operations and different reconstructed serialization. Semantic equality is insufficient. Preserve the exact JSON.stringify representation accepted by the writer, including order, through durable reconstruction; disposable search rows must never become its only authority.

## Acceptance

1. Define the normalized supported JSON domain and exact serialization contract, including non-index object insertion order, JavaScript integer-index ordering, nested objects, arrays, undefined/absent/null handling, string escapes, non-BMP characters and lone surrogates. Keep literal source evidence unchanged; this concerns operational source details, not reformatting original files. Define how outer-envelope metadata order and the operational intake slot will reconstruct at activation, including initial raw text/whitespace outside the declared writer domain. Do not quietly broaden a JSON.stringify guarantee into arbitrary raw-text preservation or silently normalize public search bytes.
2. Extend the intake-specific primitive/codec with validated changed-order evidence and an order-sensitive state/replay identity. A key move or insertion cannot serialize all unchanged values or a growing complete key-order/reference list on every write. Preserve existing bounded frame/head/receipt sizes and source/profile/hash binding, transaction publication, rollback, cold reconstruction and lock/close cache behavior. Keep chat-journal semantics unchanged unless a separately justified compatible shared change is reviewed. No old-format decoder, migration or automatic reset; identify unsupported earlier authority explicitly.
3. Qualify pure reorder with equal values, reorder plus changed values, new middle keys, deletion/reinsertion, nested order changes, integer-like keys, repeated equal values and Unicode/escaping. Reusing an operation UUID for a different serialization must fail; valid replay must not rewind later state. Reopen and complete accepted-history cache rebuild must reproduce identical serialized bytes, not only deep-equal objects. Missing/corrupt/unsupported evidence must fail explicitly.
4. Prove changed durable bytes for a small key move/insertion do not grow with unchanged object payload or a growing order manifest. Record initial and 100/200/300 mutation frame/head/receipt/accepted-storage bytes, SQL allocation, reads and copies; disclose full host traversal/hash/copy costs separately. Cover transaction failure before and after durable publication using existing fixtures. Do not claim general array/string move locality beyond what is demonstrated; unresolved generic-delta amplification remains a CRS-210 qualification concern.
5. Document the implemented serialization API and activation/copy obligations in maintained intake storage/access references. Repoint CRS-208/209/220 to that contract when complete. Run focused codec/state/recovery tests, formatting/types and full PR CI, and obtain independent grading. Delete this ticket when its bounded contract ships; retain search projection and actual mutation qualification in their own tickets.

Reassess before implementation; split again if this cannot remain medium effort. No model calls, large-import retry or production persistence change is in scope.
