# 👣 CRS-146: Log every sign-in and failed attempt and show them to the patient

Status: open. Opened during backlog grooming on 2026-09-30, from the owner's request. No existing ticket covered it; `docs/todo` and `docs/security` were searched. Agent-buildable. Line numbers were checked at `1e6fa50`; re-verify before editing.

## Decision and why

Owner, 2026-09-30: log every sign-in (profile unlock) and every failed attempt, and show them clearly to the patient on their next sign-in.

- **Privacy-sensitive patient** ([CRS-130](CRS-130.md)): the one person who can tell whether an unlock was theirs is the patient, so they need to see each one.
- **Caregiver:** manages several profiles on one machine. An unlock of a profile they did not open is something they should notice.
- **Emergency contact:** any future break-glass access ([CRS-145](CRS-145.md)) must be visible to the patient the same way. This log is where it would appear.
- **Security:** it is a detection control for risks in [`docs/security/model.md`](../security/model.md), such as R4 (stolen session, local compromise) and R9 (unauthorized recovery from an old copy). [CRS-084](CRS-084.md) sizes that. It is not a prevention control and must not be described as one.

## Where it stands

- **Unlock paths ✅.** Recovery-key unlock is `POST /api/profiles/{id}/unlock` and passkey unlock is `POST /api/profiles/{id}/passkeys/authenticate` (`src/server/vault-app.ts:251-270`).
- **The only record today is a passkey's last use ✅.** After a successful passkey unlock, `recordUse` overwrites that credential's `lastUsedAt` in the keyring (`src/server/profile-passkeys.ts:300-315`), shown as "Last used DATE" under Manage passkeys (`src/app/components/ProfileManagement.tsx:1561-1562`). It keeps only the latest time, per passkey. Recovery-key unlocks and failed attempts of either kind are not recorded anywhere.
- **The keyring is readable before unlock ✅.** It holds wrapped keys and credential metadata, and the public profile card reads it without opening private data (`docs/security/profile-encryption.md:28, 38`; `hasPasskey` in `vault-app.ts:146`). It is one candidate home for a pre-unlock log. That is a design choice for this ticket, not a decision.

## Design question

A failed attempt happens before unlock, so it cannot be written into the encrypted profile. The log needs a small separate store beside the profile that contains **no health data**: time, method (passkey or recovery key), outcome, and a coarse client description if one is available. It must not contain names, record content, recovery material or credential secrets. Successful unlocks could be copied into the encrypted profile afterwards, but the patient-facing view has to cover both.

## Requirements

1. Record every unlock attempt, successful or failed, by passkey and by recovery key, with time, method and outcome. A cancelled passkey prompt is not a failed attempt; a wrong recovery key or a failed passkey assertion is.
2. Keep the log outside the encrypted vault, bounded in size (a fixed number of entries, oldest dropped), and free of health data, names and secrets. Writes scale with the event: append one entry, never rewrite the history (`AGENTS.md`).
3. After a successful unlock, show the patient clearly what happened since their last sign-in: every sign-in and every failed attempt, with time and method. Show it in a way they cannot miss, and let them dismiss it once seen. Keep an accessible full list, for example beside Manage passkeys.
4. Logging never blocks or delays unlock, and a logging failure never turns a successful unlock into an error (as `recordUse` already does).
5. Record honestly what the log cannot prove: an attacker with write access to the data directory can remove entries; the log detects, it does not prevent. Say so in `docs/security/model.md`.
6. Fictional tests: a wrong recovery key, a failed passkey assertion, a cancelled prompt (not logged as a failure), two successful unlocks, then a sign-in that shows exactly the entries since the previous one; bounded size; no health data in the stored log.

## Proposal: detect passkey capability drift

Review feedback supplied on 2026-10-01 proposes a separate patient-facing explanation when a previously usable credential stops working after a browser, OS or password-manager update. A later recovery-key unlock records the successful method, but must not be mistaken for evidence that the earlier passkey still works. Do not attribute a failure to an update unless the evidence establishes that cause.

- Record a fixed coarse reason for a failed attempt: `prf_missing`, `prf_unwrap_failed`, `assertion_rejected` or `challenge_expired`. Associate it with the affected credential only when the host can establish that association; pre-credential failures stay unattributed. Keep `lastUsedAt` as successful use, not failure time. Use the bounded append-only attempt store required above, rather than rewriting the full keyring or copying histories on every failure. Store no raw assertion, PRF output, recovery material, health data or provider error body.
- After the next successful authorized unlock, show a one-time notice per credential and reason, with a reviewed path to re-add or remove that passkey. Deduplicate notices, not attempt logging; retain the full bounded event list and its disclosed loss limits. Do not delete a credential or replace wrappers automatically, and do not expose credential/profile details before unlock.
- Add a controlled virtual-authenticator browser regression in which a fictional passkey first unlocks successfully, then returns no PRF result. The failed attempt is classified honestly, recovery still unlocks, and the next authorized session shows the notice once. Keep cancellation separate from failure. Physical drift/provider support still belongs to CRS-153.

Settle reason-code storage, notification presentation and retention with the existing decisions below before implementation. This is a proposal carried into the open ticket, not a claim that drift detection or notices have shipped.
