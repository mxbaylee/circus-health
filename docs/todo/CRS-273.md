# 🧭 CRS-273: Restore accepted-record person-change previews for native report members

Status: open; reproduced during CRS-124 preparation on 2026-10-16. A valid first preview for moving accepted prescriptions and procedures to an existing Person returns HTTP 500. This is a current ownership-reader defect, separate from the broader correction experience in [CRS-139](CRS-139.md) and report-preview decision retention in [CRS-256](CRS-256.md). No new owner decision is required.

## User Story

As a [Caregiver](../design/personas.md#correct-a-record),
I want to review a correction when saved records belong to another person,
So that I can put them with the right family member without losing their sources or history.

## Plain-English User Walkthrough

1. I select saved records whose person needs correcting.
2. I choose the intended person and inspect the proposed changes and affected sources.
3. I approve the checked correction, or cancel and leave the records unchanged.

## Current evidence and scope

A bounded encrypted public-API fixture created Self and a non-Self Person, uploaded fictional text, stopped automatic processing, submitted fictional JSONL proposals, and reviewed and accepted one prescription and one performed procedure with the current missing-identity warning. No direct database seed or live model was used. The first `POST /api/profiles/:profileId/record-ownership/preview` selected the accepted medication/procedure entity IDs and supplied the existing destination note ID and current `expectedVersion`. Omitting record versions is supported for this first preview by `OwnershipRecordReference`; approval must use the returned versions and scope token.

The request returned `500 INTERNAL_ERROR`. The server threw `Ownership member reference is unavailable` in `ownershipIntakeScopeOccurrences` (`src/server/ownership-intake-scopes.ts`), reached through ownership scope-index preparation and report planning. Its v2 branch requires `view.child(version, 'members')`; the failure establishes that this accessor does not obtain the member reference in this accepted native state. Determine the correct bounded read from the actual envelope representation rather than treating an unavailable child as evidence of missing durable members. The source path is unchanged by the CRS-124 UI repairs. Raw fictional reproduction state and logs remain outside Git; the public regression must recreate the scenario through supported APIs.

Repair the existing consumer and preserve the [ownership correction contract](../import/identity-review.md#correcting-accepted-person-assignments), selected snapshot proofs and durable history. This ticket does not authorize a new assignment policy, broad correction UI redesign, full-document materialization or recovery from SQLite as authority.

## Acceptance Criteria

### Scenario: Preview an accepted native report correction

Given an encrypted profile with publicly reviewed and accepted fictional prescription and procedure records backed by current native report-member snapshots,
When the user requests a first person-change preview using those accepted record identities and a current existing-Person version,
Then the preview resolves the exact retained members and returns reviewable ownership effects instead of HTTP 500,
And rendering the preview changes neither ownership nor original or accepted evidence.

### Scenario: Keep reviewed correction and stale-proof safeguards

Given that preview and its returned record versions and scope token,
When the user approves the unchanged correction,
Then the intended records and sources move under the existing correction contract and remain recoverable from durable authority,
And stale records, destination versions or snapshot proofs refuse the correction without partial publication.

### Scenario: Preserve bounded native and legacy reads

Given current referenced members, legacy supported members and malformed or unavailable references,
When ownership scopes are consumed,
Then supported representations resolve exact members with bounded addressed reads and current-snapshot checks,
And malformed or unavailable evidence is explicitly refused rather than silently skipped or replaced with a broad materialized copy.

Add a focused public-API regression for the reproduced first-preview failure and relevant native/legacy consumer checks. Validate the successful correction through retained history and reconstruction, using existing qualification helpers where possible. Preserve unrelated records, scope isolation and durable-write scaling. Reassess the effort estimate if current-code investigation reveals a wider compatibility boundary; do not weaken these contracts to keep the estimate small.
