# ⏸️ CRS-253: Pause native conversion preparation instead of failing it at the reading slice

Status: open; review finding from PR #71. For an already-native conversion, the
reading checkpoint stays empty until host preparation inside the model turn
finishes; if that preparation outlasts the 15-minute reading slice, the timer
fails the response and aborts preparation instead of pausing it. At base, every
conversion had a checkpoint, so the same overrun became a resumable pause.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want a long import that is still being prepared to pause and resume,
So that re-uploading a large history never turns slow preparation into a failure
I must restart by hand.

## Plain-English User Walkthrough

1. I start reading a large, previously imported history.
2. The app spends a long time preparing it before the first reading request.
3. If the reading slice ends during preparation, the import shows as paused for
   time, not failed, and resuming continues from the preparation already saved.

## Acceptance Criteria

### Scenario: Slice end during native preparation is a recoverable pause

Given a fictional native conversion whose plan-history indexing or plan creation
is still running when the reading slice ends,
When the slice timer fires,
Then the conversion ends, at once or at preparation's next durable checkpoint, as
`idle` with reading reason `time_limit`, and
`chat.reading` is a paused state the batch treats as recoverable,
And no "exceeded 15 minutes" failure message is recorded.

### Scenario: Host preparation is not killed by elapsed time

Given the same preparation,
When it is still making counted progress,
Then the slice boundary stops only the next provider request; host preparation is
either allowed to reach its next durable checkpoint or stopped only by Stop, lock,
cancellation or a generation change,
And resumed preparation reuses completed durable work rather than repeating it,
shown by work counters (index records written, hashes) in the test.

### Scenario: Stop and lock still stop immediately

Given preparation in progress,
When the person presses Stop or the profile locks,
Then preparation aborts promptly with the existing stopped/locked reasons.

## Evidence and Implementation Scope

At PR head `2706c5d`, `src/server/assistant.ts`:

- `:4224-4228`: `checkpoint` is `null` for an `isNativeAssistantConversion` intake.
  It is assigned only at `:4520-4522`, after `prepareNativeAssistantConversion`
  (`:4484-4508`) and `createIntakePlanRead` (`:4509-4516`), which run under
  `assertPreparationRunning` (`:4445-4453`).
- `:4398-4413`: with a checkpoint the timer marks the soft deadline and finishes
  `idle`/`time_limit`; without one it calls `finish('failed', 'This response
exceeded 15 minutes…', 'time_limit')`. `READING_SLICE_MS` is 15 minutes (`:196`).
- `finish` updates `chat.reading` only when `checkpoint` is set (`:4326-4350`), so a
  null-checkpoint failure leaves reading state unpaused.
- Base `b8a5a01` `assistant.ts:3349` always built a checkpoint for an intake, so
  the timer took the soft branch (`:3511-3520`).
- `src/server/intake-batches.ts:587-597` lists `time_limit` among recoverable
  reasons on load.

AGENTS.md forbids seconds-based pass/fail bounds on host work; the 15-minute slice
may remain a provider-request boundary, but must not decide host-preparation
outcome. Cover both plan-history indexing and plan creation.

## Queue context

Pause, rather than fail, native conversion preparation that outlasts the reading slice.
