# 💽 CRS-152: Complete deployment qualification with real provider persistence and import

Status: open. Remainder of CRS-071 after the host/container filesystem qualification tool. Mount probes do not certify the full installation.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to know my chosen installation keeps records and provider access after restart,
So that I can rely on it before using household records.

## Plain-English walkthrough

1. Choose the installation drive and identify the provider route already in use.
2. Run a small fictional upload, review its results and save them explicitly.
3. Recreate the installation, check provider access and retained records, then check recovery from the retained evidence.

## Given–When–Then acceptance

The detailed contracts, owner decisions and evidence gates below remain required.

- **Given** the intended supported Compose installation, chosen drive and adopted provider, **when** a fictional upload completes reading and explicit acceptance, **then** original download hashes and accepted versions match after recreation and cache-loss rebuild; mount probes alone do not pass this workflow.

- **Given** proxy and provider state are separately mounted, **when** fresh supported containers start, **then** the master key and actual provider authentication persist on the named route; OAuth refresh evidence is coordinated with CRS-155 but kept separate.

- **Given** macOS-only drive automation and another intended supported host, **when** the container probe is extended and run there, **then** safe mount identity, UID 1000 ownership and owned-scratch cleanup are verified separately; an unavailable drive/host and physical power loss remain unqualified.

- **Given** external raw receipts and recovery material, **when** qualification is published, **then** only safe commands, build/provider scope and scoped conclusions enter maintained docs; no private paths, credentials or claim of filesystem/controller certification appears.

## Implemented boundary

`npm run qualify:drive` exercises exclusive creation, hard links, publication rename, file and directory fsync, concurrent-writer rejection, retained lock inodes, normal release and forced-kill reacquisition on the actual chosen filesystem. It repeats those checks through UID 1000 on an isolated bind mount, then uses a fresh container to verify the exact prior publication and reacquire its writer lease. macOS Docker Desktop and Linux drivers now use nonce-proven mount identity and owned-scratch cleanup; Linux still needs an actual separate host receipt. The command writes an owner-only external receipt and removes only its own fictional scratch directory. See [Docker runtime](../setup/docker-runtime.md#deployment-drive-qualification).

`npm run qualify:deployment` reuses the one-page/four-observation provider fixture, independent literal/extraction oracle and public acceptance APIs. Its deployment mode adds the same-mount drive probe, accepted-history/original checks across recreation and actual cache loss, unchanged encrypted vault inventory, private configuration/master-key comparison and fresh authenticated tool requests on the retained route. The prepared driver is not passing full-installation evidence until that workflow actually runs. See the [portable procedure](../setup/docker-runtime.md#fictional-deployment-qualification).

## Remaining requirements

- On the intended installation and drive, use the supported npm → Compose → LiteLLM path with a real adopted provider and an independently fictional encrypted profile.
- Complete the actual upload, reading, explicit review, acceptance and original-download workflow. Check original hashes and accepted versions after container recreation and cache-loss rebuild.
- Verify that the proxy master key and actual provider authentication survive recreation in the intended separate state mount. State the provider and route, and coordinate setup with live OAuth-refresh qualification while retaining separate acceptance evidence.
- Keep raw paths, credentials, recovery kits, diagnostics and personal environment details outside Git. Publish only portable commands and scoped conclusions in maintained documentation.
- State filesystem and power-loss limitations honestly; successful fsync calls and container recreation do not simulate physical power loss or certify every filesystem/controller.
- Run the extended UID 1000 container probe on intended Linux host setups and qualify those hosts separately. macOS Docker Desktop ownership-view differences are checked from the actual UID 1000 writer; neither its result nor fixture tests qualify a separate Linux installation.
