# 🧷 CRS-262: Release vault staging witnesses on every failure path

Status: open; PR #71 review finding. A record-source prior-field preparation can
throw without releasing its vault staging witness, and while any witness is held,
accepted reads wait and then fail on a 30-second wall-clock deadline. The
reproduced non-stream path is not reachable in production today; a compact
maintenance cancellation path plausibly is.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want a cancelled or refused background step to leave my profile readable,
So that one interrupted maintenance task does not make later reads fail until I
restart the app.

## Plain-English User Walkthrough

1. Background maintenance is tidying an import when I press Stop or it refuses.
2. I keep reviewing and opening records; they load normally.
3. If something does need recovery, the app says so once, clearly, rather than
   every later action failing with a timeout.

## Acceptance Criteria

### Scenario: Every failure path releases the witness

Given a fictional vault-backed profile and injected failures in both the stream
and non-stream branches of prior-field preparation, and in compact maintenance
after certification,
When each preparation throws, is cancelled or is disposed without commit,
Then its staging witness is released and `owner.stagingWitnesses` is empty,
And a following accepted read is admitted without waiting.

### Scenario: Admission waits on ownership, not elapsed time

Given a witness that is legitimately held by running work,
When an accepted read arrives,
Then it waits for that work's release, cancellation or close, or refuses
explicitly naming the owner,
And no pass/fail bound in seconds decides host-only admission.

### Scenario: Contributor discard matches vault semantics

Given a contributor-runtime preparation discarded with nothing staged,
When later captures run,
Then they succeed as the vault equivalent does,
And poisoning remains only for discards that leave staged or installed state.

## Evidence and Implementation Scope

- `prepareRecordSourcePriorFields` (`record-versions.ts:6042`) captures the
  witness at :6068. The stream branch releases it in its `finally`
  (~6204-6216); the non-stream branch's `catch` (~6300-6303) only closes
  `fields`, skipping `closeCompactContributorOriginal` (:6314-6320).
- Caller `intake-state-migration.ts:846,927-933` discards only when `priorFields`
  was returned, so a throw inside preparation leaks.
- `owner.stagingWitnesses` is a strong `Set` (`vault-store.ts:146,950`);
  `awaitVaultAcceptedAdmission` (:289-310) loops until
  `ADMISSION_DEADLINE_MS = 30_000` (:280), then throws. Frontier retention also
  refuses while a witness exists (~:822), turning later proofs into cold replays.
- Not reachable in production today: vault plus file-backed DB always streams
  (`intake-state-migration.ts:670-671`, `record-versions.ts:4895-4901`,
  `database.ts:842`).
- Plausible production variant: compact maintenance calls `assertRunning()` after
  certification (`intake-compact-metadata.ts:87-88`); its `finally` calls
  `disposePreparation` → `discard` (`intake-state-collections.ts:843-852,2890`),
  which does not release `data.compactMetadata.priorFields`
  (compare `intake-state-maintenance.ts:301`).
- Contributor: current `contributor-record-staging.ts` ~2470-2490 already preserves
  a reused frontier when preparation was never attempted and nothing was staged.
  Attempted preparation followed by cancellation can still mark the frontier
  `poisoned: true` without staged state, so later captures throw
  "Contributor retained backing requires recovery" (:849) until close; vault
  discard poisons only staged/installed state (`vault-store.ts:983-986`).

A reproduction for the compact maintenance variant is part of the work. Count
admission waits and witness lifetimes in tests rather than measuring time.
