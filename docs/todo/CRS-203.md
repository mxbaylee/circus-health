# 🧱 CRS-203: Add transaction-backed incremental intake state storage

Status: open. First focused implementation split from CRS-201. Adds the storage primitive and its verification; production intake continues using its current authoritative representation until [CRS-205](CRS-205.md). Unblocks [CRS-204](CRS-204.md).

## Problem and chosen boundary

Small intake updates currently version the growing `source_files.details_json` document. The implemented [compact history projection](../data/record-version-storage.md#compact-history-projection) removes duplicate envelopes and ancestor field payloads, but retains each complete version's contents. The [incremental encrypted index](../security/vault-index.md) removes separate encrypted-index amplification. Neither makes intake workflow authority incremental.

Reuse the existing profile-authorized record transaction and encrypted manifest publication. Represent operational intake state as immutable changed-content contributions in ordinary durable `app_meta` records, selected by a small source-scoped head. These records participate in the existing accepted-record commit. Do not create a second independently committed journal or make SQLite the recovery authority. A full operational view may exist only as a disposable reconstruction; do not persist it as another growing current row, version, receipt or reference array.

## Acceptance

1. Provide a typed storage API bound to the database/profile, intake source ID, original source hash and current format. Support initial state and exact subsequent changes, including arrays, object additions/removals, strings, null versus absent values and Unicode. Reuse the existing validated JSON change codec where its semantics fit; keep domain-specific identity and reference validation explicit. No old-schema decoder or migration is required before production.
2. Frame initial or large changed values into bounded immutable linked contributions (at most 64 KiB serialized per frame, including metadata), with a small bounded head. A tiny edit after a large state writes only changed evidence and bounded linkage. No growing reference list or full previous/current snapshot is copied into each event, record version, transaction result or receipt. Validate primitive identities, exact schema, UTF-8, hashes, links, sequences, duplicate definitions, profile/source/hash scope, and cumulative reconstruction budgets. Warm and cold limits must agree; reject before committing an unrecoverable state.
3. Reserve a documented durable `app_meta` key namespace that is not excluded by `record-versions.ts` internal-key filtering. Contribution keys are insert-only: an identical replay is verified, and a conflicting collision fails without replacement. Mutation results and persisted transaction receipts stay bounded and must not contain the reconstructed state. Publish contributions and their head atomically through existing record transactions. Preserve the current durability ordering, single-writer lease and session/profile authorization. Staged or orphaned contributions cannot become authority without the committed head. Exercise failures before staging, during immutable writes, before/after head publication and ambiguous completion. Reopen follows actual committed authority; it cannot fabricate a successful acknowledgement or silently reset missing/corrupt evidence.
4. Reconstruct once on cold open and avoid ancestor payload rereads during ordinary successful mutations. Keep the committed cached basis private and unchanged while preparing a candidate. Storage calls made inside an existing application transaction reuse it; do not introduce nested `BEGIN` or savepoint semantics. Handle multiple storage mutations/read-your-writes within that transaction, its outer rollback, rejected transactions and ambiguous flush correctly. State clearly which API owns an outer transaction and which requires one. Clear disposable state on lock, close and failed activation/publication. If transaction outcome hooks are needed, scope them to cache lifecycle without changing accepted-record publication order. Count reconstruction, candidate copying/diff work and durable work separately; do not claim all in-memory work is incremental merely because writes are.
5. Verify hundreds of primitive mutations at multiple sizes, including a tiny change after a large initial state and multi-frame values. Count all contribution, head, immutable record-version/commit/receipt bytes and SQLite projection bytes, plus new objects and history rereads. Prove exact reconstruction after cache loss and preserve unrelated accepted-record and original bytes. Cover corruption, cross-profile/source references, cumulative limits, retries, idempotent operation replay and rollback visibility. Use fictional fixtures; full real batch/review qualification remains CRS-205.
6. Document the implemented primitive and its current limits without claiming production intake uses it. Run formatting, type checks, focused tests and full PR CI; obtain independent grading. Delete this ticket on implementation and repoint CRS-204/205 to maintained storage documentation.
