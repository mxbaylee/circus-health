# 🔖 CRS-238: Serve and change intakes stored with referenced (V3) names end to end

Status: open; remaining work from the implemented
[V3 bridge and schema-directed envelopes](../data/intake-state-storage.md#v3-bridge-and-schema-directed-envelopes). Several
GET readers already accept a referenced V3 intake row under one complete accepted
proof, but no production path writes a V3 descriptor: the writer is
intentionally off, because one V3 row would make other routes fail with
unsupported authority. This ticket owns making every remaining consumer accept
V3 rows, then turning the writer on with an end-to-end upload test. It does not
change CRS-232 or CRS-233 scope.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want to file originals with very long names and locators and keep working with them everywhere in the app,
So that a large history imports completely without renaming files by hand or losing the exact original name.

## Plain-English User Walkthrough

1. I upload a collection whose file names or internal paths are extremely long or unusual.
2. The import list, feed, report queue, source details, history and search all open normally and show a shortened name that I can expand to the exact original.
3. I can correct an intake's details, annotate it and finish review as with any other upload; nothing fails just because a name was long.

## Acceptance Criteria

### Scenario: Every intake route accepts a referenced row

Given a profile contains at least one V3 intake row produced by the real compact writer, on contributor and vault storage,
When the operator uses `GET /intakes/import-feed`, `GET /intakes/report-queue`, an intake mutation such as `POST /metadata`, the source-passage, preview, history, search and annotation routes, and the package-failure-fragment POST,
Then each answers from the accepted proof instead of returning 500 or unsupported authority,
And the already-accepting readers (`GET /intakes/:id`, the mixed intake list, plan, read, package-failures, source-text, source-issues and source-attention preview) keep their current behavior and tests,
And review answers from accepted-scope bindings rather than 409 `INTAKE_REVIEW_UNAVAILABLE`, or keeps that refusal with an explicit, documented reason.

### Scenario: The production writer is enabled only after its consumers

Given every consumer above accepts V3 rows,
When the compact writer passes a referenced target candidate into `certifyCompactMetadataAsync`,
Then an end-to-end upload test produces a V3 row through the real upload route and drives the feed, queue, mutation, source and review routes over it on both adapters,
And no route returns 500 for that row.

### Scenario: Compact presentation stays exact for hostile values

Given oversized original names and locators, existing-native upgrades, assistant serialization and giant Unicode, BOM and NUL values,
When they are presented, serialized and read back as exact source-bound fragments,
Then compact previews never replace or alter the exact source-bound fragment,
And integrated paths (not only focused tests) are qualified,
And bounded host chunks alone are not accepted as proof of bounded native SQLite materialization.

## What already exists

- `GET /intakes/:id` on a V3 row serves `health-intake-summary-v3`: compact
  filename preview, exact source-bound fragments, accepted current metadata and
  acquisition when each field fits the 16 KiB budget (otherwise `unloaded`), and
  mime predicates instead of a raw type. Review counts, the active plan and the
  provider name stay `pending`/`unloaded` because they depend on rows outside the
  accepted scope.
- Source attention review previews a V3 original from its predicates. The import
  browser presents V3 names compactly, reads exact filename fragments, walks V3
  ancestry and refuses retain-only reading.
- The intake list (mixed legacy/V3) and the plan, read, package-failures,
  source-text and source-issues GETs accept a V3 row under one complete accepted
  proof per request (per V3 row for the list), on contributor and vault storage:
  `src/server/intake-referenced-reads.ts`, `REFERENCED_GET_ACTIONS` in
  `src/server/intake-routes.ts`, tested by `src/server/test/intake-referenced-readers.test.ts`
  with a V3 descriptor from the real compact writer. Plan is the V3 summary; read
  binds its literal window to the accepted path, bytes, hash and MIME type;
  package failures page under the accepted pins; source text and issues must name
  the accepted source hash. The mixed list keeps the exact SQL order and
  `rootOnly` filter, applies them to V3 rows from their accepted summaries, and
  prepares only legacy rows on the page; with no V3 row it is the old list.
- Review deliberately refuses V3 with 409 `INTAKE_REVIEW_UNAVAILABLE`.
- `certifyCompactMetadataAsync` (`src/server/intake-state-collections.ts`) already
  accepts a `referencedTargetCandidate` option; the production writer
  (`src/server/intake-compact-metadata.ts`) does not pass one.

## Remaining work

1. **Feed and queue.** `GET /intakes/import-feed` and `/intakes/report-queue`
   reach `intakeSourceVersion` → `intakeEnvelopeAuthorityBinding`
   (`src/server/intake-state-access.ts` / `src/server/intake-authority.ts`) from
   the intake-queue-native bindings; both are synchronous and cannot certify V3.
2. **Mutations.** That intake's mutations fail: `POST /metadata` → `checkVersion`
   → `intakeSourceVersion`.
3. **Other source routes.** Source-passage, preview, history, search and
   annotation, and the package-failure-fragment POST.
4. **Review host.** Accepted-scope bindings for the review host.
5. **Reader index.** Reader-index coverage for V3; source-issues currently omits
   `readerCoverage` for V3 rows.
6. **Writer.** Then pass a referenced target candidate into
   `certifyCompactMetadataAsync`, plus an end-to-end upload test.

## Open questions

- Whether review should serve V3 through accepted-scope bindings or keep a
  deliberate, documented refusal for some V3 cases.
- Whether `intakeSourceVersion`/`intakeEnvelopeAuthorityBinding` get an
  asynchronous accepted-proof form or a synchronous V3 certification; the current
  synchronous design is why one row breaks the feed.
- How [vault accepted-source routing](CRS-240.md) affects which readers these
  routes use on the vault adapter.
