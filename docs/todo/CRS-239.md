# 🚚 CRS-239: Finish cooperative copy, recovery and lookup work

Status: open; remaining work from the implemented
[intake storage](../data/intake-state-storage.md) and
[record storage](../data/record-version-storage.md) contracts. Most
record rebuild, backup, private-copy export and startup rebuild paths now yield
between bounded windows with a proof at each window start, at completion and on
abandoned exit. Several copy, recovery and validation phases are still
synchronous or read whole values, lookup appends still re-derive each changed
source completely, and the supported copy changes are not yet qualified in
actual deployments. This ticket owns that remainder. It does not change CRS-232
or CRS-233 scope.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want backups, restores, copies and rebuilds to run without freezing the app,
So that I can keep my household's records safe on a small laptop without losing or misreading any evidence.

## Plain-English User Walkthrough

1. I start a backup, restore or copy, or reopen the app after its working cache was lost.
2. The app keeps answering other pages while that work runs, and shows that it is still working.
3. If an original or saved history changes underneath it, the copy or restore stops with a clear refusal and leaves nothing half-written.

## Acceptance Criteria

### Scenario: Remaining copy and recovery phases cooperate

Given fictional profiles large enough to make each phase measurable,
When `openPortableRows`/`streamPortableJson`, `restoreBackup`, published-copy activation (`activatePublishedCopy`), `rebuildProfile`, the copy worker's own reconstruction and `validateProductionIntakeAuthority` (intake-state bootstrap) run,
Then each yields between bounded windows with a proof at every window start, at completion and on abandoned exit, or records an explicit, reviewed limit for why it cannot,
And an unrelated host request completes during the phase while a synchronous control blocks it,
And a same-byte HEAD rewrite during the phase is refused and leaves no target.

### Scenario: Native whole-value materialization is stated honestly

Given native SQLite target statements still run as single synchronous statements that materialize whole values,
When a giant value passes through copy, restore or rebuild,
Then the maintained documentation records this as a distinct boundary with its measured limit,
And no bounded host chunking is described as bounding native SQLite materialization,
And any change that does bound it carries its own counted evidence.

### Scenario: Small accepted changes cost work proportional to the change

Given lookup preparation after first accepted use and after subsequent small accepted changes, including actual changed-source public operations,
When the catalog delta is appended,
Then work scales with the changed receipts, not with complete re-derivation of each changed source,
And the delta carries what receipt-only append needs (each receipt's accepted change, not only row-field digests), or the complete re-derivation remains with a measured, documented limit,
And logical witness correctness and warm lookup tests are not accepted as the complete scaling claim, and neither path is an all-file physical certificate.

### Scenario: Supported copies are qualified where they actually run

Given contributor and encrypted copies on the supported Linux deployment with disk-backed storage,
When shared equality, asynchronous original capture, manifest fingerprinting and source-text worker validation run with incremental native reads,
Then exact grammar, original read intervals, complete physical checks and existing format limits are preserved,
And history and original proof through publication are not weakened.

## What already exists

- Step-wise record APIs (`attachRecordDurabilitySteps`, `rebuildRecordDatabaseSteps`,
  `writePortableSourcesSteps`); the synchronous functions are thin drivers.
  `rebuildContributorDatabaseAsync`, `writePortableSourcesAsync` and
  `rebuildProfileAsync` yield between windows of 1 to 16 steps with proofs at
  window start, completion and abandoned exit (fresh HEAD wire, original read
  descriptor, and physical HEAD and directory identity for contributors).
  `createBackup`, private-copy export and the bounded startup rebuild use them;
  counted regressions are in `record-stepwise-rebuild` and `portable-streaming`.
  Note that `rebuildProfileAsync` exists while `rebuildProfile` is still synchronous.
- Source-text rebind and intake-state staging use a private bounded transfer;
  plain tree copy and flush cooperate between bounded file operations. Copy
  equality performs one complete original proof per resumed step; published-copy
  activation performs two complete reconstructions instead of three; backup
  output and copy comparison prove once per window of up to 16 quanta. Bounded
  restore staging, raw-range helpers and the selected source-row index have
  focused passing evidence. Portable startup streams original inventory and
  compares reference and target projections with final physical closure after
  activation callbacks.
- Contributor and vault original-proof reuse across exact own publications: six
  own publications cost six incremental advances and no cold replay; forged
  preimages refuse; a same-byte rewrite or foreign replacement falls back to one
  cold replay. Cold replay decodes each version once per transaction within a
  bound. Status HEAD reads are cached behind the `headIdentity` stat-identity hook.
- Lookup maintenance outcomes are recorded, and preparation appends a new-original
  or changed-source catalog delta across the complete original-snapshot chain,
  accepted HEAD continuity, source-field digests and catalog membership, in pages
  of 100 up to 10,000 rows, with the full fallback for a consumed link.

## Measured remaining cost (context, not a cooperative boundary)

Profiling in CRS-231 placed remaining copy-fixture cost in: the worker's one full
legacy replay validation (about 8–9 s for 129 frames, kept as the original proof),
contributor HEAD/object reads (`contributor-record-storage` `read`, 12,575–36,062
opens per fixture), per-file durability fsyncs (kept), the two attach
reconstructions in `record-versions.ts`, and contractually fresh HEAD reads.
Schema-envelope builds still make one publication per 63 changes (three immutable
writes each) and the format stores roughly eight keys per field; fewer
publications remain open. The unchanged 30 s sparse/package and 90 s copy guards
remain required regression checks for changes to these paths; a prior pass does
not qualify a later candidate.

## Evidence carried from CRS-231

The two CRS-231 bullets this ticket draws on, as they stood at the split
(`6226151`), for their measurements and focused evidence. Their unmet parts are
the requirements above; implemented parts move to maintained documentation.

### Large legacy-record changes

Qualify large legacy-record changes through the actual encrypted adapter.
Preserve accepted field history, refuse modified disposable source columns,
and verify consumed immutable backing before publication. Bound cold replay
and the encrypted pre-publication workspace/source checks as well as the
selected metadata update; a bounded header alone is insufficient.
Contributor and portable adapters must also reject mutually forged source
and accepted-version SQLite preimages while immutable accepted storage is
unchanged. Contributor original-proof reuse across exact own publications has
focused counted evidence: six own publications cost six incremental advances
that decode only the new commits, with no cold replay. A forged
accepted-version preimage, a same-byte rewrite of a retained member and a
foreign HEAD replacement each refuse or fall back to one complete cold
replay. The catch-up still runs whole-database integrity, foreign-key and
target checks, and a staged publication drops the retained replay. The vault
adapter now advances the same way, with focused counted evidence: six own
publications cost six advances and no cold replay; forged preimages refuse,
and a same-byte rewrite or foreign manifest replacement falls back to one
cold replay. Vault admission waits for held reads instead of refusing. Cold
replay decodes each version once per transaction within a bound. Status HEAD
reads are now cached behind an optional storage stat-identity hook
(`headIdentity`): `recordDurabilityStatus`, and so the envelope authority
binding check, reuse a parsed HEAD only while the genuine storage reports the
exact settled identity (contributor: directory and HEAD dev/ino/size/mtime/
ctime with a racy-timestamp settle window; vault: the unlocked manifest value)
and no own publication renewed its epoch. A counted fictional selected-pages
flow fell from 2,707 to 333 real HEAD reads (2,374 reuses) with a settled
clock, and 25 binding checks from 25 reads to none; in-place same-byte and
same-size foreign HEAD rewrites still force a read, and the latter still
conflicts. Read owners, publication verification and terminal reads are
unchanged. The ~30k figures came from a larger run that was not
re-measured, and freshly published HEADs (under 50 ms old) are still read.
Qualify both adapters through the integrated paths.

### Combined supported-copy changes

Qualify the combined supported-copy changes: shared equality, asynchronous
original capture, manifest fingerprinting and source-text worker validation
use incremental native reads. Preserve their exact grammar, original read
intervals, complete physical checks and existing format limits in actual
contributor/encrypted copies and Linux deployment. Source-text rebind and
intake-state staging now use a private bounded transfer, and plain tree copy
and flush cooperate between bounded file operations. The transfer spool now
writes and reads back each value once (no in-spool TEXT rewrite, one compiled
insert), copy equality performs one complete original proof per resumed step
plus result/exit proofs (3,912 instead of 7,851 on the 2 MiB fixture, with a
same-byte in-step HEAD rewrite still refused), and published-copy activation
performs two complete reconstructions instead of three. Counted regressions
cover each. Native SQLite target statements still run as single synchronous
statements that materialize whole values. Step-wise record APIs now
exist (`attachRecordDurabilitySteps`, `rebuildRecordDatabaseSteps`,
`writePortableSourcesSteps`), and the synchronous functions are thin drivers
over them. `rebuildContributorDatabaseAsync`, `writePortableSourcesAsync` and
`rebuildProfileAsync` yield between windows of 1 to 16 steps. A proof runs
at every window start, at completion and on abandoned exit: fresh HEAD wire,
original read descriptor, and physical HEAD and directory identity for
contributors. `createBackup`, private-copy export and the bounded startup
rebuild use them. Counted regressions (`record-stepwise-rebuild`,
`portable-streaming`) show four things:

- a host request completes during a 160-commit rebuild, while the
  synchronous control blocks it;
- a same-byte HEAD rename mid-rebuild is refused and leaves no target;
- reconstruction replay counters equal the synchronous ones, with only one
  HEAD read per proof added;
- indexed-cache attachment replays into SQLite once (491 insert attempts)

  object, version and original, and reruns intake validation. Catch-up

published-copy activation (`activatePublishedCopy`), `rebuildProfile`, the

## Verification

same-byte HEAD rewrite refusal, lookup append work counts after small changes on
both backends, deployment qualification on disk-backed Linux, and the
encrypted-adapter legacy-record fixtures. Run formatting, type checking, affected
tests, independent review and required CI; update the storage, recovery and
release contracts when it lands. No implementation is claimed by this ticket.
