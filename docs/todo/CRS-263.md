# 🧩 CRS-263: Make package inventory chunk appends idempotent

Status: open; PR #71 review finding, defense in depth after the blocker fix.
This change serializes plan-creation inventory builds under the clinical
operation, closing the reproduced concurrent-builder race. Chunk writes are
still position-implicit, and a corrupted published inventory has no rebuild
path.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want an interrupted or repeated ZIP inventory step to produce the same
inventory as a clean one,
So that a retry never leaves a package I can neither open nor re-prepare.

## Plain-English User Walkthrough

1. I upload a large fictional ZIP; its member list is being prepared when the
   app is stopped or the step is retried.
2. When preparation resumes, the member list matches the ZIP exactly.
3. If a saved member list is ever found damaged, the app says so and can prepare
   it again from the retained ZIP, without changing the original.

## Acceptance Criteria

### Scenario: A repeated or resumed chunk write is idempotent

Given a multi-chunk inventory record partly checkpointed,
When the same chunks are offered again (resume, retry or an injected duplicate),
Then each chunk is addressed by its own index or the stored count is re-read at
flush, so no chunk is stored twice,
And retained chunks are still compared byte-for-byte with the verified source.

### Scenario: Publication verifies each record

Given a completed build about to publish,
When the inventory is published,
Then each multi-chunk record's stored byte length and hash match its manifest,
And a mismatch refuses publication with a structured error, not a JSON parse
failure.

### Scenario: A corrupt published inventory is detected and rebuildable

Given a published inventory whose record bytes fail verification,
When a reader opens it or a plan is created,
Then the corruption is reported explicitly and the inventory can be rebuilt from
the retained original,
And work counts show only the affected inventory is rebuilt, not the package's
accepted history.

## Evidence and Implementation Scope

Line numbers are at PR #71 head with this change's serialization fix applied:

- `buildDurablePackageInventory` (`src/server/intake-package-state.ts:367-378`)
  now runs under `runExclusiveClinicalOperation`; its comment records that
  "Inventory chunk appends and attempt/reuse checks are not idempotent".
- `storedChunks` is read once when a record starts (:595-596); later chunks with
  `index >= storedChunks` are added as `appendBytes` (:614-627) with no index.
- `appendBytes` writes at `orderedKey(values?.count ?? 0)`
  (`src/server/intake-state-collections.ts:1462-1472`), so a duplicate append
  lands at the next position.
- The publication check (:718-722) compares manifest and record key counts only,
  not chunk counts or byte lengths.
- `readRecord` (:162-199) concatenates byte pages and calls `JSON.parse` (:191)
  before any hash check; the member reader hashes afterwards (:271).
- An existing published inventory is reused as-is (~:411-430), so a damaged one
  is never rebuilt.

Keep the change inside the inventory builder and reader; do not alter the
retained original, the ZIP grammar bounds or accepted package history.
