# 🧺 CRS-248: Reclaim superseded build collections

Status: open; PR #71 review finding. At PR #71 head the intake state store has no
operation that removes a name from the `builds` area, so every draft save,
acceptance and maintenance retry adds permanent, mostly unreachable build
collections that later copies and cold paths carry forward.

## User Story

As a [High-precision tracker](../design/personas.md#build-a-history),
I want repeated saves, re-uploads and retries to cost storage in proportion to
what actually changed,
So that a long history stays fast to copy, back up and reopen years from now.

## Plain-English User Walkthrough

1. I save review drafts, accept records and occasionally retry or stop
   background work over many months.
2. My profile grows by roughly what I added, not by leftovers from each attempt.
3. When I copy or back up the profile, only the working data that current
   records need comes along; my accepted history and originals are untouched.

## Acceptance Criteria

### Scenario: Superseded builds can be dropped

Given a fictional intake whose head selects some builds and whose `builds` area
holds earlier, unselected ones,
When a reclaim/drop operation runs,
Then names unreachable from the selected manifests (and from any retained
resumable checkpoint) are removed from the current head,
And accepted history, receipts, originals and the selected builds are unchanged.

### Scenario: Copy keeps only reachable builds

Given the same intake,
When it is copied to another profile,
Then the copy rebinds only build names reachable from the selected manifests,
And copy work and bytes scale with reachable builds, not with all builds ever
published.

### Scenario: Growth per operation is bounded

Given repeated draft saves, acceptances and canceled or retried maintenance,
When each finishes,
Then retained build entries grow by at most what that operation still needs,
And the work counts (entries scanned, bytes written) are asserted in tests,
with no additional durable write amplification from the reclaim itself.

## Evidence and Implementation Scope

- No removal: `IntakeCollectionChange` (`intake-state-collections.ts:140-170`)
  has `delete` only for map keys (:1392, :1475); each new head starts from
  `before.head?.builds` (:1291).
- Envelope candidate finalization only adds builds (`intake-envelope-candidate.ts`
  ~551-661); history keeps prior heads.
- Portable copy collapses history but rebinds every builds entry
  (`intake-state-graph.ts:524`).
- Per-operation UUID builds: `workflow.<uuid>` with `.facts` etc.
  (`intake-workflow-update.ts:332-336`), `model.<uuid>`
  (`intake-model-section-update.ts:79`), `lookup.<id>.indexes`
  (`intake-lookup-state.ts:355`), `report.catalog/snapshot/text.<uuid>`
  (`intake-report-snapshot-catalog.ts:137,387,491`), `schema.upgrade.<uuid>`
  (`intake-envelope-upgrade.ts:100`), `review.questions.build.<uuid>`
  (`intake-review-question-state.ts:124`), `reading.reindex.<uuid>`
  (`intake-reading-legacy.ts:202`).
- Cold paths walk the whole builds root (`intake-state-graph.ts:271,303`;
  migration scans in `intake-state-migration.ts`).
- Disclosure exists only for envelope builds: `docs/data/intake-state-storage.md`
  :348 ("Earlier randomly named incomplete builds remain retained history and are
  not reclaimed") and :66-71; update docs when reclaim lands.

Open question: should reclaim run inline with each publisher (drop its own
superseded name), as a separate maintenance pass, or only at copy time?
