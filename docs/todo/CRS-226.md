# 🛂 CRS-226: Check passkey compatibility from a hosted page

Status: open. Owner-requested prerequisite for [CRS-163](CRS-163.md), 2026-10-03. This change specifies the checker and updates the backlog only; implementation and GitHub Pages publication belong to a later reviewed task. No checker is implemented or deployed, no physical run is performed, and CRS-163 remains open.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to open one link, try my passkeys and download a clear account of what worked,
So that I can choose usable browser and password-manager combinations and know what still needs checking on my installation.

## Plain-English User Walkthrough

1. Open the checker link myself in the browser I want to test. Read that it uses fictional material and tests this page, while my household installation still needs its own checks.
2. Check or correct the browser, operating-system and passkey-provider names and versions. Leave anything I cannot identify marked unknown.
3. Follow the real prompts to create and confirm a test passkey, then use it three more times. See whether each attempt could open the fictional test value, alongside any failure or unfinished step.
4. If another passkey is available, add it and test it independently. Record what I observed using Worked, Failed or Couldn't test, with optional notes.
5. Return after a reload to the progress this browser retained, or receive a clear explanation if it could not be saved. A different browser or device starts its own local test.
6. Download a readable report showing verified results, my observations and the remaining installation checks. I can give it to another LLM to help update CRS-163 without sharing passkey secrets or treating the hosted result as a full release qualification.

## Scope and existing code

Build one standalone browser-only qualification tool served over HTTPS by GitHub Pages. It requires no Circus Health server, Docker, LiteLLM, model configuration, account backend or server-side result storage. The operator opens each browser manually; no browser automation, automatic matrix iteration or new authentication platform is required.

Keep source and build instructions in the normal reviewed codebase. Publish generated site assets exclusively to `gh-pages`; never publish the production health app, real archives, local test state or reports. Hosting this checker does not adopt remote household access or make remote production deployment a release requirement. Phones and additional operating systems may be tested conveniently at the checker origin without changing the localhost release scope.

Relevant existing implementation, inspected 2026-10-03:

- [`passkey-prf.ts`](../../src/app/components/passkey-prf.ts) provides `withBinaryPrf` and `prfFrom`, including strict 32-byte result handling across native buffers, canonical base64url and the reported plain-array compatibility case.
- [`passkey-enrollment.ts`](../../src/app/components/passkey-enrollment.ts) creates a credential, then requests a confirmation assertion for that exact credential with the same salt. [`passkey-unlock.ts`](../../src/app/components/passkey-unlock.ts) obtains fresh PRF output for later unlock. Both orchestrators depend on the production server; they cannot simply be presented as working standalone flows.
- [`profile-passkeys.ts`](../../src/server/profile-passkeys.ts) generates production requests with required resident credentials and user verification, per-credential PRF salts and an exact-credential confirmation. Later authentication uses credential-specific salts. Its server challenge/origin/RP/signature and session checks remain production-only evidence.
- [`qualify:passkeys`](../../src/scripts/qualify-physical-passkey.ts) and the [physical qualification procedure](../security/profile-encryption.md#physical-passkey-qualification) already drive real Chrome/Edge against a fresh fictional application installation. They require that installation and human gestures; the hosted checker complements them and does not replace them.

Reuse relevant browser helpers and request semantics where practical. Document each reused component and every material difference, including browser-generated challenges, fictional encryption, missing backend verification and any credential-selection differences. A browser-side simulation is not verification of the corresponding application behavior.

## Acceptance Criteria

### Scenario: Open a self-contained checker

Given the published checker URL and an actual browser,
When the Operator opens it manually,
Then the tool runs in that browser over HTTPS without any application server, Docker, provider or model setup,
And it checks the actual secure context and native credential API, uses only fictional material, and sends no test results to a server.

### Scenario: Identify the tested environment honestly

Given browser/version, OS/version and authenticator or password-manager/version fields,
When reliable browser metadata is available or the Operator corrects a field,
Then auto-collected values and human corrections are distinguishable, unknown values remain unknown, and labels appear in the report,
And a user-agent string or provider hint is not treated as proof of an exact version or authenticator identity.

### Scenario: Confirm a usable PRF result

Given a fresh fictional test and an identified provider,
When the Operator completes real credential creation and confirmation,
Then the checker requests confirmation with the exact newly created credential and the same test salt, requires actual valid PRF output and establishes the encrypted fictional test value,
And credential creation, a capability flag or a successful signature alone cannot mark PRF/decryption compatibility as passed.

### Scenario: Verify three subsequent uses

Given a confirmed test credential and its encrypted fictional value,
When the Operator completes each of three subsequent authentication attempts,
Then each attempt obtains fresh actual PRF output and successfully decrypts and compares the retained fictional value before being automatically marked verified,
And missing or malformed PRF, incorrect decryption, cancellation, unsupported behavior and incomplete attempts remain explicit per-step outcomes; a cached plaintext or decryption key cannot substitute for a new attempt.

### Scenario: Test a second distinct credential

Given a second available authenticator or passkey,
When the Operator enrolls it for the same checker test,
Then the checker confirms it is a distinct credential locally and guides confirmation plus three independent authentication/decryption attempts for each credential,
And accidentally using the first credential cannot pass the second credential's steps; unavailable combinations remain Couldn't test rather than success.

### Scenario: Record observations separately

Given a prompt or other behavior the tool cannot verify itself,
When the Operator selects Worked, Failed or Couldn't test and optionally adds notes,
Then the report labels this as a human observation and retains any separate automatic result,
And a manual Worked choice never overrides failed PRF/decryption evidence or verifies production application behavior.

### Scenario: Resume within browser-local limits

Given partial or completed local progress,
When the page reloads in the same browser and origin,
Then the supported local state restores the step history and permits further real attempts without persisting raw PRF output or an unprotected decryption key,
And detectable unavailable or incompatible state is explained, available history is reset only deliberately, and missing progress never implies past success; the page states that clearing, eviction and private-session limits can lose local progress even when the exact cause cannot be detected,
And the page explains that browser-local progress does not automatically follow a passkey to another browser/device; clearing checker state does not remove a credential from its provider.

### Scenario: Download a useful, sanitized handoff

Given any completed, failed or partial test,
When the Operator downloads the report,
Then a human-readable Markdown or text file includes tool build/version, date, tested origin and relying-party scope, environment labels and their provenance, per-step evidence/outcomes, sanitized errors, optional observations and unfinished checks,
And it separates automatically verified hosted results, human observations and checks still requiring the real release-build installation so another LLM can update CRS-163 without treating omissions as passes,
And the export contains no recovery secrets, raw PRF outputs, private/decryption keys or credential IDs, including through raw responses, errors or debug dumps; safe local aliases can distinguish credentials,
And JSON may be offered additionally but is not the only report format.

### Scenario: Keep the qualification boundary explicit

Given successful hosted PRF/decryption evidence,
When the page, report or a follow-up ticket describes coverage,
Then it names only the observed browser/OS/authenticator combination at this HTTPS origin and states that its credentials belong to this relying-party domain, not localhost,
And production backend verification, session authorization, actual profile recovery, locked private/original-access refusal and retained access after Compose recreation remain unverified by this tool,
And CRS-163's real localhost release-build requirements, its prerequisite relationship to CRS-088 and CRS-088's later feature/salt-migration requalification remain intact.

### Scenario: Publish only the reviewed checker

Given reviewed source, a reproducible static build and a chosen GitHub Pages configuration,
When a later authorized implementation publishes the checker,
Then generated site assets go exclusively to `gh-pages`, the report identifies the built revision, and published files contain no runtime records, local progress, reports or secrets,
And the repository documents its source/build/publication path and explicitly identifies it as a qualification tool, not a production health-app deployment.

### Scenario: Preserve real physical evidence

Given the checker is being used for physical qualification,
When any credential operation is performed,
Then it uses the browser's real prompts and native credential API with valid HTTPS,
And no virtual authenticator, credential API override or TLS bypass participates; controlled development tests, if used to verify tool logic, are labeled separately and never counted as physical observations.

## Report evidence boundary

| Evidence class                                 | What a report can say                                                                                                                                             | What it cannot establish                                                                                                    |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Automatically verified hosted results          | Actual valid PRF returned and fictional value decrypted on each recorded attempt; local credential A/B distinction; secure-context/origin and tool build metadata | Production backend signature/challenge/origin verification, profile/session authorization or localhost credential usability |
| Manual observations                            | Operator-labeled provider/version, prompts and Worked/Failed/Couldn't test notes, with provenance                                                                 | Automatically verified success or unobserved application/recovery behavior                                                  |
| Real release-build installation still required | Explicit remaining CRS-163 checklist for actual localhost enrollment/unlock, recovery, locked private/original access and container recreation                    | Closure of CRS-163 from a hosted report or simulation alone                                                                 |

## Engineering decisions still open

These choices are implementation work to resolve and document, not implemented capabilities or reasons to expand this into an authentication platform:

1. **Local test-state persistence.** Choose and version a minimal browser-local representation (for example IndexedDB versus localStorage), which public credential references/salts and fictional ciphertext are necessary, how partial writes/reload/resets and unavailable storage behave, and how to segregate runs and origins. Keep PRF/decryption key material transient. State what survives a reload and what requires re-enrollment; do not imply cross-browser synchronization. Use deliberate reset and export affordances without silently discarding prior outcomes.
2. **Production-code reuse and encryption.** Decide whether to import the existing pure browser PRF helpers or extract narrowly shared helpers without changing production semantics. Specify the fictional value's PRF-derived encryption/decryption method, confirmation and per-credential selection, and document differences from production wrapping and server verification. No health profile or real recovery phrase is needed.
3. **GitHub Pages publication.** Choose the repository Pages URL versus a dedicated approved hostname, path/base configuration, static build entrypoint and reviewed publish mechanism/permissions targeting `gh-pages`. The repository currently has no checker publishing workflow or advertised `gh-pages` branch; the Pages API returned 404 during read-only inspection, so a configured site or live URL is not established. A project URL path does not create a separate origin or relying-party domain; document origin/storage scope and the need for new enrollment if the hostname changes. Do not create or enable a site in this ticket-creation change.
4. **Metadata and report schema.** Define reliable automatic fields versus editable observations, sanitized error vocabulary, local credential aliases, report versioning and a concise remaining-checks checklist usable by a human or another LLM. Export allowlisted results rather than raw WebAuthn responses or debug logs; prompt users to keep secrets and real health information out of free-text notes.

## Completion and dependency handoff

Implementation completion needs focused browser/crypto/state/report checks, evidence that the static build is independent of the health app/backend, normal formatting/type checks, full PR CI and independent review. Publish only through the later reviewed scope and document the actual hosted URL and its build provenance. Operator-run physical results are subsequent evidence, not fabricated by those development checks.

CRS-226 unblocks the owner-requested easier compatibility-gathering step for CRS-163. Completing the checker does not close CRS-163, qualify a release or remove its actual installation checks. CRS-163 still precedes CRS-088; CRS-088's new flow and salt migration still require their own later qualification. This specification-only ticket creation does not advance the merged-completion grooming counter.
