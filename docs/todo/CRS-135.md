# CRS-135: Finish productive automatic continuation left from CRS-039

Status: open. Corrective follow-up to the automatic-recovery work at `dc96b6c`, whose ticket (CRS-039) was deleted there without an independent passing grade. Independent grading afterwards gave it B−: most of the coordinator works, but Stop can strand a file permanently, and several waits still end in a pause the person must clear. This ticket covers only what is unfinished or defective. Line numbers were verified at `46e8b95`.

## Decision and why

[CRS-126 D2](CRS-126.md#d2-no-size-or-time-limits-on-reading-detect-stuckness-instead) and [D3](CRS-126.md#d3-waits-are-backoffs-never-pauses) are authoritative. Reading has no size or time limit. Stuckness means no progress for a period: retry from the checkpoint, then list that part as an exception and carry on with the rest. Waits are backoffs. The person needs Resume only after **Stop imports**, or to fix something only they can fix, such as signing in to the provider again, and even then work continues without a Resume click once the fix is made. The maintained rationale is in [automatic recovery](../import/automatic-recovery.md#rationale-and-authorization). Every defect below breaks one of those two sentences.

- **High-precision tracker** ([CRS-130](CRS-130.md)): uploads a backlog from about fifteen sources and re-uploads full-history exports. Stop, Resume and the estimate must work across many files, and a non-progressing model must not loop forever on a long file.
- **Low-effort self-tracker**: should never see "needs your review" for a race the app can retry on its own, and should never have to press Resume to recover from a routine error.
- **Caregiver**: switches between profiles. Keeping locked work dormant until unlock is **correct** until [CRS-081](CRS-081.md) adds scoped authority. This ticket must keep the dispatch/publication authorization checks and must not add post-lock processing.

## Requirements

1. **Stop and Resume every automatic item, not only `items[currentIndex]`** (unrecoverable today). `stop()` (`intake-batches.ts:1516-1553`) marks only the current item as paused, in both branches (`:1525`, `:1540`). If file A is waiting on the provider and file B has finished, `currentIndex === items.length`, so A stays `queued` with `automaticRun: false`. Resume is hidden because no item satisfies `hasPausedIntakeReading` (`shared/intake-batch.ts:195-202`, `ImportPage.tsx:2226-2235`). Server `resume()` searches only from `currentIndex` and returns 409 "No paused delivery needs another pass" (`:1572-1579`). Re-creating the batch returns the old stopped batch (`:1394-1397`). **Direction:** Stop must mark every item that had automatic intent, whatever its position or status, as `paused`/`stopped`, cancel its timers, and cancel its in-flight chat. Resume must restore every item with `resumeAutomaticRun`, searching the whole batch and restarting from the first eligible item. The UI must offer Resume whenever a stopped batch has a resumable item. A stopped item selected for Reprocess resumes that item rather than silently returning the stopped batch. Journal records written before this change must decode to the same result. Serves: high-precision tracker (many files) and D3.
2. **A transient source-text error is a backoff, not a review request.** The runner error handler (`intake-batches.ts:380-400`) maps every `SOURCE_TEXT_*` code to `source_review_required` and pauses the **whole batch**. The drain and blocked paths do the same (`:795`, `:912-921`). The message then says "Source text needs your review… then resume reading" (`reviewQueue.ts:39-40`), which is untrue for a revision race, and nothing wakes the batch before the next unlock. **Direction:** classify the codes explicitly:
   - Retry with backoff: `SOURCE_TEXT_CHANGED`, and `SOURCE_TEXT_EXTRACTION_ACTIVE` in every path. Today it is a capacity wait only when the current item is `queued` (`:360-368`). Only the affected item waits, with a persisted deadline; other files continue.
   - `SOURCE_TEXT_DURABILITY` means the profile journal is locked or conflicted (`intake-source-text.ts:86-94`). A locked journal leaves work dormant until unlock. A conflicted one is a durability problem, described as such, not as a source review.
   - Needs review: genuine human-review conflicts such as `SOURCE_TEXT_REVIEW_CONFLICT` (`intake-source-text.ts:1021`).
   - Any other code: a located technical exception with honest wording, not a claim that the person must review.

   Confirm where each code comes from before classifying it. D2 still applies: three consecutive no-progress retries on the same unit become a located processing-stalled exception, not an endless loop. Keep the review wording only for real review. Serves: low-effort self-tracker.

3. **Reprocess corrected source must never report a pass it did not start.** The button (`SourceAttentionReview.tsx:493-509`) calls `batch.create([intakeId])` (`ImportPage.tsx:2031-2036`). That call returns the existing batch (`intake-batches.ts:1394-1397`), which counts as success, so nothing happens. **Direction:** until CRS-118 reopens terminal items, the server must report whether new work was scheduled. Use a distinct result or error code, not a guess from a message string. When nothing was scheduled, the UI says so plainly and says what will happen instead. For a stopped item, apply requirement 1. Serves: low-effort self-tracker.
4. **Activity wording and estimate** (the unmet part of R34):
   - With 15 files, 14 of them queued, the page shows "Estimating…" indefinitely, because any unmeasured file voids the whole estimate (`ImportReadingActivity.tsx:36,43`). Estimate from measured files, and state that queued files are not yet included, or use an observed rate across files.
   - A single file reads "across files" (`:46,84`).
   - Hours are shown with decimals, such as "555.6–1666.7 hours" (`:67-77`). Use whole units, and days once a range passes about two days ("about 23–70 days"). A long range says it narrows as files are read, so a wide first estimate is not read as a promise.
   - A provider or quota wait with only a local backoff deadline produces a confident range. `uncertain` omits `waiting_for_provider` (`ImportPage.tsx:1068-1073`), and a backoff deadline is not a provider reset time.
   - Show "N of M files done" separately from units and records.
   - Add a distinct **Queued** label.
   - `model_unavailable` must say it retries automatically and when (`reviewQueue.ts:51`, `ImportPage.tsx:965-966`).
   - An identical re-upload reconciles to the existing intake (`intake.ts:1021-1024`) but reports "retained and queued for reading" (`ImportPage.tsx:1641`). Say it was already retained, and give its current state.

   Serves: high-precision tracker (backlog and full-history re-uploads).

5. **Stall accounting must not forgive unproductive work.**
   - When a slice ends on a provider error, all of its active time is forgiven (`intake-batches.ts:1234-1236`); a shared-prerequisite slice is treated the same way (`:1139-1141`). A model that makes no progress on a flaky provider therefore never stalls. Forgive only the failed request's own dispatch-to-failure time, and the wait itself.
   - At restart, migrating a legacy cumulative budget (`:304-308`) spends one of the three stall attempts before any request is sent. When changing a job to `progress-window`, reset its baseline so the first slice starts a full window.
   - **Investigate** (suspected, unverified): the batch chooses the unit its stall streak is bound to at `:983-989` (not completed, no exception, coverage kind not context/unreadable). The assistant chooses its work unit at `intake-continuation.ts:656-657` (not accounted, no exception). If those choices disagree, `item.stalls.unitId` could change every slice and the streak would never reach 3. Write the failing case first. If it reproduces, make both sides use one shared selector. If it does not, record the result here.

   Serves: high-precision tracker.

6. **Provider sign-in waits for sign-in; `model_unavailable` backs off.**
   - Authentication rejection is re-sent every 30 s without any prerequisite change, because `prerequisiteKey` is skipped for authentication (`intake-batches.ts:519-525`). The existing test (`intake-provider-wait.test.ts:181`) never advances past 30 s. Gate authentication on a prerequisite key that changes when the credential or connection is re-established, then continue with no Resume click. This is the one D3 exception. The UI keeps saying to sign in (`ImportPage.tsx:961-962`), but only on the Import page. The app-wide `ConnectionBoundary` (`src/app/components/ConnectionStatus.tsx`) reports the local server, not the model route. While imports wait for sign-in, show a notice the person sees on any page, linking to the model connection settings, and clear it when reading resumes. **Why:** the high-precision tracker leaves a backlog running and moves on; a wait that is visible only on one page can last for days unnoticed.
   - `model_unavailable` retries every `providerRetryBaseMs` (5 s) with no growth (`:624-630`, `:1056-1060`). Use the shared exponential backoff.
   - Delete the dead branch `modelFailure({ message: chat.error })` (`:1239-1251`). `modelFailure` checks `code`, so the branch can never run, and if it did it would pause the whole batch, which D3 forbids.
7. **A wake error must not fail a saved upload.** `intakeBatches?.wake(profileId)` (`intake-routes.ts:213`) runs after the original is retained. If it throws, the client is told a saved upload failed and may upload it again. Catch and record the wake error, still respond 201, and let the enqueue-intent reconciler recover the item.
8. **Capacity exceptions and missing continuation tests** (dropped from CRS-039 R7 and R45):
   - A failed inventory becomes one file-level exception (`intake-batches.ts:738-747`). That is honest when the page count is unknowable. Investigate whether a named bound such as `maxReferences` or `maxIndexOutputBytes` (`intake-files.ts:12-24`) can fail inventory for a readable large file. If it can, inventory in bounded parts, or list the exact range that could not be indexed as a capacity exception and process the rest.
   - Add tests for: a non-default `sourceStallMs` (no test sets it); an in-flight request that outlasts the no-progress window; a legacy budget across restart; and backoff growth with injected randomness at both 0 and 1, asserting successive delays and the cap.

9. **Stall detection and request deadlines must not assume a model's speed** (owner direction, 2026-09-30; see the performance rule in `AGENTS.md`). The model is bring-your-own, so a small local model can take many times longer per request than a frontier route, and routes will change over the years.
   - The model no-progress window is three minutes of active time (`DEFAULT_INTAKE_READING_LIMITS.activeMs`, `src/server/intake-reading-budget.ts:12-19`, checked at `:130`). It also carries count limits: requests, turns and measured tokens. Verify first whether a slow but productive route can trip the time limit, for example when a unit needs two requests that each take longer than the window and only the second adds progress. If it can, make the stall decision count-based (consecutive completed requests without progress), and keep elapsed time only as diagnostic data. Keep the host-side extraction watchdog (`SOURCE_STALL_MS`, `intake-batches.ts:91`) time-based: it guards local qpdf and OCR steps the app runs, not the model.
   - The per-request deadline defaults to 300 seconds and cannot be set above 600 (`src/server/proxy-model-bridge.ts:584-586`, `docs/setup/model-providers.md`, `docs/setup/environment.md`). Verify whether a slow local route returning a large page response can exceed 600 seconds. If it can, raise or remove the upper bound, or judge liveness by response data still arriving instead of total duration where the route streams.
   - The 15-minute reading slice (`assistant.ts:117`) ends a slice, not the work, and does not consume stall attempts (`docs/import/automatic-recovery.md`). Confirm that under a slow fake route and pin it with a test.
   - Test with a fake provider whose every request takes longer than the current window and still makes progress: reading completes with no stall exception. **Why:** a stall means no progress (D2), not a slow model; a time threshold tuned to today's fast routes would turn someone's local model into a stream of false exceptions.

10. **A packet built from a partly read source says so.** Not verified: [note exports](../../src/server/NOTE-EXPORTS.md) describe retained uncertainty and page locators, but not whether a source with processing-stalled, capacity or unreadable exceptions, or with pages not yet read, is disclosed in the provider packet. Check the export path first. If it is not disclosed, the packet and evidence JSON state for each included source which pages or ranges were not read and why, from the located exceptions this ticket already keeps. **Why:** the receiving clinician ([CRS-130](CRS-130.md#medical-records-practice)) cannot tell an absent finding from an unread page; a packet that reads as complete when it is not is a clinical risk.

## Regression scenarios and their reasons

Use fake clocks, injected randomness, fictional files and fake providers. No paid inference is needed.

- Two files: A waits on the provider while B finishes. Stop, then check that Resume is visible and that Resume restarts A, and do the same after restart. Also Stop with the waiting file at every index. **Why:** Stop is the one person-facing pause (D3), so a stopped file must always be resumable. Today it is lost permanently.
- An injected `SOURCE_TEXT_CHANGED` on the first extraction step retries automatically after a persisted deadline without the "needs your review" wording, while the other files keep reading. A real review conflict still asks for review. **Why:** a race the app can retry is a backoff; telling the person to review untouched text is false and needs a Resume.
- Reprocess on a completed item and on a stopped item either schedules work or says it did not. **Why:** a button that reports success and does nothing is worse than a disabled one. CRS-118 owns the real reopen.
- A 15-file backlog with 14 queued shows a bounded estimate or explains its gap. A single file never reads "across files". A long run shows whole hours or days. A quota wait with no provider reset reads as uncertain. An identical re-upload names its existing state. **Why:** the high-precision tracker plans around these numbers, and a confident but false range misleads more than an honest "unknown".
- A slice of unproductive successful requests that ends in a provider error still counts toward the stall window. A legacy budget restored after restart starts a full window. **Why:** stuckness means no progress (D2). Forgiving the time before an unrelated error, or charging a stall attempt at restart, hides real stuckness or invents it.
- An authentication rejection sends no further requests until the prerequisite key changes, then continues without Resume. `model_unavailable` delays grow up to the cap. **Why:** re-sending a known-rejected credential every 30 s changes nothing and adds load. Sign-in is the one thing only the person can fix.
- A wake that throws after retention still returns 201, and reconciliation later schedules the item exactly once. **Why:** the original is durable evidence; reporting it as failed invites a duplicate upload.
- A locked profile dispatches nothing, and unlock recovers every automatic item, including one that was not at `currentIndex`. **Why:** dormant-until-unlock is correct until CRS-081; recovery must not depend on the cursor position.

Add short why comments to the non-obvious tests, linking to the maintained rationale.
