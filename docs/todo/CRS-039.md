# CRS-039: Productive automatic continuation and bounded large PDFs

Status: open.

Continue productive reading through long files without an arbitrary document-wide page, step or elapsed-time stop. Keep per-operation resource limits, explicit Stop and authorization boundaries. Use observable progress and checkpoints to recover stalled work, retain completed proposals, and isolate unreadable pages.

Retry transient provider limits and interrupted extraction automatically with provider deadlines and backoff. Recover running jobs after restart when authorized unlock occurs; start accepted uploads on the server rather than relying on an open tab. Reconcile unknown provider outcomes where possible; preserve possibly billed attempts and prevent duplicate local publication on retry. A wait is not successful completion.

Cover failed-page retry, human transcription resolving extraction issues, capacity overflow as located exceptions, and progress wording. Lock/logout authority is separate in [CRS-081](CRS-081.md). Former reliability feedback R1–R7, R34, R37–R38 and R45 belongs here.

## Owner decisions

[CRS-126 D2](CRS-126.md#d2-no-size-or-time-limits-on-reading-detect-stuckness-instead) and [D3](CRS-126.md#d3-waits-are-backoffs-never-pauses): no size or time limit on reading, stuckness means no progress for a period, and waits are backoffs. The person never needs Resume except after **Stop imports** or to fix something only they can, such as provider sign-in.

**Why:** a high-precision tracker importing a long history should not have to babysit arbitrary page or time allowances. Progress-based recovery isolates work that is actually stuck while retaining productive work. Provider waiting is a lack of available service, not proof that a source page failed; it must not exhaust the local stall counter. Unknown outcomes remain possibly billed so automatic retry is honest about usage and cannot publish twice. The paired authorization rationale is recorded in [CRS-126 D8](CRS-126.md#d8-leaving-does-not-revoke-already-authorized-import-work). The five-second backoff and three-minute watchdog defaults below are engineering choices that can be tuned without reopening those product decisions.

## Implementation specification

The owner decisions above are authoritative. The defaults below are engineering choices for implementation and deterministic testing, not additional owner approvals or measured optimal settings.

### Scope and current code

Implement reliable serial processing first. Keep the existing per-profile model serialization and current shared extraction limits; parallel clinical workers belong to CRS-086. Authorized background work can continue after the browser tab closes. General archive authorization is still revoked on lock/logout; processing under a separate scoped authority remains CRS-081. Recovery after process loss begins only after authorized unlock.

### Decided behavior and dependency on CRS-081

Continued import processing after logout or profile switch is already required by CRS-126 P15 and scenarios 2/14. The separate tickets divide implementation responsibility; they do not leave that product decision open. CRS-039 supplies durable scheduling, automatic-run intent, checkpoints, retries and recovery. [CRS-081](CRS-081.md) supplies the restricted authorization and runtime lifetime needed to execute that same work after general session access ends. It must reuse this coordinator rather than create a second queue or retry loop.

Define the shared authorization boundary while implementing CRS-039: the coordinator must check current permission for the exact profile/job/operation at dispatch and publication, independently of whether that profile is selected in the browser. Before CRS-081, only the existing unlocked/session-authorized path can grant permission. After CRS-081, a valid scoped import authorization may also grant the limited processing operations it explicitly covers. Ordinary clinical acceptance, identity confirmation, browsing and unrelated profile mutations still require a live authorized user session. Durable automatic-run intent alone never grants access.

CRS-081 depends on this scheduler/recovery contract; its authorization work may proceed in parallel once the boundary is agreed. CRS-039 can land as a separately useful increment, but cannot be reported as completing the entire “leaving is not stopping” experience. Completion of CRS-126 scenarios 2/14 requires both tickets and the cross-ticket journeys listed in CRS-081. Until then, describe locked work as waiting for unlock, not as continuing in the background or as requiring a manual Resume after unlock. If CRS-039 lands first, repoint CRS-081's dependency to the maintained implementation contract when deleting this ticket.

Current responsibilities:

- `intake-batches.ts`: scheduling, durable batch/item transitions, provider waiting and source capture. It currently has the five-retry cap, cumulative capture allowance and restart-to-paused behavior.
- `intake-model-attempts.ts`: provider dispatch/terminal evidence and unknown-outcome accounting. Unknown attempts currently prevent all subsequent dispatch.
- `intake-source-extraction-operation.ts`: idempotent extraction operations and interrupted receipts. Preserve its operation identities while adding automatic recovery coordination.
- `intake-reading-budget.ts` and the assistant request guard: bounded slices and reading progress. A slice boundary yields and continues; it must not impose a total document limit.
- `intake-batch-journal.ts`, `shared/intake-batch.ts`, intake routes and runtime/profile lifecycle wiring: durable recovery state, server-side enqueue and authorized wake-up.
- Import activity and batch hooks: display state from the server and issue explicit Stop/Resume actions. They no longer own automatic scheduling.

### Durable state and transitions

Separate processing intent from observed execution state. Persist automatic-run intent, explicit user Stop, the current located work unit/checkpoint, last durable progress marker/time, consecutive no-progress attempts for that unit, and the scheduled retry deadline/reason. Keep these as small journaled records proportional to the changed state; do not copy document text or a growing receipt history into every transition. Existing original, proposal and attempt receipts remain authoritative.

- Accepted upload -> durably queued -> running when the profile is authorized and capacity is available.
- Running -> waiting with an absolute `retryAt` for a transient/provider/capacity wait -> running automatically when eligible.
- Running -> needs user action only for something automation cannot repair, such as provider authentication. Keep other eligible work runnable. When the prerequisite is fixed, recover work with automatic-run intent; a separate Resume click is not required.
- Running -> located exception when a particular unit is reproducibly unreadable, unsupported or repeatedly stalled -> continue with remaining units/files.
- Any authorized active/waiting state -> stopped only on explicit Stop. This clears automatic-run intent and cancels queued timers and in-flight work where cancellation is supported. Resume explicitly restores intent.
- Process loss or loss of all applicable processing authorization -> dormant durable work. Authorized unlock restores eligible automatic-run intent and reconciles in-flight receipts before dispatch. Explicitly stopped jobs stay stopped. After CRS-081, ending general session access alone does not revoke a still-valid scoped import authorization; explicit revocation of that authority does.
- No runnable or waiting units and all source regions accounted for -> done, or done with exceptions. Provider waiting and needs-user-action states are never successful completion. Extraction/model completeness claims remain governed by the existing coverage contract.

Add semantic fields with backward-compatible journal decoding; the exact internal enum representation can reuse existing statuses. Historical `stopped` records remain stopped. Historical machine interruption, provider-wait and allowance reasons can recover after unlock; an unrecognized historical pause reason stays visible for explicit review rather than being guessed to authorize work.

### Retry and provider outcomes

Use structured provider classification rather than error-message substring matching to authorize retries. Authentication, policy refusal, malformed requests and unsupported capabilities are actionable failures; plain 429/503, connection loss and shared-capacity waits are recoverable. A context-size failure reduces/restructures the bounded request while retaining all unresolved source regions; it must not discard evidence or repeatedly resend the same oversized request.

Start transient retry delay at five seconds, double up to five minutes, and apply injected equal jitter between half and all of that delay. Honor a provider's later `Retry-After`/reset deadline even beyond five minutes. Persist the actual deadline before scheduling; restarting must not reset every job to an immediate retry. Tests inject clock and randomness. Reset the consecutive failure backoff after durable progress or a completed usable request. Provider waiting has no attempt-count or document-time cap and does not count as a local extraction stall.

For unknown outcomes, retain the original attempt as unknown and possibly billed. First use a supported provider reconciliation/idempotency mechanism or a recoverable local result. If no result can be established, D3 requires automatic backoff and retry with a new physical request identity. This can consume usage twice; do not silently label the unknown attempt rejected, free or resolved. No automatic paid-credit purchase or provider/model switch is part of recovery.

Separate permission to retry from the old attempt's accounting outcome. Persist a recovery decision linking the replacement attempt to its predecessor and logical work unit. Permit only one current replacement for that unit; restarting the coordinator must reuse the decision instead of creating another replacement. Late responses are recorded against their actual attempts and checked against current authorization, generation, source dependencies and work-unit ownership before publication. A usable result commits at most once for that logical unit; a late stale/superseded response cannot publish duplicate proposals or bypass Stop.

### Progress, stalls and extraction

Remove cumulative document-wide step, elapsed-time, request and token limits from automatic continuation policy. Keep accounting and bounded individual operations, context windows and shared-capacity limits. A productive yield schedules its next slice automatically with the same durable checkpoints.

Progress means newly committed source coverage/disposition, a completed located extraction unit, a new accounted reading unit, or a newly retained candidate/version. Polling, rereading unchanged content, repeated identical proposals, creating retry receipts and merely starting requests are not progress. Track unique logical progress; retries do not reset the watchdog by incrementing counters alone.

For local extraction, start the no-progress watchdog at the greater of three minutes or twice the configured per-step timeout, so the existing raster/OCR operation deadline can report first. Do not apply that threshold to provider waiting or a legitimate inference request still within its separate request deadline. On a local stall, cancel the attempt, preserve its interrupted receipt, and retry from the last committed unit checkpoint with a new operation identity. A successful unit resets its streak. After three consecutive no-progress attempts for the same unit, record a located exception and continue elsewhere. A global environmental failure, such as a missing decoder, is reported once as a shared prerequisite rather than launching identical failing work on every page.

Apply a separate no-progress policy to model reading, including completed successful requests that repeatedly reread or propose identical content. Bind each reading attempt to an unresolved plan unit or exact bounded group of units before dispatch. Persist its distinct progress baseline, active no-progress duration and stall streak. Start with a three-minute active no-progress window; provider/capacity backoff, queued time and locked/dormant time do not consume it. A legitimate in-flight request retains its existing per-request deadline: when the no-progress window expires during that request, wait for its terminal outcome before deciding whether progress occurred. At the next dispatch boundary, renew the window only for new durable logical progress, never merely because a request succeeded, a slice ended or the model started another turn. Request timeouts/unknown outcomes still use the provider-outcome recovery rules rather than falsely declaring the source unreadable.

When the active model window expires without progress, end that reading attempt, retain its proposals and usage, and automatically start a fresh bounded reading context from the committed checkpoint for the same unit. After three consecutive such stalled attempts, record a located **processing stalled** exception and continue other eligible units/files. This is unresolved extraction, not evidence that the original is unreadable or fully processed; retain its exact scope for later retry. Do not attach a document-wide exception merely because the model failed to identify a unit. The coordinator must retain the dispatch scope needed to locate it. Repeated provider errors follow provider backoff and do not increment this model-stall streak. Both productive reading and long legitimate requests can exceed three minutes; the rule limits repeated unproductive completed work, not total reading time.

Replace the old `readingBudgetReached`/request-boundary manual-pause path with this continuation policy, including persisted cumulative and progress-window jobs. Retain request/slice resource bounds and lifetime usage counters for scheduling and accounting; a boundary automatically yields or runs the no-progress recovery decision instead of requiring Resume. Test fake-clock model success without unique progress, not just a hung extraction tool. A new candidate version with unchanged substantive content and an identical already-accounted read cannot renew the window.

Retry failed extraction units without losing completed pages. Explicit human transcription may resolve the matching OCR-unavailable issue only after the existing original/text review validation; it must not claim OCR succeeded or silently resolve unrelated issues.

Replace any total evidence-store ceiling that can be handled with bounded partitions using those partitions. If a remaining hard storage/decoder limit prevents processing, list the exact affected page/member range as a capacity exception, preserve the original and process eligible remaining work. Never label unread regions complete or silently omit them. Test continued processing beyond the former ten-step and 120-second capture allowances.

### Enqueue, wake-up and scheduling

Make retaining an upload and recording its pending processing intent crash-recoverable together. Persist an enqueue intent keyed to the retained delivery and logical operation; a server reconciler ensures the batch exists exactly once. If a crash falls between retention and queue creation, authorized recovery repairs it. Prepared originals that need no conversion still enter the existing review workflow without an unnecessary model request.

Connect wake-up to authorized runtime/profile restoration, accepted upload intent, elapsed retry deadlines and resolved prerequisites. Do not depend on a GET request or an open Import tab to start work. The existing batch-create API and older clients' enqueue calls must reconcile with the same intent rather than creating duplicate jobs.

While one file waits, allow unrelated eligible files to make progress without exceeding existing model/extraction concurrency or a shared provider limit. Choose the next eligible item fairly; no timer may monopolize a profile. Persist deadlines rather than serializing timers. Use generation and current-authorization checks on every delayed continuation and publication so Stop, deletion, revoked processing authority and changed source scope win races with retries. A browser profile switch must never retarget a job to the newly selected profile. Lock revokes the ordinary session path; CRS-081 defines the separate limited authority that may remain valid.

### UI and diagnostics

Distinguish queued, extracting/reading, retrying, waiting for provider, needs user action, stopped, done and done with exceptions. Show the reason and next attempt/reset time when known. A technical interruption must not say the source needs human transcription unless it actually does. Reserve Resume for explicit Stop or historical states whose intent cannot be recovered safely.

Display pages/units accounted for and exceptions separately from saved clinical records. Show “Estimating…” until there is a useful rate, then a range that includes known waiting time and combines files. Unknown provider availability means an uncertain estimate, not a fabricated finish time. Expose unknown/possibly billed attempts through existing bounded diagnostics without document content or credentials. Keep independent explicit clinical acceptance and existing source-staleness guards.

When an unknown-outcome retry is relevant, show a concise activity explanation such as **The previous request's result is unknown; retrying may use additional provider usage**, alongside the existing Stop control. This makes the approved automatic recovery understandable without adding a recurring confirmation, usage cap or invented price estimate.

### Implementation sequence and acceptance

1. Add backwards-compatible durable intent/recovery fields and deterministic state-machine tests.
2. Implement provider retry/reconciliation accounting and one-publication guards before removing the unresolved-attempt dispatch block.
3. Replace capture allowances with unit progress/stall recovery; verify existing extraction operation replay and source dependency guards.
4. Move enqueue/wake-up to the server and authorized unlock lifecycle; retain compatibility with existing clients and persisted batches.
5. Update activity UI and diagnostics, then run complete interrupted-import journeys against retained fictional state.

Completion requires all of the following:

- Six or more consecutive transient rejections eventually recover; a future Retry-After is honored across restart, and jitter is deterministic in tests.
- Unknown outcome followed by retry, late success, crash between attempts and repeated recovery all preserve accounting and publish each logical result at most once.
- The same local unit stalls three times, becomes a located exception, and later units still run. Productive files exceed former step/time allowances without manual Resume. Repeated identical work cannot fake progress.
- Repeated successful model calls with no distinct progress exhaust the active no-progress window, retry the located unit automatically, then produce a processing-stalled exception after three stalled attempts. Other units still run. Unique durable progress resets the streak; provider backoff does not consume the window or streak. An in-flight request is allowed its request deadline and its eventual progress is evaluated before a stall decision. Persisted legacy reading budgets cannot restore a manual-pause dead end after restart.
- A real server process is stopped/restarted against the same encrypted fictional profile. Without CRS-081's scoped authority, no work dispatches while locked; authorized unlock recovers automatically; an explicitly stopped job remains stopped. Closing the browser tab alone does not stop work. Once CRS-081 is integrated, add its locked-profile authorized-worker versus unauthorized-session checks rather than removing the access checks.
- Crash between upload retention and enqueue is recovered once. Duplicate client create requests do not start a second import.
- Stop, lock, deletion, source correction and person/profile changes racing a late provider/extraction result do not publish stale or unauthorized work.
- Full files, repeated uploads and multi-file imports preserve original bytes, existing proposals, exact clinical ownership and acceptance receipts, with bounded journal growth.
- Mounted/browser tests verify the distinct wait, action-required, stopped and completion states; no waiting file is reported done. Existing source and clinical acceptance tests stay intact.
