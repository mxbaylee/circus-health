# 🛡️ CRS-084: Prioritize security recommendations

Status: open. The implementation lead assesses risk evidence, sizes and order under the 2026-10-16 persona/Operator/record-integrity delegation. Personal rollback and key-compromise risk acceptance remain separate owner decisions.

## User Story

As an [Operator](../design/personas.md#operate-and-recover),
I want to understand and prioritize the remaining risks to my family's records,
So that I can choose protections and recovery practices without mistaking proposals for protection already in place.

## Plain-English User Walkthrough

1. Read each remaining risk with the evidence for present safeguards and their limits.
2. Review the evidence-backed likelihood/impact assessment and recommended work order prepared for my household.
3. Review unresolved backup, compromised-key and future-access choices separately.
4. Follow links to the resulting protection work; implemented controls are documented in the security reference.

## Acceptance Criteria

- **Given** the current register and additional risks below, **When** prioritization finishes, **Then** every risk has lead-assessed likelihood/impact sizes and a reasoned position under delegated persona and Operator guidance, with each Large/Large risk linked to its own open ticket.
- **Given** existing integrity, backup and security mechanisms, **When** risks are assessed, **Then** current code/tests and maintained documentation support each evidence claim; restore success is not freshness proof and clinical correction history is not a sign-in log.
- **Given** unresolved rollback or compromise-driven key-rotation choices, **When** recommendations are presented, **Then** those decisions stay explicit and no proposed worker key, emergency grant or sign-in monitoring is described as deployed.

Prioritize the current [security risk register](../security/model.md#residual-risk-register). Track proposed protection here rather than presenting it as deployed: every control below is a proposal until it is implemented and described in maintained security documentation. Re-check each register entry against current code as it is sized, including automatic recovery, partial saves, ownership corrections and independent restore evidence; an older risk assessment is not proof of the current boundary.

- Contain deployment and credentials; restrict anonymous costly probes, setup/activation and session resource use.
- Bound recovered-read memory and preserve uncertain-save recovery.
- Review session expiry, TLS/cookie/origin handling, CSP/framing, parser isolation and plaintext lifetime.
- Verify independent backups, version freshness and restore procedures. Archive rollback protection and compromise-driven data-key rotation require separate recovery decisions.
- Evaluate adversarial model/tool use and provider disclosure without promising perfect semantic detection.

Risk IDs R1–R11 in the security reference are separate from CRS identifiers and from the reliability review's R1–R52; write them as "security R3", not a bare "R3".

## Decision and why

**Ranking** (owner, 2026-09-30): size each risk's likelihood and impact as T-shirt sizes, S, M or L. Every risk that is Large likelihood and Large impact gets its own ticket, to be prioritized. That earlier decision assigned relative sizing to the owner; it did not replace the register's evidence column. The 2026-10-16 delegation now assigns this routine assessment and ordering to the implementation lead, while preserving the S/M/L method, Large/Large ticket rule and personal risk-acceptance questions below.

## Risks and mitigations to add and size

These are not in the register yet. None of the mitigations below exists today.

- **Import worker key** ([CRS-081](CRS-081.md)): a job-scoped key lets a worker write encrypted checkpoints for one profile while another is unlocked. It is a new credential that outlives the ordinary session. Size its exposure if the host is compromised, and how Stop, revocation, deletion and process loss end it.
- **Emergency-contact break-glass access** ([CRS-145](CRS-145.md)): an emailed one-time code proves identity but cannot decrypt, so the patient must grant a separate key in advance. It adds an outside email service and a standing grant. Size the grant's misuse and the email channel; a pre-prepared emergency packet is the low-tech alternative available now.
- **Sign-in log** ([CRS-146](CRS-146.md)): showing every sign-in and failed attempt to the patient is a proposed detection control, not an existing one. Size which risks it helps detect, for example an unlock by someone else holding the recovery key or an authenticator, which nothing shows the patient today. A failed attempt happens before unlock, so its log sits outside the encrypted profile and must hold no health data.

## Owner decisions needed

- The size of each risk and resulting order were previously owner-only questions; the lead now resolves them under the delegation above.
- **Archive rollback protection** (security R3): whether to add an independent freshness anchor, and what recovery from an old copy should then allow.
- **Rotating the data key after a compromise:** whether to support it, and what happens to old backups and wrappers that the old key still opens.

## Operator readiness additions (grooming proposal, 2026-10-02)

For [operate and recover](../design/personas.md#operate-and-recover), distinguish the implemented integrity mechanisms from the implemented [independent backup/restore qualification](../setup/archive-restore.md) and the [safe release-update/refusal/recovery procedure and bounded qualification](../setup/release-updates.md). An authenticated old copy can restore earlier clinical state and removed passkeys; neither encryption nor a passing restore drill proves freshness. Retain the owner decisions on an independent freshness anchor and compromise-driven key rotation. Record backup/recovery-key retention and restore limitations plainly, without promising forensic erasure or deciding a schedule here. Clinical actor/time history is separate from CRS-146's still-proposed unlock-attempt detection. No new remote deployment or household administrator identity is assumed.
