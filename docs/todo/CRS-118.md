# CRS-118: Precise source dependencies

Status: open. An agent can do it.

Pin interpretations to the evidence actually consumed: owned source pages/spans plus report headers, subject/date/units context, relationships and amendments. Final citations alone do not describe every dependency.

Appending unrelated source text must not stale existing work. Material changes must invalidate affected unaccepted proposals and approval state, including package relationships; unknown dependency coverage must invalidate conservatively. Preserve accepted history. Verify sibling publication, late responses, source corrections and acceptance races. This consolidates reliability R8 with the async processing requirements.

## Where it stands

The core has not landed: proposals are still pinned to the whole source revision.

A stopgap from the automatic-continuation work (CRS-135) keeps those pins stable instead. `beginItem` in `src/server/intake-batches.ts` finishes a file that already has a reviewable proposal as `review_ready` (`already_reviewable`) before any further source capture or model dispatch ("Never mutate source-text pins after an existing reviewable proposal."). The test "an existing reviewable proposal prevents automatic text continuation from staling its pins" (`intake-automatic-source-capture.test.ts`, near `:167`) asserts no dispatch, an unchanged source revision and a `review_ready` item.

That trades completeness for stable pins: later pages of such a file are neither captured nor read, a gap against [CRS-126](CRS-126.md) P3 (never drop silently) and P17 (keep the complete extracted text). [CRS-115](CRS-115.md#where-it-stands) and [CRS-086](CRS-086.md#prerequisites) note the same gap. Removing the stopgap belongs to this ticket's done condition.

## Review findings, 2026-09-28 (R8)

Proposals are pinned to the whole source revision. `invalidateIntakeSourceTextDependencies` and `nextPin` in `src/server/intake-source-text-dependencies.ts` write a new pin (revision ID and dependency token) on every material revision, and the source-text save calls it inside the revision's transaction (`intake-source-text.ts`, near `:959`). Without the stopgap above, background capture of page 300 would therefore stale proposals from page 2. Pin each proposal to the page hashes and context it consumed, and invalidate only those whose inputs changed. This is a prerequisite for [CRS-086](CRS-086.md): with revision-wide pins, sibling workers stale each other's work.

## Issue-to-field dependencies

Moved from [CRS-116](CRS-116.md) on 2026-09-30. A review issue (a warning or question about a proposed record) depends on particular fields and source evidence. Record which fields and which consumed evidence each issue depends on, so that a source change or a field edit reopens only the issues it affects, and an acceptance racing an issue's change is rejected rather than accepting against a stale resolution.

## Carried from the incremental-writes work, 2026-09-28

The intake's source pin (current material revision, dependency token, "requires interpretation" flag, revision count) now lives in its own record, `intake_source_pin:v1:<intake>` (`src/server/intake-source-pin.ts`), so a source change no longer rewrites the intake row with its proposals. Change what the pin records (the pages and context each proposal consumed), but keep it out of the intake row; moving it back would reintroduce per-write copies of every proposal. See [record versions](../data/record-version-storage.md#source-text-write-amplification).

[CRS-129](CRS-129.md) needs the same per-page consumption data to record source verification state separately from staleness; design the two together.

## Terminal batch invalidation

Source corrections after a batch finishes need an explicit coordinator transition. Currently `createIntakeBatchManager.create` reconciles an already-owned original to its retained batch even with a new operation ID, and `resume` cannot reopen a completed `review_ready` item. Corrected evidence is rejected as stale at review, but re-enqueueing alone does not start another reading pass. Define and test reopening affected work while preserving original-operation replay, durable ownership, explicit Stop intent and accepted history. Fresh replacement evidence must close the reopened work without an endless rereading loop. The readiness fixtures in `intake-source-batch-readiness.test.ts` cover current/stale/fresh evidence at first enqueue; they do not establish this post-completion transition.

This overlaps [CRS-140](CRS-140.md#owner-decisions-needed)'s open owner question about Stop on an item already `review_ready` with paused reading: make it resumable there, or leave it to this reopen. Decide the two together.

## Completion

Done when proposals are pinned to the evidence they consumed, unrelated appended text stales nothing, the stopgap in `beginItem` is removed so capture and reading continue past an existing proposal, and the terminal reopen above is defined and tested. Describe the dependency rule in maintained import documentation before deleting this ticket.
