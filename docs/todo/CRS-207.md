# 🔎 CRS-207: Exact incremental source-search projection

Status: open. Search prerequisite split from high-effort CRS-205. Unblocks [CRS-209](CRS-209.md). Current source search uses path LIKE or the entire serialized details JSON LIKE, with the same predicate for count and page queries.

## Contract and proposed design

Preserve exact current source-search matches without retaining a growing full serialized workflow in a rewritten durable or SQLite row. A proposed implementation is a disposable serialized-text rope: bounded content pieces, stable occurrence/link rows and a small selected head, excluded from accepted-record capture. A request may reconstruct candidate serialized text to evaluate SQLite LIKE; it must not hydrate every operational intake JSON object. Initial authoritative reconstruction may hydrate each view once. This design is a proposal, not a claim that locality is already proven.

## Acceptance

1. Preserve path OR details matching, embedded % and _ wildcards, SQLite ASCII case/non-ASCII behavior, JSON punctuation/escaping and matches crossing keys, values and piece boundaries. Preserve visibility/provider filters, path ordering, count, pagination and source-file details DTOs. Compare with the current SQL over the exact serialized envelope, including property order and unusual Unicode. Per-field tokens or FTS are not equivalent substitutes.
2. Define how exact serialization is reproduced from durable authority after restart/cache loss. Current intake-state fingerprints sort object keys and its generic delta ignores pure key reordering; semantic fingerprint equality alone does not establish byte/LIKE parity. Preserve relevant order as changed evidence or prove the applicable writer contract makes it invariant. Do not silently change public search semantics or make disposable search rows the sole owner of required ordering evidence.
3. Implement and prove change-local piece/link updates for a small insertion/deletion, multiple distant edits, duplicate/periodic text, max-sized boundaries, reorder/moves and surrogate/UTF-8 boundaries. Fresh global content-defined chunking alone may shift all periodic boundaries and is insufficient proof. Retain prior anchors or splice a validated serialized delta; never rewrite a growing occurrence list into one row. Count initial bytes, changed content/link bytes, rows, rereads, reconstruction, serialization/diff and copy work separately at 100/200/300 sizes.
4. Keep projection freshness, profile and selected-authority binding explicit. Changes share the caller's transaction; rollback/reopen/cache-loss/private copy yields identical search results. Rebuild only derived data; corruption or absence of durable authority must fail rather than fabricate an empty workflow. No persistent derived-table trigger may break copy or cache reconstruction.
5. Ship a coherent tested search adapter against current source authority if that can be done without duplicating growing writes. The subsequent activation ticket must integrate its authoritative serialization contract. If bounded locality or integration still needs multiple designs, split this ticket before implementation instead of accepting a full-snapshot fallback.

No authority cutover or heavy import retry is part of this slice. The existing source details may remain large until [CRS-209](CRS-209.md); [CRS-210](CRS-210.md) must measure the combined path.

Validation uses fictional data, focused local tests, formatting/type checking, full PR CI and independent grading. Before implementation, reassess effort and split again if the remaining work exceeds medium effort. On completion delete this ticket and its index entry, document implemented behavior and repoint dependents.
