# ⚙️ CRS-086: Async artifact processing with bounded context

Status: open.

## Independent production requirement

Async artifact processing, bounded model context and safe adaptive scheduling are necessary independently of a large-document trial (owner clarification, 2026-10-01). This ticket remains the implementation requirement and is marked for production. Preparatory design can advance while [CRS-196](CRS-196.md) prepares downloadable diagnostics and its unpaid scripted 900-page baseline. Run that current baseline before writing the full implementation specification below; the paid-provider qualification and owner trial are not prerequisites for beginning async implementation once that specification is ready. CRS-196's diagnostics readiness supplies an instrumented serial baseline for this ticket's before/after work-count validation and identifies separate production fixes. Preserve the concurrency prerequisites below. Large-upload qualification and owner feedback belong in CRS-196 rather than replacing this implementation scope.

## Processing implementation

Replace serial clinical processing with bounded artifact work that reuses durable source extraction and supports overlapping report/header context, explicit requests for more evidence, compaction and reviewable aggregation. Use model-agnostic code defaults; model suggestions may adjust useful scope but cannot establish provider/account limits. Avoid an extra startup inference call.

Adapt concurrency and sizing to verified capabilities, actual rate/overload signals and observed progress. Share upstream limits across applicable work, preserve fair scheduling and account for retries and unknown usage. Do not widen ownership across known person/report boundaries or silently skip source content.

Preserve idempotent publication, dependency checks, originals, accepted history, cancellation and authorization. Incremental source-text writes ([implemented](../data/record-version-storage.md#source-text-write-amplification)), [precise source dependencies](../import/processing.md#durable-evidence-and-review-boundaries) and the implemented [automatic recovery contract](../import/automatic-recovery.md) are related work.

No additional broad optimization campaign is a prerequisite: these documents are mostly separable artifacts with some shared headers and cross-page relationships. Validate mechanics and domain edge cases, then compare work counts and quality on a small paired fictional workload. Historical results are evidence, not a universal optimum. No new live runs or paid credits are authorized by this TODO.

## Prerequisites

These are required before parallel clinical workers, not merely related:

- Preserve [measured page/span source dependencies](../import/processing.md#durable-evidence-and-review-boundaries) when parallel workers capture related text. Unrelated capture can leave an earlier proposal current; unknown coverage still uses the whole-source pin, so do not infer a narrow dependency from a model citation.
- Preserve the implemented [provider-wait and unknown-outcome recovery](../import/automatic-recovery.md#provider-outcomes) under concurrency: retries have no attempt cap, unknown usage stays retained, and only one replacement owns publication for its unit. A unit that keeps timing out cools down instead, through its own backoff, lower concurrency or a longer deadline, as [CRS-140 requirement 1](CRS-140.md#requirements) specifies (owner, 2026-09-30).

## Measure first

Count the work, per `AGENTS.md`; never set a pass/fail bound in seconds for model work. Begin with [CRS-196's scripted full-size baseline](CRS-196.md#scripted-full-size-baseline-before-the-async-specification), using the current pipeline and no paid inference. This is one baseline, not a broad campaign; local-extraction counts also need no paid inference. Later adopted-route measurements need their separately scoped owner authorization.

- **Model requests** (absorbs CRS-079, 091 and 092): from one long-import diagnostics export (`CRS_QUALIFICATION_SCENARIO=long`, `CRS_QUALIFICATION_FORMAT=auto`, `CRS_QUALIFICATION_REPEAT=1`; see [representative provider qualification](../import/import-performance.md#representative-provider-qualification) and [page attribution](../import/import-performance.md#page-attribution)), report model requests, attempts and retries per unit, input, cached and output tokens per request, and rereads per page. Attribute each request's input by message/tool category and page count, show how it grows with pages already read, and compare it with the parameters in `src/scripts/processing-cost-model.ts`. Provider waits and elapsed time are observations of one installation, not targets; relate tokens to requests, not to latency.
- **Local extraction** ([CRS-109](readme.md#crs-109)): on one long scanned and one long native fictional file, count text-layer, raster and OCR pages, extraction-step timeouts and retries, and queued units. Host time may be reported only as a coarse ratio on the same machine. Local extraction has one raster worker, with a 75 s raster timeout (`SOURCE_RASTER_TIMEOUT` in `intake-source-extraction.ts`) and a 60 s OCR timeout (`intake-source-ocr.ts`). If most host work is OCR, more local workers help scanned files and parallel clinical workers do not.

Candidates to measure the same way, whose counts also inform [CRS-083](CRS-083.md)'s laptop-or-hosting decision (owner, 2026-09-30):

- Async/background processing with bounded context (this ticket), against today's serial request history, measuring the compaction already implemented rather than assuming every prior payload is resent unchanged.
- The Bifrost gateway instead of LiteLLM, now one option in [CRS-089](CRS-089.md) (a lighter, less patched gateway): added requests, retries and bytes per model request. The supported setup stays on LiteLLM unless a replacement is implemented and verified.

## Usage

Concurrency spends the same tokens sooner: it raises the rate against usage windows, not the total. Splitting work can raise the total, through repeated fixed request overhead (about 70,000 characters of system, tools and schema, as estimated in the T1 brief), duplicated header and identity context and merge passes. In the scripted 800-page run, two-page units used 1,222 requests and about 988M characters against 896 and about 393M for ten-page units. Bounded fresh contexts can lower the total by not resending history. Size concurrency against the route's window (the subscription route's windows are unpublished; see [CRS-107](readme.md#crs-107)), not only against 429s.

## Rules carried forward

From the retired [implementation specification](https://github.com/mxbaylee/circus-health/blob/2ae9a0f6f158bcf274d86b2a771d223bc14e4a6e/docs/import-processing.md#6-batching-context-and-execution-policy) and the earlier CRS-086 entry, archived at `2ae9a0f`:

- Keep three units separate: physical extraction work, clinical interpretation work and proposal publication.
- Every source region has exactly one owned disposition. Overlapping context is allowed but never creates duplicate ownership, records or coverage credit. A page too large for one request becomes located sub-page units with parent coverage, or an exception.
- Never skip first/middle/last, administrative, repeated or re-exported pages. Fingerprints may support reuse or reconciliation, not omission.
- Before dispatch, assemble the actual request and account for system/tool overhead, source text, context, images and an output reserve. Persist the estimate, method, route limits and margin, and pin them in the plan. Never silently truncate text, tools or images.
- A continuation summary, notebook or compaction is navigation only: never evidence, never quoted as page text.
- A missing header or unresolved date relationship stays unresolved; aggregation may not borrow it from a nearby record.
- Whole-document reading is an experimental alternative until the paired route comparison succeeds.

## Foreground usability acceptance

Make the repository's interactive-responsiveness requirement explicit in this implementation (owner follow-up, 2026-10-01). While a long import is capturing, interpreting, waiting on the provider or recovering, the person can browse saved records, open available evidence, review available proposals and submit foreground chat. An active background response alone must not reject chat with `ASSISTANT_BUSY` or occupy the profile's response slot for the entire import. Shared provider limits still apply; expose genuine waits and queue foreground model work fairly, without promising a response while the provider is unavailable.

Verify these journeys in the mounted/release UI with independently fictional content, including review and acceptance during continuing publication, relevant versus unrelated source changes, cancellation and profile authorization. Count answered interactive requests, queued work, dispatches and contention; compare host responsiveness with an idle baseline on the same machine. Preserve review-before-acceptance and dependency checks. CRS-196's measurements reveal failures, but recording contention does not satisfy this acceptance requirement.

## Proposal: progressive review during a long import

Proposed on 2026-10-01; the exact publication policy remains to be decided before implementation. Make safely completed proposals reviewable while other units continue, rather than requiring whole-document completion before any useful review. Specify when report/header, identity and cross-page dependencies are sufficiently resolved to publish, how incomplete scope is disclosed, and what later evidence invalidates or updates. Do not imply that an early proposal establishes complete or correct interpretation of the report. An accepted record remains durable; later evidence follows the existing reviewed-version contract.

Use CRS-196 to measure work until the first reviewable proposal and the first correctly reviewable result against a fictional oracle, separately from full-document completion and user acceptance. Count pages captured, requests, retries and input tokens at each milestone; elapsed rates are installation observations, not model-time pass/fail bounds. This proposal is not an additional release blocker until its behavior and acceptance criteria are settled.
