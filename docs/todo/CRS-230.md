## Investigation already grounded in the tested source

The supplied checkpoint records the following source inspection. Review the exact tested revision, then compare any proposed fix with current `main`:

- [`core.ts`](https://github.com/mxbaylee/circus-health/blob/b5f6347e43a9a93a7a597e78d57891cb554f9258/src/app/passkey-checker/core.ts): `createCredential` reuses the run's `user.id`, `user.name` and `user.displayName` for A/B. It includes existing credential IDs in `excludeCredentials`. The A/B alias is not included in the native account display fields. Therefore identical display labels are a concrete usability investigation target; merely making them more specific does not remove the exclusion.
- The same source restricts confirmation and fresh-use requests to the selected credential in `allowCredentials`. It compares the returned `rawId` before extracting PRF output. Keep the mismatch refusal; do not accept another credential to turn the reported failure into a pass. A mismatch report does not reveal which other credential was returned.
- [`passkey-prf.ts`](https://github.com/mxbaylee/circus-health/blob/b5f6347e43a9a93a7a597e78d57891cb554f9258/src/app/components/passkey-prf.ts): `withBinaryPrf` converts JSON/base64url salts into binary inputs. `prfFrom` already handles strict 32-byte buffers/views, canonical base64url and complete plain-byte arrays. The exported “No valid 32-byte PRF result” message combines absent and rejected results; it does not prove a malformed input, a particular output shape, or universal lack of provider support.
- Confirmation uses `prf.eval`; subsequent uses use `prf.evalByCredential`. The Proton runs failed during confirmation and never reached the fresh-use path, so they cannot establish an `evalByCredential`-specific failure.

The owner additionally reports that Proton's **“input format was wrong.”** Preserve this as an unresolved observation: establish which input or prompt, the expected versus actual format, and a safe reproduction. Do not silently reinterpret it as a proven PRF input-type bug or confuse it with the PDF/Markdown export format.

The Google/Chrome second-registration result is consistent with intentional exclusion of an authenticator already holding A. [Google's duplicate-registration guidance](https://web.dev/articles/webauthn-exclude-credentials) describes that refusal. It is a hypothesis about this run, not proof of a Google defect; Firefox's unclassified result does not establish the same cause. Check whether the selected provider/authenticator already holds A and distinguish a synced copy from a genuinely independent credential.

[WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) defines binary PRF inputs, credential-keyed evaluation, and registration exclusions. Preserve the same-profile identity and exact credential/salt association. Changing `user.id`, dropping exclusions or weakening verification merely to force a green second test is not an approved fix.
