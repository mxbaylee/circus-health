# Conversation journal

Conversations use the current `health-chat-delta-v2` journal in `src/server/assistant-journal.ts`, with generic JSON decoding in `chat-journal-codec.ts`. The journal is conversation recovery authority. Original clinical documents and accepted-record versions keep their existing, separate authority. Earlier whole-snapshot envelopes have no compatibility decoder or migration (owner decision before production use); unsupported history fails explicitly.

## Changed content and commit boundary

A conversation has immutable `events/<sequence>-<SHA256>.json` generations and a small `events/current` commit marker. Each generation records its profile, chat ID, sequence, exact previous generation filename, reason, save time and changes. Its filename hashes the complete generation bytes. The marker uses `health-chat-head-v2` and identifies one committed tip, together with constant-size cumulative recovery counters. It never contains a growing history or reference array.

The initial generation stores the initial conversation once. Later generations contain only changed JSON values and paths: object sets/removals, array item appends/updates/truncations and string splices. Appending text retains only the added text; changing one operation does not copy the preceding operations or request attempts. A no-op save retains its reason and ordering in a small empty-change generation. Generic decoding reconstructs the conversation without rerunning assistant business logic.

A save validates its candidate state and cumulative recovery allowance before publication. It writes and fsyncs the generation, publishes it without replacing another immutable file, then atomically replaces and fsyncs the commit marker. The encrypted wrapper publishes the changed generation and marker together through its existing vault manifest flush. An error is reported rather than claiming encrypted durability. The archive's existing single-writer lease remains required.

Warm writes use a disposable previous state tied to the caller-owned chat object. They read the small marker and latest generation, verifying the latter's hash, instead of scanning or replaying the whole growing journal. A cold writer verifies and reconstructs the committed chain once. Comparison still walks the current in-memory conversation; this contract establishes changed-content journal writes and bounded warm disk reads, not constant-time comparison or linear work across the entire encrypted archive. The vault's separate manifest/ciphertext growth remains part of [storage qualification in pending PR #35](https://github.com/mxbaylee/circus-health/pull/35).

## Validation and limits

Readers verify the complete committed chain, including contiguous positive sequences, exact predecessor filenames, content hashes and profile/chat identities. Missing or corrupt required generations, malformed changes, symlinks, hardlinked content, unsupported envelopes and changed identities fail explicitly. Paths have at most 64 components; keys have at most 1,000 characters and cannot be `__proto__`, `constructor` or `prototype`. Array indexes must be canonical, existing or exactly the next append position; truncation cannot expand an array. String splice ranges must fit the existing value. Undefined object fields are omitted and undefined array entries become null, matching JSON serialization.

Ordinary recovery has an aggregate 256-MiB physical read allowance and 100,000 inspected event-directory entries. Writes reserve 4 KiB for the marker and permit at most 99,999 committed generations. Across the entire replay, decoding allows one million allocated JSON nodes, one million patch/path work units and 100 million UTF-16 units of string-copy work. Individual containers have at most one million items. The marker's cumulative counters are recomputed and verified on cold reads; a warm writer refuses a save before it would produce history exceeding ordinary recovery limits. These are storage/decoding bounds, not elapsed model-work targets.

`readChat` diagnostic options impose a smaller aggregate byte/entry budget across the marker and every required generation. Actual bytes read are charged even when parsing or validation fails. The journal cache never bypasses explicit diagnostic limits. Resource limits use `CHAT_READ_LIMIT`; corrupted or unsupported content remains a separate failure.

## Failure, closure and backup

A failed append invalidates its remembered basis. Failure before marker publication leaves the previous committed conversation authoritative; after an ambiguous marker/directory-fsync failure, cold validation determines which generation actually committed. The writer never advances recovery state solely from its cache.

Temporary publication files live in a private `unpublished/` directory outside the scanned event inventory. A complete immediate next-generation file left by a process crash is not adopted when a valid earlier marker exists. A cold retry verifies its profile, hash and predecessor, then moves it into that pending directory before publishing the explicitly retried state. Pending files are excluded from encrypted workspace flushes and backups. If the marker is missing while any published-format generation exists, the journal fails closed: those bytes cannot distinguish a failed first publication from a lost committed marker. Reads, lists, backups and retries never silently erase or reset that conversation. Preserve the archive for recovery from a verified backup or use a fresh fictional conversation when reproducing a failure.

App closure, profile lock and failed profile activation clear scoped remembered copies. The encrypted wrapper also invalidates the caller's basis after a flush failure. Weak keys do not keep caller-owned plaintext alive. This cache is neither archive authority nor a substitute for profile/session authorization.

Backups capture one commit marker and its exact required immutable chain. They verify and copy the bytes actually read, then write the captured marker, so an append during copying cannot retarget the backup to an uncopied generation. Later generations and unpublished files are excluded. Restored conversations replay the same committed state; originals and accepted records are handled by the existing backup/recovery contracts.

Focused tests append 400 fictional operations and physical-request attempts, verify proportional new bytes and no warm directory scans, edit one historical item and append text, and check reconstruction, deletion/truncation and no-op reasons. They also exercise publication faults, missing markers, corruption and links, aggregate diagnostic/decode bounds, and a coherent backup while the source advances. Encrypted recovery and affected import qualification remain distinct validation dimensions; these journal checks do not establish production import completeness.

## Bounded import recheck

A 2026-10-02 independently fictional dense 151-page recheck used the scripted runner with this journal implementation, real extraction/OCR, normal automatic coordination, host-backed scratch/archive storage and the unchanged 1 GiB runtime. It made 531 physical requests across 76 slices and physically read/delivered all 151 pages, then failed with `ENOSPC` before a final review grade could be retained. Physical page delivery does not establish clinical completeness. The original hash still matched, no records were accepted, and diagnostics remained partial with 41,857 known persisted events omitted.

The final live receipt recorded zero runtime space available: SQLite occupied 1,015,787,520 bytes, its WAL 38,822,792 bytes and shared-memory file 98,304 bytes. All runtime JSON files together occupied 4,466,368 logical bytes; that total includes conversation and intake-batch events and must not be attributed entirely to chats. The largest observed chat event was 2,787 bytes. Separately, 4,598 retained encrypted indexes occupied 3,914,790,639 bytes, while 7,630 encrypted content objects occupied 6,374,480 bytes. The owned runtime was closed afterward. No table/index allocation receipt was captured, so the exact SQLite growth mechanism is still unproven.

These measurements support the scoped journal improvement and identify remaining SQLite and encrypted-index capacity work in the [pending large-import investigation](https://github.com/mxbaylee/circus-health/pull/35). They do not qualify the bounded import, the unchanged 900-page fixture, full-run diagnostic coverage or production readiness. Earlier capacity failures remain recorded in that investigation; no capacity limit was raised.
