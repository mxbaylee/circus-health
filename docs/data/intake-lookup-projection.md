# Checked intake lookups

Discovery allocation, acceptance replay and ownership name review read the selected intake authority. Disposable SQL records source insertion order and binding information. Prepared native receipt addresses and negative lookup results additionally require a complete, current authority-bound preparation certificate; SQLite alone is not their proof. Without that certificate, acceptance lookup independently derives and checks the required native scope before returning a result.

Connection-local source triggers coalesce dirty IDs with an explicit absence check, so source UPSERTs cannot override their duplicate handling. Updates invalidate both old and new IDs; rollback restores the source rows and derived lookup state together.

For native `health-intake-collections-v4` envelopes, reconciliation stores the checked logical root/domain version and removes any former compatibility payload rows once. It does not reconstruct the workflow, recount its collections or copy receipt text. Auxiliary build/progress/receipt changes leave that logical binding unchanged and write no lookup contributions.

Explicit cold workflow maintenance derives and atomically publishes three lookup indexes alongside the other workflow indexes: maximum discovery group, first acceptance per operation and ordered identity receipt occurrences. They share the checked logical completeness binding and `health-intake-workflow-index-v6` policy. `prepareIntakeLookupIndices` can prepare the same lookup contributions independently, under `health-intake-lookup-index-v1`, without model or review-count work. It checkpoints unselected work, yields between bounded change batches and adopts completeness only after the checked stream finishes. A changed logical root without an updated index reads unavailable. Reconnect GET explicitly awaits lookup preparation; it does not reconstruct whole workflow summaries to hide a stale or incomplete index.

Unchanged warm lookup preparation retains one scalar certificate per connection, not receipt payloads. Reuse requires a fresh accepted-authority and profile check, the exact SQL change/schema/peer and TEMP schema stamp, and unchanged collection and lookup cache generations. Cancellation is checked first. After preparation writes finish, an unchanged read-only frontier covers address-catalog construction and the complete final header/discovery-frontier validation; writes receive no reuse credit. SQL changes, rollback, cache loss or an unknown state fall back to the complete preparation checks. The fictional one- and eight-original regressions both visit zero original rows on unchanged warm preparation, with no collection-node reads or durable writes. Changed-source preparation and the global discovery revision still traverse the complete source frontier. Selected-original physical verification remains the consuming operation's responsibility; this certificate does not establish physical verification of every unselected original.

Cold address-catalog construction streams SQL-first receipt operation fields into a private disposable SQLite index and reads each source's already-complete maximum point. It stores only operation keys, source binding scalars and addressed targets, with a fixed SQLite page cache, never receipt bodies or live readers. It checks cancellation and yields at receipt checkpoints and between sources, including empty sources. Every yield requires fresh unchanged-frontier validation; a partial or invalidated catalog cannot answer a lookup. An attempt token prevents an older builder from publishing over a newer one. Closure, rollback and lookup-cache disposal close the private index.

A SQL witness change invalidates all lookup answers, but does not itself discard previously derived addresses. Recertification freshly checks every current source's authoritative logical root, source hash, insertion order, native shape and complete maximum index. Only an exactly matching per-source binding can retain its prior derived receipt addresses; changed sources are rederived and removed or non-native sources are pruned, with receipt deletion in bounded checkpointed batches. No receipt text is retained. This avoids rereading unchanged receipt bodies merely because unrelated SQL changed, while keeping complete source membership validation. A changed source still requires its own receipt derivation; this is not a claim of changed-receipt-only work within that source.

On that exact prepared frontier, maximum discovery rechecks one selected indexed group and acceptance lookup rechecks one selected operation target against its actual source row and published index. Missing operations require the same complete certificate. A terminal certificate check covers first-source and negative scope after selected reads. Duplicate receipts preserve first occurrence within the earliest source. Unsafe discovery integers retain the original synchronous refusal, including nonwinning negative contributors. Native originals cannot contribute fake maxima or receipt payloads through compatibility cache tables. Warm lookup regressions count zero full-catalog rows at one and eight originals; selected addressed reads still perform source and tree checks, and their node work is not claimed constant.

Mixed legacy/native acceptance lookup reuses a current catalog's complete native subset, then compares its earliest native result with the checked legacy projection's earliest result. Compatibility reconciliation precedes catalog selection because it can expire preparation. Both the original catalog token and legacy answer witness remain required through payload decoding and the final return, including true absence. Warm mixed regressions at one and eight native originals count zero full-catalog rows and zero rederived operation headers for native, legacy and absent operations. This does not change the all-native requirement for other catalog transitions or discovery allocation.

Without a current catalog, acceptance lookup visits every actual native original and drains its complete SQL-first acceptance contributions. It retains only the queried operation's first address per original, then compares that expected address or absence with the derived operation key. A missing, redirected or spurious key refuses explicitly; an earlier valid receipt cannot hide a damaged later native contribution. The lookup does not repair indexes or copy whole receipt bodies to establish completeness. Cold synchronous fallback therefore scales with all native acceptance headers, not just the returned receipt. Public receipt checking and exact-request replay share this checked selection; damaged working indexes cannot produce a successful not-found answer or justify accepting again. No automatic repair is provided for a corrupt native build that still claims completeness: clearing lookup caches or restarting may still refuse it. Retain the original exact request, operation ID and accepted authority for diagnosis or recovery; this change adds no repair procedure. Accepted receipts remain unchanged.

Raw duplicate fields follow the original SQLite behavior: the first `intake`, `workflow`, contribution array and acceptance operation field select the lookup occurrence. Discovery uses SQLite integer conversion. The selected receipt payload subsequently follows `JSON.parse` last-field behavior, including scalar `json_each` transport conversions for identity confirmations. The addressed subtree reader preserves the exact outer occurrence while selecting last fields within it.

`retainedIntakeAcceptanceReference` and `iterateIntakeIdentityReferences` expose checked record capabilities. `openIntakeIdentityReference` reads the selected header and streams target record IDs; `intakeIdentityTargetMembership` drains every target before reporting membership. It retains no global receipt or supersession ledger. Missing late evidence and a changed selected logical root refuse the read.

The existing complete-object acceptance and identity APIs are compatibility adapters. A native receipt decode, or complete native identity ledger, has an explicit 128 KiB returned JSON budget. Exceeding it fails with a request for addressed consumption; it does not return a partial object or list. Identity header fields have the reader's explicit 64 KiB field budget. The native ownership route uses the addressed plan described in [Ownership name evidence](ownership-name-evidence.md), including large matching receipts. The synchronous legacy ownership-name API remains a complete-object compatibility adapter.

Proposal publication updates discovery from the previous checked maximum and only appended SQL-first groups. Its owned compiler witness certifies that existing discovery values and acceptance/identity subtrees were not changed; equal handles and counts alone are not that proof. Mutations of shadowed last-selected raw arrays preserve the first-selected lookup. The global discovery revision binds ordered selected original headers and logical roots. The host rechecks it inside publication, and a caught mismatch still rejects the transaction.

Retained supported v3 envelopes keep disposable lookup format 2, complete-value decoding and their compatibility limits. Reconciliation still traverses their contributions. Only one legacy payload hash memo is retained; transaction failure, reconstruction and profile closure discard it. Native public package processing uses the [paged authority and consumer contracts](intake-bounded-views.md); the complete-object compatibility APIs are not its large-inventory path.
