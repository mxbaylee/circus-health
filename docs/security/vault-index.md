# Incremental encrypted workspace index

The unlocked profile vault maps logical private file names to immutable encrypted objects. Workspace publication adds only changed file bindings and new object metadata to its retained index. It does not copy the growing file/object maps into each publication. Original content objects and immutable accepted-record versions remain separate evidence; nothing is pruned to reduce index growth.

## Publication and recovery

`vault-index.ts` stores authenticated `circus-health-vault-index-delta-v2` generations under `vault/indices/`. Each carries profile and generation identities, a consecutive sequence, its exact predecessor reference, newly introduced object sizes/digests and changed file bindings. References bind the generation's identity, sequence, plaintext byte count and SHA-256. Encryption also authenticates the profile and exact generation purpose. Object identities and digests must be primitive strings; duplicate definitions, unsafe names, dangling bindings, inconsistent links and unsupported envelopes fail explicitly.

`vault/manifest.enc` is the small authenticated `circus-health-vault-head-v2` commit. It publishes the proposed index tip, cumulative usage and accepted `recordsHead` together. Newly staged object bytes are verified before index publication; each new index generation is read back to verify authentication, size and digest before publishing the manifest. Existing committed index generations are not reread by hot publication. A large pending change is split into bounded generations, with its complete chain and cumulative limits checked before staging any generation. The manifest commits the whole proposed chain once.

`syncWorkspace(..., { publishNow: false })` keeps valid staged bindings outside the committed manifest. An independent reopen sees the previous committed state until publication succeeds. Accepted-record publication retains this staging boundary: its workspace changes and record head become visible through the same manifest. Byte-identical object reuse still verifies actual bytes; a disposable digest lookup avoids scanning every object metadata entry to find candidates.

Cold open reads the committed chain once, recomputes cumulative usage, validates object metadata and file bindings, and reconstructs disposable maps. Referenced content files must exist and be ordinary unlinked files. Content authentication, size and digest are checked when read or materialized. Historical content and index generations remain retained. A captured manifest selects its exact index ancestry and record head even when later, unreferenced generations are also present in a backup.

Publication failures close the affected writer and discard reconstructed maps, pending bindings/metadata, digest lookups and workspace fingerprints. A failure after manifest replacement can have committed successfully despite the exception; reopen follows the actual authenticated manifest. A failure before replacement leaves the previous commit authoritative. Unreferenced staged artifacts are not adopted or deleted as evidence. Missing manifests with retained artifacts fail explicitly rather than initializing over them. Profile locking/closure clears the same disposable state.

## Bounds and schema boundary

Each generation permits at most 64 KiB of plaintext; the manifest permits 16 KiB, including at most 8,192 characters of canonical base64 record-head data. Committed-chain reconstruction and publication share limits of 256 MiB of index plaintext, one million generations and one million object/binding entries. Logical paths permit at most 4,096 UTF-8 bytes. These host-resource bounds count committed index work; they do not limit model execution time or automatically prune uncommitted artifacts. Contributor/test options can impose stricter valid limits, never raise the defaults. A writer refuses a candidate before publishing a chain that exceeds its cold-read budgets.

Only the current encrypted head and delta format are supported. The older full-map encrypted index has no decoder or migration (owner decision before production use). Unsupported archives are rejected without resetting data. The in-memory `Vault.metadata()` view retains its existing reconstructed API shape for current consumers; it is not a new full-map durable write.

Fictional tests exercise hundreds of changed bindings after a large existing index, new-generation verification versus prior-history rereads, exact materialization/deduplication, staged publication, cold/cache-loss recovery, strict bounds and corruption, publication failures and captured-manifest backup coherence. These checks do not qualify a full large import. The [selected intake envelope authority](../data/intake-envelope-authority.md) is implemented, while [real-mutation qualification](../todo/CRS-210.md) remains open; diagnostic completeness and broader scripted qualification remain separate open work.

On a fictional baseline with 1,000 distinct original bindings stored in five generations, 100, 200 and 300 single-file changes add 100, 200 and 300 generations totaling 58,303, 116,803 and 175,303 ciphertext bytes. Each new generation is read exactly once for publication verification; no baseline generation is reread by those hot updates. The object count rises from 1,000 to 1,100, 1,200 and 1,300; byte-identical reuse adds no content object. Baseline ciphertext and original metadata remain unchanged. These counted fixture results cover index publication, not whole-profile storage, model performance or import qualification.
