# Circus Health encrypted object format

Implementation format v1 uses libsodium's maintained `secretstream_xchacha20poly1305` for file encryption, `crypto_aead_xchacha20poly1305_ietf` for wrapping 32-byte profile keys, Node `randomBytes(32)` for independent profile/recovery entropy, HKDF-SHA256 for purpose-separated wrapping keys, and @scure/bip39 for encoding entropy as 24 English words with checksum. Recovery does not derive a cryptocurrency wallet or accept an extra password.

Encrypted objects contain the eight-byte magic `CIRCUS01`, the libsodium stream header, and length-prefixed ciphertext frames of at most 1 MiB plaintext each. An authenticated empty FINAL frame is mandatory. Truncation, trailing bytes, wrong ownership/purpose, modification and reordered frames fail. Additional authenticated data binds each frame to format, opaque profile ID and object purpose. Libsodium manages stream nonces and rekeying; each rewrite uses a fresh stream. Writes fsync a restricted staging file, rename atomically and fsync its directory. Plaintext extraction is published only after complete authenticated decoding.

A recovery wrapper uses a fresh 24-byte nonce, a 32-byte key derived from the random recovery secret with profile- and method-bound HKDF info, and authenticated encryption of the independent profile data key. Passkey wrappers use a verified PRF output with a distinct method identifier. Raw keys and recovery phrases remain in memory or the user's explicit download, never archive files. Public keyrings contain only wrapped keys and unlock metadata. Public card identity is checked against unlocked private state.

Authoritative objects remain in a profile's vault. Runtime plaintext is outside the durable archive with restricted permissions; SQLite is a derived encrypted cache. This does not promise protection from a compromised unlocked host, swap or intentional exports. See [profile encryption](profile-encryption.md) for lifecycle and verification gates.

References: [libsodium secretstream](https://libsodium.gitbook.io/doc/secret-key_cryptography/secretstream), [scure BIP-39](https://github.com/paulmillr/scure-bip39), [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server).

The small encrypted `vault/manifest.enc` atomically publishes the encrypted workspace-index tip and accepted record-stream head. Immutable original bytes live in `vault/objects/`; immutable record versions and commit envelopes live in `vault/versions/`. The [incremental index protocol](vault-index.md) writes only changed file bindings and new object metadata into bounded authenticated generations, verifies new staging and commits its complete proposed chain through the manifest. Ordinary edits append changed record versions and replace the small authenticated head without copying whole index maps or decrypting old record segments into runtime files. Cold open reconstructs the committed index once; hot publication does not replay its ancestors. Field and editing-session history is indexed in SQLite and is reconstructed from accepted record versions after cache loss. Index/head v2 is the supported current format; the older full-map index has no decoder or migration and fails explicitly without data reset. The encrypted-object framing above remains v1.

Opening a profile decrypts originals into a restricted runtime directory and validates an encrypted SQLite cache against the accepted stream/schema. Missing, damaged or inconsistent caches rebuild from accepted record versions, verifying referenced originals. The cache is disposable; `metrics.cacheHit` and `metrics.loadMs` distinguish a cache load from recovery. Lock cancels active responses, saves the cancellation journal and encrypted cache, clears live key references, and removes the profile runtime directory. A failed cache write still locks the profile; accepted encrypted versions remain the recovery authority.

Interrupted setup can resume with its downloaded recovery kit after process restart. The server verifies profile-bound decryption before issuing a replacement setup token. A private copy requires an unlocked source and generates independent profile and recovery keys; it starts a new history from copied current state. The public card and keyring are not an export of medical information. Legacy plaintext backup endpoints are unavailable in the encrypted runtime; back up the durable encrypted data directory instead.

Current validation uses synthetic fixtures for recovery, multi-frame authentication, modified/truncated streams, within-profile byte reuse, API access boundaries, selective-profile locking, setup restart, independent-copy recovery and complete cache-loss reconstruction. Real-device WebAuthn PRF compatibility and a complete container/browser import journey still require validation before calling this release-ready.

Fault tests interrupt immutable ciphertext before head publication and fail after durable head publication but before SQLite commit. Reconstruction preserves acknowledged history, ignores unattached partial objects and replays accepted operation IDs once. Public-card write failures keep the previous published registry and retry identity, activation and deletion changes. Controlled WebAuthn verification tests exercise lock/delete races, competing counters and incorrect PRF material against real profile encryption and keyring writes; their mocked signature verification does not establish browser or authenticator compatibility. Separate HTTP sessions verify selected-profile isolation and byte-identical original downloads after total cache loss.
