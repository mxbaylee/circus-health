# Encrypted profiles and recovery setup

Status: encrypted runtime, mandatory recovery verification, reusable unlock and later-enrollment UI are implemented. Startup reads public cards and loads a profile after unlock; it does not rebuild all profiles eagerly. Separate recovery setup screens, verification-file input, and the Add passkey / Skip choice after ordinary recovery unlock are implemented. Passkey enrollment automatically creates and confirms the selected credential before saving its wrapped key. Real-device passkey/PRF acceptance remains open. Existing external plaintext backups and separate visual fixtures have not been retroactively encrypted. See the [current storage contract](../data/profile-storage-and-rebuild.md) and [remaining work](../todo/readme.md).

## Product contract

Every new profile starts encrypted, including generated **Placebo accounts** (generated fictional profiles) and private copies. A verified recovery key is required; adding a passkey is optional and may happen later. There is no user-chosen password, empty-password mode or automatic unlock secret stored beside the archive. Use the canonical `placebo` flag throughout storage and APIs, without an obsolete demo-flag compatibility layer. It does not change encryption or recovery requirements.

The recovery key is a reusable secret, not a one-time code. The phrase and recovery file represent the same secret. Using either unlocks the profile normally; the required flow then offers Add passkey with an option to Skip. It does not consume the secret, invalidate existing passkeys or re-encrypt records. Recovery-only use is supported. Anyone holding both the recovery secret and archive can unlock it. The recovery kit does not contain the health records and does not replace an archive backup.

## Creation flow

1. **Name and icon.** Choose the display name and existing icon-pack icon. Explain briefly that these appear before unlock; the name may be an alias. Assign an opaque profile ID independent of the name.
2. **Save your recovery key.** Display the generated 24-word phrase, a **Download recovery key** action, an **I have saved my recovery key** checkbox, and one **Open profile** action. Keep Open profile disabled until acknowledgment. Copying or downloading is supported; the next page still verifies the saved material. Passkey enrollment is offered after verification, not as the action for leaving this screen.
3. **Open profile.** Present a login-style POST form with the profile display name in a hidden `autocomplete="username"` field and an initially empty `type="password"`, `autocomplete="current-password"` recovery-key field. Require the full phrase to be typed/pasted, filled by the user's password manager, or loaded by selecting the downloaded file again. Do not prefill from the displayed phrase, cached setup state or a hidden copy of the generated secret. Read the submitted form value, including autofill that does not fire a React change event. Validate the submitted secret by actually unwrapping the staged profile key and checking authenticated data bound to this profile/setup. A download click or acknowledgment alone is not verification. Browsers cannot establish that the user kept an independent durable copy; this step checks that the submitted recovery material works.
4. **Optional passkey, then onboarding.** Only successful verification permits final activation. Enrollment then starts automatically with a progress message and Skip. Success or Skip continues to skippable clinical onboarding; failure retains Skip and recovery. A failed recovery check stays on Open profile with a useful error. Both passkey and recovery-only use have the same recovery gate.

Ordinary recovery unlock uses the same Open profile form and keeps Use passkey as a separate action. The hidden username is a password-manager hint for the explicitly selected profile, not a new authentication identity. Resuming an unfinished setup obtains its original display name from the encrypted setup only after validating the recovery material. The application does not persist plaintext recovery keys in browser storage or URLs. These form semantics follow [1Password's website guidance](https://www.1password.dev/web/compatible-website-design); the extension controls its save/fill prompts, so actual Firefox/1Password behavior remains an acceptance check.

Handle passkey cancellation or unsupported PRF without losing setup: leave the recovery-only path available. Do not make successful passkey registration a shortcut around recovery verification. After a setup interruption, require recovery or an already registered compatible passkey to resume protected staging, and still require the recovery check before activation. If no usable secret was saved, restart the unfinished empty setup; never persist an unprotected secret to make resuming convenient. No medical uploads or accepted personal edits occur in unverified setup.

Use plain setup copy: **Keep this file somewhere safe. It can unlock your profile without a passkey.** Do not generate real keys in documentation or checked-in fixtures. A placebo's invented medical fixtures may be deterministic; its live encryption keys must be fresh.

## Keys and passkeys

Use a fresh independent 256-bit profile data key and 256-bit recovery secret from Node's operating-system-backed cryptographic generator at runtime. Abort setup on randomness failure; never fall back to timestamps, Math.random, identifiers, AI-generated words or a seeded placebo generator. Encode the recovery secret as a standard 24-word mnemonic with checksum using a maintained implementation and test vectors. Mnemonic encoding is not Bitcoin wallet seed derivation or an additional mnemonic passphrase feature. [Node randomBytes](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptorandombytessize-callback), [BIP-39 encoding](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki).

The profile data key encrypts the vault; each unlock method protects a separate copy of that key. Store only wrapped keys plus required version, algorithm and credential metadata in the unlock header. Never persist raw recovery secrets or data keys in the data directory, chat history, request logs, browser persistent storage, telemetry or build layers. The explicit recovery download is the user's separate secret copy. Version the kit format and include the profile ID so a file from another profile is rejected clearly. [OWASP key wrapping](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html#encrypting-stored-keys).

Ordinary WebAuthn signatures do not decrypt a vault. Use WebAuthn PRF with supported authenticators and browsers; verify actual PRF output and the resulting unwrap before considering a passkey usable. Do not export or store the passkey private key in the health archive. Maintain normal WebAuthn challenge/origin/RP validation and operation/session binding. Passkeys need a tested stable hostname and secure Docker origin; changing hostname may require recovery followed by enrollment. Do not promise universal cross-device PRF support. [WebAuthn PRF](https://www.w3.org/TR/webauthn-3/#prf-extension).

Creation can report PRF capability without returning a PRF result. Verify the registration, retain its public credential metadata and salt only in a short-lived server challenge, then request a required-user-verification assertion for that exact new credential using the same salt. Verify the assertion's challenge, origin, RP ID and credential before using its 32-byte PRF result to wrap the unlocked profile key. Only this final confirmation publishes the durable keyring entry and counter. Normal unlock decodes per-credential PRF salts and uses the stored wrapper; existing RP IDs and wrappers remain unchanged.

Normalize native BufferSources, canonical base64url JSON results, and exactly 32 integer bytes in a plain array. The array form accommodates the [reported 1Password Firefox/Chrome return-type issue, FS-5593](https://www.1password.community/developers-69/browser-extension-webauthn-prf-extension-not-spec-compliant-24672). Reject sparse arrays, non-integers, out-of-range values and incorrect lengths without coercion. Representation compatibility does not substitute for a PRF result or weaken WebAuthn verification.

Entering the passkey screen starts one attempt. Skip or dismissal cancels browser prompts and the matching server challenge during creation/confirmation; late results cannot complete enrollment. The final durable save briefly disables dismissal. Success closes the screen or continues onboarding without another confirmation button. If the browser/authenticator cannot supply the required result, explain that the passkey cannot unlock this encrypted profile and leave recovery available. A password manager may already have saved a credential even when application enrollment does not finish; that is not evidence of a usable archive unlock method.

When a user opens a locked profile, start passkey sign-in once if its public card reports a confirmed passkey for the current hostname. This boolean comes from the keyring without opening private data; it does not disclose credentials or imply that the current browser/password manager still possesses the key. Incomplete enrollment and credentials for another hostname do not trigger the prompt. Keep the recovery form visible and provide **Use recovery key** to cancel the pending browser request and its session/profile-scoped challenge. Cancellation or failure leaves manual **Use passkey** retry available without another automatic prompt until the login screen is reopened. The final unlock operation briefly blocks dismissal and switching methods. Profile navigation and unmount suppress late client results; authentication still verifies challenge, origin, RP ID, user verification and PRF before unlocking.

Multiple passkeys can independently unwrap the same profile key. Adding a passkey requires an unlocked, authorized profile operation and does not re-encrypt the vault. The implemented algorithms, nonce handling and key derivation are documented in [vault format](vault-format.md).

## Disk and identity

The [storage reference](../data/profile-storage-and-rebuild.md#one-owner-per-profile) documents the current physical layout. Public cards and wrapped-key metadata remain outside encrypted medical objects.

The public card is readable before unlock, not public on the internet. It is the minimal display-name/icon projection of Self; do not add another independent username or confuse it with authenticated medical identity. Interrupted public-card writes retain the prior published registry and retry metadata. Public card metadata is untrusted until checked against the unlocked profile. Locked profile listing must not require opening SQLite.

The picker may also show stored-byte totals without unlocking. Detailed content categories and plaintext deduplication indexes stay protected. Follow [file reuse and storage accounting](../data/storage-accounting.md) for retaining all original occurrences while storing identical bytes once within a profile.

Encrypted manifests preserve the logical sources, personal, curation, mappings, attachments and chats ownership. Accepted edits use [append-only record versions](../data/record-version-storage.md), replacing full-table snapshots after each edit. Encrypt filenames, medical metadata, original bytes, derived records, all historical versions, pending imports and operational content carrying patient data. Use opaque physical names; sizes, counts and filesystem timestamps are not concealed by this design. Preserve attribution and byte-for-byte original downloads after decryption. No cross-profile object or encryption-key sharing, including private copies. User-requested exported PDFs and downloaded originals leave this at-rest boundary intentionally.

The recovery secret is not copied into this folder or its backups. Its wrapped-key entry may be stored there. Removing a passkey updates current key-management state without removing medical history. Restoring medical state does not restore old unlock settings. Old external backups can retain old wrapped keys; revocation cannot retroactively alter them. Routine recovery does not rotate the data key or revoke access through old backups. Compromise-driven data-key rotation is not implemented.

## Unlock, caching and locking

The application permits one unlocked profile at a time across its HTTP sessions. A successful recovery unlock, passkey authentication or new-profile activation locks every other open profile, invalidates its pending passkey challenges and revokes its session grants before acknowledging success. Switches are serialized. Failed recovery/passkey proof leaves existing access intact; a failure while closing the previous profile locks the newly opened profile as well and reports failure. Copy creation retains access to its source until recovery verification and copy initialization succeed, then applies the same locking rule. Locking disposes private runtime files, database connections and key buffers while retaining accepted durable data and history.

Clients clear a selected profile after a scoped `PROFILE_LOCKED` response and refresh public cards when returning to a tab. That refresh does not automatically select another profile. Appearance belongs to the browser rather than a profile: System/Light/Dark remains available on the startup page and persists across locking, unlocking and reload.

Start the app by reading public cards only. Open a selected profile through passkey or recovery, then show unlocking/loading progress. Validate and reuse that profile's encrypted SQLite cache against its committed record-version sequence and projection/schema version; catch up new committed versions atomically or rebuild when necessary. SQLite includes both current data and searchable history. Deterministic indexing of accepted versions uses no AI. An invalid cache is disposable; corrupt authoritative data must produce an error rather than a guessed database. There is no compaction scheduler or periodic full-archive checkpoint feature.

Durable acknowledgments still require encrypted portable writes; cached SQLite never becomes the sole owner of an accepted edit. Publish an authenticated cache from a consistent committed state with a manifest/version check. Cache failure or total loss must not lose acknowledged data. Record nonclinical timing metrics for unwrap/load/rebuild and cache hits/misses. Startup does not rebuild every profile.

Keep working decrypted SQLite, WAL/SHM, extraction previews and other temporary plaintext outside the durable/synced directory in a restricted runtime area. Locking must close the profile database, stop or safely suspend its jobs, invalidate session/tool/file access, and clear plaintext UI/runtime caches. Bind every API, stream, preview, assistant operation and export to an authorized unlocked profile; a publicly enumerable ID is not authorization. Do not claim protection from a compromised host, the unlocked app, swap/core dumps or data intentionally sent to a configured model. Specify and test supported runtime cleanup rather than promising perfect memory erasure.

## Verification limits

Controlled fictional tests exercise recovery verification, invalid/wrong-profile kits, setup interruptions, independent keys, encryption authentication, locked-profile routes and cache-loss rebuild. These checks do not establish physical authenticator/PRF support or password-manager behavior on every browser. [Device acceptance](../todo/readme.md#crs-072) remains open.

Encryption does not retroactively protect earlier plaintext backups, exports, downloads or Git history. Recovery verification proves the submitted secret works; it cannot prove that an independent copy remains available.
