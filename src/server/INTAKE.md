# Source intake

The maintained HTTP implementation is `intake-routes.ts`; shared review and workflow shapes are in `../shared/intake.ts`. All routes below are relative to `/api/profiles/:profileId` and require the selected profile's authorized session and the API origin boundary. Original files and proposals are immutable evidence. Only explicit acceptance of supported reviewed mappings creates clinical projections.

## Upload, conversion and acceptance

### Durable text and human source review

Assistant plan, batch and proposal responses carry a shared `ProposalSourceTextHandoff` as `proposalSourceText`. Its `status` is `unavailable` (both revision fields null), `read_required` (current revision known, usable proposal pin null), or `ready` (both revision fields contain the same actually read current revision). `readRequired` and the next-step `instruction` remain available. A new intake version never substitutes for `sourceTextRevisionId`; advancing the durable text revision withdraws the usable pin until the current passages are read. This model-tool response contract does not change immutable batch or proposal request schemas.

The composed route is documented in [processing and evidence review](../../docs/import/processing.md). Sources → Files exposes source review inside the selected original, independently of proposals or a model connection; Import exposes compact source-section rows in **Needs attention**. Extraction is local and explicit: native PDF text/geometry, literal text/structured-file windows, and serial English Tesseract PSM 3 OCR for supported PDF/image rasters. Native text is retained before OCR. Confidence, reader disagreement, uncovered ink and structural/full-page review issues are attention cues, never completeness detectors. Original bytes stay unchanged. ZIP roots retain their inventory; readable retained members have their own text revisions. DICOM, audio/video and unsupported binary formats remain retain-only.

The deployed image includes Tesseract and English language data. Raster work is isolated and bounded: 32 million decoded image pixels, 1,800-pixel maximum derivative dimension, 60-second OCR timeout inside a 75-second worker limit, 8 MiB TSV output, at most two admitted extraction jobs and two admitted raster jobs with serialized execution. Busy work stays pending. Missing engines/unsupported decoding remain located exceptions. These limits do not qualify handwriting, non-English OCR, HEIC or multipage TIFF. Literal logical pages contain at most 24,000 UTF-16 code units. A step processes at most two pending pages; reviewed pages are protected while untouched pages continue.

Source actions include confirm, correct, not-text, unreadable, later and external clarification. Corrections can edit all displayed context and relationships, not only warning boxes. A source revision and expected source hash bind each idempotent review operation. Every new revision conservatively invalidates older proposals and ancestor-package dependencies; repeated identical clinical JSON then requires its own candidate review version. Earlier accepted history is not rewritten. This is intentionally broader than minimal dependency invalidation. Source review alone never accepts clinical records.

See [the API routes](API.md#retained-import-text) for literal preview, history, bounded passage/annotation retrieval and case-sensitive search. Follow every returned cursor; annotation previews retain exact retrieval references. Source extraction/search and the assistant cannot interpret an imported instruction as authorization to access another profile or accept a record.

Automatic batches retain cumulative usage and a count-based no-progress attempt for one exact plan unit. Unique source reads, substantive candidate versions and accounted units renew progress. Productive work has no cumulative reading allowance. Physical requests retain durable identities, source/route pins and honest measured or unknown usage. Transient provider waits retry with durable deadlines and unlimited backoff. Unknown outcomes retain possibly billed accounting while a durable decision authorizes one replacement. See [automatic recovery](../../docs/import/automatic-recovery.md) for rationale, state transitions and the separate post-lock authority dependency.

Tab closure does not cancel authorized server work. Sign-out, lock and profile switching still revoke the interactive runtime. Job-scoped background key authority remains CRS-081; this implementation does not retain general unlocked profile access to claim that requirement is complete.

- `GET /intakes/limits`: configured upload/extraction limits.
- `GET /intakes?offset=0&limit=30&visibility=visible`: paginated deliveries and `meta.intakeDurability`; visibility also supports `archived` and `all`. Add `rootOnly=true` for uploaded originals without retained ZIP children. Each item exposes `parentSourceFileId`; child evidence remains available through its parent and direct scoped routes.
- `POST /intakes`: raw file body with URI-encoded `X-Filename`, optional `X-Source-Id` or `X-Source-Name`, and original `Content-Type`. Missing source uses Unknown source. Retains bytes/hash before indexing. Valid prepared JSONL is ready; other formats await conversion. Same acquisition source, filename and bytes returns the existing delivery with `repeatedUpload:true`. Changed attribution/name retains a separate delivery; identical bytes can be reused within a profile without losing occurrences.
  The encrypted route checks known content length against the configured limit and immediate runtime staging capacity after authorization. Larger processing estimates remain advisory, and archive reuse is determined after hashing. Completed staging bytes are adopted by same-filesystem rename, independently verified and fsynced before publication; only cross-filesystem mounts take the exclusive-copy fallback. These paths emit separate `upload_original_adopt` / `upload_original_copy` timings. Incoming and published byte verification remain mandatory.
- `GET /intakes/:id`: `Intake`, including original metadata, proposals, conversionChatId, version, acquisition, reviewed metadata, workflow and durability. Validation previews are bounded samples.
- `GET /intakes/:id/read?offset=0&limit=12000`: bounded original text with UTF-16 offsets, nextOffset, totalCharacters and complete. Binary originals require file-aware tools; the last page of a partial read does not certify whole-file coverage.
- `POST /intakes/:id/convert {version}`: automatically preflights the model connection, additionally verifying image capability for image originals and PDFs that require or declare raster fallback, before resuming the linked conversion chat or creating one if none remains. Rechecks version and busy state after the probe; returns `{chatId}` and persists conversionChatId. Failure is visible and retryable. Later conversion passes on an accepted original are supported.
- `POST /intakes/:id/proposals {version,jsonlText,summary,runId?}`: validates and retains separate derived JSONL, never overwrites the original. Equivalent original/proposal bytes reuse the proposal on retry. Invalid lines reject the proposal as a whole.
- `GET /intakes/:id/review?proposalId=<id>`: `IntakeReview` with version, reviewToken, additions/duplicates/unsupported/uncertain summary, coverage gaps, informational `sourceContext` and editable clinical records. Omit proposalId for prepared original JSONL. Records include candidate/version identity, evidence, typed issues, saved draft and reviewState. Pure context envelopes retain their payload text, provenance and evidence outside clinical decisions and counts.
  Exact duplicate records retain `duplicateOf` for classification and replay safety. Its presentation flags distinguish the exact source row already saved (`sameSourceRecord`) and an unsaved duplicate found only in the current proposal (`persistedMatch:false`) from a genuinely different retained source match; clients must not describe the first two as another saved source comparison.
- `POST /intakes/:id/import {version,proposalId?,reviewToken,decisions}`: accept a reviewed selection after source/hash/asset/ownership and stale-review checks. Each decision has `{recordId,action:accept|skip,mapping,rememberRule?,comparisons?}`. Replaying an accepted token is idempotent; a fresh review supports later passes. Raw rows, earlier assertions, all source occurrences and importHistory remain retained.
  Unsafe reuse of an issuing source identity across incompatible or unverified report subject/member scopes returns HTTP 409 `CLINICAL_SOURCE_SCOPE_COLLISION`. Review stays readable, marks affected rows unsupported, and explains the refusal in coverage gaps. Acceptance and pair decisions recheck retained scope inside the transaction; changing a reviewed mapping does not bypass the guard. Existing key formats are unchanged. See [clinical source reuse](../../docs/import/import-reconciliation.md#refuse-unsafe-clinical-source-reuse).
- `POST /intakes/:id/related-records {proposalId,recordId,candidateVersionId,query?,cursor?,limit?}`: profile-scoped related-record search for the exact current pending candidate. Returns `{intakeId,proposalId,recordId,candidateVersionId,intakeVersion,reviewToken,comparisons,page}`. The service is `getIntakeRelatedRecords` in `related-records.ts`; route dispatch is registered by the application. Pages default to 20, allow 1–50, and expose a 200-result cap with `truncated` and `nextCursor`. Queries search literal label, source record ID, or code. Changed profile revisions/searches invalidate cursors. Discovery reasons locate evidence only.

Incoming `comparisons` decisions echo the displayed comparison's `scope` verbatim. `IntakePairScope` in `shared/clinical-review.ts` pins both exact records, incoming envelope and original evidence; fresh or counted acceptance rejects missing/stale scopes. A fresh intake choice of `same_event` adds the internal `occurrenceEvidence:'attach'` discriminator and links that one retained source occurrence to the selected accepted entity without rewriting its clinical row, provider, mapping, version or primary source. Hydration and resave never add the discriminator to legacy relationship-only choices. V2 scopes keep transient request revision/version CAS separate from the durable candidate/person/report/source/evidence authority stored with the attachment, so a successful transaction does not stale itself while unrelated drift still does. `INSERT OR IGNORE` materialization is not authority: before projection the server proves the deterministic incoming source row still has the exact proposal file, key, kind, label, raw envelope, locator, batch and acquisition or exact member-scoped reviewed provider transition. Review records expose `comparisonDrafts` statuses, including off-page targets, and `hasUnreviewedPairChoices` gives the shared readiness predicate. Verbatim carry-forward of an existing stale/missing-scope draft choice permits unrelated autosaves but never authorizes acceptance. Older accepted decisions remain readable with legacy scope status and are not rewritten. A saved pair from any search page receives the same durable question/answer history as a first-page pair.

- `POST /intakes/flush {}`: retries durable publication; a pending publication is not a rolled-back mutation.

Model PDF reads prefer a transient single-page PDF after the exact route passes a fictional PDF challenge. `CRS_AI_PROXY_PDF=auto` is the default; `true` still requires proof, while `false` disables native PDF. Declared capabilities are configuration hints; `capabilities.pdf` reports the ephemeral tested result. The host choice cannot be set through model tool arguments. Before first model work after startup, readiness verifies the tool loop and configured media with fictional content, without opening private originals. Receipts are configuration/profile scoped and never durable. An explicit unsupported-PDF response later downgrades the current receipt, including across model turns; Connection details offers a fictional retest.

qpdf derives only the selected page from the hash-pinned original. Two bounded passes project a strict allowlist of the reachable rendering graph and serialize that projection. Catalog and nested resource metadata, associated files, private application data and actions are omitted, with newly unreachable objects removed. Common transparency groups, structural-parent markers and empty annotation lists are handled; visible annotations, XFA, optional content and unknown rendering semantics take same-page raster fallback. qpdf removes unused Font/XObject resources, but does not reliably prune other resource maps. Nonempty Pattern, Shading, ExtGState, ColorSpace or Properties resource maps, Type3 glyph programs and shared JBIG2 global streams therefore use PNG until their exact usage can be established. Directly referenced image ICC/soft-mask streams remain native. This prevents unused shared resources from carrying another page’s data without introducing a second PDF content interpreter. Encoded rendering streams (images, fonts, CMaps and page content) remain exact: this is graph isolation, not semantic redaction of arbitrary bytes embedded inside a valid rendering stream. The graph is bounded to 4096 objects, depth 48, 100,000 traversal steps, 1 MiB of dictionary serialization, 5 MiB of raw streams and final PDF, and 10 MiB of JSON transport. Both qpdf passes share a 60-second deadline and each has a Linux 384 MiB address-space limit. The second pass inherits an immediately unlinked, mode-0600 seekable descriptor; Linux verifies tmpfs backing before writing any graph bytes. Healthy unsupported-format/size fallbacks retain the already verified worker; source changes, cancellation and parser failures retire it.

The tool keeps the exact original page and member references, bounded text cursor and incomplete coverage; derivative page 1 does not mean original page 1 or whole-document inspection. Derivatives are never new durable sources. Unsupported page structures or output bounds use the same selected page's raster preview. An explicit provider PDF rejection may invoke a host-only lazy raster read and retry once on the same route with verified image support, without replaying completed tools or writes. Other provider failures and changed originals do not authorize this retry. PDF-only routes fail explicitly when a page needs unavailable raster fallback.

PNG is the fallback because lossless encoding preserves small text and existing image routes already accept it; no lossy default is selected without readability evidence. Direct UI PDF previews also default to PNG. `INTAKE_PDF_BOUNDS.imageEncoding` keeps encoder and quality together; worker results carry actual `mimeType` and `image` bytes, with a 10 MiB `maxImageBytes` bound. Uploaded PNG, JPEG and WebP retain their source format and existing 1,800-pixel longest-edge/80-million-source-pixel bounds. Every upload preview is encoded from the decoded raster so EXIF/XMP/ancillary metadata is not forwarded, using JPEG quality 100 or lossless WebP. Retained originals stay byte-identical. `node src/scripts/compare-intake-image-formats.ts` compares independently fictional dense text, painted scan and vector pages using PNG, lossless WebP and JPEG q80/q90/q95, with byte sizes and decoded-pixel checks. This is transfer-size evidence, not clinical readability or vision-token savings.

## Named People review

The optional `health-record-v1.people` array is defined in `shared/intake-people.ts` and the envelope JSON schema. It contains at most 50 named clinician/relative proposals per envelope, with bounded literal evidence anchors and per-field support. Nonempty People proposals require `kind:"record"`; a people-only envelope omits `clinical` and retains a report group without creating an unsupported clinical row. The report queue exposes separate `peopleCounts` and includes pending/deferred People in its work accounting.

- `GET /intakes/people/:groupId?limit=50&cursor=...` returns `{groupId,people,totalPeople,peopleNextCursor}`; the page maximum is 100. Each proposal includes its exact ID/version, state, source/original/member evidence, proposed fields, advisory existing-person matches and any saved destination. Match counts and truncation are explicit. Only literal same-envelope name/field support is accepted; this is not independent verification of model transcription.
- `POST /intakes/people-disposition` accepts `{operationId,intakeId,intakeVersion,proposalId,proposalVersion,state}` with `state:pending|later|excluded`. It journals the exact proposal/version decision. Changed operation payloads conflict; saved proposals cannot be deferred. Originals remain retained.
  Clinician evidence may establish a named signer through a recognized title or a medical, dental, or optometry credential immediately after that same name. An OD/OS table elsewhere in a patient's passage does not establish a clinician role. Credentials remain literal evidence, not verified professional registration.

- `POST /intakes/people-apply` accepts `{operationId,intakeId,proposalId,proposalVersion,action:"add"}` or `action:"update"` with an explicit `noteId` and current personal `version`. Updates must target one of the current named-person matches. Known Self matches and Self update targets are rejected. The operation preserves unrelated fields and appends incoming medical history rather than replacing earlier history.

Apply returns the saved note/person IDs, destination URL, original saved version, replay status and source/personal durability. Source publication precedes the existing personal transaction; the latter includes the Person, original evidence association and replay receipt. Failure between stages leaves retained evidence and pending People work, not a fabricated successful Person. Exact retries return the original receipt; a changed request requires fresh review and cannot reuse that receipt. Earlier personal edits and accepted clinical records remain unchanged.

## Sequential reading batches

- `POST /intake-batches {operationId,intakeIds,appendToRunning?}` queues 1–100 explicitly selected uploaded root originals. The response-only `scheduled` boolean says whether this call started new work; an already completed selection returns `false`, and a stopped selection resumes saved automatic work and returns `true`. The operation ID makes a repeated request idempotent and rejects reuse with a changed ordered selection. With `appendToRunning:true`, new originals join the running batch durably; the 100-file bound applies to each selection, without an aggregate batch cap. Without this opt-in an active batch still returns a conflict. Append receipts retain the exact operation ID and ordered selection, including after a lost acknowledgment, backup, or rebuild. Publication precedes in-memory queue mutation; a rejected append does not strand an unjournaled item. With no running batch, the same request creates one normally. Existing ownership of a selected original is reconciled rather than duplicated; mixed selections enqueue only unowned originals. Accepted uploads already retain enqueue intent atomically and wake this same coordinator, so the browser need not create a queue.
- `GET /intake-batches` and `GET /intake-batches/:id` expose pinned original hashes, the current item, linked conversion chats, proposal IDs and honest per-file reading/paused state.
- `POST /intake-batches/:id/stop {}` stops the whole queue and cancels its active linked conversion. `POST /intake-batches/:id/resume {}` restores explicit Stop or historical interrupted intent. `POST /intake-batches/:id/retry-exceptions {}` reopens located processing failures from retained checkpoints without erasing protected human review.

The production proxy distinguishes reading source bytes on the host from delivering those bytes to the model. A successful source read first retains its exact window as pending, with only cursor/shape metadata. Only a subsequent valid provider response acknowledges the preceding tool results and advances consumed-read scopes. A deadline, transcript limit, provider context error, cancellation or invalid response before that acknowledgment leaves the window pending for the next slice. Newly requested tools on the terminal 64th round are not dispatched, so the loop cannot finish immediately after an undelivered read or write. A read and extraction claim in the same tool group cannot use the new read as evidence. Durable batch coverage and human acceptance remain separate. Existing checkpoints predating this protocol retain historical host-read accounting; the change does not retroactively prove delivery or rewrite completed proposals/accepted coverage.

The server serializes model conversion per authorized profile. Bounded slices continue automatically while unresolved work remains. Three stalled attempts on one exact unit retain a processing-stalled exception and continue other units; provider waiting and dormant time do not count toward that streak. Prepared JSONL and already-reviewable deliveries with current dependencies remain independently reviewable without unnecessary model calls. Clinical acceptance is always explicit. The [processing queue journal](../../docs/data/intake-batch-journal.md) retains initial state and exact tracked changes under a selected hash-bound head. Warm writes avoid replaying retained queue history, including in encrypted publication. Cold recovery verifies the complete selected chain; complete response copies and unrelated workspace inventories have separate costs. Saved Stop state clears its diagnostic queue timestamp before acknowledgment. Authorized unlock automatically recovers durable intent; Stop survives restart. Dispatch/publication require current profile/job authorization. Restricted authority after logout remains [CRS-081](../../docs/todo/CRS-081.md); persisted intent is never an unlock credential.

Uploads default to 128 MiB (`CRS_INTAKE_UPLOAD_MIB`, maximum 1024 MiB). Extraction paths that load a complete non-PDF document default to 64 MiB (`CRS_INTAKE_EXTRACTION_MIB`, maximum 256 MiB). PDFs use one isolated child process and one profile/source-hash-scoped session: the retained file is verified once per session in 256 KiB chunks through the same file descriptor used for PDF.js range requests, then reused for page indexing, exact text and bounded visual derivatives. The child is recycled between operations after 32 renders or a completed operation reports at least 320 MiB RSS, releasing native image/font caches that a JavaScript heap cap alone does not bound. A single operation can exceed that recycle threshold; it is not a hard resident-memory guarantee. The child receives no model credentials or application preload hooks. Only one Node PDF worker is active; native extraction runs at most one qpdf child beneath it. Native extraction uses the bounded rendering-graph projection described above: both qpdf passes share one 60-second deadline, the projected dictionaries are limited to 1 MiB, JSON transport to 10 MiB and the final PDF to 5 MiB. Each qpdf process has a 384 MiB address-space limit on Linux; that limit is not a measured RSS guarantee and is not applied by macOS contributor checks. Stop/profile teardown kills the process group. Parser requests allocate at most 32 MiB, rendered output is capped at 10 MiB, operations have finite wall limits, and Stop/profile teardown immediately terminates worker/parser state. Queued reads recheck the profile generation before opening another child. These are safety bounds, not a claim that every uploaded PDF can be parsed or completely interpreted. Interrupted transfers restart the file; extraction can resume after receipt. Each assistant proposal call is limited to 1,000,000 characters; validation allows at most 50,000 rows with a 2 MiB row bound. Larger inputs require separately reviewable batches and explicit coverage gaps.

Linked conversion chats retain an encrypted `conversionCheckpoint` scoped to profile, original ID and source hash. Unique consumed source windows, substantive candidate versions and accounted units drive progress. Repeated unchanged reads cannot renew the watchdog. Each automatic attempt dispatches with one unresolved plan unit, and tool reads/publication must match it. Generation checks reject stale callbacks after Stop or profile teardown. Request and slice resource bounds remain; their boundaries yield to the coordinator without imposing a document-wide allowance. Source text uses partitioned storage without a total page/span/revision-byte ceiling. Changes to original scope remain rejected.

For a fresh top-level image with no extraction-plan history, the first authorized visual read also creates the existing deterministic one-unit image plan under the current source, model, instruction and mapping pins. The tool result returns the exact current plan, unit and version so the converter does not need separate plan-create and metadata-only `read_unit` turns. The pixel read still records the ordinary source checkpoint, and only a later durable batch can give the unit an explicit disposition. Existing or superseded plans, package children, PDFs and failed scope/version checks never use this shortcut; a visual decoding failure leaves the new unit pending.

`health_intake_plan` action `create` requires the exact current positive safe-integer `conversion.version`. A missing or malformed create version is rejected before plan mutation and receives at most two bounded repair responses; a third invalid attempt retires the current context and enters automatic recovery for the affected unit. This repair path never supplies or guesses a version. A supplied stale numeric version remains the ordinary terminal compare-and-swap conflict, as do changed plan pins, scope, operation and durability errors. Other plan actions do not acquire a global version requirement.

`health_intake_plan` action `read` supports one explicit current-context entrypoint: `freshStart:true` with a named section at offset 0 and both `version` and `mappingVersion` omitted. It synchronously returns that section's current bounded first page, the actual current pins and a `contextStart` instruction. The caller must discard every previously assembled model-context page or partial section under different intake or mapping pins. Every continuation page still requires the returned exact pins; nonzero fresh offsets, supplied fresh-start pins and unrelated action fields are rejected. This read does not verify literal evidence, replace a plan, rebase/replay a batch, accept data or authorize a write. Any later intake or mapping change retains the ordinary continuation and batch conflicts. Repeated fresh starts remain subject to the active no-progress and individual-operation bounds.

If `health_intake_batch` receives the exact pre-write `VERSION_CONFLICT` because ordinary review changed the delivery while the model was preparing a batch, the same model run gets at most two bounded repair responses without related durable batch progress. It must first read the current plan and revalidate the active plan, completed batches, candidate versions, questions, accepted history and source evidence. The same operation ID remains valid only for an exact unchanged batch retry; changed proposal, coverage, plan or evidence scope requires a new operation ID. A third consecutive stale attempt without a successful batch adding a candidate version or newly accounting a source unit retires the current context and enters automatic recovery for the affected unit. Successful reads, questions, new operation IDs, unrelated tool calls and repeated inspected/no-op batches do not reset this budget; later durable batch progress can replenish it for another independently reviewed source unit. Individual requests, tool repairs and slices remain bounded; productive automatic work has no cumulative request, token, turn or time limit. `OPERATION_CONFLICT`, changed extraction configuration, source/scope rejection, uncertain durability and every other conflict remain terminal; none authorizes automatic acceptance or a stale write.

One narrower host-only optimization applies when the sole intervening durable transaction is exactly one counted acceptance of a disjoint retained proposal from this same intake. The server binds the request-start profile/run/model/instruction/mapping/checkpoint state, exact intake and durable acceptance journal, active plan and each materialized child source ID/hash/size. It rechecks those bindings and Stop/profile/durability state immediately before submitting the identical received batch through the ordinary validation and final CAS path with only the current version. Incoming candidate identities and canonical versions must be disjoint from every newly accepted version; the new proposal remains pending and current accepted data wins. A second change, changed source/member/plan/unit/pin, uncertain publication, occupied operation ID or any unsupported acceptance shape fails closed and is never retried again.

The chat's `reading` field reports `status`, `reason`, `turns`, `readyRecords`, `remainingUnits`, `pendingReadWindows`, `readWindows`, `distinctReads`, `proposalsProduced`, `accountedUnits`, `totalUnits`, tool/model `phase` and `coverage:reading_progress_only`. `readWindows` counts every window marked seen, including children satisfied by inference from one JSON structure read; `distinctReads` counts only the windows the model actually read, so the two are equal for plain paginated sources and not in general. `proposalsProduced` sums the extraction batches of every plan of the conversion, not only the active one, so it stays comparable with `distinctReads` — which rides a checkpoint that is never reset — when a plan is superseded and replaced with an empty one. Neither is a claim about clinical completeness. `readyRecords` counts retained non-context candidate identities; one source entry can expose both a clinical review item and separate People proposals, so this is not the number of visible Import review items. Batch items retain cumulative `readingJob` accounting and diagnostic active-time and completed-response no-progress counts. Import shows these real counts and elapsed time beside Moxie, with Stop or explicit recovery in the same place; source-section accounting is not a clinical completeness percentage. Pause reasons include `no_progress`, `reading_exhausted`, `time_limit`, `context_limit`, `job_limit`, `tool_error`, `stopped`, `error` and `interrupted`. Slice and count-based no-progress boundaries stop the next request, while an admitted request retains its normal deadline and publication guards. Stop and profile lock revoke the ordinary path immediately. Authorized unlock recovers automatic intent; explicit Stop remains stopped. Failed outcomes preserve measured and unknown accounting through the recovery policy.

Browser API requests carry a random `X-Client-Request-ID` without changing read coalescing semantics. A bounded in-memory diagnostics ring retains route templates, timestamps, timings, status and cancellation reason, never request/response bodies, profile IDs, filenames or credentials. Set `sessionStorage['circus:import-debug']='1'` to also emit those metadata events to the browser console. Profile changes and caller cancellation use distinct explanatory errors instead of an unexplained browser AbortError; an interrupted mutation remains uncertain until its exact receipt/retry resolves it. This browser ring is not a durable or full-payload trace.

The sidebar’s **Download performance diagnostics** action (shown only with `CRS_IMPORT_DIAGNOSTICS=true`) combines its 500-event browser ring and 64 completed browser operations with `GET /api/profiles/:profile/import-diagnostics`. Default-on recent summaries retain up to 64 operations, 256 events per operation, 512 KiB total and a seven-day inactivity expiry in a separately encrypted profile sidecar; optional detailed events (`CRS_IMPORT_DIAGNOSTICS=true`) retain up to 10,000 in memory. `POST` to the same authorized endpoint accepts a strict, bounded browser timing schema. Neither endpoint publishes medical evidence. Operation/request IDs connect browser and HTTP events, and one export salt connects import references to durable page attribution. Profile lock clears plaintext and best-effort flushes summaries; locked ciphertext is inactivity-pruned at next unlock. Hard termination may lose pending observations; five-second coalesced publication is best-effort and can be delayed or fail. Resource samples run only during active work and describe this process, not upstream model compute. Eviction and persistence failures are reported. Console output remains separately opt-in; private payload traces remain separately protected and are excluded from this download. See [Import performance diagnostics](../../docs/import/import-performance.md) for exact phase semantics and retention limits.

`import.phase.started`/`.completed`/`.failed` fire for the `upload_receive` phase (starting after header validation — the Content-Length and `X-Content-SHA256` shape checks — and ending once the receive is hash-verified, fsynced and published, in that order) and the `index_pdf` phase (PDF indexing); `completed` carries `durationMs` plus `receivedBytes` or `pages`, and `failed` carries `durationMs` and a `reasonCode` instead. `upload_receive`'s `durationMs` covers receive **and** publish, so pairing it with `receivedBytes` does not give a transfer rate; `publishMs` on the same `completed` event covers the publication callback, including original retention and curation publication; it is not an exclusive database or disk-write measurement. A `reasonCode` is the failing error's code lowercased when that code is a string of the bounded diagnostic-code shape, and `unexpected_error` otherwise; a non-string code is one real case, since a PDF worker error can carry the numeric code pdf.js raises for a password-protected file. The `chat_journal` phase additionally brackets encrypted conversion-chat writes with `durationMs`, message/operation/proposal counts and a bounded failure reason; diagnostics failure cannot change the journal outcome. Journal events are separate from tool duration and must not be added twice. Additional paired phases now cover preflight, continuation dispatch, retry backoff, upload streaming (with cumulative wait/hash/write fields), staging fsync, original retention, curation/encrypted publication, review query/assembly/identity and acceptance validation/application. Nested intervals overlap and must not be summed. The direct package-member route also brackets its host read. The exported timeline retains parent/span IDs, active stage and time since progress. A PDF page read additionally attributes `model.tool.completed.durationMs` instead of leaving it opaque: the isolated worker in `intake-pdf-worker.ts` reports `verifyMs`, `textMs`, `renderMs` (covering a second render pass when an image exceeds the 10 MiB ceiling; image encoding is `encodeMs`, nested inside `renderMs` rather than separately additive, and summed across both passes when there are two, so the discarded oversized image's encode is not lost) or `nativePdfMs` for selected-page PDF extraction, and `annotationMs`, and the host adds `queueWaitMs` (waiting behind other requests in the process-global FIFO queue, ending the moment this request leaves it), `sessionSetupMs` (what the request then paid to have a ready worker session: `fork()`, the pdf.js document open, and `verifiedOpen()`'s chunked SHA-256 over the **entire** retained original — near zero on a reused session, and paid again on each recycle, which happens every 32 rendered pages) and `base64Ms` (the response media base64 encode) alongside `page`, `textLayerCharacters` and either `imageBytes` or `pdfBytes`. A native extraction fallback also reports `nativePdfFallback:true`; `failedNativeReadMs` separately measures the entire failed native attempt (queue/setup/IPC included) before the raster retry. Provider-triggered fallback rendering occurs after the original tool event and reports a separate `import.phase.completed` event with `phase:pdf_compatibility_fallback`, `durationMs` and `pageCount`. This interval covers successful host fallback reads and representation replacement, not the provider retry or a failed fallback; `pageCount` counts converted PDF parts, including repeated windows on one original page. Note that `verifyMs` brackets only the per-read `fstat` identity check, which is microseconds; the expensive verification is the full-file hash inside `sessionSetupMs`. `queueWaitMs + sessionSetupMs + verifyMs + textMs + (renderMs or nativePdfMs) + annotationMs + base64Ms` is a **partial** accounting of `durationMs`. **The remainder is unmeasured** — nothing brackets it, so its size is unknown and is not asserted to be small. It contains at least IPC transit and bookkeeping, the retained-original reference lookup, the mapping-rules SHA-256, `retainIntakeChildren` writing any embedded attachments into the vault, while the encrypted chat-journal persist is now measured separately outside the tool call by `chat_journal` events. The same event also carries `reReadCount` and `firstRead` from a tally kept only for this purpose: `reReadCount` is the number of prior reads of that read window **in this assistant run**, incremented on every successful read whether or not it made progress, and `firstRead` is `reReadCount === 0`. A read window read four times, with one other read between the second and the third, reports `0, 1, 2, 3`. This tally is deliberately separate from the `repeatedReads` pause tracker that trips a 409 after three _unproductive_ repeats: that tracker resets its count whenever reading makes progress, which is correct for a runaway-loop guard and useless as a re-read total. Both are cleared with the run's state, which makes the tally's scope one assistant run rather than one import: a create, send or retry builds fresh state, and a reading slice ends at the 15-minute deadline, so a long chart read across several continues restarts the tally at each one. Treat `reReadCount` as a lower bound on a window's lifetime reads, and `firstRead` as true-for-this-run rather than true-for-this-import. Carrying it across continues would mean persisting the tally in the checkpoint, which was deliberately not done here. These are counts, sizes, durations and booleans, never page content. Worker timing and byte fields are populated on direct and package-member PDF-page reads; JSON structure and package-inventory reads lack them. The assistant-run reread tally includes exact package `read_member` windows and treats an omitted PDF page as page 1; inventory and structure reads are distinct windows.

For a deliberately reproduced private import, raw payload tracing additionally requires `CRS_IMPORT_PRIVATE_TRACE=contains-health-data`, `CRS_IMPORT_PRIVATE_TRACE_DIR=/absolute/private/directory` and `CRS_IMPORT_PRIVATE_TRACE_GRANT_FILE=/absolute/private/grant.json`. The trace directory must already exist, be canonical (no symlink path), owned by the server user, owner-only, writable and outside every Git worktree. The grant is reloaded before every capture so an operator can authorize a newly created throwaway profile without restarting the app; it must be a canonical, nonsymlink, server-user-owned 0600 regular file of at most 4 KiB outside Git containing exactly two string fields: `profileId` with the exact profile ID and `expiresAt` with a millisecond-precision UTC ISO-8601 timestamp. The expiry must be in the future and no more than 24 hours away. Replace the grant atomically; removing it, expiring it or changing it to another exact profile immediately denies further capture. Wildcards and a public trace-control API are intentionally unsupported.

In Docker, mount the trace directory and grant from a protected external location. The host records only the authorized profile's scoped import model request/response bodies and dispatched tool arguments/results, never transport headers or connection configuration. These compressed files **contain plaintext health information when decompressed** and may contain sensitive source text; do not paste them publicly or treat them as redacted logs. Only trace status/counts/configured limits enter the normal diagnostic export. The trace defaults to 24 MiB per complete entry, 512 MiB aggregate uncompressed payload and 8,192 entries. A correctly configured operator runtime may lower or raise those caps with integer `CRS_IMPORT_PRIVATE_TRACE_MAX_ENTRY_MIB` (1–32), `CRS_IMPORT_PRIVATE_TRACE_MAX_TOTAL_MIB` (1–2,048), and `CRS_IMPORT_PRIVATE_TRACE_MAX_ENTRIES` (1–16,384). Defaults remain unchanged. Any present empty, noninteger, zero, negative or above-maximum value disables private tracing with `invalid_limits`; it never silently substitutes a larger cap or stops the import. These environment variables and protected mounts are application-runtime inputs, but the repository's current supported `compose.yaml` does not yet forward/mount them; Make/Compose release wiring remains an explicit open deployment gate rather than an inferred capability. A separately controlled validation container must prove its exact environment and mounts independently.

Complete model bodies within the transport bound are retained even when malformed JSON; responses beyond that bound and later/oversized trace entries are omitted whole and reported. Bounded upstream error-body captures explicitly report truncation. Grant, permission, Git-ancestry, invalid-limit or write failures deny or stop tracing without stopping import. Trace files are retained for operator inspection and require separate cleanup; profile deletion does not delete an operator's diagnostic directory. Default tracing is off.

## Bounded model history and performance checks

The proxy compacts successful, consumed `health_intake_read` results and `health_intake_package` `read_member` results with `original.text` only after a later valid model response. It replaces repeated schema instructions and any page text with an explicit `HOST_TRANSCRIPT_RECEIPT`, including counts and a text fingerprint; the receipt is not evidence and tells the model to re-read the retained original. One consumed read remains exact alongside the current read. Failed/unconsumed reads, package inventories and package structure results remain exact. Package member receipts name only fields actually replaced; absent instructions are never claimed as removed. This changes only the transient provider request, not the retained original or durable journal. Successful proposal arguments and consumed image messages have their own bounded receipt projections.

Prompt caching is separately opt-in through `CRS_PROMPT_CACHE` / `CRS_AI_PROXY_PROMPT_CACHE`. Its breakpoint is on the first system message's static text block, after the tools in the provider prompt order; the continuation notice stays in a separate system message so that prefix is unchanged across rounds. Missing cache support leaves normal requests working. Cache usage remains unknown when the provider omits it; see [provider configuration and acceptance](../../docs/setup/model-providers.md#configuration-and-routing-controls).

The per-turn loop remains capped at 64 rounds without a configuration override. `proxy-transcript.ts` separately bounds serialized text to 3 × 1024 × 1024 characters and combined image/PDF URLs to 16 MiB. A provider-free host benchmark measures native and raster work on identical fictional source bytes: from the repository root, run `CRS_PDF_BENCHMARK_PAGES=100 CRS_PDF_BENCHMARK_READ_ALL=1 CRS_PDF_BENCHMARK_FORMAT=both npm run benchmark:pdf`. The mixed fixture alternates dense text/vector pages and painted scanned-image pages; optional target-byte padding is reported separately and is never described as visible content. Without `READ_ALL`, only first/middle/last pages are sampled. Summaries separate index/cold session costs, per-page phases, worker recycling, native fallback, transport bytes and sampled qpdf process-tree RSS (a lower bound, not peak memory). Reverse representation order to assess ordering effects. Host runs do not measure model latency, tokens, extraction quality or the model-round/transcript stopping point. A deterministic 100-page assistant/batch integration check separately tests continuation and request bounds; real-provider acceptance remains I17.

The [controlled continuation fixture](test/intake-pdf-controlled.integration.test.ts) uses genuine accepted-record authority and the normal source-text APIs with independently known fictional page markers. Those seeded passages establish neither OCR quality nor human review. The scripted transport still receives every native PDF page and reads the corresponding durable passage before proposing records. Two supported 50-page units allow a real mid-unit 64-round continuation followed by unit advancement; ten batches retain separate proposal receipts. The first four batches within each unit remain inspected, and only its fifth can mark the unit extracted after all 50 pages were delivered and read. The fixture keeps the production round, unit-size and transcript bounds and does not measure model accuracy or large-import capacity.

## Reviewed metadata and deferred work

`POST /intakes/:id/metadata` takes `IntakeMetadataUpdate`: `{version,operationId,metadata:{source?,careArea?,documentType?,topics?}}`. Nullable strings clear optional fields; topics is a string array. The server derives sourceProviderId. Source metadata history is retained. This does not rewrite original filename, bytes, hash or acquisition ownership, and does not establish an issuing system. Source-file query DTOs keep database acquisition attribution in `providerId`/`provider` and expose the latest reviewed label separately as nullable `reviewedSourceProviderId`/`reviewedSource`. Explicit `acquisitionProviderId` and `reviewedSourceProviderId` list filters keep those scopes separate; the older `providerId` filter remains a compatibility effective-source filter. The reviewed source, falling back to acquisition source, scopes exact-label mapping rules.

The exact Import detail exposes this transaction without combining it with clinical acceptance. Evidence-aligned hints and manual edits share the same versioned request. A version conflict displays the newer saved and requested metadata for an explicit keep-or-reapply choice; an uncertain response retains the exact operation body for deliberate retry.

`POST /intakes/:id/review-draft` takes `IntakeReviewDraftUpdate`: `{version,operationId,proposalId,recordId,candidateVersionId,mapping?,resolutions?,disposition?,decision?,answers?,correctionReason?,correctionPatch?}`. Use `proposalId:null` for the prepared original. Disposition is `pending`, `review_later` or `keep_original_only`. Each resolution supplies `{issueId,outcome,mapping?}`; outcome is `this_is_me`, `other_person`, `unknown`, `confirmed`, `corrected` or `acknowledged`. The shared types define the exact mapping and decision fields. Operations have stable retry IDs and reject changed retry content; stale candidate versions are rejected. Pending and Review later pair choices remain drafts. An explicit terminal Keep original decision atomically retains each resolved exact-scope pair relationship and, for a fresh marked `same_event`, attaches the retained incoming source occurrence as direct evidence of the unchanged accepted entity. A fresh exact non-same outcome withdraws only that verified attachment row; omission is no action. Terminal review never accepts or rewrites clinical data or turns a previously unresolved unmarked choice into a relationship.

`POST /intakes/:id/draft-repair` takes `IntakeDraftRepairUpdate`: `{version,operationId,groupId,corrections:[{proposalId,recordId,candidateVersionId,field,before,after}]}`. It atomically changes only the selected pending draft `date`, or an observation draft's `method`/`observationCategory`. Every row must remain in the exact report group and candidate version, and every `before` value must still equal the current reviewed draft. Mixed groups, accepted/kept records, unsupported fields, stale values and changed stable-operation requests fail without a partial write. Each operation appends draft history. The UI's Undo submits the displayed inverse as a new versioned operation, so it never erases the correction or its history. The retained original and acceptance state remain unchanged.

The Import selected-row editor builds an exact `intake-draft-repair-selection-v1` context. Its optional Moxie action resolves that client selection on the server into a profile/intake/version/group/original/candidate/evidence-bound scope before any model request. Repair chats advertise and dispatch only progress, `health_intake_draft_repair_read`, and `health_intake_draft_repair_review`, including follow-ups and retries; generic conversion, mapping and accepted-record tools are rejected before their handlers. The reader returns only an authorized hash-pinned original PDF page, bounded text window, or scaled image for one selected row and locator. Native PDF and raster results carry the original reference, exact repair evidence receipt and selected-row instructions together in the model-visible metadata; a lazy PDF fallback revalidates that same repair scope. Review requires retained host read receipts for every cited evidence ID, and accepts only proposed before/after changes for allowed fields. The result is a preview; the proposal cannot add rows, change identity/source/kind, edit accepted records or accept anything. Apply revalidates the current scope and read receipts and writes through `draft-repair`; exact replay reconciles its durable operation receipt. Missing, over-bound, changed, uncertain or malformed source/model output leaves the direct editor and existing drafts usable.

On a stale draft conflict, Import loads and displays the full newer saved draft beside the retained local draft, including mapping, disposition, comparison decisions, issue resolutions, answers and reusable-rule intent. Immediately before either explicit choice it reloads the candidate and requires another comparison if those saved fields changed again; local reapplication pins that freshly displayed version. Neither choice is inferred from a `409`.

Drafts and resolutions are version-scoped profile metadata, encrypted in the default runtime. Review later leaves work pending while retaining edits; it never adds annotations to the original file. Keep original only records a terminal candidate-version disposition without clinical acceptance. Accepted or kept-original decisions cannot be replaced by another draft. Earlier accepted groups remain retained when other groups are deferred.

Issues have kind `identity`, `date`, `uncertain_reading` or `information`, blocking/status fields and original locator; optional textAnchor, page and memberId support clickable evidence. Source/Self suggestions remain reviewed actions. Exact supported name/DOB matches and same-original/person confirmations establish a durable Self attribution without another per-row action. Missing identity remains a visible, nonblocking warning: explicit clinical acceptance attributes the reviewed record to active Self without inventing source identity facts. A supported name or DOB that contradicts populated Self blocks both report-level and generic per-row This-is-me paths. Missing dates can remain unknown. Informational notices do not require guessed answers. Existing candidate resolutions are reused. Accepted history and reviewed projection upgrades are not reopened for identity, and prepared original JSONL retains its existing subject-review behavior.

Current converters propose fields under `clinical` even when `subject` is unknown. Review also recognizes retained `proposedClinicalMapping` objects and explicit document-level/payload optical values, with canonical fields and explicit nulls taking precedence. This does not accept a mapping. An earlier acceptance that omitted retained optical values can expose `projectionUpgrade:true` and a pending review; a new explicit acceptance appends the changed version. Accepted import receipts include `clinical.records` with source review ID, accepted entity ID/kind/title, optical flag and added/matched/updated outcome for direct navigation.

Explanatory date provenance is informational. A resolution or question answer can change dates only with an explicitly scoped supported field; a null-field uncertainty outcome preserves current dates. Earlier recorded resolutions remain in history and are not silently reversed. Same-field date questions may share one UI decision while every underlying issue ID remains retained. An existing scoped `date` or `documentDate` issue suppresses the generic unknown-document-date fallback. Separate `startDate`/`endDate` issues do not suppress it. Unscoped date prose and issues targeting unsupported nested literal fields remain informational, retain their evidence/history and cannot expose writable correction fields or inflate pending-question counts.

`POST /intakes/:id/questions {version,key,prompt,locator,candidateId?,candidateVersionId?,field?,operationId?}` retains a scoped question; its stable key cannot be reused for different evidence. `POST /intakes/:id/answers {version,operationId,questionId,answer,mapping?}` appends a record-scoped answer. Answer mapping accepts only the string fields explicitly allowlisted in `answerIntakeQuestion` in `intake.ts`; use review-draft for structured optical mappings. Answers alone do not accept assertions or create reusable rules. Remove from review uses `PATCH /visibility/source_file/:id {archived,version}` (visibilityVersion from Intake), and restore uses archived:false. This is personal archive visibility, not physical deletion. Originals and direct evidence links remain available; no file purge endpoint is implemented.

## ZIP inventory and resumable extraction

- `GET /intakes/:id/package?offset=0&limit=50` (limit 1–50): `IntakePackageInventory`, with stable member IDs, locators, hashes, byte counts, exact-byte duplicates, role summaries and any plan state. Inventory always reports `coverage:inventory_only` and `complete:false`.
- `POST /intakes/:id/package-member {memberId,offset?,jsonPointer?,jsonOffset?,limit?,page?}`: bounded inspection of a supplied member. Structure windows allow at most 50 entries. JSON structure entries expose `literal`, `literalComplete`, `offset`, `nextOffset` and `totalCharacters`; `jsonOffset` advances through supplied child entries, while an oversized child remains explicitly partial with its own cursor. Structure output is capped at 48,000 characters inside the 64,000-character assistant tool envelope. Text offsets and JSON structure reads preserve exact source spelling; reading every returned window never implies clinical extraction. PDF members expose their retained sourceFileId for page reads. Empty/unreadable members remain explicit evidence gaps. Nested archives require separate explicit inspection.
- `GET /intakes/:id/plan`: `{intakeId,version,plans,candidates,questions,pendingWorkCount}` including retained plans. `POST` with `{version,operationId,unitSize?,overlap?,replacePlanId?}` creates a plan; `version` is the exact current positive safe integer and changed pins require explicit replacement. Unit size is 1–50 with smaller nonnegative overlap. A newly created PDF plan defaults to two-page, non-overlapping target units; callers can still request overlap explicitly. Retained plans keep their serialized units, IDs and pins rather than being regenerated from later defaults. Pins cover original hash, configured model/connection, instructions, mapping rules and reviewed metadata when present.
- `POST /intakes/:id/package-roles {version,operationId,planId,roles}`: persist 1–50 member roles with evidence reasons. Each role has `{memberId,role,reason,coverage,references?}`; role is clinical/context/attachment/historical/unknown/nonclinical and coverage is pending/context/unreadable. - `GET /intakes/:id/unit?unitId=...&offset=...`: bounded plan-unit read.
- `GET /intakes/:id/navigate?action=search&query=...` or `action=follow&referenceId=...`: literal search or navigation to supplied evidence. Neither performs OCR, executes HTML, fetches remote references nor completes extraction.
- `POST /intakes/:id/batch {version,operationId,planId,jsonlText,summary,coverage,runId?}`: atomically retain a proposal and coverage, using 1–50 distinct `{unitId,kind,notes}` entries. Kind is inspected/extracted/context/unreadable. Units separately track pending/partial/completed processing; queue exhaustion is not clinical or full-chart completeness.

ZIP members must use stored or DEFLATE compression. BZIP2, LZMA and other ZIP methods are refused with an explicit unsupported-method error; re-export those packages using DEFLATE. Inspection runs in a bounded Node worker and verifies sizes, local headers and CRCs.

Retained `packageFailures` describe source-bound pending inventory, extraction or structure operations with an original link and exact member location when known. Matching successful work clears only that operation; repeated identical failures do not add another mutation. Model plan reads expose the bounded `package_failures` section with a separate pending count. These failures keep the intake needing review without changing `pendingWorkCount`'s meaning as unaccounted plan units. Locked/cancelled or uncertain durable publication states require their existing lifecycle/recovery handling, not a new failure mutation.

Worker capacity failures return `507 PACKAGE_STORAGE_FULL`; unavailable writes return `503 PACKAGE_STORAGE`. The API preserves these worker reason codes and the exact pending location rather than presenting storage failure as a `413 PACKAGE_LIMIT` format/processing refusal. Safe host-stage errors keep their existing response codes.

The native [streamed member and paged inventory path](../../docs/data/streamed-package-originals.md) has no file-count, aggregate-name, expanded aggregate or member-byte product cap. Disk-backed metadata validation and explicit long-name fragments replace whole inventory arrays; pending plan units are implicit. Explicit legacy array APIs and the buffered embedded-child API retain their protective limits. Inventory hashes every file through bounded streaming reads and validates actual expanded sizes against declared sizes and CRCs; inventory alone still does not extract clinical records. Unsafe paths, duplicate names, symbolic links and encrypted members are rejected. Every occurrence remains attributable even when byte-identical content permits read/storage reuse. Filenames, timestamps, member counts and roles do not establish clinical authority. Package instructions are evidence, never executable directions. Every relevant member/section and missing dependency needs explicit accounting.

## Clinical fidelity and durable storage

The row contract is [health-record-v1](../shared/schemas/health-record-v1.schema.json). `INTAKE_SCHEMA_INSTRUCTIONS` in `intake-format.ts` includes the clinical instructions from `clinical-instructions.ts`; Moxie's host instructions are `assistant-instructions.md`. Numeric spelling, unknown fields, source identity and literal payload markers remain preserved. Plain JSON is not silently accepted as prepared JSONL.

An observation keeps `clinical.valueText` and `clinical.unit` exactly as reviewed even when the printed result cell already includes that same unit token. The rebuildable numeric query projection may separate only an exact terminal structured unit from a strict number/comparator; the exact structured unit can corroborate spaced or attached notation. Mismatched units, exponent-like unit suffixes, ranges, prose and malformed numbers remain text-only. Import and saved-measurement presentation shows the exact unit once without rewriting either retained field.

Optional reviewed clinical envelopes project Self observations, medication assertions, procedures or documents. Optical prescriptions use document mapping field `opticalPrescription` (`../shared/vision.ts`): normalized type spectacle/contact_lens/unknown; optional exact source `typeText` and `statusText`; supplied prescribed/expiry date text; eye side and source sideText; literal valueText and optional unit for SPH, CYL, axis, add, prism, PD, base curve and diameter. Optional literal fields are nonempty strings copied without normalization. Never infer missing type/status wording, units, dates or eye identity. `GET /vision-prescriptions` exposes accepted document mappings and retained evidence occurrences for Test results → Vision.

Before proposal submission, map every explicitly supported classification as well as the primary value:

- A reported result uses `clinical.eventKind:"performed"`; retain an explicit result state in `clinical.status`, and use `clinical.observationCategory` when a panel heading, section or structured resource type establishes it. For example, `FINAL` in an identified laboratory panel supports `clinical.status:"FINAL"` and `clinical.observationCategory:"laboratory"`.
- When the same otherwise-supported patient-specific clinical assertion is printed at multiple locators, keep one reviewable record envelope and exact locator per printed occurrence. Repeated demographics, identifiers, report keys, generic headers and supporting context do not become clinical mappings. Equal labels, dates or values do not establish event identity, and a missing printed provider ID remains a null `provenance.sourceRecordId`; only qualified source identity or an explicit reviewed same-event decision can establish reuse.
- `clinical.medicationKind` describes the assertion form, while `clinical.eventKind` describes the event independently. An old or stopped provider order remains `clinical.medicationKind:"order"` and `clinical.eventKind:"order"`, with its literal state in `clinical.status`. `historical_mention` is for later prose that only mentions an earlier event.
- When evidence explicitly says a named procedure or scan was performed for the evidenced report subject within the same original/member/report boundary, propose a separate procedure with `clinical.eventKind:"performed"` as well as any result observations. A title, report date, result table, modality, acquisition source, named scan plus date without an event assertion, or historical measurement date alone does not establish performance. Identity remains unknown until separately reviewed; an explicit earlier procedure mention remains `historical_mention` and is never upgraded by a measurement date.
- A visit/document carries `clinical.documentCategory` and `clinical.visitSpecialty` when an explicit type, heading, department or author specialty supports them. These fields remain absent when unsupported. `clinical.subject` remains `unknown` until the evidence binds the record to the selected person. A same-named field in `payload` remains literal source evidence and never substitutes for the canonical clinical mapping.

Shared panel headings and timing can live once in a retained context envelope when each component references a stable panel ID and keeps its own value, unit, reference range, source record ID and locator. This avoids duplicating context without dropping relationships. Coverage is still per envelope: `complete_response` means that envelope retains the complete literal source item or precisely scoped section it claims, while a selected row/excerpt is `partial` even when all source pages were inspected. A complete context envelope does not upgrade selective clinical envelopes.

`provenance.capturedVia` is a human-readable acquisition/transcription description supplied by the host or source, or null when unknown; it is never an intake, source-file or member ID. `sourceSystem` names the issuing software/system only when supported, and `sourceRecordId` keeps the stable printed/provider identifier when present.

Exact supported identity plus identical structured assertion may reuse clinical rows; changed assertions retain separate versions. Dates/values alone do not authorize merging. Every original occurrence stays attributable. Narrow source/kind/label rules can rename/classify, never propagate values, dates or doses. Reviewed correction and restoration append versions; originals and prior accepted versions remain retained.

Delivery metadata, candidates, review drafts, plans and decisions live in original source-file details in the rebuildable SQLite projection. Default encrypted profile storage durably retains original bytes, derived proposals, accepted record versions and workflow metadata outside SQLite. Mutations mark intake_mutation_revision transactionally and publish durable generations; pending publication is visible with retry. Rebuild restores accepted extraction and review state without asking a model to reinterpret originals. See [import and rebuild](../../docs/import/import-and-rebuild.md).

Controlled fictional checks exercise the encrypted runtime, reviewed acceptance and cache-loss recovery. Full supported-size PDF/ZIP extraction, broader OAuth/provider compatibility, physical passkeys and printing remain separate [release checks](../../docs/todo/readme.md). Protocol probes and representative accepted records do not establish whole-file clinical completeness.

## Report review queue

The following block contract remains available while every selected intake uses the legacy envelope. When native collection authority is present, these routes dispatch to the explicit native contracts described below; clients must branch on `format`.

- `GET /intakes/report-queue?view=active&limit=30&cursor=…` returns `IntakeReportQueue` in the normal profile API envelope: `{view,groups,totalGroups,nextCursor,activity}`. `view` is `active`, `deferred` or `all`; limits are integers 1–100. Cursors are opaque, profile/view scoped and remain usable when earlier work is completed.
- `GET /intakes/report-queue/:groupId?view=active&limit=50&cursor=…` returns `IntakeReportQueueDetail`: `{view,group,blocks,totalRecords,nextCursor}`. Selection/restoration uses the stable encoded group ID, independently of the currently selected page. A completed group's active detail is empty; `all` retains its history. A missing or archived source returns `REPORT_GROUP_NOT_FOUND`.

Group summaries expose stable `groupId`, current `groupVersionId`, `intakeId`, `intakeVersion`, discovery order, supported title/source/date (unknown or conflicting dates are null), original link, exact package-member reference when available, extraction's unverified report anchor and counts. `pending` excludes deferred work and includes blocked current versions; `blocked` counts blocked current versions across pending and deferred. `questions` counts unresolved actionable issues on those current versions. Accepted, kept-original and superseded history has separate counts. Source context never becomes a clinical queue row. Group counts are authoritative for this queue; raw cumulative group membership and legacy delivery pending counts are not selected-result counts.

Older accepted and kept-original versions retain their status. A later proposal repeating an older envelope cannot make it current again. Unrelated current candidates from earlier proposals remain available. One report may therefore require several proposal blocks.

Every block includes exact `intakeId`, `proposalId` (null for original JSONL), `intakeVersion`, `reviewToken`, `proposalContentUrl` and `records`. To save drafts or accept a selection, use the existing review-draft/import endpoints with the returned exact block fields. After any mutation, reload detail before mutating another block because the delivery version/token can change. The legacy import endpoint still accepts one proposal at a time. For a counted selection spanning blocks, use the versioned report-acceptance endpoint below; keep its exact operation request until its receipt is recovered.

Legacy groups without ordinals retain a deterministic preceding order; reading the queue never migrates or rewrites them. New valid retained child JSONL originals initialize candidate/group metadata during publication and remain idempotent on repeated extraction.

`activity` reports running, paused and queued files from the latest retained reading batches, files awaiting conversion, remaining extraction-plan units, extraction-unknown files and whether current report work is reviewed. A ready proposal, accepted report, completed batch or fully inspected plan does not certify complete extraction. No current host contract establishes complete extraction for a nonempty delivery, so `extractionComplete` remains false while any visible delivery exists. Bounded response pagination does not reduce original verification to a partial trust check: a page may verify a complete retained proposal to derive accurate blocked counts and tokens. Read failures are surfaced rather than silently omitting candidates.

Legacy identity questions without a pinned version retain their durable history. For a changed candidate version, an old answer does not resolve the current identity issue without an exact-version draft or acceptance. No clinical history is rewritten. A source's reversible visibility action remains file scoped; it must not be presented as removal of only one report.

## Counted report acceptance

Reusable-rule creation is excluded from this contract.

The server validates the active profile, source visibility, proposal membership, exact occurrence, current candidate version, pending status, intake version, review token and selected-record blockers. Unselected, blocked, deferred and kept-original work is never implicitly selected. Blockers on unselected records do not prevent selected eligible records from being accepted. All selected reviews and mappings are prepared against one unchanged profile revision before applying any block. Application uses those frozen reviews rather than silently refreshing tokens, mappings, source interpretation or rules. It runs in one existing durable profile transaction, including multiple proposals from one source and multiple sources. Later blocks merge into the metadata produced by earlier blocks in the transaction. A validation or projection failure rolls back every block. Originals and earlier accepted versions remain intact. Existing explicit source-identity matching may produce `matched` outcomes; coincident dates or values never establish identity.

The result is `IntakeReportAcceptanceResult`: `{receipt,replayed,durability}`. Its outcome is `assigned`, `enriched_unknown` or `preserved_known`; the last value means the known scalar destination provider stayed unchanged while the additional reviewed occurrence was retained. Counts describe accepted selected source assertions, including matched occurrences, not raw proposal rows or newly created entities. Use these exact receipts for destination links and summaries.

The operation ID/fingerprint/result also accompanies the existing durable transaction journal. This is application-owned metadata; model envelopes cannot replace it. Backup/rebuild retains the original receipt independently of the source's latest accepted proposal.

Repeating POST with the same operation ID and exact request returns the original receipt without accepting again, even after later operations. Reusing the ID for a changed request returns `OPERATION_CONFLICT`. A lost reply is not evidence of failure: retain the request and first query or replay its operation; never refresh mappings/tokens under an uncertain operation ID. After a definite stale/validation rejection, review again and use a new operation ID for the new selection.

issues, identity warnings, report links and draft resolution witnesses. Their

same-count change outside the displayed page requires fresh review. Token

The native reconnect read explicitly awaits source-bound receipt lookup preparation when a later intake mutation or disposable-cache loss invalidated it. Warm reads reuse complete indexes. Fresh atomic approval verifies the complete review at request entry, then may refresh generated pair transport pins only across host-certified auxiliary publications. Ordinary intervening writes still require a fresh review.

After a definite pre-write `VERSION_CONFLICT`, the browser may read once and retry the same unchanged explicit action only when both native evidence commitments are well formed and equal, and every other review field matches. It checks exact snapshot/token relationships before normalizing version-derived bindings, keeping the original operation ID, attestation and selected blank values. Missing or unsupported proof, meaningful changes, a second conflict and uncertain outcomes require review or exact-request recovery; they do not refresh the displayed baseline.

Overflow advisory warnings use `health-intake-identity-warnings-v2` references with `scopeToken`, `count`, `sha256` and `snapshotId = identity-warnings:<scopeToken>:<sha256>`. The source-scoped report catalog retains immutable warning content by hash and a small scope/content binding. A saved Person edit can change warning content without changing the main scope. Inline warnings show the current reading; overflow references select current content while earlier references retain historical rows. New main snapshots can fork that content tree without explicitly republishing unchanged warnings.

For the warning section only, `identity-scope-page` and `identity-scope-fragment` accept an optional `snapshotId` selector. The host opens the authorized main scope first, validates the warning binding/content in the same source catalog and binds the selector into cursors, pages and item references. Fragment requests carry it, and the client resets its evidence window when it changes. Omitting it preserves legacy direct-warning reads. A foreign section, scope, snapshot or cursor refuses; missing or corrupt retained content cannot become an empty review. Reuse verifies the complete retained warning count/hash.

Native snapshot publication uses an authenticated source/group locator and immutable complete-evidence alias in the existing report catalog. The host computes fresh complete evidence from the checked current source before reuse. Equal accepted evidence permits a fork with only a new version-specific scope header. Changed evidence generates the complete desired primary and derived keys, compares retained values in bounded chunks, writes differing keys and deletes absent lookup, issue, occurrence and warning tails. Ordinal shifts may change many rows. Original scope references, historical warning rows and receipt bytes remain immutable.

Initial alias certification checks the exact complete namespace against an independent fresh-producer key/value seal, then reconstructs the retained primary scope and warning commitment. These are two separate bounded retained traversals, with counted work; a stored self-description or caller Boolean is insufficient. Owned disposable SQLite retains bounded desired-key/hash metadata and is guarded against content, schema and physical changes through generation, comparison, cleanup and certification. Fixed row budgets yield even when every compared row is unchanged. Accepted alias hits avoid initial certification work but still require fresh complete proof, exact source/profile/group/schema and header relationships. Present corrupt locators, aliases or references refuse; an absent pre-upgrade locator permits checked construction. Observed drift never refreshes an old source or physical proof.

Preview locators exist only in the build report catalog. Confirmation retains logical receipt authority: its existing owner can borrow only exact alias/locator references from the same accepted source build catalog under both captured catalog bindings, then publish the exact version-specific scope logically with the clinical transaction. The locator's selected-area provenance stays bound while resolving its named alias; a missing target cannot fall back across areas. Confirmation never updates the build locator, and historical receipt lookup stays logical-only.

Fragmented snapshot text keeps the existing byte format and accepts only owner-branded prior references. Fixed UTF-16 leaves have surrogate-safe boundaries; differing or appended leaves are published and obsolete trailing leaves removed. Stable aligned equal-length edits can reuse unchanged leaves. Character insertion or deletion can resegment and rewrite the changed scalar's suffix; this does not provide arbitrary minimal-edit locality. Prior branded references are adopted before asynchronous generation. Tiny replacements return to inline storage with no byte-leaf changes or deletes, but still incur the constant adoption and mapping changes. Final count, bytes, order and streamed hash are checked before attachment. Digest reads, retained comparisons, key changes, byte-leaf changes and tree/contributor publications are counted separately. No operator setting or scope/receipt migration is required.

PDF claims must point to the same explicit existing `page N`; only that page is read through the hash-pinned PDF range session, with a 250,000-character identity-text bound and the independent parser wall/resource limits. Text-bearing pages with unmatched quotes cannot bypass checking through visual attestation. Direct package groups require the exact retained inventory member, child parent/locator and member hash; an equal-byte sibling is insufficient. Opening a member retains it through the existing package workflow; preview itself does not extract or publish children. Missing member links, different-page PDF claims, unsupported originals, text-layout differences and ambiguity require individual review. Literal matching cannot detect every misleading model claim or semantic contradiction, and a human attestation is not independent clinical verification.

Identity item fragments also support an explicit sequential mode: send `cursor=start` with `offset=0`, then send each returned `nextCursor` with its exact `nextOffset`. In this mode incomplete responses carry a bounded opaque cursor and complete responses carry `nextCursor:null`. The cursor authenticates the selected profile, original, source/group/snapshot, section, ordinal, total bytes, current authority and exact byte position. Malformed, foreign or expired cursors refuse without restarting or falling back. Preview-cache invalidation, rollback, profile lock and database close revoke transport keys; retained scope and receipt bytes do not change. The current Import view uses this mode and retains complete-fragment inspection gating.

Sequential fragments address existing variable-length byte leaves directly and preserve raw UTF-8 splits. Page reference sizing uses the checked owner descriptor without reading the entire item. Numeric-only requests remain compatible with exact arbitrary byte offsets, but use a cooperative, counted prefix scan; repeatedly requesting those offsets can reread earlier bytes. Only the cursor traversal has bounded per-page leaf work and linear cumulative leaf work. All fragment reads hold the existing verified-original descriptor lease; request cancellation and physical/source drift refuse after a yield and before returning bytes. Retained question digests also yield through the existing checked work runner.

## Source reading accounting

`activity.readingAccounting` separates durable source accounting from clinical extraction quality. `state` is `empty`, `pending`, `unknown`, `accounted`, or `accounted_with_gaps`. `allSourceOccurrencesAccounted` becomes true only when every visible source has a current source-hash-pinned host plan/inventory with an explicit retained disposition for every unit, or is an exact retained child occurrence already accounted in its parent's inventory. A ready proposal, accepted clinical record, arbitrary completed status, package role or equal-byte sibling alone cannot establish this status. A missing/stale plan remains unknown. Host-enumerated package occurrences remain independent, including exact-byte copies. The result does not rewrite source plans or clinical history.

Unit counts distinguish pending/inspected work, extracted **claims**, context-only dispositions and unreadable dispositions. A disposition must match the unit's durable batch receipt. A host-indexed image has one whole-image unit. The normal linked-assistant path requires a successful source-pinned visual read before it can submit extracted coverage, while rebuildable reading accounting derives from the source-hash-pinned plan and durable batch receipt rather than transient chat state. These are retained accounting assertions, not independent verification of source truth or successful clinical extraction; model prose and exhausted read checkpoints are not completion authority. Known missing/uninspected/ambiguous dependencies and unknown package roles remain visible; a fully accounted inventory with such limits reports `accounted_with_gaps`. Clinical extraction remains `unknown` for every nonempty delivery: the server has no contract proving that a model extracted all clinical facts. Existing `extractionComplete` therefore remains false for visible deliveries; consumers should use source accounting to describe completed disposition work, without labeling it complete extraction.

Host checkpoint counts are independently source/profile pinned. They distinguish known pending windows, raw windows set aside by explicit context/unreadable dispositions, unknown checkpoint coverage and exhausted reads. `pauseReasons` retains per-source reason counts, including time limit, no progress, errors and reading exhaustion. A completed batch or a reading-exhausted reason without a valid checkpoint never certifies reading coverage. Raw cursors stay retained; displaying accounting is read-only and invokes no provider or parser.

Explicit `context` and `unreadable` unit coverage no longer drives repeated automatic processing of the same scope. Those units retain `status:partial`, their original coverage notes and all receipts. Pending-work counts and continuation use the matching retained disposition; exact unit/member/page cursors can be set aside, and a whole-source text cursor is set aside only when all matching text units are explicitly context/unreadable. Overlapping unaccounted PDF units and unrelated member windows remain pending. Accounting new units counts as bounded progress without accepting clinical records or marking context as extracted. To deliberately retry an unreadable/context scope after a tool/provider change, submit new `inspected` coverage for that unit (or explicitly replace the plan), then use the retained cursor/read tools. This reopens processing and preserves earlier disposition history. A model claim can be wrong; these mechanics do not replace source review or real-provider completeness acceptance.

Candidate-fallback report groups display the current reviewed clinical label/name/title, with the original filename when no readable label exists. This is a queue presentation projection only: persisted group IDs, version IDs and original title/history are unchanged.

A report queue header can also expose `sourceLabelScope` for an explicitly anchored report without a model label suggestion. To enter a personal source label, submit the exact returned context ID and current report/intake versions to `report-source` with `basis:"manual_report_label"`. This confirms only a user-entered label on the current pending members of that report; it makes no claim that the model found an issuer. The durable confirmation retains that basis and may extend to later members only under the unchanged anchored report and any unchanged linked/shared context described above. Accepted versions, adjacent reports, acquisition metadata and original bytes remain unchanged. A changed report/context boundary requires a fresh confirmation.

A report identity scope may contain `questions` with deduplicated prompts and optional literal anchors, plus the exact `issueIds` on each target. Show all those questions before confirming; nonempty questions require `confirmed_displayed_identity_questions`, while the existing generic report-subject path remains available. The scope hash binds the prompts, issue IDs and candidate versions. Conflicting report boundaries, explicit other-person subjects and other-person resolutions remain outside common confirmation. Browser-facing evidence URLs are canonicalized only for the exact active profile when verifying the echoed scope.

A routine model ownership question does not require another human confirmation when its exact printed name uniquely matches an established owner and the host verifies the complete question anchor against the current retained original. This applies to recognized generic “Does this report belong to you?” questions, including a name followed by numeric demographic columns. An unlabelled name/sex/date banner cannot supply DOB evidence or strengthen a match. Suppression of its routine ownership question requires at least one valid date reading compatible with the uniquely named saved person, when that person has a saved DOB. If no reading matches, the question stays blocking until explicit report confirmation; the column is not promoted to evidenced or offered DOB. The host's own original-header read (`originalSubjectBirthDateEvidence` `bannerDates`, checked in `assessIdentityPolicy`) applies the same test without any model question: a banner date that no reading (either month/day order, any century for a two-digit year) fits to the uniquely matched saved person's DOB makes the report `confirmation_required` and blocking; a compatible date leaves the name-only match unchanged, and a labelled birth date in the header takes precedence over the banner. Specific uncertainty questions, human unknown/other-person answers, conflicting names or labelled DOB, and competing owners remain blocking. Ambiguous labelled numeric DOB text is not normalized or offered as a profile value; both valid readings require human review even when one matches the uniquely named owner. Question proofs retain only bounded scope/anchor hashes, expire with changed report membership or a competing subject at the same report boundary, and are rechecked against current saved identity. The bounded cache counts distinct questions, so repeated copies across a report do not create a new question per result.

#### Retained person names

Display names remain presentation labels. Identity matching uses the established names on Self or a Person: the compatible `fullName` and `knownNames` fields plus server-owned `sourceKnownNames`. Name comparison normalizes case and whitespace and the explicit `surname, given names` convention; it does not reorder arbitrary words or invent nicknames. A unique exact name can identify either owner. A name shared by multiple owners, contradictory date of birth, unresolved current identity refusal, or ungrounded/ambiguous identity evidence requires human choice. Clinical acceptance is still separately reviewed.

Matching examines every active Person, independently of the bounded chooser's page limit. DOB alone cannot select an owner or break a shared-name tie. Archived People cannot receive a new automatic or explicit assignment, and current visibility is checked again at clinical acceptance. A model proposal's structured name and subject-only fallback both require literal original grounding before automatic attribution. The synchronous review uses a bounded, database-local proof keyed to the exact source/report/group membership; a rebuilt database or changed membership requires another identity preview. The original JSONL path may use its own validated literal structured name. If repeated report anchors in payload and metadata prevent a unique report window, structured subject metadata alone does not establish the boundary and the queue requires explicit report confirmation. Image-only human attestation remains an explicit choice rather than automatic name verification.

Every successful report-person confirmation stores `confirmedPrintedName` in its immutable receipt. A spelling with at least two name tokens is also retained in the selected person's `sourceKnownNames`, including when it equals an existing primary/manual name; a single-name spelling stays only in the report receipt. Each source-backed entry retains `name`, `operationId`, `intakeId`, `sourceHash`, `groupId`, and `subjectText`. The existing encrypted record journal publishes the person change and identity receipt together; SQLite is only their rebuildable projection. Ordinary profile edits and historical field restoration preserve these entries and their mirrored `knownNames`; clients cannot forge the protected provenance. Up to 32 independent manual names and 1024 distinct source spellings are supported. Capacity rejection aborts the complete confirmation rather than silently omitting the name.

A grounded structured name is preferred. With no structured suggestion, a conservative parser can select a name-only subject or a labeled `Patient:`/`Name:` field without demographic suffixes. If no safe selection exists, the confirmation body must include `printedName`: an exact name substring of the displayed `scope.subject.text`. Missing, invented, or whole demographic sentence selections fail `IDENTITY_PRINTED_NAME` before saving the person or confirmation. This explicit selection does not rewrite the original or retroactively strengthen the model's extraction.

When all known read windows are consumed and candidates exist but source units still lack an explicit disposition, an unproductive model turn gets one directed reconciliation continuation per authorized run. This is not a retry of a failed provider request and does not reset active no-progress accounting, accept records, or infer coverage. The `reconcile_coverage` diagnostic marks that attempt; another unproductive turn retires the current context and enters automatic recovery for the affected unit. A turn ending with no remaining windows or units reports reading exhausted even if that final turn made no additional changes.

A literal, unambiguous patient-labelled DOB remains identity evidence even when its anchor also includes collection/report dates or the model omits the separate DOB suggestion. Ambiguous date formats and multi-person anchors are not resolved by guessing against Self. A recognized patient DOB label whose value is not one complete date (masked, free text, invalid, partial or with a two-digit year) is never treated as a missing DOB: identity review returns blocking `confirmation_required`, never `evidenced_match` or `missing_warning`, and only a confirmation for that same report answers it. See [processing and evidence review](../../docs/import/processing.md#source-attention-and-identity-follow-up) for the recognized labels and date layouts. The existing server confirmation check rejects a contradictory evidenced Self DOB; report identity and clinical value review remain separate. Metadata diagnostics expose DOB presence/conflict booleans, never the date itself.

A Self confirmation borrowed from another report on the same original compares the current report's unlabelled demographic banner against Self's saved DOB, even when the printed name matches another owner or more than one owner. If multiple saved owners match that name, the other report's receipt does not choose among them. The current report's own applicable confirmation still resolves its choice; a compatible banner does not become DOB evidence, and labelled DOB ambiguity or conflict retains its separate blocking rules. Preview, feed and both acceptance paths use this shared policy. See [report-scoped banner decisions](../../docs/import/identity-review.md#banner-compatibility-and-report-scoped-decisions).

### Transcription approval versus material source changes

Source-text confirmation retains an immutable review revision and exact-head CAS receipt. When spans and relationships are unchanged, no unreadability is explicitly resolved, and no substantive unreadable/unsupported/nontext disposition changes, it preserves the intake version and material source dependency. Existing proposals and active model source-read pins remain valid. Model source handoffs use the material revision; source review and pagination continue to use the exact review head. Corrections, clarification and substantive dispositions still invalidate interpretation. Bulk UI approval performs sequential existing source-review requests, stops at the first failure and reports earlier successes; there is no blanket clinical acceptance or automatic model dispatch.

`GET /intakes/source-attention?offset=0` returns profile-scoped metadata `{sections,total,items:[{intakeId,sections}],offset,nextOffset}`. The global section total counts distinct pages with open, later or unreadable issues, across visible originals including extracted package members. Only files with retained pending source issues occupy its 30-file windows; uncaptured originals and completed source reviews do not. The endpoint prepares disposable per-source counts from current durable indexes, including a read-only fallback for older revisions. Cold preparation visits sources in bounded, yielding steps; later source changes invalidate only their counts, and warm pages return at most 30 source headers. Visibility and exact global totals are queried in SQLite without a complete source array. Dropping the temporary projection or reopening the connection reconstructs it from retained source revisions. The response returns no extracted wording and never starts processing.
