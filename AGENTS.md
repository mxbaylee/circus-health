# Repository guidance

These instructions apply to the whole repository.

- Start ordinary commit subjects with any Unicode emoji (or an existing Gitmoji shortcode), for example `✨ Add import review` or `🐛 Fix upload retry`. Merge operations are exempt. This is a contributor default, and `git commit --no-verify` is available when an exception is useful. See `CONTRIBUTING.md` for setup.
- Validate touched behavior locally with formatting, type checking, and focused tests. GitHub Actions runs the full validation suite on pull requests and supplies the merge checks. Use an emoji-prefixed pull request title, obtain independent review, and squash merge after review and required CI checks pass. Do not push directly to `main`. Run the full local suite only when persistent CI failures justify reproducing them locally; see `CONTRIBUTING.md` for the complete lane reproduction commands.
- Treat `README.md` and `docs/README.md` as public entry points. Keep setup on the supported npm → Docker Compose → LiteLLM path.
- Put browser code in `src/app/`, server code in `src/server/`, cross-runtime contracts in `src/shared/`, deployment code in `deploy/`, and durable model instructions beside their server consumer.
- Reuse existing components, tokens, data adapters, and domain contracts before adding a parallel implementation.
- Keep health records, recovery material, credentials, local model state, logs, screenshots, and generated runtime databases outside Git. Tests and documentation must use independently fictional data.
- Treat originals and accepted record versions as durable evidence. Do not make SQLite, temporary extraction output, or model responses the recovery authority.
- Durable writes must scale with what changed. Never copy a whole document, revision or table into a journal entry, transaction result or receipt on each write; that write amplification is a defect, not a trade-off. See `docs/data/record-version-storage.md`.
- State performance requirements in terms the app controls. The model is bring-your-own, so its speed can differ by orders of magnitude between a frontier route and a small local model, and between years. Count work instead of timing it: model requests, retries, bytes or tokens sent, rereads, hashes, intake reviews and durable writes per operation, each scaling with what changed. Keep interactive requests answered while background work runs. Detect a stall from missing progress, not from elapsed model time, and derive estimates from rates observed on the installation. Never set a pass/fail bound in seconds for model work; for host-only work, prefer counts, and use any timing only as a coarse ratio against a baseline on the same machine. A dated measurement is evidence about one setup, not a target.
- Keep private operations profile scoped and session authorized. Model output must remain reviewable before an accepted write.
- The public repository supports Docker Compose with LiteLLM. Root npm commands launch and verify the Compose deployment; direct server execution remains a contributor facility.
- Use TypeScript for application and Node tooling. Keep Python confined to deploy/litellm/ for the proxy and its in-process compatibility tests. Host tooling, application code, ZIP inspection and filesystem locking use Node/TypeScript.
- During implementation, run focused tests for touched behavior. GitHub Actions runs the full suite on pull requests. Use the full local validation and offline proxy compatibility commands in `CONTRIBUTING.md` when persistent CI failures require local reproduction. Do not weaken validation solely to make a failing change pass.
- Update maintained documentation when an API, storage, security, import, model, or deployment contract changes. Documentation outside `docs/todo/` describes implemented behavior, supported procedures and current limitations. Open work lives in `docs/todo/`: short items in `docs/todo/readme.md`, and a `CRS-NNN.md` file when an item needs more room, including its specification, proposal, owner decisions, open questions and review findings. Fold feedback into the CRS items it concerns rather than keeping a separate report. When a ticket's work lands, delete the ticket in the same change: its index entry and its CRS file. Describe what shipped in the maintained documentation, not in a closed ticket, and repoint links to that documentation. If only part of a ticket landed, still delete it, and open a new ticket for the unfinished part: its requirements, owner decisions and open questions, with context scoped to that subset (what already exists, where the code is, why it remains). IDs are never reused; the index records the next unused number. Existing `docs/experiments/` material is isolated pending a separate retention review.
- Every new or edited ticket must include a user story grounded in the canonical personas and jobs in `docs/design/personas.md`. Use their existing names, link the relevant job, and explain the user benefit plus any technical ambiguity in language a product manager can assess. Short index-only items may include the story inline; larger tickets use a `User story` section. Follow the template in `docs/todo/readme.md`; do not invent conflicting personas.
- Split work when distinct complexity, scope or dependency boundaries make implementation and review clearer. High effort alone is not a reason to split, defer implementation or require owner grading. Coherent high-effort work may proceed through the normal implementation and independent-review workflow. Preserve actual dependencies and external authorization/evidence gates; ticket genuinely unfinished work after implementation instead of declaring it complete.
- Do not treat an old plan or validation receipt as proof of current behavior. Verify claims against code and current tests.
- Choose agent model and effort to match the work and reduce cost: use low effort for test execution or monitoring and routine documentation; reserve higher effort for complex implementation and independent correctness review.
- Before marking a ticket complete, have an independent, capable subagent review the implementation against the ticket's requirements, persona/user benefit, owner decisions and current validation. Provide the scope and evidence, not a desired score or expected conclusion. Ask for an unbiased numerical grade, concrete findings, useful improvements and evidence limits. Prefer the latest available capable model at high reasoning effort. Address blocking feedback, verify fixes and repeat independent review until it passes; report any remaining limitations. Completion also requires deleting the ticket's index entry and CRS file, if one exists, and updating maintained documentation as described above.

Personal environment details and raw validation artifacts are excluded from this repository. Public documentation and contributor checks must be self-contained, without references to private maintainer repositories or their layout. Keep approved open requirements and release gates in the public work list; `docs/architecture/workspace-and-handoffs.md` describes included source material, exclusions and portable evidence.
